# 数据库初始化与升级

服务端使用一份 SQLite 数据库：程序目录下的 `Data/game.db`。账号凭据、角色、任务、技能、物品、钱包、仓库、图鉴和审计均在此文件中；认证与游戏仍由各自 Repository 管理。运行时 SQLite 可能产生 `game.db-wal`、`game.db-shm`，它们是同一数据库的日志与共享内存文件，不是拆分的业务库。

## 初始化与打开

组织方式参考 S4A21，将完整结构、初始化流程和增量迁移分开：

| 文件 | 职责 |
|---|---|
| [game_schema.sql](../../Server/DfoServer/Sqlite/game_schema.sql) | 当前完整结构，只含建表、约束与索引，不携带账号或玩家数据；随构建和发布复制到程序旁的 `Sqlite/` |
| [SqliteDatabaseBootstrap](../../Server/DfoServer/Persistence/SqliteDatabaseBootstrap.cs) | 新库执行完整 SQL，已有库进入版本检查与升级；成功后启用 WAL |
| [SqliteMigrations](../../Server/DfoServer/Persistence/SqliteMigrations.cs) | 维护基线标识、当前版本、连续编号的升级步骤，以及必需表和列检查 |
| [SqliteGameDatabase](../../Server/DfoServer/Persistence/SqliteGameDatabase.cs) | 统一连接设置，开启外键，连接等待超时为 5 秒，不使用连接池 |

数据库基线标识仍为 `s5a9-database-v1`，当前结构版本为 **v18**（`PRAGMA user_version = 18`）。v2 增加账号租赁点数，v3 增加副本成长事件账本，v4 增加邮件、托管附件、每日寄金币额度及邮件审计，v5 将成长账本的资源标记列改为 `resource_source` 并保留历史值；新事件记录资源表路径。v6增加账号通用设置与角色选项表，v7增加角色主设置快照表，均不写默认数据，具体见[客户端设置](../模块/客户端设置.md)。新库一次建立当前完整结构；已有 v1 库按连续迁移升级，保留原角色、库存、UID和详情，具体字段见[邮件](../模块/邮件.md)。开发账号由认证初始化逻辑在缺失时创建，后续启动不重置其凭据或禁用状态，见[认证与会话](../模块/认证与会话.md)。

v8增加角色副本身份高水位与成长附属owner，v9增加冻结掉落与拾取账本，两步均只建表，不补发历史奖励。v10增加冻结通关经验账本；v11增加character_skill_point_sources（角色额外SP）和account_expert_contracts（账号达人到期秒数），迁移只建空表，不推断旧角色来源或赠契约。v12增加character_tp_sources（额外TP）、character_skill_commands（角色/树/技能的指令BLOB）与character_skill_combos（角色/树/根的u16子ID序列），三表只建空结构，不迁移旧布局。来源接管与技能原子保存见[技能学习](../模块/技能学习.md)。

v13相对master的v12只增加一次迁移：为进行中任务建立持久接取身份，同时创建权威清图账本和3145完整领奖账本。迁移保留原槽位、条件与角色revision，不依据已有条件值补造通关或发奖。接取身份、两张账本及版本号在同一事务创建，任一步失败回滚全部结构与数据变更。

通用任务系统增加任务生命周期、任务掉落及无奖励跳过回执、账号完成表、角色周期和装备槽标志，并为角色与账号完成记录保存每日周期及可空的零基回答。已发布master的v1–v17迁移保持原顺序；本版仅追加一次v17→v18，扩展接取型49、阈值父任务70的领奖约束及任务券/手动跳过的操作身份。全部待执行DDL、数据转换和版本号在同一事务提交，任一步失败回滚全部变更。

原v13任务接取身份、槽位、条件、角色revision及清图/领奖记录均保留。原领奖表的rowid、26列历史值、七项UID/Core和原规则版本完整保存，允许零经验、可变/选择奖励、实际材料消耗及重复任务倍率1–65535。普通领奖类型包括寻物0、猎杀怪物2、会面4、猎杀敌人6、角色状态12/31/39/40、寻物会面25、问题42、顺序父任务44、接取型49、范围64、演出65及阈值父任务70，不要求清图字段；单地图清图3和条件通关1/subtype6、11要求完整权威清图凭据。旧分类67及历史回执保留，新规划只使用已确认分类。约束转换保存原列、rowid、索引及触发器，不重放历史业务触发器。

角色周期与装备槽标志初始为0，未回答记录为NULL；新增回执和账号完成表为空。迁移不推断历史分支，不补发奖励、回填任务完成或按等级解锁装备槽。任务掉落复用已有成长事件，普通副本成长与结算允许`quest_id=0`；真实任务表仍要求合法任务编号。无奖励跳过以`operation_id`及`operation_kind`保存完整冻结规划：QuickClear保留真实接取身份、parent key和question，操作身份等于接取身份；Manual和Ticket使用独立操作身份，三项接取字段均为NULL。Ticket快照另保存原券槽、UID/Core、数量、期限和库存前后状态；指定130券追加实际动作、目标原序和提交后装备槽标志，觉醒119/122券追加实际动作、目标职业及完整双树学习快照，保留普通77回执原JSON形状。券消费、完成、回答、关联寻物及活动槽、必要装备槽解锁或逐级觉醒、双树和技能、回执和一次revision同事务提交；其余跳过不消费券。回放1459复用正式副本身份预留，不新增任务完成或领奖表。同步marker按已确认的本角色级联集合保存。实际规则与跨角色边界见[任务系统](../模块/任务.md)。

v18识别已发布master的领奖约束、此前任务分支缺少49而已有70的约束，以及最终49/70约束；跳过回执识别旧八列结构及最终十列结构。旧跳过新增的操作身份沿用原接取身份，类型为QuickClear，已有Manual/Ticket操作及NULL接取字段原样保存。需要调整的两张回执表各重建一次，保留所有历史列值、rowid、冻结快照、显式索引和触发器，恢复历史数据后才建立触发器。两表对齐任一步失败整体回滚；最终结构再次初始化不重建，不重放事件。未知定义拒绝升级，不自动改写。

旧任务分支v14按实际版本执行后续已发布迁移，并在同一v18步骤接入本版扩展。若原库已存在完整的已发布疲劳两表，初始化事务精确核验表定义后保留原表和数据，不重跑v15建表或补写固定疲劳值；两表均缺失时执行原v15。部分表或未知疲劳定义拒绝升级。随后原v16仍保全成长及全部外键子账本，原v17按已有任务字段决定是否补建任务结构，不修改版本号冒充回退。

正式副本末次可信死亡与经验、两树SP、任务达成和清图receipt同事务保存；旧实例不能推进另一次接取。领奖将真实接取清图、规则与来源、经验前后状态、唯一角色revision、全部实际UID/完整Core/槽位/数量一同记账，并与资产、两树SP、活动槽和完成表一同提交。相同身份重读不再次授奖；已加载完整库存后的重复请求不重放增量奖励包。

`character_dungeon_state`保存角色与账号归属、下一个副本对象key、已预留尝试号及经验胶囊/熟练度附属状态。普通新建角色明确初始化；v8迁移只建表，不为存量角色推断或清零这些值。缺记录的角色仍可选角和进入城镇，但正式副本准入拒绝，须先有保留原状态的合法初始化依据。每次正式准入将完整路线的key高水位、尝试号与角色revision同事务预留；通知失败、重登或重启不回绕已预留身份，key空间耗尽时拒绝新准入。实例本身不持久化，断线后重新建立挑战，详见[单人副本实例](../模块/单人副本实例.md)。

已有库必须属于同一基线，且版本在当前程序支持范围内。无标识、其他基线、版本过高或必需表/列缺失都会拒绝启动，不覆盖原库，也不自动降低版本。

新建结构、基线标识与版本号在一个事务提交；建库失败时清理本次创建的数据库文件。已有库的全部待执行升级步骤和版本号在一个事务提交，任一步失败均回滚，不删除原库。结构与版本检查不代替资产读取时的业务合法性检查。

普通分支既有v14确认master v13已有的完整领奖表，以兼容此前发布的v14编号而不重复建表；v15保留此前发布的疲劳owner与地图receipt结构；v16将成长/结算的任务身份扩为非负、房间receipt地图扩为正索引。升级保持v13任务步骤、已有疲劳值、全部奖励与资产记录，连同成长的掉落/拾取和任务外键子表同事务重建。已发布任务v14的`character_quest_drop_receipts`存在时，连同成长父表重建，保留全部历史任务掉落、rowid、索引和触发器；没有该表的普通分支仍沿原升级链处理。已有集合批次、对象及拾取三表时，沿原DDL、全部行、索引与触发器参与同一重建；三表不完整拒绝整次升级。集合建表与正式版本登记仍由掉落模块负责，普通迁移只接管已存在的外键依赖。v17按实际周期/装备槽/完成记录字段区分两类已发布结构：任务v14已有字段时不重复建表；普通v14–v16补齐任务结构。两路保留既有版本和数据，再由唯一v18步骤扩展回执。不关闭外键，不修改版本冒充回退。普通费用行为见[单人实例](../模块/单人副本实例.md#普通图疲劳owner)。

## 修改结构

后续结构变化从 **v19** 起，在 `SqliteMigrations.Steps` 按顺序追加版本、名称和升级委托，并同步更新 `game_schema.sql` 的完整结构及必需列检查。新库直接建立最新结构；旧库按版本只执行未完成步骤。保留已发布的基线标识和迁移顺序，不通过修改版本号跳过升级。

升级中的每条 SQL 使用传入的同一连接和事务执行，不另开写事务；多条 DDL 逐条执行，避免批处理隐藏中途失败。数据转换保留已有资产、UID、进度和审计，不补发物品或重置账号。变更字段时同步对应 Repository、业务模型和所属模块文档。

[DatabaseSchemaTests](../../Server/DfoServer/SelfTests/DatabaseSchemaTests.cs)覆盖新建单库、账号与角色共同存储、外键、重开、错误基线/版本/残缺结构拒绝、新建失败清理、连续迁移、整链回滚和重复执行。新增真实迁移时补充前一版本的代表性数据及失败用例，再按[贡献指南](../../CONTRIBUTING.md#验证)运行完整自测与 TCP；启动组还检查发布布局下的建库和重启。

## 备份与恢复

升级前正常停服并备份整个 `Data/`，或由受控工具使用 SQLite Backup API 获取一致快照。不要在运行中只复制主文件而遗漏 WAL 中未合并的数据。恢复时停止准确的服务实例，保存当前备份，使用相匹配的程序与数据库；较旧程序不会打开更高版本的库。多个实例使用各自程序目录，不能共享一个运行库。
