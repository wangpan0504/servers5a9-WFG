# 数据库初始化与升级

服务端使用一份 SQLite 数据库：程序目录下的 `Data/game.db`。账号凭据、角色、任务、技能、物品、钱包、仓库、图鉴和审计均在此文件中；认证与游戏仍由各自 Repository 管理。运行时 SQLite 可能产生 `game.db-wal`、`game.db-shm`，它们是同一数据库的日志与共享内存文件，不是拆分的业务库。

## 初始化与打开

组织方式参考 S4A21，将完整结构、初始化流程和增量迁移分开：

| 文件 | 职责 |
|---|---|
| [game_schema.sql](../../Server/DfoServer/Sqlite/game_schema.sql) | 当前完整结构，只含建表、约束与索引，不携带账号或玩家数据；内置于程序集，目录发布同时复制到程序旁的 `Sqlite/` |
| [SqliteDatabaseBootstrap](../../Server/DfoServer/Persistence/SqliteDatabaseBootstrap.cs) | 新库执行完整 SQL，默认外部 SQL 缺失时使用内置版本；显式 schema 路径仍严格使用指定文件。已有库进入版本检查与升级；成功后启用 WAL |
| [SqliteMigrations](../../Server/DfoServer/Persistence/SqliteMigrations.cs) | 维护基线标识、当前版本、连续编号的升级步骤，以及必需表和列检查 |
| [SqliteGameDatabase](../../Server/DfoServer/Persistence/SqliteGameDatabase.cs) | 统一连接设置，开启外键，连接等待超时为 5 秒，不使用连接池 |

数据库基线标识仍为 `s5a9-database-v1`，当前结构版本为 **v38**（`PRAGMA user_version = 38`）。v2 增加账号租赁点数，v3 增加副本成长事件账本，v4 增加邮件、托管附件、每日寄金币额度及邮件审计，v5 将成长账本的资源标记列改为 `resource_source` 并保留历史值；新事件记录资源表路径。v6增加账号通用设置与角色选项表，v7增加角色主设置快照表，均不写默认数据，具体见[客户端设置](../模块/客户端设置.md)。新库一次建立当前完整结构；已有 v1 库按连续迁移升级，保留原角色、库存、UID和详情，具体字段见[邮件](../模块/邮件.md)。开发账号由认证初始化逻辑在缺失时创建，后续启动不重置其凭据或禁用状态，见[认证与会话](../模块/认证与会话.md)。

v8增加角色副本身份高水位与成长附属owner，v9增加冻结掉落与拾取账本，两步均只建表，不补发历史奖励。v10增加冻结通关经验账本；v11增加character_skill_point_sources（角色额外SP）和account_expert_contracts（账号达人到期秒数），迁移只建空表，不推断旧角色来源或赠契约。v12增加character_tp_sources（额外TP）、character_skill_commands（角色/树/技能的指令BLOB）与character_skill_combos（角色/树/根的u16子ID序列），三表只建空结构，不迁移旧布局。来源接管与技能原子保存见[技能学习](../模块/技能学习.md)。

v13相对master的v12只增加一次迁移：为进行中任务建立持久接取身份，同时创建权威清图账本和3145完整领奖账本。迁移保留原槽位、条件与角色revision，不依据已有条件值补造通关或发奖。接取身份、两张账本及版本号在同一事务创建，任一步失败回滚全部结构与数据变更。

通用任务系统增加任务生命周期、任务掉落及无奖励跳过回执、账号完成表、角色周期和装备槽标志，并为角色与账号完成记录保存每日周期及可空的零基回答。任务系统在v18保留v1–v17迁移顺序，并以一次v17→v18迁移，扩展接取型49、阈值父任务70的领奖约束及任务券/手动跳过的操作身份。全部待执行DDL、数据转换和版本号在同一事务提交，任一步失败回滚全部变更。

原v13任务接取身份、槽位、条件、角色revision及清图/领奖记录均保留。原领奖表的rowid、26列历史值、七项UID/Core和原规则版本完整保存，允许零经验、可变/选择奖励、实际材料消耗及重复任务倍率1–65535。普通领奖类型包括寻物0、猎杀怪物2、会面4、猎杀敌人6、角色状态12/31/39/40、寻物会面25、问题42、顺序父任务44、接取型49、范围64、演出65及阈值父任务70，不要求清图字段；单地图清图3和条件通关1/subtype6、11要求完整权威清图凭据。旧分类67及历史回执保留，新规划只使用已确认分类。约束转换保存原列、rowid、索引及触发器，不重放历史业务触发器。

角色周期与装备槽标志初始为0，未回答记录为NULL；新增回执和账号完成表为空。迁移不推断历史分支，不补发奖励、回填任务完成或按等级解锁装备槽。任务掉落复用已有成长事件，普通副本成长与结算允许`quest_id=0`；真实任务表仍要求合法任务编号。无奖励跳过以`operation_id`及`operation_kind`保存完整冻结规划：QuickClear保留真实接取身份、parent key和question，操作身份等于接取身份；Manual和Ticket使用独立操作身份，三项接取字段均为NULL。Ticket快照另保存原券槽、UID/Core、数量、期限和库存前后状态；指定130券追加实际动作、目标原序和提交后装备槽标志，觉醒119/122券追加实际动作、目标职业及完整双树学习快照，保留普通77回执原JSON形状。券消费、完成、回答、关联寻物及活动槽、必要装备槽解锁或逐级觉醒、双树和技能、回执和一次revision同事务提交；其余跳过不消费券。回放1459复用正式副本身份预留，不新增任务完成或领奖表。同步marker按已确认的角色级联集合保存，合法无奖励账号同步位同时进入既有账号完成表。实际规则与跨角色边界见[任务系统](../模块/任务.md)。

v18识别已发布master的领奖约束、此前任务分支缺少49而已有70的约束，以及最终49/70约束；跳过回执识别旧八列结构及最终十列结构。旧跳过新增的操作身份沿用原接取身份，类型为QuickClear，已有Manual/Ticket操作及NULL接取字段原样保存。需要调整的两张回执表各重建一次，保留所有历史列值、rowid、冻结快照、显式索引和触发器，恢复历史数据后才建立触发器。两表对齐任一步失败整体回滚；最终结构再次初始化不重建，不重放事件。未知定义拒绝升级，不自动改写。

旧任务分支v14按实际版本执行后续已发布迁移，并在同一v18步骤接入本版扩展。若原库已存在完整的已发布疲劳两表，初始化事务精确核验表定义后保留原表和数据，不重跑v15建表或补写固定疲劳值；两表均缺失时执行原v15。部分表或未知疲劳定义拒绝升级。随后原v16仍保全成长及全部外键子账本，原v17按已有任务字段决定是否补建任务结构，不修改版本号冒充回退。

正式副本末次可信死亡与经验、两树SP、任务达成和清图receipt同事务保存；旧实例不能推进另一次接取。领奖将真实接取清图、规则与来源、经验前后状态、唯一角色revision、全部实际UID/完整Core/槽位/数量一同记账，并与资产、两树SP、活动槽和完成表一同提交。相同身份重读不再次授奖；已加载完整库存后的重复请求不重放增量奖励包。

`character_dungeon_state`保存角色与账号归属、下一个副本对象key、已预留尝试号及经验胶囊/熟练度附属状态。普通新建角色明确初始化；v8迁移只建表，不为存量角色推断或清零这些值。缺记录的角色仍可选角和进入城镇，但正式副本准入拒绝，须先有保留原状态的合法初始化依据。每次正式准入将完整路线的key高水位、尝试号与角色revision同事务预留；通知失败、重登或重启不回绕已预留身份，key空间耗尽时拒绝新准入。实例本身不持久化，断线后重新建立挑战，详见[单人副本实例](../模块/单人副本实例.md)。

已有库必须属于同一基线，且版本在当前程序支持范围内。无标识、其他基线、版本过高或必需表/列缺失都会拒绝启动，不覆盖原库，也不自动降低版本。

新建结构、基线标识与版本号在一个事务提交；建库失败时清理本次创建的数据库文件。已有库的全部待执行升级步骤和版本号在一个事务提交，任一步失败均回滚，不删除原库。结构与版本检查不代替资产读取时的业务合法性检查。

普通分支既有v14确认master v13已有的完整领奖表，以兼容此前发布的v14编号而不重复建表；v15保留此前发布的疲劳owner与地图receipt结构；v16将成长/结算的任务身份扩为非负、房间receipt地图扩为正索引。升级保持v13任务步骤、已有疲劳值、全部奖励与资产记录，连同成长的掉落/拾取和任务外键子表同事务重建。已发布任务v14的`character_quest_drop_receipts`存在时，连同成长父表重建，保留全部历史任务掉落、rowid、索引和触发器；没有该表的普通分支仍沿原升级链处理。已有集合批次、对象及拾取三表时，沿原DDL、全部行、索引与触发器参与同一重建；三表不完整拒绝整次升级。集合建表与正式版本登记仍由掉落模块负责，普通迁移只接管已存在的外键依赖。v17按实际周期/装备槽/完成记录字段区分两类已发布结构：任务v14已有字段时不重复建表；普通v14–v16补齐任务结构。两路保留既有版本和数据，再由唯一v18步骤扩展回执。不关闭外键，不修改版本冒充回退。普通费用行为见[单人实例](../模块/单人副本实例.md#普通图疲劳owner)。

v19只补齐已有同账号`character_dungeon_state`、缺`character_fatigue`且没有历史扣点回执的角色，使用原本服初始值`0/156/0/156/0/0`。不新增表或列，不改角色revision、实例高水位、资产或任务；已有疲劳六字段及全部receipt保留。缺副本owner或有扣点历史而缺当前状态的角色不初始化，防止初始值覆盖未知历史。写入与版本号在原迁移事务中提交，失败回滚；达到v19后重开不重复执行。

v20将完整地面掉落集合纳入正式数据库：新增 `character_dungeon_drop_batches`、`character_dungeon_drop_objects` 和 `character_dungeon_drop_pickups`，分别保存原死亡批次、完整冻结对象与逐件实际提交结果。新库直接包含三表；旧库仅建立空结构，不补发历史物品或金币。已安装完整三表的旧库先检查全部业务列并原样接管，部分表或缺列拒绝整次升级。三表DDL及版本在原升级事务提交，末表失败回滚前两表和版本。正式启动始终要求完整三表；不能以当前版本号接受全部缺失的集合账本。原掉落分支已部署的v18已有集合三表，但任务回执仍为旧结构；v20沿已发布任务v18的精确结构补齐任务回执，再验证并保留现有集合。旧掉落v19尚未执行master的疲劳v19，v20按相同资格补齐遗漏状态；已有疲劳和历史扣点回执不变。master的v1–v19保持迁移顺序，master v19与旧掉落v18/v19均在原升级事务进入v20，未知任务定义、部分集合或缺列均拒绝且回滚；不改旧资产、UID、冻结结果或版本号冒充降级。资产事务和结果恢复见[单人副本实例](../模块/单人副本实例.md)。

v26在已发布的v25称号簿迁移后只新增空的 `character_tutorial_state` 与 `character_tutorial_receipts`，不改旧角色列、等级、资产或完成任务；存量Lv1也不自动补训练资格。状态与建角同事务创建，奖励、真实击杀成长及掉落与对应检查点同事务保存；升级两表和版本共同提交，末表失败整笔回滚。已发布迁移编号保持不变。具体行为见[新角色训练](../模块/角色.md#新角色训练)。

## 修改结构

v21新增 `character_dungeon_card_rewards`，按角色及通关实例唯一保存冻结计划、实际免费牌奖励、可空的满背包邮件ID及提交revision，并外键关联本次通关回执、真实账号角色及邮件。迁移只创建空表，不补发旧空翻牌、不改账号、角色或既有资产；新建库包含该表，已有库连续迁移，失败整笔回滚。奖励发放及重复报告恢复见[免费翻牌](../模块/单人副本实例.md#通关经验与翻牌奖励)。

v22新增账号到期表 `account_card_memberships`、角色业务日使用表 `character_gold_card_uses`、实例付费/会员冻结及领取表 `character_dungeon_card_options`。三个DDL和版本号在同一迁移事务执行，失败整笔回滚；已有v21免费回执、角色资产和账号数据原样保留，新表为空，不补造会员或历史奖励。会员资格由服务端设置，付费金币/完整奖励/永久邮件/黄金次数和领取回执同事务提交；重复选牌从唯一实例回执恢复，不再次扣费或消耗次数。

v23调整击杀、通关和任务三类经验回执的到账约束：保存原冻结额度，实际到账允许在0至该额度内，经验不倒退。原有字段和数据保留；按外键依赖一起复制及重建父子表、rowid、索引和触发器，同事务升级，失败整笔回滚。此迁移不补发或改写历史奖励。

v24只将 `account_completed_quests.character_id` 放宽为可空，使来源角色删除后仍保留账号完成事实。原来源、接取身份、周期、回答、全部列、rowid、索引及触发器原样复制；恢复历史行后才重新建立触发器，不重放领奖。迁移不修改任何既有角色或账号完成记录的值，删除用例才在原业务事务中解除来源。未知来源定义或外键子表明确拒绝升级，失败回滚结构、数据和版本；不关闭外键或通过CASCADE删除未知历史。

v27在已发布v25称号簿和v26训练迁移之后只新增空的 `account_hotkey_settings`，按账号与profile保存原生键位文本。迁移不覆盖已有设置、称号进度、训练状态或资产，DDL与版本在原事务中提交；失败整体回滚。具体行为见[客户端设置](../模块/客户端设置.md#账号键位)。

v28在已发布v25–v27之后追加 `characters.emotion`，取值0–32767，旧角色及新角色缺省0。升级只补心情列，保留原角色revision、资产、称号、训练和键位；DDL与版本在原事务提交，失败整笔回滚。具体行为见[客户端设置](../模块/客户端设置.md#角色心情)。

v29增量建立`account_adventures`，保存账号名称、等级、经验、胶囊与结晶等基础状态，不补发历史经验或奖励。迁移与版本号在同一事务提交，已有训练、键位、心情及角色资产保持不变；具体行为见[冒险团](../模块/冒险团.md)。

v35追加 `account_wallets.premium_contracts`，以类型到 Unix 绝对到期秒数的 JSON 对象保存契约，缺省为空对象。保留钱包余额、revision、幸运值及旧 GM 账号契约，不补发权益或创建消耗品。兼容上游已知的契约版v34，保留原期限及资产；未知残缺v34拒绝升级。契约获取或使用沿原库存事务同时提交费用、源数量、账号期限与审计，期限变化递增同一账号钱包 revision，失败整体回滚。

v36追加免费牌 `claimed` 领取位和 `server_events` 时间表，不新增回归玩家字段。旧已发免费牌缺省已领取，活动缺省关闭，不补发或推断奖励。原会员56/58期限增量接入统一 `premium_contracts`，与已有同类型期限取最大值，不改变22/27等其他契约；只有期限实际改变才推进钱包revision。旧会员列保留历史值但正式业务不再读取，关闭契约不能被旧列重新激活。只有完整的旧本地翻牌v34形状允许补齐缺失的两张任务效果表，再连续执行v35和v36；部分领取字段、任务表或未知活动结构均拒绝。已有本地库的额外 `returning_player_expires` 列原样保留，但业务不读取它或据此恢复回归资格；旧冻结JSON字段仅兼容回执形状。全部DDL、期限接管和版本号同事务，失败整体回滚，重开幂等。

v37新增拍卖行挂牌表 `auction_listings`（跨账号可见，不归属单个角色，因此不建立指向 `characters` 的外键：卖家为机器人时 `seller_character_id` 为 NULL 且没有角色行），同一步建立到期、卖家、模板三个索引，并直接包含 `deposit_gold`（挂牌阶段实收的保证金，金币，`CHECK` 非负，默认 0）。只建空表，不预置挂牌、不改角色资产。**`deposit_gold` 的历史语义**：本列出现之前上架的挂牌一律记 0，到期结算按这一行实际收过的金额退，不会用当前政策常数凭空造出 10,000 金币。表结构与字段含义见[拍卖行模块](../模块/拍卖行.md)。

v38追加`account_adventures.name_initialized`及大小写不敏感的名称查询索引。已有行缺省已命名，原名称、revision和进度保留，不自动给免费改名资格，不因历史重名删行或重写名称；新账号显式保存未命名标志。DDL和版本同事务提交，命名、重复检查和改名券行为见[冒险团](../模块/冒险团.md#命名与改名)。

后续结构变化从 **v39** 起，在 `SqliteMigrations.Steps` 按顺序追加版本、名称和升级委托，并同步更新 `game_schema.sql` 的完整结构及必需列检查。新库直接建立最新结构；旧库按版本只执行未完成步骤。保留已发布的基线标识和迁移顺序，不通过修改版本号跳过升级。

升级中的每条 SQL 使用传入的同一连接和事务执行，不另开写事务；多条 DDL 逐条执行，避免批处理隐藏中途失败。数据转换保留已有资产、UID、进度和审计，不补发物品或重置账号。变更字段时同步对应 Repository、业务模型和所属模块文档。

[DatabaseSchemaTests](../../Server/DfoServer/SelfTests/DatabaseSchemaTests.cs)覆盖新建单库、账号与角色共同存储、外键、重开、错误基线/版本/残缺结构拒绝、新建失败清理、连续迁移、整链回滚和重复执行。新增真实迁移时补充前一版本的代表性数据及失败用例，再按[贡献指南](../../CONTRIBUTING.md#验证)运行完整自测与 TCP；启动组还检查发布布局下的建库和重启。

## 备份与恢复

升级前正常停服并备份整个 `Data/`，或由受控工具使用 SQLite Backup API 获取一致快照。不要在运行中只复制主文件而遗漏 WAL 中未合并的数据。恢复时停止准确的服务实例，保存当前备份，使用相匹配的程序与数据库；较旧程序不会打开更高版本的库。多个实例使用各自程序目录，不能共享一个运行库。

v32保留冒险团商店限购表，v33保留账号赛丽亚幸运值列。任务效果的v34步骤只补建`character_quest_effect_receipts`和`character_quest_special_reward_claims`，兼容本地旧v32部署已经保存的同名表和补领记录；这种旧v32缺少master商店限购表时，在同一升级事务补建该空表，随后核验全部必需列，已有角色和任务账本保留。不执行旧角色数据补全迁移或选角自动修复。已有补领记录及已保存修复结果原样保留，但运行时不扫描它们，也不新增补领声明；新跳过只保存本次实际效果回执，用于整笔提交与真实UID恢复。
