# 开发环境与启动

## 构建要求

- .NET 10 SDK；目标框架 `net10.0`，构建启用 `TreatWarningsAsErrors`。
- 可用的 NuGet 源。依赖版本以 [DfoServer.csproj](../../Server/DfoServer/DfoServer.csproj) 为准。
- 服务端使用 SQLite，不需要独立数据库服务。
- Windows 启停与仓库检查脚本支持 PowerShell 5.1；macOS/Linux 的仓库检查使用 PowerShell 7 (`pwsh`)。服务端自测和隔离 TCP 回归使用 C# / .NET 10，不依赖 Python。

仅源码即可构建，不依赖客户端或 PVF：

```powershell
dotnet build ServerS5A9.sln -c Debug --nologo
powershell -NoProfile -ExecutionPolicy Bypass -File Tools/Check-Repository.ps1
```

## 候选冷构建诊断

仅 `DFO_STARTUP_DROP_DIAGNOSTICS=1` 且服务端有日志出口时，候选首次构建启用分段诊断；其他值关闭。关闭时不创建诊断工厂、逐项计时、线程分配采样或额外候选摘要遍历。此开关不改变资源解析、缓存策略、排序或启动/TCP超时。

`server.jsonl` 的 `startup_drop_diagnostics` 记录根脚本与导入脚本各自的 ReadText/字段索引累计 worker wall 时间、当前线程分配差分、调用与失败数，以及 TemplateResolution（creation-rate 筛选及 Get/single-flight）桶。ReadText 含解码、缓存、读取和等待，不是纯解码 CPU；worker wall 可重叠，不能直接相加当进程启动耗时，线程分配不等于保留内存。既有 `startup` 阶段继续记录整体 CPU/GC/分配。

成功时附有原正候选顺序的五字段 `Id,Kind,Grade,Rarity,CreationRate` SHA-256 摘要及 count，编码为版本域分隔符、逐行五个小端 int32、末尾 count；不对 PVF 整包计算摘要，也不表示全部模板字段等价。空摘要不代表相等。`SnapshotReused` 表示复用已有成功快照，此时不是冷构建测量。

诊断没有 Timer 或后台采样；所有 worker 收束、候选锁退出后只汇总一次，失败不发布成功摘要，回调异常不覆盖原构建异常。外部强杀可能没有最终报告，不可据此推断各分段无成本。摘要计算计入原阶段耗时，对照两侧必须使用同样的诊断开关。

## 资源解析与固定目录

运行服务端和资源相关测试需自行准备 `Script.pvf`。服务端解析资源内容并检查格式、必要字段、索引范围及数值合法性。史诗碎片存档通过条目顺序检查避免余额错位。

启动使用命令行参数，不读取服务端 JSON 运行配置。默认路径及自定义相对路径基于 `AppContext.BaseDirectory`，即服务端程序所在目录；改变工作目录不会产生另一份默认数据库。

哈林材料的可选业务规则通过 `DFO_HARLEM_MATERIAL_RULES` 环境变量传入JSON，启动时一次读取；默认值、字段及关闭方式见[副本的哈林材料本服规则](../模块/副本.md#哈林材料本服规则)。它不替代服务端启动参数，也不读取或修改PVF与玩家数据库配置。

旧地区深渊碎片逐骰命中率由`DFO_HELL_EPIC_FRAGMENT_PERMILLE`控制，默认1000，范围0至1000；0显式关闭，非法值拒绝启动。片种与等级仍由PVF映射及深渊等级引用表决定，哈林不混入旧史诗碎片。

加百利碎片商人读取`etc/epicpieceshop.etc`，出场值按本服百分比规则解释；`DFO_EPIC_PIECE_SHOP_APPEAR_PERCENT`可在启动时覆盖为0至100，0关闭、100用于确定性联调。未设置时保留PVF值，缺少该配置文件时不注册交换入口。覆盖值与规则只属于本实例，不修改PVF或玩家数据库；语义与未验收边界见[图鉴与碎片交换](../模块/背包与装备.md#账号史诗碎片图鉴与制作)。

```text
程序目录/
  DfoServer.exe 或 DfoServer.dll
  start-server.bat / start-server.sh
  Sqlite/game_schema.sql
  Data/
    Pvf/Script.pvf
    game.db
    server.lock
  Logs/
    server.jsonl
    ready.json
```

PVF 默认位于 `Data/Pvf/Script.pvf`，账号和全部游戏数据默认共用 `Data/game.db`；可通过 `--pvf-path <文件>` 和 `--data-dir <目录>` 覆盖资源及存档位置，数据库名称仍为 `game.db`。日志固定在程序目录的 `Logs`。Data 布局与完整 SQL / 增量迁移组织参照 S4A21，表结构属于本项目。首次启动使用默认完整 SQL；目录模式保留程序旁的 `Sqlite/game_schema.sql`，文件缺失时使用程序集内置的同一 SQL，单文件包无需外置 SQL。已有库按基线与版本检查升级，不读取或合并其他数据库文件。初始化、维护与备份见[数据库](数据库.md)。

源码构建前把 PVF 放在 `Server/DfoServer/Data/Pvf/Script.pvf`，构建与发布复制该资源及目录说明。自包含包把 PVF 放在程序旁的同一相对路径。仓库不携带客户端、PVF、玩家数据、日志或预编译文件；这些文件均已忽略。

## 命令行与启动脚本

从仓库根目录执行：

```powershell
dotnet build ServerS5A9.sln -c Debug --nologo
./start-server.bat
./start-server.bat --server-ip auto
./start-server.bat --server-ip 192.168.0.10
dotnet run --project Server/DfoServer -- --help
```

macOS/Linux 使用 `bash ./start-server.sh`，参数相同。脚本依次查找同目录的程序、`dist/<平台>/` 自包含输出及 Debug 构建，切换到程序目录运行。自定义构建输出可直接执行 `dotnet <构建目录>/DfoServer.dll [运行参数] [命令]`。

Windows 的[本机测试构建](#本机测试构建windows)同时生成单文件 `DfoLauncher.exe`。双击该程序，或无参数运行同目录的 `start-server.bat`，会打开游戏服务启动器；带参数的批处理仍直接运行命令行服务。启动器须与完整服务包同目录，目标机器无需另装 .NET 或 Python。

启动器提供服务地址、频道/游戏端口、PVF 文件及存档目录选择，以及启动/停止、复制连接地址和打开日志目录。默认 PVF 和存档仍位于程序旁的 `Data/Pvf/Script.pvf` 和 `Data`；选择其它存档目录使用其中的 `game.db`，空目录会新建存档，不自动搬迁、复制或合并原存档。首次本机测试构建在程序旁生成 `launcher.local.json`，已有配置在重新构建时保留。启动器打开时读取配置，成功启动后更新选择；配置只供启动器使用，服务端仍接收命令行参数。

默认配置的 `PvfPath` 为 `Data/Pvf/Script.pvf`、`DataDirectory` 为 `Data`，地址为 `127.0.0.1`，频道/游戏端口为 `23100/23101`。配置中的相对路径始终以启动器所在目录为基准，与终端工作目录无关；保留相对路径并移动整个服务包即可沿用配置。手工填写的相对路径（包括 `../`）在保存后仍保持相对；浏览选择程序目录内的文件/目录会转为相对路径，选择外部路径则保持绝对路径。移动服务包时，绝对路径仍指向原位置，需按实际资源位置修改。

服务确认就绪后才显示实际地址和存档位置，`auto` 使用服务端选择的 IPv4。启动中可以取消；关闭窗口会等待本次创建的服务正常退出。端口、资源或数据库实例锁冲突会显示失败原因，不接管已运行的进程。路径只能在停服后修改。运行输出分批刷新并限制保留量，完整服务日志仍在 `Logs`。GM 使用原有独立工具，启动器不提供 GM 选项。多个实例仍须使用独立的程序目录及端口，不能仅通过切换存档目录共用同一日志目录。

`Data/launcher.lock` 在窗口打开期间独占；更新程序前须停止服务并关闭启动器。只有 `Tools/Build-Server.ps1` 生成 Windows 启动器，单独发布服务端项目和其它平台仍使用命令行入口。

命令行也可指定路径，运行参数放在业务命令之前；相对路径始终以服务端程序目录为基准：

```powershell
./start-server.bat --pvf-path "<资源文件>" --data-dir "<存档目录>"
```

| 运行参数 | 含义与默认值 |
|---|---|
| `--server-ip <IPv4\|auto\|connection>` | 返回给客户端的服务端地址，默认 `127.0.0.1`；`auto` 在启动时优先选择具有网关的活动网卡 IPv4；`connection` 按每条连接实际抵达的服务端 IPv4 返回，默认监听 `0.0.0.0` |
| `--listen-ip <IPv4>` | 显式监听地址；非回环 `--server-ip` 默认监听 `0.0.0.0`，本地默认 `127.0.0.1` |
| `--channel-port <端口>` / `--game-port <端口>` | 默认 `23100/23101`，两者须不同 |
| `--native-port <端口>` | 默认 `0`，由系统分配独立Native监听端口，LOGIN端点返回实际值；需要固定映射时显式指定，须避开所有其它监听和分类入口范围 |
| `--channel-entry-port-base <端口>` | 默认 `0`，附加分类入口自动分配端口；非零时从该端口起连续绑定，默认目录共29个附加入口，须避免与频道、游戏、GM及包查询HTTP端口重叠 |
| `--gm-port <端口>` | 默认 `0`（关闭）；启用后仍只监听 `127.0.0.1`，不能与频道或游戏端口相同 |
| `--packet-http-port <端口>` | 默认 `0`（关闭）；启用本机只读包查询HTTP，固定监听 `127.0.0.1`，须与其他监听端口不同 |
| `--session-ttl <秒>` | 认证元数据有效期，默认 `300`，范围 `30–3600` |
| `--promotion-page <Off\|On>` | 默认 `Off`；`On` 显式启用原生活动目录10999及累计赠礼机器只读协议，值区分大小写。独立于活动购买开关，活动关闭时仍可读取已核历史；不启用整套活动。原生页见[商城累计赠礼只读页面](../模块/背包与装备.md#商城累计赠礼只读页面)，机器查询见[聊天页面入口](../模块/聊天.md#商城累计赠礼机器页面) |
| `--dungeon-entry-probe <模式>` | 默认 `Disabled`；独立诊断可选 `Information`、`StartMap`、`FinishLoading`、`FinishLoadingMonsters`，限制见[副本协议](../协议/副本.md) |
| `--auction-probe <参数>` | 默认关闭（关闭时拍卖行搜索读真实挂牌）；拍卖行搜索应答记录布局的开发诊断，键与候选布局见[拍卖行模块](../模块/拍卖行.md)与[拍卖行协议](../协议/拍卖行.md) |
| `--auction-seed <条数>` | 默认 `0`（不种子），范围 `0–10000`；启动时若挂牌表为空则写入该条数的开发挂牌，取值见[拍卖行模块](../模块/拍卖行.md) |
| `--teleport-potion-gates <模式>` | 默认 `Open`：瞬间移动药剂可传送到全部有 `[dungeon gate]` 的区域（如黑市 54/2 哈林入口），不再按药剂 `[int data]` 地下城选择地图白名单拒绝；`Pvf` 恢复严格白名单（白名单外回 237 失败码 23，客户端显示 36288）。任务、等级、私有房间和可走位置检查两种模式都保留，见[城镇模块](../模块/城镇.md) |
| `--adventure-weekly <Off\|Slots\|Full>` | 默认 `Slots`：角色就绪和791保存成功后回读账号配置，下发720/721（721固定5槽，`0xFF`未选择）；`Off` 保持旧行为；`Full` 为719列表预留，当前与 `Slots` 相同，见[冒险团模块](../模块/冒险团.md) |
| `--packet-capture [目录]` | 启动并记录应用层帧，默认关闭；须放在运行参数之后 |

文件抓包直接将每个字节编码为两个大写十六进制字符，避免逐字节创建临时字符串。正文与原帧仍使用单空格分隔，空正文保持为空，认证及 Native 关联材料沿用原有脱敏方式。

重复登录固定为 `ReplaceExisting`：先验证凭据，再替换旧连接；旧 owner/generation 不能继续写库或释放新 owner。频道与游戏入口不校验客户端来源 IP，原生登录仍须验证账号和凭据。账号初始化及接管细节见[认证与会话](../模块/认证与会话.md)。

同一进程同时服务本机和局域网客户端时，可使用 `--server-ip connection --listen-ip 0.0.0.0`。频道目录和游戏登录端点使用已接受套接字的本地地址，目录保留各分类游戏端口，LOGIN返回同实例Native端口；不会返回客户端自身 IP、`0.0.0.0` 或通过扫描网卡替另一条连接猜测地址。固定 IPv4 与 `auto` 的行为不变。该模式不推断 NAT 的公网地址或外部映射端口；有 NAT/反向代理时仍显式配置可达地址，并保持游戏及Native入口的端口映射一致。GM 和包查询仍仅监听本机。

运行参数放在业务命令之前。重复参数、缺值、无效 IP/端口和未知命令以退出码 `2` 拒绝，不创建数据库。`--help` 单独使用，不加载资源；`--gm help` 同样不加载运行库。命令分派见 [ServerCommand](../../Server/DfoServer/Application/ServerCommand.cs)，参数校验见 [ServerOptions](../../Server/DfoServer/ServerOptions.cs)。

局域网客户端连接服务端可达地址与频道端口；分类切换还需要目录中各游戏入口可达。需固定防火墙或端口映射时，指定 `--channel-entry-port-base`，例如 `23103` 对应默认目录的附加端口 `23103–23131`；主游戏入口仍使用 `23101`。自动分配的端口在启动后的 `Logs/ready.json` 的 `ChannelEntries` 中查看，重启可能变化。分类身份及共享业务见[帧与频道](../协议/帧与频道.md#分类入口与共享服务)。

## 自测与发布

基础检查不需要资源：`Tools/Check-Development.ps1` 统一运行构建、依赖检查和合成测试；服务端也可单独使用 `--selftest-core`。下列完整自测与 TCP 入口需要准备 PVF。

```powershell
dotnet run --project Server/DfoServer -- --selftest
dotnet run --project Server/DfoServer -- --selftest-tcp
dotnet run --project Server/DfoServer -- --selftest-tcp "commands,startup,native-login"
dotnet publish Server/DfoServer/DfoServer.csproj -c Release -r win-x64 --self-contained true -o dist/win-x64
```

TCP 回归用独立程序目录、空闲端口和固定 Data/Logs 布局启动子进程，产物写入忽略的 `build/tcp-tests`，不写开发者的玩家库。自定义构建输出直接执行 `dotnet <构建目录>/DfoServer.dll --selftest-tcp`。验证要求见[贡献指南](../../CONTRIBUTING.md#验证)。

普通副本目录与掉落池的启动装配复用 `startup` 事件，固定阶段写入开始、完成及单调耗时；结构化日志附加本进程 CPU、内存及累计分配快照、GC 次数及暂停累计值/阶段差值，不记录 PVF 内容或玩家数据。指标仅用于定位启动停顿，不能单凭峰值或缺少完成日志判定根因。TCP 夹具仍使用原 45 秒就绪门槛，超时时只读原子进程句柄的 CPU/内存及最多 64 KiB 日志尾部；取不到的指标标为未知，不附加跨进程 GC 猜测、不重试启动，也不放宽业务断言。


发布输出包含启动脚本、`Sqlite/game_schema.sql` 和 `Data/Pvf/` 目录；跨平台更换 RID。该命令只生成本地文件，不部署。多个正式或开发实例须使用各自的程序目录及端口。

## 本机测试构建（Windows）

[Build-Server.ps1](../../Tools/Build-Server.ps1) 发布 Windows x64 Release 自包含游戏服务和单文件 Windows 启动器。可双击仓库根的 [build-server.bat](../../build-server.bat)，或从任意当前目录运行脚本；`OutputDirectory` 和 `PvfPath` 的相对路径均以仓库根目录为基准。

```powershell
# 默认运行目录 dist/win-x64，不需要目标机器另装 .NET
./Tools/Build-Server.ps1
# 自定义运行目录；也可以传入本机绝对路径
./Tools/Build-Server.ps1 -OutputDirectory ../play-ServerS5A9 -PvfPath "<匹配客户端的 Script.pvf 路径>"
# 默认目录启动；自定义目录时打开该目录中的启动器
./dist/win-x64/DfoLauncher.exe
```

输出目录就是程序、资源、存档和日志的固定根目录。后续构建始终指定同一目录；更换输出目录会使用另一份 `Data/game.db`，不会自动搬迁或合并旧存档。使用匹配的 S5A9 客户端连接 `127.0.0.1:23100`，游戏端口为 `23101`；服务端生成文件不包含客户端及其补丁。

脚本先在独立临时目录完成服务端及启动器发布和 `--help` 检查，再取得运行目录的 `Data/server.lock` 与 `Data/launcher.lock`。更新前先正常退出客户端、停止该目录的服务端并关闭启动器；目录被占用时拒绝覆盖，不停止任何进程。源码、工具、临时构建目录及含目录链接的输出不能用作运行目录。

重复构建只更新程序、依赖、内置资源和 SQL，不删除已有 `Data`、`Logs` 或启动器设置。程序目录内的整个 `Data`（含数据库、WAL/SHM、PVF，排除服务端和启动器实例锁）在覆盖前复制到输出目录旁的 `<输出目录名>.backups/<时间戳-随机标识>/Data`；备份失败即停止更新。自定义到程序目录外的存档和 PVF 不在此备份范围，也不会被构建脚本修改。备份不自动清理，需自行管理磁盘空间。发布或帮助检查不初始化玩家库；首次实际启动才会创建数据库或按[数据库规则](数据库.md)升级兼容旧库。恢复前正常停服，并配合相匹配版本的程序使用备份。

`PvfPath` 只在运行目录缺少 `Data/Pvf/Script.pvf` 时复制。已有 PVF 始终保留；未传参数时可使用源码中准备的 PVF。编译不要求资源，缺少 PVF 时脚本提示放置位置。临时发布失败不会覆盖现有运行文件；复制过程中发生错误时保留临时产物和已完成的备份，排除原因后重新运行脚本。程序文件更新不是整目录原子替换，失败后应重新构建成功再启动。

## Windows 单 EXE 分发

双击仓库根的 [build-single-server.bat](../../build-single-server.bat)，或使用同一构建脚本的单文件模式：

```powershell
./Tools/Build-Server.ps1 -SingleFile
# 自定义目录，以及本机可选的外部资源复制
./Tools/Build-Server.ps1 -SingleFile -OutputDirectory dist/share-server -PvfPath "<匹配客户端的 Script.pvf>"
./dist/win-x64-single/S5A9Server.exe
# 命令行使用同一个 EXE 的服务端入口
./dist/win-x64-single/S5A9Server.exe --server --help
./dist/win-x64-single/S5A9Server.exe --server --pvf-path "<资源文件>" --data-dir "<存档目录>" --gm list
```

默认输出 `dist/win-x64-single/S5A9Server.exe`，分发时同时保留构建脚本复制的 `LICENSE`、`THIRD-PARTY-NOTICES.md`、`THIRD-PARTY.md` 和 `LICENSES/`，并按[项目许可](../../README.md#许可证)提供对应源码。启动器通过同一个 EXE 的 `--server` 模式创建和管理后台服务进程；托管依赖从 .NET 单文件 bundle 加载，默认频道脚本和建库 SQL 为程序集资源，不自解压整套服务端目录。SQLite 等原生依赖由 .NET 自动释放到用户系统缓存，目标机器不需要另外安装 .NET 或 Python。分发不要求附带 DfoServer.exe、DLL、Resources、Sqlite 或批处理。

PVF、`Data/game.db`、`Logs` 和 `launcher.local.json` 不打入 EXE。双击仍使用现有 PVF/存档选择界面，默认及相对路径仍基于当前 EXE 所在目录。使用既有进度时选择原存档目录；更换目录不会自动搬迁或合并旧库。设置在首次成功启动后保存，复制 EXE 到新目录不会携带玩家数据。发布脚本的 `PvfPath` 只复制外部 PVF 到新目录的默认资源位置，不将它放进程序。

单文件和目录模式默认使用不同输出目录，构建单文件不覆盖原 `dist/win-x64`。重新构建同一模式时沿用前面的占用检查、Data 备份和设置保留规则；新目录发布一个 EXE 及上述许可文件，不复制外部 DLL 或 SQL。已有目录中用户自行添加的文件不会被删除。直接发布服务端项目及其它平台保留原命令行目录模式，分发前须从仓库根复制许可文件。

## 手动打包 Release

[发布工作流](../../.forgejo/workflows/release.yml)合入默认分支后，具有仓库工作流运行权限的成员在 Codeberg 仓库的 **Actions → 打包 Windows 单 EXE Release → Run workflow** 中选择 `master` 并运行。版本号留空时，首次使用 `v0.1.0`，以后读取已有标签和 Releases（含草稿与预发布）中的最高 `v主.次.修订[-后缀]`，将修订号加一；例如 `v0.1.2` 后生成 `v0.1.3`。也可手填一次 `v1.0.0` 升级主/次版本，后续继续自动递增。发布任务串行调度以避免同一工作流争用版本号；人工同时创建同名版本时拒绝覆盖。只支持手动发布 `master` 的本次选定提交；普通提交和 PR 不触发打包。

发布成功（附件齐全并已发布）后，`Tools/Publish-Release.ps1` 会自动清理旧版本：只保留最新 3 个已发布 Release（含本次，`-KeepLatest` 可调，0 表示不清理），更旧的 Release 连同附件删除，git 标签保留，草稿与本次版本永不删除；清理失败只警告，不影响发布结果。上传遇到 HTTP 413（配额不足）时，会先按“旧版本保留 KeepLatest-1 个”清理一次再重试上传。`-CleanupDryRun` 只列出将删除的版本。保留逻辑可用 `pwsh -NoProfile -File Tools/Test-ReleaseRetention.ps1` 以 mock 数据验证。

任务先在独立 job 运行 Release 无资源基础检查；只有检查成功后，打包 job 才检出同一本次选定提交、检查版本及标签不存在，通过与 [build-single-server.bat](../../build-single-server.bat) 相同的 [Build-Server.ps1](../../Tools/Build-Server.ps1) 单文件入口生成包。上传 ZIP 和 SHA256 全部成功后，自动在仓库 **Releases** 显示可下载的预发布版本。使用工作流自动令牌，不需另存个人 Token；仓库须启用 Releases 和 Actions，并有可用的 `codeberg-medium` runner（每个 job 最多 10 分钟）。基础检查与打包发布分别设置 9 分钟预算，为 runner 收尾预留时间；两者通过依赖关系串行执行，不共享工作区，避免累计耗时触发单个 runner 的上限。已有版本或标签一律拒绝，不删除或覆盖；上传失败可能留下草稿，核对后使用新版本号重新运行。

下载附件 `S5A9Server-<版本>-win-x64.zip` 及同名 `.sha256`，不是页面自动提供的源码归档。ZIP 包含 `S5A9Server.exe`、`README.txt`、`build-info.json`，以及 `LICENSE`、`THIRD-PARTY-NOTICES.md`、`THIRD-PARTY.md` 和 `LICENSES/`；构建信息记录版本、源码提交、工作区是否修改以及 Windows 启动检查状态。包内说明提供上游源码基线地址；分发本地修改包时须另行提供包含实际改动的完整对应源码。包不携带客户端、PVF、玩家库、日志或本机配置。解压后按前述单 EXE 说明自行选择资源和存档，更新时正常停服、关闭启动器、更新许可文件并保留原数据。

远端使用 Linux .NET SDK 镜像交叉编译 Windows x64 包，显式启用 `EnableWindowsTargeting`；分层分析器和独立检查入口按构建机目标生成，继续参与编译，不继承服务端的自包含单文件发布属性。打包任务固定使用 `Asia/Shanghai`（北京时间），ZIP 内文件修改时间按该时区记录；本机打包仍使用本机时区。无法在该 runner 上执行 Windows EXE，因此标为预发布并明确记录未完成 Windows 启动检查。基础检查通过不代替 Windows 实机和客户端验收。手动打包仍可能等待公共 runner 排队，与 PR 检查分别运行。

本机也可通过原批处理生成相同格式的分发包：

```powershell
./build-single-server.bat -PackageVersion v2026.10.15-test1
# 或自定义空的输出目录（相对路径以仓库根为基准）
./Tools/Build-Server.ps1 -SingleFile -PackageVersion v2026.10.15-test1 -OutputDirectory dist/release-test1
Get-FileHash ./dist/releases/S5A9Server-v2026.10.15-test1-win-x64.zip -Algorithm SHA256
```

打包默认输出 `dist/releases`，要求输出目录为空且不接受 `PvfPath`；不会压缩或更新已有运行目录。Windows 上执行原有启动器/服务端帮助和内置 GM 检查，非 Windows 仅允许此分发模式，普通本机更新入口仍限定 Windows。源码状态不干净的本机包会如实标记，远端上传脚本拒绝发布该包。打包命令只生成本地文件，不自动上传；只有工作流最后一步调用 [Publish-Release.ps1](../../Tools/Publish-Release.ps1) 进行远端发布。

## 后台实例与 GM

Windows 启动器可勾选“启用 GM 工具（仅本机）”，GM命令/网页端口默认23102/23103。启动服务时启动器向服务端传入 `--gm-port` 与 `--gm-web-port`，GM 网页内嵌在服务进程中，服务就绪后点击“打开 GM 网页”即打开 `http://127.0.0.1:{GmWebPort}/`，无需另外启动 Python。开关和端口在成功启动后记住（`launcher.local.json`），旧设置缺少这些字段时默认关闭；`Build-Server.ps1` 生成的默认配置开启 GM。修改前先停服。目录模式和单EXE一致，详细使用见[开发GM](GM.md#4-单独的本机网页)。

Windows 开发者可使用 [Start-Server.ps1](../../Tools/Start-Server.ps1)：

```powershell
./Tools/Start-Server.ps1 -Action Start -ServerIp auto
./Tools/Start-Server.ps1 -Action Restart -GmPort 23102 -PacketCapture
./Tools/Start-Server.ps1 -Action Stop
```

该脚本构建 Debug 程序，按固定布局运行，在 `Data/server-instance.json` 保存 PID、创建时间、执行路径和启动参数，停止前核对身份。程序日志仍在 `Logs`；脚本的 stdout/stderr 按运行批次放在其子目录中。

前台服务用 Ctrl+C 停止，也可在本实例 `Logs` 中创建 `stop.request`。再次启动前移除旧停止请求，检查 `ready.json` 中 PID 与本次进程相符。macOS/Linux 后台管理须自行保存进程身份，Windows 启停脚本不可用于这些平台。

停止会取消频道、游戏及 GM 的待接入操作并等待连接清理。Windows 在已取消的待接入操作中返回 `SocketError.OperationAborted`（995）时按正常停止处理；未取消的套接字错误及其他监听故障继续传播，不据此报告正常退出。无资源自测覆盖监听取消、重复取消及故障传播，真实启动与停服仍由对应 TCP 组验证。

在线 GM 须在服务启动时显式启用本机端口，网页使用相同端口：

```powershell
./start-server.bat --gm-port 23102 --gm-web-port 23103   # 内嵌 GM 网页：http://127.0.0.1:23103/
dotnet run --project Server/DfoServer -- --gm-port 23102 --gm-web-port 23103
dotnet run --project Server/DfoServer -- --gm-port 23102 --gm list
```

离线 GM 直接操作当前程序目录的 Data；命令与在线/离线限制见[开发 GM](GM.md)。

## 控制台日志

正常服务默认向 stdout 输出英文纯文本日志，格式为 `[yyyy-MM-dd HH:mm:ss.fff] [INFO|WARN|ERROR] [event] message`；时间为进程所在系统的本地时间。参考 S4A21，资源加载显示 `Loading Script.pvf...` 和 `Script.pvf: OK (123.4 ms).`，监听信息逐行显示 `Channel #ch.10 listening on TCP ...`、`Game server listening on TCP ...`、`Advertised game endpoint: ...`、`GM control: ...`、`Packet capture: ...`。业务事件使用英文说明和 `key=value` 字段，嵌套位置等字段以点号展开，路径直接显示，stdout 不输出 JSON 对象。前台终端和后台重定向使用同一格式，不要求开启抓包。原 `Logs/server.jsonl` 继续保存完整结构化事件。

启动日志覆盖配置、PVF 打开、城镇/物品/角色/任务/技能资源、数据库及当前 schema、Runtime 装配与命令注册，并显示各加载阶段的结果和耗时。数据库记录成功完成已有初始化/迁移检查后的版本，不额外扫描资源或玩家数据。监听记录分别显示频道名称、频道与游戏监听端点、向客户端通告的游戏端点、GM 状态与本机端点、抓包状态及目录、服务日志路径；只有监听、原就绪日志刷新和 `ready.json` 写入均完成才输出 `Server ready`，同时给出本次 PID、程序版本、构建提交号与存档 schema 版本。已有缺失地图信息作为资源警告显示；启动失败显示失败阶段及异常类型，stderr 保留详细错误并返回非零退出码。

`Logs/ready.json` 除端口、频道入口、PVF/数据目录与 PID 外，还带 `ServerVersion`、`Commit` 与 `SaveVersion`：前两项来自构建期写进程序集的版本与 git 提交（`AssemblyInformationalVersion` 的 `+` 后缀），从源码 zip 构建时 `Commit` 为空串；`SaveVersion` 是本次程序使用的存档 schema 版本。启动器据此在服务端版本旁标注存档版本与提交号，据此判断这份程序读哪一版存档。

运行日志显示连接、频道握手、认证、选角/退出、区域切换、副本选图/入场/结算/回城、任务接取/交付、GM 和已有拒绝事件。常规 `send`/`recv`、移动坐标、客户端通知和逐怪击杀不逐条显示。控制台输出采用同步逐行写入，没有后台队列；控制台管道写入失败后停用控制台输出并向 stderr 报告，不改变原文件日志及游戏连接。

请求分派返回 `Unhandled` 时打印一次 `Unhandled packet`，包含连接编号、会话阶段、kind、十进制/十六进制 opcode、枚举名、正文长度与完整十六进制正文；空正文显示 `empty`。未注册命令及处理器返回未处理的子型都经过该入口，响应行为保持原样。`LOGIN`、`LOGIN_PRECHECK`、`CLIENT_SPEC_STATISTIC` 沿用认证脱敏，正文显示 `[login-redacted]`；已完成登录的连接仍拒绝重复登录包，不另行输出其正文。帮助、资源查询/扫描和自测命令保留各自输出格式，不启用正常服务的控制台事件输出。

## 包体抓包

```powershell
./start-server.bat --packet-capture
./start-server.bat --packet-http-port 18081
./start-server.bat --packet-http-port 18081 --packet-capture
dotnet run --project Server/DfoServer -- --packet-capture "<抓包目录>"
./Tools/Start-Server.ps1 -Action Start -PacketCapture
```

省略目录时写入固定 `Logs/packet_log.txt`；显式抓包目录相对于启动工作目录解析。文件使用无 BOM 的 UTF-8 追加写入。

启用 `--gm-web-port` 即可在同一个 GM 网页 HTTP 端口读取包查询，不需要另开 `--packet-http-port`。查询共用当前服务的 `PacketCapture`，不另建历史或在线状态；仅启用网页不会创建 `packet_log.txt`。GM 原有 `/api/status` 和 `/api/online` 保持原意。

| GM 网页路径 | 返回内容 |
|---|---|
| `/api/packets` | 本次进程最近最多400条包记录 |
| `/api/packets?connectionId=编号` | 指定客户端连接的保留包 |
| `/api/packets/sessions` | 活跃客户端连接摘要及收发计数 |
| `/api/packets/status` | 监听配置、连接与完整收发帧计数 |
| `/api/online` | GM 既有的在线角色内存快照 |

GM 包查询仅允许本机 Host 和对应监听端口的 Origin，不接受 GET 正文，最多同时处理8个查询、每个10秒截止，忙时返回503。沿用 GM 的安全响应头、取消及退出收尾，不经过 GM 写命令或查询玩家数据库。

旧脚本仍可单独启用 `--packet-http-port` 使用以下兼容接口；它与 GM 网页可共享同一份缓存，但端口不能相同。当前仅需要 GM 网页时应省略该选项：

| 路径 | 返回内容 |
|---|---|
| `/health` | HTTP入口存活，不代表游戏业务验收通过 |
| `/api/status` | 当前进程、监听配置、累计连接与完整收发帧计数 |
| `/api/sessions` | 活跃客户端连接的 `connectionId`、协议、`remoteEndpoint`、建立时间、收发计数和最后实收opcode |
| `/api/packets` | 本次进程最近最多400条包记录，按实际记录顺序排列 |
| `/api/packets?connectionId=编号` | 仅返回该客户端连接的保留包，编号从 `/api/sessions` 或包记录取得 |
| `/api/characters/online` | 从现有会话读取已选角色的账号、角色ID/名称、就绪标记、细阶段和粗user状态 |

每条包记录包含 `timestamp`、`connectionId`、`protocol`、`direction`、`kind`、`opcode`、`name`、`totalLength`、`bodyLength`、`bodyHex`、`bodyTruncated` 和 `redacted`。`bodyHex` 最多保留前4096字节，原正文长度不变；完整常规帧仍使用文件抓包。认证正文为空且 `redacted=true`，与文件及未处理日志共用脱敏判定。客户端过滤发生在同一全局有界历史上，不建立单客户端无界缓存；未知编号返回空数组，非法、空值、重复或未知查询参数返回400。断线后客户端摘要移除，已保留的包仍可按原编号查询；重启清空内存历史，未启用前不补采。

`activeSessions` 是活跃TCP连接数，`activeGameSessions` 只计游戏连接，不等于已选角色数量。在线角色直接取现有owner保护下的内存快照，不扫描数据库或另建在线状态；已选角但未就绪时 `ready=false`，旧generation不发布新会话结果。查询不会改变游戏状态、协议正文或包序。

GM 合并入口复用 Kestrel；独立兼容入口仍使用本机 TCP HTTP，不依赖 Windows HTTP.sys URL 权限。兼容入口只允许本机Host/Origin和GET，未知路径404，写方法405，查询失败500，不伪造成功。请求头上限8192字节，GET不接受正文或分块编码；同时处理最多8个查询，网络等待设10秒截止，退出取消并等待本次请求清理，慢HTTP连接不串行拖住其它本机查询。在线角色快照仍取得原owner锁，不宣称完全独立于业务锁等待。响应使用 `no-store`，不开放CORS。接口无登录鉴权，角色信息、连接地址和包体属于运行诊断数据，不能通过反向代理或端口转发暴露给其他机器。

例如先执行 `curl http://127.0.0.1:18081/api/sessions` 查找客户端编号，再执行 `curl "http://127.0.0.1:18081/api/packets?connectionId=12"`。无资源自测覆盖HTTP安全、过滤、容量及取消；隔离TCP组 `packet-capture` 覆盖真实收发与文件抓包开关，`packet-http` 覆盖HTTP只读入口的真实收发、选角/断线及与文件抓包的独立性，两者不代替Windows客户端实机验收。

`server.jsonl` 与抓包文件各自复用一个文件句柄和固定大小缓冲，不为每条记录创建任务或排队。缓冲满时同步写入，定时器每秒刷新未写出的内容；正常退出先等待连接清理，再排空并关闭日志。启动就绪文件写出前会刷新服务日志。实时读取应允许文件共享写入，强制结束进程可能丢失缓冲尾部；刷新不等于磁盘掉电持久化保证。资产审计仍随数据库事务提交，不依赖文本日志刷新。

记录时间、连接编号、频道/游戏协议、SEND/RECV、kind、opcode、枚举名、帧长、body 十六进制及完整 raw。接收在业务解析前记录，发送只记录已完成写入的帧；游戏 C2S/S2C 包头分别为 13B/16B，频道为 11B。频道 body 保留线上编码，不自动解密或解压。日志记录完整应用层帧，不代表 TCP 分段或 PCAP，未收完的帧不记录。

包含凭据的 C2S `LOGIN`、`LOGIN_PRECHECK` 和旧扩展 `CLIENT_SPEC_STATISTIC` 只记包头，并标记 `authentication payload redacted`，不输出 body/raw。其余包不截断。首个 `CHANNELINFO` 的线上编码见[原生登录](../协议/原生登录.md)。抓包格式化和缓冲写入仍会增加磁盘占用和收发延迟，不自动轮转；目录不可写或写盘失败时停用抓包并向 stderr 报告一次，不中断游戏连接。服务日志写入失败会报告并保留异常，后续写入或关闭继续返回该错误；定时刷新失败不会从定时器线程抛出未处理的 I/O 异常。抓包文件不提交。
