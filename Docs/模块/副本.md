## 角色死亡与复活币

正式单人副本加载完成后接收 `DIE_CHARACTER(40)` 的两个 u16 坐标，普通角色另带一个保留原值的 u16 上下文字段，由当前 Session 的角色 key 发布 `DIE_STATE(32)` 死亡状态。死亡资格保存在当前正式实例内；重复死亡不写数据库，返回城镇、换角或新实例不会继承旧资格。死亡期间不能过房，仍可按原放弃流程返回城镇。

`USE_COIN(41)` 只处理当前死亡角色的本人 key。普通副本每次成功复活从角色钱包扣除一枚复活币，复用原库存事务及 revision 校验；提交后安装实际角色快照，再依次发送完整 ACK41、32 的复活状态和 Main 槽1的绝对剩余余额14。普通副本零余额返回失败；修炼场免费复活并同步原余额。活角色、错误 key 或失效实例不扣币。数据库异常沿现有连接错误处理，事务回滚且不发布成功。发送失败不撤销已经提交的扣币，重复41不会再次消费。

复活保持原 Run、房间、怪物、掉落及结算身份；同事务产生的寻物任务条件变化按既有通知发布。每次接受死亡按 external 的 `dungeon_death_return.go` 启动10秒回城计时，重复死亡替换旧计时。到期复验账号 generation、选角 epoch、实例和本次死亡序号，再沿原回城流程发布24及任务刷新；没有ACK40或ACK42。计时不绑定角色快照或房间 epoch，因此购买换快照或残留攻击不会丢失计时；成功复活、主动回城、换角及断线使旧回调失效，每个连接的任务在断线时取消并等待退出。

死亡窗口的现场购买使用普通商城CMD64及真实PVF商品：`100004`为100点券购买1枚复活币。费用与发币沿原商城库存事务提交，完整ACK64后刷新14及53；购买成功仅增加余额，随后仍由客户端发41使用，不重置死亡计时。购买或复活失败保留当前死亡与计时。入口资格及价格来源见[背包与装备](背包与装备.md#npc-商店买卖与限购)。

字段来源及本版 ACK41 与 external 的差异见[角色死亡与复活协议](../协议/副本.md#角色死亡与复活币)。自动回归覆盖正式Session、请求codec和 `--selftest-tcp dungeon-revive,formal-dungeon,cash-shop,dungeon-settlement`。直接使用复活币、死亡窗口现场购买及10秒自动回城均已通过匹配客户端实机验收。

## 副本练习模式

普通选图的 C2S16 在 offset8=1、FFFF token、任务号0且其余模式字段为0时进入练习；5000修炼场、7142职业体验及非零任务号的1459授权回放仍独立处理。练习沿正式副本Run、账号owner、选角epoch及user状态推进，不维护另一套在线实例。仍验证城镇入口、等级、难度、地图与原生战斗对象；`[prohibit practice]` 非零或声明形状未知时拒绝，未声明或显式0允许。只从无任务连接的普通maze抽取，不根据活动主线改走剧情路线。

练习不要求持有、不校验或扣除入场门票、材料、金币和疲劳，也不校验、占用每日或其它玩法入场次数；重复入场和再练习没有玩法次数上限。练习与普通/传奇深渊、随机密门及强袭付费入场互斥；原副本maze含深渊声明不影响练习，但只使用普通地图，不扣深渊票、不安装深渊波次或奖励。深渊及普通正式入场继续沿各自原收费与次数规则，不能将“普通图支持练习”解释为普通模式免费。

练习死亡只确认本次内存事实，不产生击杀经验、普通/任务/被动物件掉落、任务进度、宠物经验、幸运星或翻牌奖励。普通练习、修炼场和职业体验统一通过`HasFreeCombatConsumption`免扣普通客户端效果道具、技能及装备脚本材料、复活币，但仍验证源物品、数量、冷却和实际死亡状态；晶之契约不扣周期材料，宠物不进入战斗饱食消耗。免消耗不免除主动购买、丢弃、契约或礼包等独立资产业务，也不把普通副本的禁止翻牌标记当作免扣资格。道具大类与扣除合同见[背包与装备](背包与装备.md#普通恢复药)。入场沿既有存档预留尝试号和对象key，用于实例身份及防重放，不作为玩法次数限制；不新增练习库表或奖励账本。

## 剧情房间推进

普通与剧情房间共用特殊父对象和控制子怪规划。子怪等级为0或负数时使用副本基础等级，正数保持资源指定等级；子怪退场沿场景对象处理，不授予普通击杀经验。剧情暂停请求191按本人场景回复170，同步暂停状态及类型，不修改角色存档。已加载的Dungeon或Settlement场景收到state=1恢复请求后，按170→3补发本人角色状态，使演出隐藏的角色重新激活；三个type共用此流程。Loading阶段仅同步170，后续真实加载确认仍发送初始角色状态；重复恢复只重发状态投影，不重建Actor、加载、任务或结算。

同坐标叠层仍有后续资源层时，先按资源顺序推进，不能提前走向普通邻格；末层结束后恢复正常过房，返回同坐标时恢复实际来源基础房间或剧情阶段及其状态。任务maze的Boss坐标重复时，将对应地图行按资源顺序建立独立剧情阶段，保留普通起始房间；一行多个地图编号保持为同一阶段的候选列表，剧情使用资源首项。每阶段使用独立房间状态和对象key，沿原加载流程切换，最后阶段才产生终点清图事实。

任务单地图清图目标明确等于唯一Boss坐标的基础地图时，即使迷宫的对应行使用`map`标记，入场计划也将该行投影为基础Boss图；同坐标叠层目标沿用相同规则。投影只改变本次计划的房间种类，保留地图编号、路径、坐标、候选、全部真实演员及原接取身份，不改共享资源定义。普通无目标路线、非清图任务、非Boss坐标目标和歧义路线不能借此放行，通关仍经正式Run、真实死亡与原成长事务确认。

C2S45的同坐标kind1在末层没有后继且已清房时，同样表示返回来源基础房间。恢复使用NOTI29的operation2/mode0缓存正文，保留基础房间的原怪物key、死亡集合、种子和任务接取，不重新创建Actor；随后真实加载确认仍沿原流程执行。返回后的最后一个同坐标kind1仅消费本次收尾标记，不发送ACK或地图、重置加载或再次进入首层。其他坐标、旧实例和已消费标记不能充当该确认，普通清怪及邻房门禁保持。

实际Boss房间的死亡提交产生ClearFact时，若本实例接取集合中只有一个尚未达成的被动物件猎杀目标，且它是当前maze关联父任务的无奖励子任务，则同一死亡事务推进该目标。父任务、接取身份、地下城、难度及实际清图事实均复用现有任务合同；重复死亡或SQL失败不会多计进度。

普通`map/boss`行的多个地图编号为随机候选，按编号去重后在本次入场资源规划时选择并固定；重复进房沿房间缓存，不重新抽选。剧情阶段行首项保持原阶段顺序，同行其余编号与该坐标其他基础候选合并，排除该坐标全部阶段首项后选普通基础图；没有额外候选时回退首阶段模板，并使用独立基础身份。入场基础图不自动推进阶段，基础与阶段各自规划怪物、对象key和物件事件缓存，最后阶段才产生终点清图事实。`layered`行的多个编号是有序层列表，保持原始顺序，重复模板也有独立层身份。回放复用同一资源解析入口；条件传送的替换地图使用本次已经选定的基础模板，阶段切换时不覆盖对应剧情阶段，普通自动地图池排除剧情及叠层的全部声明编号。只装载本次使用的地图，选中资源不可用时返回入场失败，不临时替换路线。

maze的显式`clear condition`目前接入单条、数量1的`hunt monster/hunt boss`。目标只来自本次房间的实际普通怪物死亡；`hunt boss`额外要求真实Boss品级。命中后清退当前房间其余阻挡敌人，清退不增加击杀经验、任务进度或掉落；多Boss及敌对Boss APC仍须各自真实死亡。非终点继续原路线，实际终点才进入原死亡事务、清图凭据及结算流程。普通Boss清房流程保持生效，不要求额外命中显式目标。

`warp map condition`声明按资源原序保留有向边，同一起点可以有多个不同目标；完全重复边、半对、未闭合或非法块仍隔离为资源错误。Boss入口的同格替换只接受每个来源唯一目标，多目标不任取首项。没有Boss入口的声明不生成条件替换地图；声明解析成功也不代表正式Run已经允许非相邻传送，仍需对应的真实触发与移动合同。

`dungeon-story-events`中的资源与Session回归使用5934的三房任务路线，完整保留起点四名友方、末房107002770与友方APC15442，验证显式/普通0同接取入场、正常相邻移动及未通关退出不制造任务进度或奖励。当前非相邻kind0与跨格kind1仍拒绝；该覆盖不证明乘骑warp或Windows客户端流程已经可用。

以下差异先保留为未实现项，不计入上述支持范围：

- 多目标、数量大于1、`hunt apc/seeking`及`clear condition/clear map`列表的聚合语义尚未确认；不把任意一个目标命中解释为整组完成。
- `destroy object`的多实例、数量大于1及混合物件条件仍未接入；唯一数量1终末物件及精确零击杀结算见[单人副本实例](单人副本实例.md#战斗事件与结算)。不能伪造怪物死亡、经验或截断物件模板编号作为Boss key，副本条件也不能借用无关活动任务身份。

- 初始角色状态仍在真实加载确认后发送，不等待演出恢复。教程特有的初始状态延迟与一次性规则尚未接入；普通演出恢复使用上面的角色状态投影流程。

## Boss入口条件与条件传送

maze独立保存`boss room entrance condition`的`clear action/time condition/hunt monster`声明与`warp map condition`坐标对。时间参数和目标额外字段保留原值，目前入口按猎杀数量判定，不由时间参数猜造倒计时。统计只来自本次Run各房间已经提交的目标怪物死亡，不计重复报告、APC、控制子怪或Boss清场移除。

数量达标后，在死亡通知38之后发送一次入口开放通知312；写入完成才启用条件地图替换。请求仍沿实际逻辑房间和静态连接移动，匹配source坐标时只使用destination坐标的地图模板，保持source的坐标与Boss属性。替换房间在入场规划时预留独立key，保留自己的死亡、掉落与加载缓存，不继承原房间死亡集合。

逻辑Boss房间的替换沿原死亡事务和通关链完成，清图事实与领奖凭据使用实际替换地图；普通逻辑房间的替换不会成为终点。任务明确要求叠层终点时，替换清房后仍须按资源顺序进入该层。闭合maze块后的入口与传送声明归前一条路线，直到下一条maze开始，布局字段仍限定在块内。未达标或通知尚未发送时保留原房间。来源或目标地图不唯一、坐标不完整的声明报告资源错误；无Boss入口条件的其他传送模式仍未接入。

## 剧情电梯

电梯按地图内容识别：四个`event monster position`坐标、滚动对象1111、控制对象1113，以及特殊父对象1112声明的控制怪56716。不绑定任务、职业或地图编号。剧情入场同样预留并下发父对象与控制子怪的独立key；父子关联沿用当前客户端的特殊actor合同，不将控制怪加入普通清房阻塞或击杀奖励。

加载确认和角色状态通知后启动本连接的电梯计时，每15秒发送一次254，计数1至4、状态0。计时结束不代替控制怪退场。当前房间控制怪的真实退场先发送254结束状态，再回复空掉落38：计数不大于3时状态1，否则状态2。完成后旧计时不再发布，换图沿原资源连接和清房规则执行；未结束的电梯不能提前换图。

状态保存在当前Run房间中，计时器不占用账号锁等待，也不写数据库。每次推进和出队复验账号代次、选角epoch、副本实例、地图及电梯状态；同角色的普通revision变化不重置计时。每连接最多一个计时任务，换电梯取消旧任务，断线先取消并等待计时退出，再结束会话。

## 状态归属

[DungeonProbeState](../../Server/DfoServer/Development/Dungeons/DungeonProbeState.cs)由 Runtime 的工厂按连接创建，持有初始化计划、加载/返回标记及 [DungeonProbeRun](../../Server/DfoServer/Development/Dungeons/DungeonProbeRun.cs)。状态、运行对象和候选包体构造均属于 `Development/Dungeons`；正式 `Game` 层不引用诊断实现，共用的准入/怪物计划仍保留在 `Game/Dungeons`。

诊断Run 保存实例 ID 和当前房间序号，并核对角色、选角 epoch 与角色 revision。加载后只接受本房间已宣布 key 的死亡报告；诊断重复报告不重复通知，旧房 key 不进入新房。对象 key 在同一连接单调分配，重选不立即复用。返回选角/退出及连接关闭时通过活动生命周期结束旧 Run 并释放计划、房间状态；清理只影响本连接，并保留其对象 key 计数器。

全部已宣布怪物均收到诊断死亡报告后，才允许迷宫内真实曼哈顿邻格。先解析目标资源并构包，再发布房间状态，发送 ACK45 和 NOTI29，等待新的 C2S37；回到缓存房间不重生已报告死亡的怪物。未知生成条件和品级明确拒绝，不能用空房替代。

通用连接上下文只持有 [IGameConnectionActivity](../../Server/DfoServer/Network/Protocol/IGameConnectionActivity.cs) 门禁与清理合同，不携带诊断字段。城镇、技能、背包等处理器通过 `BlocksTownActions` 保留原有活动期间拒绝规则，不识别诊断模式。诊断期间阻止 35/631/36/1426 写城镇位置；退出成功或重新选角解除阻断，退出不恢复同 epoch 的再次初始化资格。诊断不进入正式 Loading/Dungeon/Settlement 阶段、不修改持久落点或任务；共用入口的 MapSelect 在诊断 C2S42 成功退出后结束、恢复 Town 并重新加入同屏。原诊断包序与同 epoch 使用记录保留，发送失败关闭、不重试结算；客户端死亡报告不构成正式通关事实。

## 验证边界

副本重复声明的`difficulty level`只有五个整数标志的类型、值和顺序完全相同时才共用同一难度表；冲突、残缺或未知声明仍拒绝。剧情`difficulty size`和指定难度继续独立校验。英雄冢的任务3240沿其真实八房路线进入，定向`--selftest-tcp hero-tomb-entry`覆盖接取、入场、加载、重复加载、拒绝后继续请求、回城重进及重连保持任务。

有完整`story mode`块的任务路线只按块内唯一`difficulty size`校验故事难度，不受块外普通路线的`designate dungeon difficulty`或`difficulty level`覆盖。多个故事块必须各自完整闭合、具有合法难度及唯一非空纯整数`quest list`，任务归属不能重叠；使用最终所选maze的连接任务定位唯一故事块，不能借用请求中的零任务号或父接取身份。单块保留原任务引用token的兼容行为。显式任务、普通选图匹配的任务路线及回放沿同一规则；未声明故事块时沿原指定难度与普通难度表。嵌套、未闭合、任务归属不明及未知难度声明仍拒绝，普通路线的难度范围和原始资源声明保持。真实夜之摩天楼6206、6214分支在`dungeon-entry-plan`定向检查原五房路线、完整演员及零难度边界；这些领域检查不代替Session/TCP和客户端验收。

任务迷宫在显式任务入场、普通选图的活动/完成任务路线、父任务回退和任务回放中统一去重。同一任务连接的状态、编号和难度声明必须一致，并且尺寸、Greed、起点/Boss点、普通/叠层/剧情/条件地图（含候选ID）、Boss入口条件、传送、通关条件及资源错误一致，才保留首次声明。不同任务、难度或行为不能仅因地图相同而合并；普通无任务路线的随机选择保持原规则。定向 `--selftest-tcp dungeon-entry-plan` 覆盖等价重复、真实歧义与匹配转职任务的两种选图入口。

## 正常战斗闪退的证据边界

匹配客户端正常战斗仍可发生 `C000041D` 用户回调包装异常。WOW64转储必须分别解释x86应用与native64异常结构；异常stream中的低32位地址不能直接当作故障代码。完整应用内存转储恢复了64位包装record、CONTEXT和LONGJUMP jumpbuffer，经同启动周期映像身份、事故保存Ldr/模块地址及匹配Microsoft符号交叉核验，真实包装继续点为 `ntdll!KiUserCallbackDispatcherContinue`，跳转目标为 `wow64!Wow64KiUserCallbackDispatcher`。`whNtCallbackReturn`恢复record保存 `C0000028`（`STATUS_BAD_STACK`），其LONGJUMP是WOW64回调恢复机制，不能据此认定用户组件主动longjmp。

应用调用链包含 `WM_IME_STARTCOMPOSITION → ImmSetCompositionWindow`，随后有IMM/MSCTF、输入法及UIAutomationCore回调；部分第三方帧有解栈警告，只能证明保存时的调用链。已核实native/x86栈指针位于各自边界内；native CONTEXT保留的x86 frame不能按native栈范围直接判坏。完整WOW64应用转储仍缺少4GB以上native代码页，保存上下文处于致命回调展开路径，尚未恢复首个不合法frame或最初BAD_STACK检查，不能归责输入法、UIA或特定服务端包。

部分转储对应的较早正常战斗样本仅实收14B技能使用包，没有C2S39或NOTI38；另一完整转储样本已实收C2S39并发送9B NOTI38，之后还有技能请求再发生回调异常。两种包序分别保留，不能沿用“所有闪退均无死亡包”结论，也不能以后一轮的时间邻近证明死亡通知导致崩溃。根因与修复仍需首次异常上下文及明确控制变量的有界验证。

两次CDB创建调试进程均在启动阶段遇到 `std::bad_alloc`，32位地址空间近耗尽；其中 `-hd` 已取消堆调试检查，仍沿相同路径失败。随后不带CDB的普通启动实际到达名册及选角后的赛丽亚房间，私有内存约1.2–1.3GiB；普通名册进程只读样本确认BeingDebugged与NtGlobalFlag均0，技能发送原码片段与历史匹配。因此两次调试启动失败不能视为普通客户端必然失败；两种创建配置不同，保护/解包行为与分配循环的因果仍未恢复。普通选角可用不证明正常战斗或原 `C000041D` 已修复。后续采集按各方式实测内存、新服务端需求及至少1GiB余量预算；完整调试创建曾占约4GiB，不沿用普通启动占用估计，也不通过系统设置或客户端补丁绕过。

- op235（与分解共用 opcode 0x00EB）：深渊副本内只记录 `formal_hell_party_start_observed`，不回包（参考项目 `HandleHellPartyStart` 同样不回包）。
- **深渊房间本体（实验性，未在95客户端实证）**：深渊房间不是新增房间，而是 maze `[seal door pos]` 那个普通房间在深渊派对模式下改用 `[seal door map index]` 的深渊图（例：黑暗都市 (2,2) → 313163，图里有 10 只固定小怪 107002740 + 柱子 special passive object 30528）。入场计划（`DungeonEntryPlan`）把该坐标的 MapSpecification 换成深渊图，普通入场不换；起点/Boss/分层/条件/剧情图占用同坐标时拒绝（`hell-party-room-conflict`）。同一副本有多个带深渊房间的普通 maze（如 291100319 的 313166/313173）时按抽签选一个。
- **波次（实验性）**：柱子 `[hellparty]` 子段是 (组号 权重 波次号) 三元组；怪物本体在 `etc/hellparty.etc` 的 `[hellparty monster group]`（`[group index] N` → `[group] `A` code entityType ...`，字母=难度档，`A`=模式 1，模式 2 取 `B`，entityType 1=APC）。每个波次号内只保留有该难度条目的候选，按权重抽 1 组，展开成怪物（普通怪等级=副本 `[basis level]`，APC 取 AICharacter 等级；PVF 缺定义的条目跳过）。波次怪作为 START_MAP 的隐藏模板行追加（TemplateOrder=波次号，flag0=1，flag1=0xFF，序号接着普通/APC 既有行往后排），并在 START_MAP 之后补 NOTI 679（`int32 count` + count×`(int32 code, int32 level)`，按 code 去重）。依据：参考项目 `dungeon_hell_party_wave.go`/`dungeon_hell_party_catalog.go`（对应 A21 `BuildHellPartyWaves`/`AppendHellPartyTemplateRows`/`BuildHellPartyMonsterInfo`）。
- **波次怪（实验性，未在 95 客户端实证）**：波次怪现在是真实敌对怪——入场时追加进该房间的 `Monsters`（`DungeonPlannedMonster.HellWave` 非空，阻挡型），所以它们参与清房/开门、给击杀经验、走普通怪掉落流水线、占地面槽位；START_MAP 仍按"隐藏模板行"（flag0=1/flag1=0xFF）发给客户端，普通怪行里跳过它们；`TryCreate` 单独校验它们与 `HellWaves` 一一对应。难度字母跟随档位（`rooms.HellParty.ResolveManualMode`：请求没点名时按 `etc/hellparty.etc [difficulty]` 第 4 个数加权随机，95 PVF 只有 A 有权重，所以实际总是 A）。风险：若 95 客户端并不真的按模板行生成这些怪，房间会永远清不掉（需要实测；退出/放弃副本仍可返回）。APC 型波次怪（entityType 1）按敌对 `[monster]` APC 处理、阻挡，但没有 `Source`，因此不走普通怪掉落。
- **入场票（实验性）**：票数 = dgn `[hell party required item count]`（黑暗都市 291100308 = 30）；缺省时按参考项目公式 `(40*minLevel-1800)/100+10`（91 级 = 28）；都没有依据时拒绝。候选物品 = 区域 `[item condition]`（哈林 = 3330 深渊派对邀请函），逐个尝试，第一个背包里数量够的整笔扣（可跨多格，不拆分混扣）；95 PVF 没有 `[hell freepass item]`，所以没有免票路径。流程：prepare 阶段按当前背包规划（不够以 `hell-party-item-required` 拒绝，op16 回 `[0,0x11,0,0]`——0x11 来自参考项目 `MissingRequiredItem` 的推断，未在 95 实证）；入场提交（`InstallFormalDungeon`）时按最新背包重算并 `CommitInventory` 落库，随后把背包增量用 NOTI 14 投给客户端，日志 `hell_party_entry_ticket_consumed`；提交时若票已不够则整个入场作废（不会白进也不会半扣）。注意：账号里邮件的 3330（如 licocon 的 10001 封未领邮件）必须先领取到背包才能入场。
- **奖励（实验性）**：每个波次（Order）的**静态指定的最后一只**怪带 hellparty 装备骰（参考项目是"实际最后一只死的"，这里无法在入场时预知，故静态选末位；先杀它会提前掉）。骰数 = `[difficulty]` 档位第 1 个数（A=8/B=6/C=4/D=0）；每骰命中率 `(rate+1)/1001`，rate 取 `etc/itemdropinfo_monster_hell.etc [dungeon difficulty drop prob]` 对应等级行、按档位下标取列（A=875）；稀有度行取 `[basis of rarity dicision]` 的 A/B 行（档位 2 用 B，行 B 做单调夹紧），装备等级区间 = `[item drop ref table]` 基准等级行。实现为追加到该怪普通掉落计划的额外 Trial（`DungeonHellRewardPolicy`），走现有掉落/地面流水线。
- **仍未实现（无依据 / 无法自动验证）**：史诗碎片（参考项目的概率来自环境变量，95 PVF 无依据）、材料奖励、深渊结算专用流程（参考项目 90 的深渊房间本身不结算，结算发生在迷宫 Boss 房，我们既有正式结算已如此）；`[seal door appear rate]` 只解析保存，参考项目 90 也只解析不运行，密门随机出现与进入没有依据；传奇深渊 `[hell dungeon legend]`/6081 的请求编码与流程无依据；组队规则（我们的 Run 是单人）；玩家自选难度档位（op16 `[8]` 与"重玩"标志冲突，无线协议依据）；TCP 无法自动走到深渊房间（需实际客户端实测）。
- **覆盖范围**：对所有选图区域声明 `[hell dungeon]` 1 且副本存在“无任务连接 + `[hell dungeon]` 1 + `[seal door map index]` + `[seal door pos]`（该坐标是普通 `map` 房间且深渊图文件存在）”的 maze 通用（不限黑暗都市）；`HellPartyEntryTests` 枚举所有这样的区域/副本并校验波次可展开。

## 深渊补充（实验性，标注依据）

- **奖励载体**：每个波次的奖励载体是该波次里「实际最后死亡」的那只怪（IsLastLivingHellWaveMember），不再固定某一只。依据：推断（90 参考只有掉落表，没有载体规则）。
- **史诗碎片**：额外抽取次数 = (难度 A ? 1 : 0) + {5,6,8,9,10}[副本难度]（90 参考）。碎片概率在 90 里只来自环境变量，这里同样用 DFO_HELL_EPIC_FRAGMENT_PERMILLE，默认 0=关闭。
- **材料**：PVF 和 90 参考里都没有深渊材料表，未实现。
- **传奇深渊** `[hell legend]`/6081：PVF 有 `[seal door legend map index]`（313169）、`[hell legend quest]`（6081）、`[hell legend party required item count]`（2，但 `[hell legend item condition]=-1`，没有票物品，所以不扣票）。请求编码没有任何依据（90 只解析字段，95 实测只见过 [7]=1）。默认关闭，设 DFO_HELL_LEGEND_ENTRY=1 后把 op16 [7]==2 当传奇请求（纯推测，待实测）。入场要求完成 6081，(2,2) 房间换成 313169。
- **密门** `[seal door appear rate]`（darkcity=10）：90 与 95 客户端都没有运行时依据。最小方案：默认关闭，设 DFO_SEAL_DOOR=1 后，普通入场（无任务、非训练/练习）按 rate% 概率改走深渊入场（不扣票、不查 6080），失败则回退为普通入场。rate 按百分数解读（推断）。
- **玩家自选难度**：op16 [8]=1由普通练习、修炼场、职业体验及授权回放共用，不能作为深渊档位字段；深渊档位仍按 ResolveManualMode，不由练习标志控制。
- **组队规则**：服务端没有组队副本框架，深渊仅单人；未接入队伍规则。
