# 聊天

聊天负责把客户端 `CMD 0x0011 SEND_MESSAGE` 翻译成服务端投递：普通、公会、悄悄话、服务器喇叭与频道喇叭；
并通过 `CMD 0x01A8 ITEM_HYPERLINK_MESSAGE` 把客户端聊天框的「装备链接」重新组帧为
`NOTI 0x0172 MESSAGE_HYPER_LINK`（链接文本 + 148 字节物品记录，收件人可点击查看装备）。
**聊天行已可见**：普通/公会/悄悄话按 `NOTI 0x000C` 的正文布局 `[type][层 id][v][u32 字节长度][CP936 文本]`
把真实文本投递到聊天行；下行首字节是实测可渲染的显示 type：普通/队伍/悄悄话 = `3`、公会/攻坚队 = `6`
（蓝/绿/紫 kind 在「普通」页签不渲染，是客户端限制，见[聊天协议](../协议/聊天.md#21-显示-type-映射实测蓝绿紫-kind-在普通页签不渲染)）；
**喇叭走「喇叭」页签**：两种喇叭按 `NOTI 0x0076` 投递发言人与正文
（服务器喇叭 `0x0E` = `D&F` 官方标签，频道喇叭 `0x0B` = `Ch.` 频道标签）；GM `notice` 仍走
`NOTI 0x06AD` 公告弹框。字节合同见[聊天协议](../协议/聊天.md#2-服务端下发noti-0x000c-message)。
早期"聊天行无文本载体"与"`0x0076` 无可见效果"的结论均已更正，原因见
[聊天协议](../协议/聊天.md#6-聊天行正文布局的历史归档)。

## 1. 处理流程

[ChatHandler](../../Server/DfoServer/Network/Handlers/ChatHandler.cs) 注册 `0x0011` 与 `0x01A8`，都要求 `WorldReady`：

1. 解析 `[u8 type][u16 层 id][u32 arg][u32 textLen][CP936 文本]`（固定 11 字节头）。
   长度或边界不合法直接返回 `Unhandled`，由统一入口记录十六进制，不猜测文本、不构造成功。文本用 CP936 宽松解码，
   非法字节替换为回退字符而不是断开连接。
2. **每连接节流**：1 秒最多 5 条、10 秒最多 30 条，超限只丢弃并记 `chat_throttled`（不断线）。
   计数按连接隔离（随 `GameSession` 创建/销毁），用单调时间戳窗口，不受系统时钟跳变影响。
3. **静音/封禁预留钩子**：`IsChatBlocked` 目前恒返回 false；玩家管理、举报与屏蔽列表接入后在这里读取真实状态，
   拒绝时记 `chat_blocked`。
4. **文本上限**：按 CP936 字节数截断到 200 字节（按字符边界回退，不切半个汉字），
   日志记 `chat_send`（`Connection/Type/Target/Layer/TextLength/Text`，`Text` 截断 64 字符，另带 `Truncated`）。
5. 两种喇叭先**扣物品**（见第 4 节）；扣减失败不广播。随后由
   [ChatService](../../Server/DfoServer/Game/Chat/ChatService.cs) 生成投递计划，投递结果记
   `chat_delivered`（`Kind/Recipients/LayerFallback`）；喇叭另记 `chat_megaphone`
   （`Variant=server|channel`、`Type`、`SpeakerBytes`、`TextBytes`、`Recipients`，不写正文），
   便于定位"客户端喇叭页签没这一行"是编码长度还是投递范围的问题。
6. 物品链接 `0x01A8` 由同文件的 `ItemHyperlinkAsync` 处理（见第 2.1 节）：完整解析 kind/文本/cnt/记录，
   把文本与记录一起投递，由 Network 侧组 `NOTI 0x172`（配对不足时退化 `0x0C`）；
   校验失败只记 `item_hyperlink_rejected` 并丢弃，不断线。

## 2. 投递规则

### 名字聊天

右键菜单的悄悄话type1和1vs1聊天type36由[NamedWhisperService](../../Server/DfoServer/Game/Chat/NamedWhisperService.cs)按真实角色名定位现有在线会话，经NOTI65只投递目标，保留每连接节流与CP936字符边界截断。目标必须已就绪且为本服（server0或实际serverIndex），源与目标的generation及选角epoch在发送前重新检查；换角、离线和被接管后的旧回调失效。离线或被屏蔽时记录真实拒绝，不伪造送达或错误提示。发送者本地回显和全部原生错误提示仍需实机确认。字节合同见[聊天协议](../协议/聊天.md#名字聊天)。

黑名单由社交存储按真实角色关系查询。普通、公会、喇叭和物品链接投递时排除屏蔽发起者的接收者，角色ID寻址及名字寻址私聊同样校验；不会另建在线屏蔽缓存。关系管理见[城镇同屏](城镇同屏.md#社交)。

成员来源只用既有在线状态与只读存储：在线会话来自
[OnlineSessionDirectory](../../Server/DfoServer/Game/Session/OnlineSessionDirectory.cs)（与 GM、在线协议共用，
不另建在线目录）；公会成员来自 `guild_members JOIN characters` 的只读查询
（[CharacterRepository.Chat.cs](../../Server/DfoServer/Persistence/CharacterRepository.Chat.cs)），
不在内存另建第二套公会成员缓存。

| 请求 type | 类别 | 收件人 | 下行（显示 type） |
|---|---|---|---|
| 1 / 36 | 名字悄悄话 / 1vs1 | 当前在线的指定角色名，仅本服并检查黑名单 | `NOTI65`，布局见名字聊天协议 |
| 3 | 普通 | 同场景在线角色（含自己）；场景 = 频道 + `town/area` 解析出的 PVF 地图 + 房间账号（房间按账号隔离）+ 副本实例 | `NOTI 0x000C` `[03][层 id][v=0][u32 字节数][CP936 文本]` |
| 6 | 公会 | 同公会且在线的角色：SQL 成员账号 + 目标会话锁内复核 `Selected.Guild?.Id` 一致 | `NOTI 0x000C` `[06][层 id][v=0][u32 字节数][CP936 文本]` |
| 0x2E | 悄悄话 | 只投 `u32 arg` 指定的目标**角色 id**；按 id 解析账号后定位在线会话 | `NOTI 0x000C` `[03][层 id][v=0][u32 字节数][CP936 文本]`（显示 type 映射为 3） |
| 11 | 服务器喇叭 | 全服在线（`DeliverAll(_ => true)`） | `NOTI 0x0076` 喇叭页签：`type=0x0E`（`D&F` 官方标签，客户端忽略发言人）、`str1` = 角色名、`str2` = 消息 |
| 13 | 频道喇叭 | 同频道在线（按会话频道身份比较） | `NOTI 0x0076` 喇叭页签：`type=0x0B`（`Ch.` 频道标签）、`str1` = 角色名（显示为发言人）、`str2` = 消息 |

显示 type 只取实测可渲染值（普通/队伍/悄悄话 = `3`、公会/攻坚队 = `6`）；蓝/绿/紫 kind 在「普通」页签不渲染，
依据见[聊天协议](../协议/聊天.md#21-显示-type-映射实测蓝绿紫-kind-在普通页签不渲染)。
队伍/攻坚队聊天入口尚未实现，映射已固定但暂无投递路径。

未定义的 type 拒绝并记 `chat_rejected{Reason="unsupported-type"}`；未加入公会的公会聊天拒绝并记
`chat_rejected{Reason="not-in-guild"}`；悄悄话目标不在线时当前没有合适的失败包，只记
`chat_whisper_offline`，不自造包。

投递本身分两步：先在目标会话**自己的账号锁内**复核状态与过滤条件并取出投递回调，再在锁外把包入目标连接队列。
过滤条件因此只允许比较快照字段，锁内不做查询或资源解析；跨账号嵌套锁被 `AccountOwners` 直接拒绝，
所以投递路径不持有发送者锁去取接收者锁。

### 2.1 物品链接（CMD 0x01A8 → NOTI 0x172，已实现，点击行为待实机验收）

客户端在聊天框发送「装备链接」时上送 `0x01A8`。实测正文 179 字节：
`[u8 kind][u16 未定][u32 未定][u32 文本字节数][0x7F 格式化的链接文本][u8 cnt][cnt × 148 字节物品记录]`
（完整包体与未定字段见[聊天协议](../协议/聊天.md#71-实测请求包体2026-10-21本机客户端共-179-字节)）。

- **下行改走 `NOTI 0x172 MESSAGE_HYPER_LINK`**：正文
  `[type][layer][v=0][u32 文本字节数][CP936 文本][u8 cnt][cnt × 148 字节记录][u32 尾串字节数][尾串]`；
  `0x172` 已注册（注册点 `0x2E31B40` → handler `0x2E31740`，与 `0x0C` 同表），
  布局见[聊天协议](../协议/聊天.md#72-下行正文-noti-0x172-message_hyper_link)。
  `0x1A8` 比 `0x172` 多一个 `arg u32`，**不能直接转发**，必须经
  [ItemLinkPackets](../../Server/DfoServer/Network/Builders/ItemLinkPackets.cs) 重写布局。
- **尾串必填**：记录之后还要写 `[u32 len2][CP936 尾串]`（handler 读完记录后会再读一次，max `0x11` wchar）；
  当前固定单空格（`len2=1`、字节 `20`），非空且不超过 `0x21` 字节。漏发会让客户端越界读 4 字节、
  把 `msg+0x44` 回落成「信息长度有误」；语义未定（进 link run `+0xB4`，疑似悬浮提示/来源标签），
  代码留 TODO。
- **文本逐字节原样**：不做 CP936 解码再编码，超过 255 字节时按字符边界截断；截断若让 `0x7F` 标记不成对，
  整段退化为无链接纯文本（剔除全部 `0x7F`、`cnt=0`），不写非法帧。
- **记录随通知一起走**：`cnt × 148` 字节完整解析后放进 `ChatNotice.ItemRecords`（只读、各收件人共用），
  投递时不再回读会话快照；`GameSession.LastItemHyperlink` 只保留最新一条作诊断样本。
  记录 `+0x04` 是物品 id（样本 12400），服务端原样转发、不改写。
- **退化路径**：记录为空、长度合法的记录少于文本里的收尾标记数、或截断后标记不成对时，
  退回 `NOTI 0x000C` 纯文本（现有"看得见但不可点"行为），日志标 `Degraded=true`。
- **投递范围**：`kind=3` 按普通聊天（同场景、含发送者回显），`kind=6` 按公会成员；424 不带目标角色参数，
  悄悄话（没有目标）与队伍/攻坚队（尚无入口）一律拒绝。层 id 取本连接最近一次 `0x0011` 上报值。
- **容错**：文本长度 `1..4096`，且必须容纳 `cnt` 与 `cnt × 148` 记录；头部过短、长度为 0/超限、
  文本或记录越界时只记 `item_hyperlink_rejected` 并丢弃，**不断线**。
- **日志**：成功记 `item_hyperlink`，字段
  `Connection/Kind/Opcode/TextBytes/Records/MarkerPairs/Degraded/MarkersStripped/Truncated/RecordHex/Head/Recipients`；
  失败记 `item_hyperlink_rejected`，均不写完整文本。
- **状态**：服务端已按上述布局（含尾串）实现并有逐字节单测/TCP 覆盖；**点击行为待实机验收**。
  2026-10-21 用 `inject-raw` 注入缺尾串的 176 字节 `0x172` 帧只见 `[物品名]`、点击无反应，候选原因包括
  客户端记录消费时序 / 本地物品解析 / **尾串缺失导致 `msg+0x44` 回落占位串**；正式投递已带空格尾串。

## 3. 已知限制

- **聊天行有长度与层 id 限制**：`NOTI 0x000C` 的正文长度按 CP936 **字节**数、`1..255`（0 表示无正文），
  超过或为 0 时客户端回落到占位文案「信息长度有误」。服务端按字符边界截断（不会切出半个汉字），
  且入站先按 200 字节上限收窄，因此实际长度到不了 `0xFF`。早期为绕过该包打的 `0x03E2` 旁路已废弃
  （会崩客户端），字节合同见[聊天协议](../协议/聊天.md#2-服务端下发noti-0x000c-message)。
- **喇叭页签有硬性长度与"非空"要求**：`NOTI 0x0076` 的三段字符串必须**都非空**（`len ≥ 1`），
  任一条写 `len = 0` 客户端会丢弃整帧；上限分别是 `str1 < 0x1E`(29)、`str2 < 0x200`(511)、
  `str3 < 0x11`(16) 字节。服务端在 [MegaphonePackets](../../Server/DfoServer/Network/Builders/MegaphonePackets.cs)
  按 CP936 字节数 + 字符边界截断（不会切半个汉字），截空时回退成单字节占位，因此不会生成 `len = 0`。
- **`Ch. N` 标签取自收件会话**：裸注入帧（`B = 0`）显示 `Ch. 0` 属正常现象，服务端不为此维护收件人频道字段；
  `type = 0x0E`（服务器喇叭）是官方 `D&F` 标签，客户端会把发言人换成固定名、忽略 `str1`。
- **GM 公告仍有长度上限**：`NOTI 0x06AD` 由客户端限制标题 ≤ 24、正文 ≤ 600 **UTF-8 字节**，
  超限包被直接丢弃，服务端按字符边界截断（不会切出半个汉字）。
- **层 id 兜底**：`0x000C` 的 `u16` 是收件人自己的"当前层 id"，客户端在 `type==3` 时要求它等于本机层 id；
  服务端没有该状态的权威来源，只能填**发送者的层 id**。因此普通聊天（以及显示 type 映射为 3 的悄悄话）
  在层 id 不同的客户端上会被客户端丢弃；日志以 `LayerFallback=true` 标记。只投自己时层 id 就是发送者自己的，
  不标记兜底。物品链接的层 id 取本连接最近一次 `0x0011` 上报值，同受该限制。
- 静音/封禁、举报与屏蔽列表尚未实现，`IsChatBlocked` 只是预留钩子。
- 喇叭扣减失败（槽位空、物品不符、库存不足、阶段不符、提交失败）只记录 `chat_megaphone_rejected`：
  `0x0011` 没有 ACK 合同，不伪造反馈包；客户端本地可能仍显示已使用，属于当前限制。
- 副本内普通聊天按副本实例身份匹配。本服当前是单人副本实例，因此实际只投自己；多人副本接入后沿用同一场景规则。
- 公会聊天的成员资格以 SQL 成员表为准，投递时再核对会话快照；两者不一致（例如选角后才写入成员行）时**不投递**，
  只记录投递数为 0，不替玩家改公会状态。

## 4. 喇叭扣物品

两种喇叭都从 `u32 arg` 指定的**主背包槽位**扣 1 个，并要求该槽道具 id 与类别匹配：

| 类别 | 道具 id | 资源路径 | 说明 |
|---|---|---|---|
| 服务器喇叭 | 36 | `stackable/cash/megaphone_heartbeat.stk` | `[name]` 服务器喇叭；`[action usable place]` 只有 village / seria room |
| 频道喇叭 | 37 | `stackable/cash/megaphone_echo.stk` | `[name]` 频道喇叭；同上 |

扣减走既有背包提交路径（`GameSession.UseChatMegaphone` → `InventoryDeleteService` 规划 →
`MutateInventory` 的同一写事务与 revision 复核），不手写 SQL、不绕过在线快照安装。提交成功后
由背包投影把差量发给本人连接，客户端据此移除消耗；扣减失败则不广播。
