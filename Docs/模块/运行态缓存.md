# 运行态缓存

## 入口与所有权

[GameCache](../../Server/DfoServer/Game/Caching/GameCache.cs)使用 `Microsoft.Extensions.Caching.Memory.MemoryCache`，正式 Runtime 显式创建一份底座，账号注册表、在线目录和 Session 分区共同借用。现有框架引用已提供该组件，不启动 Redis 服务、不引入 DI 容器或后台保存。底座保存所属业务的原对象引用，不克隆角色、背包或副本状态；统一的是存储和清理机制，不合并各模块的业务所有权或锁。

当前接入四类数据：`AccountOwners` 的账号注册条目、`OnlineSessionDirectory` 的账号/连接索引、每个 `GameSession` 的类型化上下文分区，以及正式副本中的怪物和特殊对象 KEY、当前游标、房间回访、未拾取物品和操作准备。副本仍由原 `FormalDungeon`、`SinglePlayerDungeonRun` 和 `DungeonGroundState` 解释；Run 和 Ground 作为同一上下文的原对象一起替换，不各建一套缓存状态。资源 Catalog 和 PvfLib 的已有只读缓存不迁入这里。

`GameCacheScope` 通过 `GameCacheSlot<T>` 保存模块静态声明的强类型槽位；同一个槽位在不同 Session 中完全隔离，同类型的不同槽位也不冲突。当前每个会话最多安装一份正式副本上下文，不按房间追加全局条目。

[GameCacheIndex<TKey,TValue>](../../Server/DfoServer/Game/Caching/GameCacheIndex.cs)提供有明确所有者的动态索引。每个索引私有的 Dictionary 只定位不透明缓存槽，不保存第二份业务值；实际值只在共享 MemoryCache 中。账号键仅在成功取得账号所有权时登记，连接键仅来自正式连接注册，不将任意客户端查询写进索引。账号、在线会话和连接条目分别随原租约、原会话和连接结束回收，容量随原有活动租约及连接规模约束；单实例对象集合仍受原 16 位范围及资源规划边界约束。这不是自动计算对象字节大小的内存预算。

## 索引与并发

`AccountOwners` 保留注册表锁、逐账号 Gate、等待获取者计数、generation 及双账号锁序，只把条目存取交给自己的索引分区。租约仍引用同一个 AccountState；缓存存在不等于身份有效，业务仍须 `Lease.Execute`。共享底座结束后租约不再有效。

`OnlineSessionDirectory` 保留账号到原 GameSession、连接号到原投递入口的两份索引。`Remove(key, expected)` 在索引锁内比较原对象引用后移除，旧连接不能删除接管后的值；不是按字段相等删除。快照只在锁内取出原值引用，账号状态查询、筛选、业务与网络投递都在释放索引锁后执行。

各索引有独立的短锁，不设置覆盖全部账号业务的全局缓存锁；缓存路径不反向取得账号锁，也不在快照锁内调用 Session、数据库或网络。原注册表锁、账号锁及提交后发布合同不因统一底座而改变。

## 失效与状态

| 行为 | 缓存处理 |
|---|---|
| 成功进入副本 | 原准入和事务提交成功后安装本次上下文；失败不缓存半成品 |
| Loading、战斗、结算 | 都属于 Dungeon 或 TutorialDungeon 粗状态，保留同一上下文 |
| 过房及合法回访 | 保留当前 Run、房间状态和 Ground；不因细阶段进入 Loading 而清缓存 |
| 进入另一个副本 index | 通过原合法入场链路安装新上下文，不把旧 index 的对象或掉落带入 |
| 相同 index 再挑战 | 仍是新的实例 Guid 和尝试号，替换旧上下文；不能只按 index 命中旧副本 |
| 回城、回到选图或其他非副本阶段 | `SetState` 验证目标状态后移除副本槽位；原事务失败时仍保留原阶段与缓存 |
| 返回选角、换角色 | 原 Session 失效流程清除全部槽位 |
| 断线、旧 generation 收尾 | 只清除并释放这个 Session 分区；在线目录按原会话引用移除，账号按原租约回收，不误删新连接 |
| 服务停止或监听启动失败 | ServerHost 等待管理入口及全部连接清理后释放 Runtime 的共享底座 |

账号、在线索引及有效副本均使用 `NeverRemove`，没有 TTL 或自动容量淘汰。它们不是可丢弃的显示优化，不能因超时自动删除有效 owner 或怪物，再通过工厂重新生成。Session 结束仅释放自己的分区，不 Dispose 共享底座；底座由 Runtime 创建并交给 ServerHost，在所有使用者结束后释放。缓存条目的移除不自动执行值对象的玩法收尾或资产提交，必要业务收尾仍由原模块完成。

KEY 的初始范围、溢出回收及存量兼容沿用现有规则。实例内使用缓存游标，丢弃物品只有原库存事务成功或确认原提交后才推进它。`character_dungeon_state.next_object_key` 仍保留为原仓储资格校验和下次范围分配的兼容镜像，本期不删除该列、不取消既有事务写入。退出后不会从这个数值恢复旧怪物、旧房间或未拾取掉落；编号范围规则见[单人副本实例](单人副本实例.md#状态与身份)。

## 实时副本回执

[DungeonTransientReceipts](../../Server/DfoServer/Game/Dungeons/DungeonTransientReceipts.cs)归原租约的运行态分区，按角色和实例 Guid 隔离。新业务的房间疲劳去重、单件/集合冻结掉落、实体/金币/钱包材料拾取结果都只在这个分区保存，不再读写以下七表的运行明细：

- `character_dungeon_fatigue_receipts`
- `character_dungeon_loot_receipts`
- `character_dungeon_drop_batches`
- `character_dungeon_drop_objects`
- `character_dungeon_pickup_receipts`
- `character_dungeon_drop_pickups`
- `character_dungeon_passive_pickups`

旧表、旧记录及原兼容迁移保持不动，不新增历史扫描、启动清理、归档或迁移到缓存。已结束实例不会恢复；回城、回选角或再挑战时删除原实例分区，租约结束释放其全部剩余分区。旧 generation 只拥有自己的缓存，不能清掉新租约的数据。

冻结集合在提交前保持原事件、数量、Core及随机结果，回滚后重试不重抽；死亡经验/任务的原持久事实仍是已提交证明。拾取及房间费用先预留最小缓存候选，包含实际UID、核心或余额与提交版本，但不保留整份角色/背包快照；只有SQL COMMIT明确成功才标记已提交，并在原owner内发布。提交返回丢失时按已确认缓存恢复，不再加资产。SQL明确回滚时候选不作为成功回放；当前持久前提已经变化而又没有明确确认时拒绝重做，不凭“缓存中有条目”补发物品。进程退出会结束Run，下一连接只加载真实已提交资产，不接续旧局未决请求。

经验、金币、库存、疲劳余额、任务、通关及必要的长期去重事实仍按原事务持久化。缓存失效不回滚已提交资产；重登恢复资产不等于恢复旧副本。

## 后续接入

后续 Game 模块若确实需要生命周期内存状态，复用 Session 持有的 `GameCacheScope`，静态声明自己的 `GameCacheSlot<T>`，由所属模块解释上下文，Session 只编排安装和失效。跨会话索引由 Runtime 在同一 GameCache 上 `CreateIndex<TKey,TValue>()` 并显式传给负责该索引的模块。不要再创建独立在线角色库，也不为模块复制账号 owner 或角色快照。

独立测试及离线用例允许显式创建自己的 GameCache；正式服务必须传入 Runtime 的共享底座。AccountOwners 和 OnlineSessionDirectory 的无参数构造仅保留原有隔离调用兼容，不作为正式 Runtime 另建存储的入口。

接入前须明确：哪次业务成功后 `Set`、哪些状态边界 `Remove`、回选角或断线时如何清理、是否存在未决提交，以及条目数量和内部集合的上限。`Get` 未命中不自动创建数据；只有原业务准入成功后才能安装上下文。索引的 `Add` 拒绝重复键，`Set` 替换当前值，`Remove(key, expected)` 防止旧实例误删新值；默认字符串键区分大小写，与现有账号目录一致。各方法线程安全不代表多步业务原子，仍须原 owner 和资产事务保护。

Session 的回选角清理会调用 `Clear`，连接结束调用 `Dispose`；两者允许重复收尾，释放后的缓存不能重新写入。副本之外的未来模块仍须接入自身的状态失效边界，不能假设每次 `SetState` 都会清除所有功能的缓存。

普通可重建的查询缓存、带 TTL 的热点结果、资源解析缓存和分布式缓存不属于本期入口的已实现能力；不能因为底层是 `MemoryCache`，就把资产或需要恢复的提交结果改成过期条目。

## 验证

无资源 `GameCacheTests` 验证共享底座、索引/槽位隔离、原对象引用、并发注册、引用条件移除、账号接管、清理和关闭后拒绝，接入 `--selftest-core`。`UserStateTests` 和 `ProtocolArchitectureTests` 使用同一底座验证账号、在线会话、连接及旧 generation 收尾，账号并发夹具保留原锁序覆盖。`FormalDungeonSessionTests` 复用真实资源与 SQL 夹具验证加载、换副本、同 index 新实例、回城、回选角、断线和缓存数量，并保留已有回访拾取、丢弃、回滚及再挑战覆盖；还在七张旧表阻止新增的条件下完成扣点和拾取，核对旧记录不变。`--selftest-tcp dungeon-entry-cost` 可独立复用原入场费用原子性用例，`dungeon-entry-plan` 仍保留原组合覆盖。协议、完整响应延迟和客户端场景效果仍由 TCP、性能测量及实机验收分别确认。
