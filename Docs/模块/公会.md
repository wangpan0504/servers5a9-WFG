# 公会

支持建会认可、信息与成员页、普通邀请、退出与踢人、搜索申请审批、职位权限与名称、公告及宣传设置，以及公会仓库、公共积分与福利、外观和真实出勤查询。建会邀请兼容双方同时在线和先后上线：目标不需要在线，创建者离线也能使用拒绝接管的账号租约完成建会。

公会关系以数据库成员行为准，在线角色只保存由本人会话安装的投影。跨账号变更提交后再经目标原连接刷新；不在操作者锁内取得目标账号锁。排行榜与红包使用各自真实统计和事务账本，据点战仍未接通。

## 1. 当前行为

| 请求 | 行为 | 判据 |
|---|---|---|
| `CMD 0x009C CHECK_GUILD_NAME_DOUBLE` | 按文本规则校验后查名称是否被占用，按客户端契约回「可用 / 已被占用 / 长度违规 / 非法字符」；**可用的文本进入创建窗口草稿** | `guilds.name` 唯一索引 |
| `CMD 0x009D CHECK_GUILD_ADDREASS_DOUBLE` | 同上，作用于公会地址（本版客户端没有发包点，服务端不依赖它） | `guilds.address` 唯一索引 |
| `CMD 0x02E3 CHECK_GUILD_CREATE_PROMOTE_MSG` | 校验创建窗口「介绍」文本：空串或普通文本回 `01`，含控制字符回 `00 6C 00`；**可用文本进入草稿** | 文本规则（不查库） |
| `CMD 0x02E5 REQUEST_GUILD_CREATE_PERMIT` | 按角色名解析目标 → 失败码 3 / 5 / 23 / 34 → 登记认证申请（有效期 600 秒）；目标**当场在城镇**则立即推 `NOTI 0x2AD` 完整邀请，否则等它入城时补投；成功一律回 `01` | 角色行 + `guild_members` + 建会草稿 |
| `CMD 0x02E6 REPLY_GUILD_CREATE_PERMIT` | 接受时通过创建者会话或离线租约提交，认可方ACK成功后安装并发布入会状态，在线创建者同步金币与建会结果；拒绝不写库、不扣费 | 申请登记表 + 唯一索引 + 金币 |
| `CMD 0x02E7 CANCEL_GUILD_CREATE` | 创建者关闭创建窗口：**只清创建窗口草稿，不取消申请**（关窗 ≠ 取消，见[关窗不是取消](#关窗0x2e7不是取消)）；客户端无处理器，**不回包** | 创建窗口草稿 |

邀请0x2AD携带完整公会名、大区、创建者角色名与介绍；0x47/0x3A携带真实公会ID和显示文本。建会后双方都收到入会、Actor及70基础资料；0x2AE只通知创建者认可结果。0x2AF仍保留空包体的取消投递合同，但当前没有发送方。准确字段和缺省字符串读取行为见[公会协议](../协议/公会.md)。

创建窗口打开时的 `0x05AD`/`0x05AE` 已分别接入搜索及账号公会目录；`0x016D` 查询当前角色待审批申请并通过NOTI308恢复窗口，不能按同号CMD回执判断消费者是否存在。`0x009E` 不发送额外ACK（见[帧与频道](../协议/帧与频道.md)）。

## 2. 建会认证链路

### 创建窗口草稿

`CMD 0x2E5` **只带大区序号与目标角色名**——公会名/地址/介绍不在这个包里，它们只出现在名称查重（`0x9C`）、地址查重（`0x9D`）与介绍校验（`0x2E3`）请求里。服务端因此按**发起角色**记住最近一次「可用」的文本（`GuildPermitRegistry`，内存态、存活 600 秒），认证通过时据此建会。

- 只有查重结果为「可用」的文本才进草稿：客户端也只在查重通过后才解锁创建与邀请。
- 本版客户端没有域名输入框，地址缺失时**回退为公会名**：`guilds.address` 是 NOT NULL + 唯一，名称唯一即可保证回退值唯一。
- 关闭创建窗口（`0x2E7`）时**只丢弃草稿**，不让旧文本进入下一次创建；登记表里的待认证申请不受影响（见[关窗不是取消](#关窗0x2e7不是取消)）。因此在窗口关掉之后要再发起邀请，必须先重新做一次名称查重（`0x9C`），否则 `0x2E5` 因没有可用草稿回 34。

### 关窗（0x2E7）不是取消

客户端在创建窗口关闭时发 `CMD 0x2E7`（空包体），它只表示**窗口关掉了**，不代表创建者收回了认证邀请。顺序模式下这正是建会的常规操作顺序：**创建者邀请完关掉客户端 → 换账号/换角色上线 → 被邀请方入城收到 `NOTI 0x2AD` → 接受即扣费建会**。

服务端因此只做一件事：清掉该发起角色的创建窗口草稿（`GuildPermitRegistry.ClearDraft`），**保留**登记表里的待认证申请，也**不推 `NOTI 0x2AF`**——那个包会让被邀请方关窗并自动回 `0x2E6[00]`，等于换一种方式取消申请，正是早期实现卡死顺序认证的原因（当时日志记为 `cancelled`）。现在的日志是 `guild_permit` / `Result = window_closed_draft_cleared`。

**申请在 600 秒内仍然有效**（有效期只由登记时刻决定，关窗不重置也不结束它，见[申请有效期](#申请有效期)）；取消能力保留在**申请自然过期**与**将来的正式取消协议**上——`GuildPermitRegistry.CancelByInitiator` 与 `NOTI 0x2AF` 的投递路径都保留，前者当前只有「`0x2E5` 当场投递失败」的回滚在用。

建会不需要草稿：`0x2E5` 受理时已经把公会名/地址/介绍复制进 `GuildPermit`，关窗丢掉草稿之后申请照样能建会。

### 申请登记与失败码

`GuildPermitRegistry` 一个被邀请角色同时只保留一条待认证申请（重复邀请覆盖旧条目），替换时同步清理旧创建者的反向索引，旧创建者取消或重新邀请不能删除其他创建者的新申请。**答复时取出即删**，过期视为不存在，不返回半成品。入城补投用**不移除**的查询（`Find`）：补投之后被邀请方仍要能拒绝，消耗只发生在答复里。

**目标不需要在线**：`0x2E5` 的判据只有「角色存在、与创建者不同账号、尚未入会、创建者有可用草稿」，受理就回 `01`（客户端按钮在发包时本地转「等待认证」，不看应答）。

| 情况 | 应答 | 客户端文案 |
|---|---|---|
| 目标角色不存在 | `0x2E5 → 00 03 00` | 玩家不在线或者不存在。 |
| 目标与创建者同账号 | `0x2E5 → 00 05 00` | 该角色与创建者属于相同账号。 |
| 目标已在公会 | `0x2E5 → 00 23 00` | 无法加入该公会。 |
| 创建者已在公会 / 没有可用名称草稿 / 创建者不在城镇 | `0x2E5 → 00 22 00` | 无法创建公会。 |
| 目标不在线（或账号在线但当前选的是别的角色） | `0x2E5 → 01`，申请留在登记表里等它入城补投 | — |
| 目标在线但不在城镇（副本/加载/结算） | `0x2E5 → 01` + `NOTI 0x2AE[0x2D]`，**不登记申请** | 对方正在挑战地下城，无法发送认可申请。 |
| 目标当场在城镇但投递失败 | `0x2E5 → 00 03 00`，回收申请 | 玩家不在线或者不存在。 |
| 申请不存在或已过期 | `0x2E6 → 00 67 00` | 公会邀请的等待时间已达到上限 |
| 创建者账号仍在线但不是发起角色 | `0x2E6 → 00 03 00` | 无法找到指定玩家 |
| 被邀请方期间已入会 | `0x2E6 → 00 27 00` | 您已加入公会或正处于等待加入公会的状态 |
| 拒绝 / 创建者在线时提交失败 | `0x2E6 → 00 22 00`（表外码，客户端静默） | — |
| 创建者离线时离线提交失败 | `0x2E6 → 00 67 00` | 公会邀请的等待时间已达到上限（表内语义最近的码，真实原因进服务端日志） |

**当场在城镇才「投递成功即受理」**：目标在城镇时 `TryDeliverGuildPermit` 先在同一把 owner 锁里复核目标角色，投递失败就回收申请并回失败码，不伪造投递。目标不在城镇时**不登记申请**：补投只在入城序列（选角入城/换频道回城）之后发生，从副本回城不走这条序列，登记一份当时投不出去的申请只会让创建者白等。

### 提交发生在创建者自己的会话里（在线）

创建者**在线且正是发起角色**时，经 `OnlineSessionDirectory` 找到创建者会话，在**它的 owner 锁内**跑完整提交（规划 → `GuildDirectory.Create`（扣费 + 公会行 + 成员行同一事务）→ 安装提交后快照），与[拍卖行上架](拍卖行.md)同一形态：

- 跨账号租约与旧 generation 都不许写库，所以这一步只能落在创建者会话上；被邀请方连接只是触发者。
- 金币差额带提交回执，交给**创建者连接自己的**背包投影发布，不在被邀请方连接上代发。

### 顺序模式：创建者离线时用离线账号租约提交

创建者可以在发起认证后下线，被邀请方之后才入城认可。接受时若创建者账号已经离线，走 `GuildDirectory.CreateOffline`；账号仍在线但已换角或未入城时，不抢线代写：

1. 取**离线账号租约**：`AccountOwners.TryAcquire(创建者账号, …, DuplicateLoginPolicy.Reject)`——与离线 GM 同一合同，账号仍被在线连接持有就**不抢线**，返回 null，本次不建会、不动任何人的钱（被邀请方按失败码 3 答复）。
2. 在租约内按**角色 id** 读该角色的最新快照（`LoadCharacterById`：含 revision 与完整背包，与选角读取同一口径）。
3. `PlanCreate`（文本规则、是否已在公会、金币是否够 `[guild create cost]`）→ `Create` 提交：**扣费、公会行、成员行同一事务**，任一步失败整笔回滚，失败时不建会、不扣钱，被邀请方收到失败码 103。
4. 提交期间创建者登录并接管账号时，租约作废（`Stale account generation`）：本次不建会，不把异常抛给被邀请方的连接。

离线提交没有创建者会话可安装快照：扣费后的revision由数据库承担，下次选角读取最新金币与公会。认可方仍安装本次已提交的公会，并收到入会、Actor和基础资料；不需要为刷新身份重新选角。

**成员行**：接受认证即入会。`GuildCreatePlan.InviteeCharacterId` 带着被邀请角色进计划，提交时写两行 `guild_members`（会长 + 被邀请角色，职位都先固定 0），与公会行同一事务；被邀请角色在申请等待期间已经入会时，事务内的成员唯一检查会拒绝整笔（不扣费）。

### 发包在目标连接自己的上下文

与邮件到达提示同一形态：`GameSession` 暴露两个回调（`GuildPermitNoticeArrived` / `GuildPermitResolved`），由 `GameProtocolHandler` 在每条连接建立时绑定到本连接的 `GuildProjection`。

- 被邀请方连接：`NOTI 0x2AD`（邀请；`NOTI 0x2AF` 的投递路径保留但当前没有发送方），发布前复核目标仍是当初那条请求的角色。
- 创建者连接：金币差额 → `NOTI 0x2AE` → `NOTI 0x47` → `NOTI 0x3A` → Actor → 基础资料70。
- 认可方连接：ACK742 → `NOTI 0x3A` → Actor → 基础资料70；旧选角或世代的回执不发布。
- `0x2E6` 先答被邀请方（自己连接的写队列），再发创建者：创建者的慢连接不拖住这一侧；创建者连接这时断掉也不会让已经提交的建会变成失败。

### 入城补投（顺序模式）

`NOTI 0x2AD` 的发送点只有一处（`GuildPermitDelivery`），两种时机共用同一份字节合同：

- **在线投递**：目标当场在城镇，`GuildProjection.Notice` 立即发出（`Post`，守卫要求 Ready + 目标角色一致）。
- **入城补投**：目标不在线或当前选的是别的角色时申请留在登记表里；它之后**入城序列发完**（最后一条 `NOTI 124` 之后）时，`TownProjection.EnterAsync` 调用注入的可选投递器，登记表里有指向该角色的未过期申请就补投。

`TownProjection` 只依赖窄接口 `IGuildPermitDeliverer`，不含公会规则：装配顺序是 `GuildProjection` → `InventoryProjection` → `TownProjection`，直接注入 `GuildProjection` 会形成构造环。补投的守卫只认「这条连接当前选中的正是被邀请角色」——入城序列结束时 `MarkReady` 还没执行，要求 Ready 会让这一包被写入泵丢掉。补投也发生在换频道回城（同一条入城序列）时：若弹窗随场景被客户端销毁，申请仍在，下次入城会再补一次。

### 申请有效期

客户端在被邀请方窗口停留 60 秒后自动发拒绝，服务端有效期取 **600 秒**（`GuildHandler.PermitLifetimeSeconds`）：顺序模式下申请必须能等到被邀请方下一次入城；有效期只由申请登记时刻决定，**关窗（`0x2E7`）既不清它也不缩短它**（草稿随窗口关闭丢弃，见[关窗不是取消](#关窗0x2e7不是取消)）。60 秒的客户端超时拒绝仍在有效期内，仍能匹配到申请。被邀请方若在有效期最后 60 秒内才入城，弹窗出现后可能因申请到期收到 103，重新邀请即可。过期条目在答复或补投查询时被清理。

## 3. 文本规则

- 长度上限按客户端提示「中文 7 字符或英文 14 字符」折算为 **CP936 字节数 ≤ 14**（7 个汉字 = 14 字节，14 个 ASCII = 14 字节）。
- 非法字符目前只拒绝控制字符（`0x00–0x1F`、`0x7F`）。客户端自己的非法字符规则更严格；在拿到实机证据前不擅自收窄名称与地址的可用字符集，避免把客户端允许的输入判成非法。
- 编码口径与角色名一致：代码页 936，解码失败按非法字符拒绝。见[游戏内角色名](../模块/角色.md)。
- 认证目标按名字查询，比较用 `characters.name` 上的 `COLLATE NOCASE`（与邮件收件人同一口径）。

## 4. 数据与归属

`guilds` 与 `guild_members` 由数据库迁移 **v44** 一步建立（空表，不预置公会、不改角色资产），保留主线已经发布的v38–v43迁移，完整结构见[数据库](../开发/数据库.md)。

- 公会跨账号可见，不归属单个角色：`guilds` 不建立指向 `characters` 的外键（会长角色被删除时公会仍需保留，由业务决定继任或解散）。
- `guild_members.character_id` 唯一：一个角色只能在一个公会。会长身份以 `guilds.master_character_id` 为准；历史 grade=0 仅在读取时投影为会长1、普通成员4，不给普通成员管理权限。显式保存的权限0优先于缺省职位权限。
- 查询入口是存储合同 `IGuildDirectoryStore`（`Game/Guild/GuildDirectory.cs`），由角色仓储实现；Handler 只依赖用例层，不直接持有仓储。离线建会读取走同一合同的 `LoadCharacterById`（按角色 id 读最新快照）。
- 扣费只扣**创建者**角色的金币（`[guild create cost]`，PVF 实测 300000）：扣费与公会行、成员行同一事务，被邀请角色不承担建会花费。
- 认证申请与创建窗口草稿**只存在内存**（`GuildPermitRegistry`），不落库：重启后申请自然失效，客户端会重发邀请或超时拒绝。
- `GameSession`仍是选角、阶段、owner及角色快照的唯一所有者。公会基础资料由既有两表联查读入`Character.Guild`，不是第二套在线成员表；普通背包提交、重新选角、换频道和同屏外观都保留该投影。建会只改变公会上下文，用户业务状态与细阶段仍为城镇，不新增平行状态枚举。

### 角色删除

角色删除事务清理该角色的成员、申请、退会限制及出勤依赖；删除会长会同时解散公会。公会仓库非空时拒绝删除会长和解散，避免公有物品成为孤立资产。

## 5. 资源

公会数值一律来自 PVF，不在业务代码里写死常数：

| 资源 | 读取项 |
|---|---|
| `etc/guild.etc` | `[guild create cost]`（建会花费，实测 300000）、`[guild cargo size limit]`（公会仓库格数，实测 56） |
| `etc/guildreform.etc` | `[guild level exp]` 五档（low/mid/high class、guardian、conqueror）×10 级经验曲线 |

读取入口：[GuildParameterCatalog](../../Server/DfoServer/GameWorld/Guilds/GuildParameterCatalog.cs)。`etc/guild.etc` 的其余段落（捐赠、印记、升级消耗、内容列表）在对应玩法接入时再读取，不提前造接口。

## 6. 限制

- 入会58的第二个u32在当前处理器中未消费，完整语义待确认；第一个公会ID和后续文本必须按已核原码发送，见协议。
- 创建者离线时不补播历史建会系统消息，下次选角仅恢复当前公会与资产；认可方不因创建者离线而遗漏入会投影。
- 入城补投只在**入城序列**（选角入城、换频道回城）之后发生：被邀请方从副本/选图回城不走这条序列，从副本回城不会补投。目标在线但不在城镇的邀请按原有 `0x2AE[0x2D]` 文案答复且不登记申请。
- 被邀请方在申请有效期（600 秒）最后 60 秒内才入城时，弹窗可能因申请到期而以 103 结束；此时重新发起邀请即可。
- 被邀请方的 8 / 0x2D 结果码只实现了「不在城镇 → 0x2D」；「对方处于拒绝公会邀请状态（8）」没有证据，不发。
- 公会名来自名称查重：若玩家查重后改了输入框内容再点邀请，服务端建的仍是**最近一次查重通过**的名字（包里没有第二个名字来源）。
- 新公会等级1、经验0、公告为空、基金与结晶0，不预置成长奖励。公共积分与公会经验是两个独立数值，礼袋和普通通关的积分不冒充公会经验。
