# 拍卖行

拍卖行的**只读搜索路径已接入真实挂牌数据**：客户端打开拍卖行或搜索时，服务端从 `auction_listings`
分页返回在售且未过期的挂牌；**上架前的均价查询（CMD 182）也会作答**，参考价取自真实在售挂牌
（无在售时用该模板的商店售价兜底，见下）。
**上架（CMD 183）已接入**：校验通过后从背包扣掉该道具、把挂牌写进 `auction_listings`，两者同一事务。
**取消上架（CMD 184）已接入**：挂牌置为已下架 + 道具还回背包 + 审计同一事务。
**「我的拍卖品」三个页签（CMD 188 我的上架 / 189 我的竞价 / 190 拍卖历史）已注册并应答**：
188 回本角色在售挂牌、190 回本角色全部状态的挂牌、189 恒回空列表（竞价未接入）。
**一口价购买（CMD 185）已接入**：请求布局由两个实机样本差分定案（30 字节），
成交把「挂牌置为已成交 + 买方扣款 + 买方道具与卖方所得两封托管邮件（卖方角色行不存在时收益那封跳过）」
放进**同一个事务**，
**只取买方一把租约**（跨账号，方案与锁序见
[并发、事务与响应延迟](../规范/并发事务与响应延迟.md#跨账号转移拍卖行一口价购买)）。
**CMD 334 仍是「只抓请求体」的桩**：它的布局只有参考实现且自标偏移未定，因此不回包、不改状态。
竞价、成交结算的定时任务仍未实现（结算与挂牌状态同事务，不需要补发任务）。
本页写当前已接入的行为、数据与开发手段；线格式与证据边界见[拍卖行协议](../协议/拍卖行.md)。

> 分类表里的**中文名称仅用于日志与文档可读性**（客户端界面上的节点名由客户端自己显示），
> 判定一律用精确 id 与维度掩码，不依赖名称字符串。

## 已接入的行为

- **入城时发送两条 S2C 183**（`serviceType` 0x00 与 0x01，`openState` 0x01），这是客户端打开拍卖行界面的前置。
  发送点在[入城投影](../../Server/DfoServer/Network/Projection/TownProjection.cs)，编码在
  [AuctionPackets](../../Server/DfoServer/Network/Builders/AuctionPackets.cs)。
- **CMD 186 / 187 已注册并回真实挂牌**：Handler 解析请求（mode、翻页偏移、分类 id、itemId）→
  [AuctionService](../../Server/DfoServer/Game/Auction/AuctionService.cs) 读用例 →
  [AuctionListingRepository](../../Server/DfoServer/Persistence/AuctionListingRepository.cs) 查询 →
  按已定案的 168B 记录合同用 **CMD 186** 应答。规则：
  - 只回 `state=0`（在售）且 `expires_at_unix > 当前时间` 的挂牌；后三个状态（已成交、已下架、已过期）不参与。
  - **匹配总数不受翻页偏移与本批条数影响**，每页 10 条（与客户端算总页数的页大小一致）。
  - **排除自己上架的挂牌**（官方规则）：按卖家角色 id 过滤；机器人挂牌的 `seller_character_id` 为 NULL，
    不属于任何玩家，因此不会被排除。没有选中角色时保持未处理、不回包——此时无法判断「排除自己」。
  - **分类过滤覆盖顶层大类与已对账子叶**，见下节；未对账的子叶按所属顶层过滤，完全没见过的 id 才不过滤。
  - 列表按 `listing_id` 升序稳定排序，保证翻页不重不漏；排序规则（价格、到期时间）尚未确认。
  - ★ **道具块 `+6`（= 记录 `[49..52]`）在 itemId 合法时必须 > 0**：客户端 186 回调里有**静默丢行过滤器**
    （`0x0235264C`–`0x023526D3`，见[拍卖行协议](../协议/拍卖行.md)的道具块一节），
    该字段 ≤ 0 且 itemId 查得到道具资源时**整行被丢掉**（总数正常、列表少行、无错误码）。
    编码器因此在 `itemId > 0` 时把它兜到 ≥ 1（[AuctionPackets](../../Server/DfoServer/Network/Builders/AuctionPackets.cs)
    的 `BlockValue`，搜索记录 / 「我的拍卖品」/ 探针行三条路径共用）：**这是防丢行、不是业务规则** ——
    合法数据一个字节都不变（堆叠数量由同一字段携带，而数量 ≤ 0 的核心在编码入口即被拒绝），
    只有「itemId 合法但 value ≤ 0」的退化数据会被兜住（例：时装/宠物的 `value` 本来就是 0）。
    ★ **该过滤器只有 186（搜索）有**（D95 反汇编定案）：188/189 的回调里既没有道具资源查询也没有
    `rep movsd`，块 `+6` 写 0 不会被丢行 ⇒ 「我的拍卖品」路径上的这条兜底是**防御性保留**。
  - 应答的 `mode` 决定**窗口类型与填充函数**（D95 反汇编定案：`mode=1` → `GetWindow(7)` + `0x26FF7D0`、
    `mode=0` → `GetWindow(6)` + `0x371A6C0`），正常路径必须回显请求首字节；
    `--auction-probe "bidmode=0,1"` 用于验证这个分流（**已实机闭环**），它**不影响竞拍入口**
    —— 本版客户端没有竞拍按钮（见下文「仍不确定的项」与[拍卖行协议](../协议/拍卖行.md)的「竞拍入口已结案」）。
- 收到的请求与回包内容分别记入 `auction_search` 与 `auction_search_result` 日志
  （含分类 id 样本、匹配总数、本批条数与每行价格），每次搜索另记一条 `auction_search_category`
  （分类 id、解析状态、实际下推的维度），这是继续确认分类表的证据来源。
  ★ 判断「这次搜索出了多少条」**只看 `auction_search_result`**（`Source=listings`，带 `Total` / `Rows` 与每行挂牌）；
  `auction_search` 里的 `ProbeTotal` / `ProbeRows` 是**探针合成行**的条数，探针关闭时恒为 0，
  **不能**当作搜索结果读数（字段名带 `Probe` 前缀即为此；2026-10-11 那次「分类搜索全 0」的误判就来自这里）。
- **CMD 182 均价查询已注册并应答**（此前未注册，客户端界面停在「正在统计拍卖行价格…」、价格输入框不解锁）：
  - 请求体按 `[1..4]` 取 itemId，**容忍长度差异**（本客户端 13B、参考实现 8B）：只校验「至少 5 字节」，
    其余字节忽略但写进日志；不足 5 字节或没选中角色时保持未处理，不回通用成功。
  - 均价**只取该模板当前在售且未过期的挂牌**（`state=0`、`expires_at_unix > now`）的显示价
    （与列表「当前竞拍」列同源：有出价取最高出价、无出价取起拍价）做**向下取整**的平均，
    并把 itemId、均价与参与统计的件数记入 `auction_average_price_result`；不写常数表、不加随机扰动。
    求和用 `long`（单价是 int，几千件 `int` 累加会静默溢出）。
  - ★ **下发的是「参考单价」而不是「有没有行情」**：`key` 字段**不能为 0**（客户端 `0x1455900` 判
    `[+0x1a4] != 0`，把它当「有价格数据」的非零门），且客户端会拿它预填一口价输入框并校验
    「不能低于商店销售的价格」。因此取值分三档：**有在售 → 均价**（算出来是 0 也夹到 1）、
    **无在售 → 该模板的商店售价**（PVF `[price]`，无 `[price]` 取 `[value]`）、
    **商店价也取不到 → 1**。日志把 `Average` / `Count` / `Floor` / `Key` / `Source` / `KeyNote` 分开记。
    依据与行号见[拍卖行协议](../协议/拍卖行.md)的「`key` 不能是 0，无在售时用下限」一节。
  - 应答按参考实现的读法**双应答**：先 `mode=0`（参考实现里唯一把价格写进客户端价格表、置「价格就绪」的分支），
    再 `mode=1`（只填物品名并启用控件）；顺序不能颠倒，否则价格进不了价格表、输入框依旧 disabled。
    参考实现的数据体是 57 字节：`mode + key + unused + vector1(i32×6) + vector2(i32×6)`，`key` 与 vector1 同源（都是均价）。
  - ★ 参考实现的结构与顺序**在本客户端全部未验证**：实测 57B/37B/33B 三种长度都被客户端回
    `C2S 217 OVERFLOW_INFO`（指名 182 包体读超），而 **1B 包体直接把客户端读崩**（连接被强杀、不回 217）。
    当前第一假设是**应答体自带 1 字节 flag**：CMD 路径的应答体首字节必须是 flag（本仓库实测 20/21 个 CMD 应答
    首字节为 `01`，唯一例外就是 182；186 的体同样是 `01 00 <total:i32> …`），而传输层帧头不补这一字节，
    因此旧候选「从 `mode` 起算」正好少给 1 字节。首选候选 `flag58` = `flag(0x01) + 57B 参考结构`。
    候选按结构收敛（flag 位置、计数字段位置与宽度、列表条数、是否补发 CMD 795），由 `--auction-probe avg=` 轮换，
    且有 **8 字节安全底线**：低于该值的数据体既不在候选表里，也发不出去。
    日志 `auction_average_price`（请求）、`auction_average_price_result`（候选名/结构/长度/发几条）与
    `auction_average_price_reply`（每次应答的 mode、长度、**实际下发的十六进制**）可与 217 反馈一一对照。
    候选表与假设见[拍卖行协议](../协议/拍卖行.md#s2c-182-应答结构仍未确认)。
- **CMD 188 / 189 / 190「我的拍卖品」已注册并应答**，见下节。
- **CMD 184 取消上架已注册并应答**，见下节。
- **CMD 185 一口价购买已接入并应答**（跨账号钱货转移，见上文）；**CMD 334 仍是「请求抓取桩」**（只记日志，不回包、不改状态）。
- 其余拍卖行信令（传奇拍卖 637、罗杰·莱文拍卖 993/994）未注册，保持未处理，不返回通用成功。

## 我的拍卖品（CMD 188 / 189 / 190）

用户上架成功后**必须能在这里看到自己的挂牌**：搜索一直按官方规则**排除自己**，因此这两个面板是
唯一的可见入口；三条请求都不应答时，玩家的观感与「物品被吞」无法区分。

三个页签共用一条实现（[AuctionHandler](../../Server/DfoServer/Network/Handlers/AuctionHandler.cs) 的
`MyListAsync`），只有数据来源与记录布局候选不同：

| opcode | 页签 | 数据来源 | 记录布局默认候选 |
| --- | --- | --- | --- |
| 188 | 「我的拍卖品 → 上架的物品」 | 本角色 `state=0` 且在售未过期的挂牌 | `a21-151` |
| 189 | 「我的拍卖品 → 我的竞价」 | **恒空**：竞价未接入（没有出价表） | `a21-159` |
| 190 | 「拍卖历史」 | 本角色**全部状态**的挂牌（含成交/下架/过期） | `a21-151` |

- **请求体恒 1 字节 = 窗口 `mode`**，应答必须回显：回错窗口会把记录灌进另一类窗口的面板、界面恒空。
  空请求体回落到普通拍卖行窗口（`0`）并在日志标 `ModeFallback`，页签不会「点了没反应」。
- ★ **`mode=0` 与 `mode=1` 是两套数据**（2026-10-12 实机定案，随后接入金币券）：
  `mode=0` 只回普通挂牌，`mode=1` 只回 `chn_Trade_Gold/gold_*.stk` 的 17 张金币券。
  搜索记 `auction_search` / `auction_search_consignment`，我的拍卖品记 `auction_my_list` /
  `auction_my_list_consignment`。`mode=1` **不消耗**记录布局候选。没有金币券时 `mode=1` 仍是空列表，
  不会把装备画进「确认寄售的金币」，面板也不会停在无响应。
  分组自测见 [AuctionWindowModeTests](../../Server/DfoServer/SelfTests/AuctionWindowModeTests.cs)
  与 [AuctionGoldConsignTests](../../Server/DfoServer/SelfTests/AuctionGoldConsignTests.cs)。
- **空列表也必须正确应答**（`flag + mode + count=0`，3 或 4 字节）。这是页签从「无响应」变成
  「至少有反应」的最小可用形态，记录体再按候选逐步收敛。
- 数据来源走既有存储合同（[IAuctionListingStore.LoadSellerListings](../../Server/DfoServer/Game/Auction/AuctionService.cs)
  → [AuctionListingRepository](../../Server/DfoServer/Persistence/AuctionListingRepository.cs)），
  Handler 里不写 SQL；条数按本角色在售上限（100）一次全发，不分页（这两个面板客户端不翻页）。
  188 与 190 的条件分开写：本仓库尚未接入成交/下架/过期流转，今天两者行集合相同，
  但「历史」不会被实现成「在售」。
- ★ **记录尺寸与道具块偏移已确认，计数宽度仍未验证**（2026-10-12 更新）：D95 转储反汇编给出
  188 = **151B**、道具块 **@30**，189 = **159B**、道具块 **@38**（记录步长与块指针，见
  [拍卖行协议](../协议/拍卖行.md)的 188/189/190 节），与参考实现完全一致，这两项不再是待确认；
  但 **188 的 `u8` / 189 的 `u16 WORD` 计数宽度仍只有参考实现，190 连尺寸都没有本客户端证据**
  （参考实现自己标注 190 是抓包桩）。因此记录布局仍做成候选，由 `--auction-probe mylist=` 轮换，
  日志 `auction_my_list` 记下页签、候选名、记录尺寸/道具块偏移/计数宽度、count、体长与实发十六进制头。
- **安全底线**：`flag` 必须是应答体第 0 字节（本仓库帧层不补）；体长不得短于结构所需
  （空列表的发满头部，带记录时精确等于 `头部 + N × 记录尺寸`）；候选自身还要放得下头部字段与 83B 道具块，
  不满足的候选既不在候选表里、也编码不出来。以上三条都由编码自检与自测锁定。
- **仍未接入**：189 的竞价行（需要先做竞价与出价表），以及三个面板里参考实现特有的字段语义
  （189 的出价状态字节、188 的平均市价与「高于市价 2 倍」提示）。

## 取消上架（CMD 184）

「我的拍卖品」里的取消按钮发 184。与上架同一套三步编排，方向相反
（[AuctionHandler.CancelRegist](../../Server/DfoServer/Network/Handlers/AuctionHandler.cs)）：

1. **只读定位与规划**（`AuctionService.FindListing` → `PlanCancel`）：读一行挂牌（只读 SQL）并校验
   **属于当前角色**且**仍在售**（`state=0`），把挂牌保存的物品条目快照**读回物品核心**，
   再交给既有的发放入口 [InventoryRewardGrantService.TryGrantCore](../../Server/DfoServer/Game/Inventory/Services/InventoryRewardGrantService.cs)
   产出「道具还回背包」的库存计划。不写库、不发包、不占 owner。
2. **一次事务提交**（`AuctionService.Cancel` → [CharacterRepository.CancelListing](../../Server/DfoServer/Persistence/CharacterRepository.Inventory.cs)）：
   **道具还回背包 + 挂牌置为 `state=2`（已下架） + 背包审计**在同一个外层事务里提交。
   事务内还要复核「这行仍是当前角色的、且 `state=0`」（`UPDATE ... WHERE state=0` 必须影响 1 行），
   任一步失败整体回滚 —— **不会出现「挂牌没了但道具没回来」，也不会出现「同一件道具被还两次」**。
3. **成功应答**（`flag + mode=0`）→ **补发背包列刷新**；请求体由会话在安装提交快照时产出（带提交回执），
   与上架走**同一条会话级发布路径**（[GameSession.CancelListing](../../Server/DfoServer/Game/Session/GameSession.Auction.cs)）。

| 项 | 规则 | 依据 |
|---|---|---|
| 归属校验 | `seller_character_id` 必须是当前角色；机器人挂牌（NULL）不可取消 | 否则任何人都能取消别人的挂牌 |
| 状态校验 | 只允许取消 `state=0`；已下架/已成交/已过期一律拒绝 | 防止一件道具被还两次 |
| 请求解析 | 至少 9 字节（前导 0 + 挂牌 id:i32@1 + 到期:i32@5）；不足即拒绝 | 不按残缺字段去动资产；`[5..8]` 只记日志对照（`ExpiresEchoMatches`） |
| 道具还原 | 从挂牌保存的条目快照逐字段读回核心（`ItemCoreFromEntry`），**属性/耐久/强化等原样还回** | 不重建白板实例；快照读不回来就拒绝取消（否则道具真的没了） |
| 背包满 | 按发放入口既有规则拒绝（`InventoryRejected` → 通用提示码 `0xd2`），**挂牌保持 `state=0`** | 道具仍在挂牌上，玩家清出空间后还能再取消 |
| 重复取消 | 第二条请求在规划期即被拒（`AlreadyInactive`，静默码 `0x7e`） | 过期操作不弹框（与 183 的「道具已不在背包」同款） |
| 审计 | `inventory_audit_log.action_name = 'auction_cancel'`，与挂牌状态同一事务 | 资产变更可复核 |
| 保证金 | **不退**（用户口径：取消上架不退，不然不叫保证金）：钱在挂牌阶段已扣，这条路径不产生任何退款 | `auction_cancel` 日志记 `Deposit=forfeited` 与金额 |

## 到期结算（到期未售：道具退回 + 保证金退还）

本仓库**没有定时任务**，因此「到期」这个时间事件挂在**卖家查看自己挂牌的读路径**上
（CMD 188「我的上架」与 190「拍卖历史」，与邮箱模块在打开邮箱时清理过期邮件同一形态）：

1. **只读规划**（[AuctionService.PlanExpire](../../Server/DfoServer/Game/Auction/AuctionService.cs)）：
   取该卖家 `state=0` 且 `expires_at_unix <= now` 的挂牌，把每一行算成「**一次状态流转 + 一封系统退回邮件**」。
   给**只结算本人行**、**解不出模板就不结算这一行**（状态不流转、道具不丢，记进 `Skipped` 等下次重试）。
2. **一次事务提交**（`SettleExpired` → [CharacterRepository.SettleExpiredListings](../../Server/DfoServer/Persistence/CharacterRepository.Inventory.cs)）：
   逐行 `state=0 → 3`（条件更新影响 0 行即跳过并记原因）→ 投递退回邮件，**同一个外层事务**；
   任一步失败整批回滚（宁可整批重来，也不留「状态流转了但邮件没发」的半成品）。
3. **退回邮件**（`auction:return:{listingId}`，系统发件人「拍卖行」）：**道具 + 退还的保证金**装在同一封里，
   卖家在自己的邮箱里领取时入包/入钱包 —— 因此**不修改卖家角色行**、没有 revision 依赖，
   也不需要第二把租约（与一口价购买同一种托管通道）。

| 项 | 规则 | 依据 |
|---|---|---|
| 退还金额 | 按该行**实收金额** `auction_listings.deposit_gold` 原额退还（迁移 v37 逐行落库） | 历史行（该列出现之前上架）为 0：没交过就不退，绝不用当前常数凭空造钱 |
| 幂等 | 唯一判据是 `UPDATE ... WHERE state=0` **影响 1 行**；重复结算/并发结算影响 0 行 ⇒ 跳过 | 不会退第二次保证金，也不会把同一件道具退两次 |
| 触发点 | 188/190 的读路径，**在取列表之前**先结算（189 竞价页签不结算） | 刚结算的行不该再出现在「我的上架」，只应出现在 190 的历史里 |
| 失败策略 | 结算的领域级失败（投递被拒等）只记 `auction_expire_failed` 并继续回列表 | 一次到期退回失败不该把整个面板打成「点了没反应」；写库失败照旧上抛，不吞异常 |
| 日志 | 每次结算写 `auction_expire_settled`：结算行数、逐行 `ListingId/Key/Gold/Delivered/Note`、`Skipped`、当前政策常数 | 退了多少、哪一行被跳过，可事后逐行复核 |
| 机器人挂牌 | 不存在结算：`seller_character_id IS NULL` 的行没有可退的对象 | 与「不给机器人建角色行」同一口径 |

- 取消**不需要整列重建背包**：道具是「回到背包」（新增或并入已有堆），常规差量即可覆盖；
  这与上架（客户端把源槽当成被上架窗口持有）不同。
- 服务端**不主动补发 188**：184 应答的 `mode=0` 让客户端刷新「我的拍卖品」面板，
  再请求 188 时数据已经是下架后的（`state=0` 过滤）。

## 一口价购买（CMD 185）

一口价购买是本仓库**唯一跨账号转移资产与金币**的玩法：买方金币出、卖方所得入、挂牌道具易主。
锁序、事务边界、幂等与失败恢复的规则在
[并发、事务与响应延迟](../规范/并发事务与响应延迟.md#跨账号转移拍卖行一口价购买)，
**请求体布局已由两个实机样本差分完全定案**（30 字节），本节写当前行为与实现落点。

### 请求体与解析

两个实测样本（点拍卖对话框**唯一**的「购买」按钮发出；本版客户端没有竞拍 UI）：

```text
A 点挂牌 5（模板 101010912、一口价 24000）: 00 C05D0000 05 000000 84D6CB6A 00×13 E04D0506
B 点挂牌 8（模板 106000064、一口价 30000）: 00 30750000 08 000000 84D6CB6A 00×13 C06E5106
```

| 偏移 | 宽度 | 含义 | 证据 |
|---|---|---|---|
| `[0]` | 1 | 前导 0（与 183/184 同款） | 两样本都是 0 |
| `[1..4]` | i32 LE | **一口价金额**（单价还是总额见下） | A=24000、B=30000，与库内 `buyout_price` 一致 |
| `[5..8]` | i32 LE | **挂牌 id**（定位用） | A=5、B=8，与 `listing_id` 一致 |
| `[9..12]` | i32 LE | **到期时间回传**（库内 `expires_at_unix` 的回显） | 两样本都是 1791743620，与库内两行一致 |
| `[13..25]` | 13 | 保留 0 | 两样本都是 0 |
| `[26..29]` | i32 LE | **物品模板 id** | A=101010912、B=106000064，与库内一致 |

- 解析在 [AuctionBuyRequest](../../Server/DfoServer/Game/Auction/AuctionBuyModels.cs)：**至少 30 字节**才解析，
  不足即拒绝（拿不到 `[26..29]` 就无法与挂牌交叉校验，不能按残缺字段动跨账号资产）；
  多出的尾部字节忽略但记进日志（与 183/184 同款的版本容错）。
- ★ **参考实现那套 26 字节布局已被这两个样本证伪**：它的 `[13..25]` 之后没有数据，而本客户端在那之后
  还有 4 字节物品模板 id。因此不按 26B 读，也不允许「金额 ≥ 某个猜测值就成交」。

### 校验口径（每条用哪个字段）

| 校验 | 用的请求字段 | 与库内哪一列比 | 拒绝码 |
|---|---|---|---|
| 请求字段可用 | 挂牌 id、金额 | — | `0xd2` |
| 挂牌存在 / 在售 / 未过期 | 挂牌 id | `state`、`expires_at_unix` | `0x7e` |
| 一口价有效 | 挂牌 id | `buyout_price ≥ 0`（`-1` 是纯竞拍，**竞价不实现**） | `0x7e` |
| 不是自己的挂牌 | 挂牌 id | `seller_character_id` | `0x69` |
| 模板一致 | `[26..29]` | `item_template_id` | `0xd2` |
| 金额相符 | `[1..4]` | `buyout_price`（单价）**或** `buyout_price × item_count`（总额） | `0x7e` |
| 金币充足 | — | 买方 `characters.gold` | `0xd2` |
| 余额/条目可托管 | 挂牌 id | 条目快照 + 模板（钱包货币与史诗碎片不能进邮件） | `0xd2` |

- ★ **金额校验是保守口径**：命中单价或总额**任一**即接受，命中的是哪一个写进 `auction_buy` 日志的
  `AmountBasis`（`UnitPrice` / `TotalPrice` / `UnitEqualsTotal`）；成交**一律按库里的总额结算**，
  绝不按请求值。两个实机样本的数量都是 1 ⇒ 单价与总额同值，**必须再点一件数量 > 1 的挂牌**才能判定
  客户端发的是哪一个口径 —— 那一次点击后 `AuctionBuyAmountBasis` 就会给出 `UnitPrice` 或 `TotalPrice`。
- `[9..12]` 与库内 `expires_at_unix` 的比对**先只记日志**（`ExpiresEchoMatches`），不硬拒：
  它是否真是乐观锁门闸在 D95 未实测，现在升级会发明一条可能误拒的规则。

### 一个事务里的四步

[AuctionService.PlanBuy](../../Server/DfoServer/Game/Auction/AuctionService.cs) 只读规划（不写库、不占 owner），
[AuctionService.Buy](../../Server/DfoServer/Game/Auction/AuctionService.cs) →
[CharacterRepository.BuyListing](../../Server/DfoServer/Persistence/CharacterRepository.Inventory.cs) 一次提交：

1. **事务内重读挂牌**并复核内容（一口价 / 数量 / 模板 / 卖家）与过期时间；
2. **挂牌条件更新** `state=0 → 1` + `settled_at_unix`，**影响行数必须为 1**（唯一幂等判据）；
   为 0 抛 `AuctionBuyRaceLostException`，由服务层翻成静默码 `0x7e`；
3. **买方扣款**走既有背包提交器（revision 复核 + `currency_audit_log` 同一路径，不写裸 SQL 改金币列）；
4. **两封托管邮件**：买方道具（幂等键 `auction:item:{listingId}`，**必须投出去**）与卖方所得
   （`auction:gold:{listingId}`，收件人角色行不存在就**跳过**）。
   顺序是「挂牌行 → 买方角色 → 托管行」，即第 2 步在第 3 步之前：这样「这一行已经被买走」在任何一笔写之前
   就能判出来，重复点击不会先扣一次钱再回滚。

- ★ **道具走「托管邮件」而不是直接进买方背包**（方案 ④），两个原因缺一不可：
  ① 参考实现的交付方式就是「成交后由系统邮件投递」，邮件模块已有成熟的领取路径，购买阶段因此不会因背包满失败；
  ② 若购买时直接入包，就必须补发含金币槽的背包差量，而客户端 185 回调会**本地乐观扣一次金币**，
  补发 `0x000D`/`0x000E` 会被叠加成「再扣一次」（参考实现实测：余额不足时界面显示「余额清空」）。
  容量判定因此落在**领取邮件**时（邮件模块既有规则：背包满则拒绝领取、邮件保留）。
- **托管行复用邮件模块既有的插入 SQL 与幂等键规则**：`CharacterRepository.DeliverMailInTransaction`
  是 `DeliverMail` 的事务内实现（同一个 `INSERT`、同一条 `delivery_content` 比对），购买事务直接调用它，
  **不另写第二份邮件 SQL**，也不在那个事务里再开一个连接。
- **卖方不取租约**：卖方所得只进托管邮件，卖方在自己的会话里领取时才落进钱包。这条对**同账号的另一个角色**
  同样成立（当前选中的角色只有一个，另一个角色行不能绕过它被改写）。
- **机器人卖家 / 卖方角色行已删**：成交照常，卖方所得不入账（系统回收）。
  ⚠ 托管行所在的邮件表**有指向 `characters(id,account)` 的外键**，所以「卖方角色行是否仍存在」是
  **事务内按 `seller_character_id` 重查**的：查不到就**不插**托管行，而不是先插再等约束报错（那会把整笔成交回滚）。
- **不给机器人建角色行**：那会占用角色槽位、出现在选角名册；挂牌表本来就不要求角色存在。

### 费用与上限

| 项 | 本仓库取值 | 说明 |
|---|---|---|
| 保证金 10,000 金币 | **挂牌阶段扣、取消不退、到期未售退还**（已实现） | 用户口径。挂牌时与道具扣减写在**同一份库存计划**里（余额不足按可见码 `0xd2` 拒绝）；取消上架只还道具、**不退钱**；到期结算按该行实收金额（`auction_listings.deposit_gold`）原额退还，历史行为 0 |
| 手续费 5% | **卖方侧成交税**：卖方实收 `floor(成交价 × 0.95)`，买方只付成交价 | 已确认（用户口径）：5% 按卖方侧收，购买时**不收保证金**。费率是本模块唯一常数（`AuctionService.SaleTaxPercent`），不写死第二份、不加列 |
| 拍卖行优惠券 | **卖方侧**：有效 premium 类型 29 时税率 3%，否则 5%。金币寄售同一套 | 商品 100122/物品 137 为 1 日，100205/物品 193 为 30 日。百分数出自 `etc/guide/41.gdata`「拍卖手续费减少至3%」。stk 说明没有另一套数字。文档曾写金币寄售 5%→1%，PVF 无此出处，不采用 |
| 拍卖额上限 4 亿 | 取 `characters.auction_gold_limit`，**在挂牌时校验** | 购买时**不按买方上限拒绝**（否则会用买方配置拒绝别人的合法挂牌） |

- 成交价 = 库里的 `buyout_price × item_count`（`long` 计算）；结果 `> int.MaxValue` 视为数据异常拒绝 ——
  客户端搜索记录里该字段已被夹到 `int.MaxValue`，不能拿一个客户端显示不出的数成交。

### 应答与客户端可见行为

- 应答走 CMD 路径：成功 `flag(0x01) + mode(0x00)`（[AuctionPackets.BuySuccess](../../Server/DfoServer/Network/Builders/AuctionPackets.cs)），
  失败 `flag(0) + errcode`（码只能取 183 的白名单，编码器再挡一道）。
  ★ **形态在 D95 未验证**：只有参考实现 §4.10 的读数；本版客户端没有竞拍 UI，`mode=1`（金币寄售窗口）不发。
- ★ **成交后不补发任何背包/金币刷新**：185 回调已本地扣过金币；道具与卖方金币都走邮件领取路径。
  唯一的客户端可见动作是给**买方本人**发一条新邮件到达提醒（邮件模块既有入口，
  [GameSession.NotifyMailbox](../../Server/DfoServer/Game/Session/GameSession.Mailbox.cs)）；它不影响成交语义。
- 成交后挂牌从在售搜索里消失，卖家的「拍卖历史」（190）里仍是已成交状态。

## 一口价购买的第二入口请求桩（CMD 334）

334 的布局**没有任何本客户端证据**：参考实现自标「残栈传参使前导字节与挂牌 id 的精确偏移无法 100% 静态确定」，
而两个实机样本证实「购买」按钮发的是 185。因此 334 保持**请求抓取桩**
（[AuctionHandler.CaptureBuyRequest](../../Server/DfoServer/Network/Handlers/AuctionHandler.cs)）：

- **只做两件事**：试探性解析 + 写一条 `auction_buy_request` 日志。**不扣钱、不发货、不改任何状态** ——
  「整库逐表 dump 前后完全一致」由自测锁定，不靠人工确认。
- **不回任何应答**（返回未处理）：客户端只有在**收到应答**时才可能把这次操作当成成交，而 334 自己的失败码
  分派表没有本客户端实测；不应答同时满足「未实现请求不返回通用成功」。
- 日志含完整十六进制请求体、参考布局名与出处、逐字段**试探**读数（每个字段都标注「偏移未定」）、
  前 16 个位置上的 i32 读值，以及 `Implemented=false` / `StateChange=none` / `Reply=none` 三个结论字段。
- 实机点出 334 的请求体后，按 185 同一套流程（定案偏移 → 严格解析 → 规划 → 同事务提交）接入。

## 上架

[CMD 183](../../Server/DfoServer/Network/Handlers/AuctionHandler.cs) 是拍卖行里**唯一会改背包资产**的路径。
Handler 只做三步编排，业务规则在 [AuctionService.PlanRegister](../../Server/DfoServer/Game/Auction/AuctionService.cs)，
事务在 [CharacterRepository.RegisterListing](../../Server/DfoServer/Persistence/CharacterRepository.Inventory.cs)：

1. **只读规划**（`PlanRegister`）：读角色快照与模板目录，做全部校验，产出「扣哪个槽多少件 + 待写入的挂牌」。
   锁内不做资源解析、不写库、不发包、不等待网络。
2. **一次事务提交**（`AuctionService.Register` → `CharacterRepository.RegisterListing`）：背包扣减 + 挂牌插入 +
   背包审计在**同一个外层事务**里提交。任一步失败则整体回滚（背包、审计、revision、挂牌表全回退），
   不留半成品；写库失败不发送成功应答。**提交成功后由会话安装提交后的角色快照并产出整列刷新请求**
   （[GameSession.RegisterListing](../../Server/DfoServer/Game/Session/GameSession.Auction.cs)）。
3. **成功应答**（`flag + mode=0`，清客户端上架锁）→ **补发整列背包刷新 `0x000D`**。

### 源道具定位（推断字段的交叉校验）

协议里 `[1]`（源列表类型）与 `[2..3]`（源槽位）是**推断**字段，因此**不按它扣道具**：

- 先按「列表类型 + 槽位」取实例，**只有槽内模板 id 与请求的 itemId 一致时才采信**（列表类型必须是主背包）；
- 对不上就**按 itemId 扫描主背包**，候选**必须唯一**；同模板有多堆时拒绝并提示玩家重新放置，
  宁可让玩家重试也绝不猜一件扣掉（扣错道具不可逆）；
- 走回退路径时把原因写进计划的 `FallbackReason`，进 `auction_register` 日志的 `Fallback` 字段
  —— 这条日志就是「推断语义是否成立」的证据来源。

### 业务规则与依据

| 项 | 规则 | 依据 |
|---|---|---|
| 容器 | 只从**主背包**（含快捷栏格）取道具 | 上架窗口只从上架页取道具；仓库/穿戴/时装容器须先取回主背包（与既有约定一致） |
| 数量 | 整件类按 1 件；堆叠类必须为正且不超过当前堆，**只从该槽扣本次数量** | 复用 `InventoryDeleteService.TryDelete` 的单实例数量规则，不跨堆补扣；拆堆时余量与原 UID 保留 |
| 物品可上架 | 已锁定（排序锁/装备安全锁）、已到期、**带期限**（租赁或 `ExpireTime > 0`）、`TradeRestriction != 0`（含任务道具与各类绑定）一律拒绝 | 与[邮箱寄送](../../Server/DfoServer/Game/Mailbox/MailboxService.cs)同一套物品字段口径，不新建第二套可交易判定 |
| `AttachType` | `free` 可交易；`trade limit` 要求 `Attr` 高 3 位仍有剩余次数；`sealing`/`seal` 要求已解封；`account` 等账号绑定类**一律拒绝** | 同上；差别只在「账号绑定在拍卖行必然跨账号，所以直接拒绝」 |
| 虚拟资产 | 账号钱包货币（色晶/灵魂/点券/代币券 2681762 与 2681917）与史诗碎片不能上架 | 金币券是 `chn_Trade_Gold/gold_*.stk` 的 17 张 `[free]` 材料，可以上架，并且只出现在金币寄售窗口 |
| 价格 | 起拍价可为 `-1`（界面留空）；一口价 `-1` = 纯竞拍。**落库的起拍价必须 ≥ 0**：留空时归一为「有一口价就用一口价，否则 1 金币」。两个价格上限都取 `characters.auction_gold_limit`（默认 4 亿），起拍价不得高于一口价 | `auction_listings` 的表约束（`starting_price >= 0`、`buyout_price >= -1`）；上限列由[数据库](../开发/数据库.md)的 `characters.auction_gold_limit` 提供 |
| 时长 | 白名单 **6/12/24/48 小时**；白名单外回落 24 小时并记日志 | 客户端下拉的四档；回落不静默改值（`RequestedDurationHours` / `DurationFallback`） |
| 在售上限 | 每角色 **100 件**（`AuctionService.SellerListingCap`），达到上限拒绝 | 参考实现里官方无拍卖券上限为 5，而触顶时客户端只弹 `0xd2` 那个看起来像「安全模式」的提示；私服单人测试场景 5 件太容易触顶且提示会误导玩家，故按参考实现放宽后的口径取 100 |

### 提交后的界面行为

- **成功应答必须回 `mode=0`**：它是客户端清「上架进行中锁」`0x20c` 的唯一路径。不回这个字节，
  界面会一直锁着（二次上架发不出请求、背包槽位解不开）。
- **必须补发整列背包刷新 `0x000D`**：只刷源槽的差量**不足以**解除客户端把源槽当成「被上架窗口持有」
  的残留状态（症状 = 背包不可操作、无法再次拖入物品上架，重选角色才恢复）。
  实现走现有背包投影：`InventoryResult.WholeListRefresh` 让该容器连同「当前占用的槽 + 虚拟货币槽」
  一起重发（清空条目仍由既有 `Delta` 语义写成 `itemId = -1`），不手搓包体。
- ★ **整列刷新请求必须由会话在安装提交快照时产出**（`GameSession.RegisterListing`），
  Handler 不得自己拼一个 `InventoryResult`：投影只发布**已安装快照**产出的提交回执
  （`InventoryCommitReceipt`，与常规背包写用例、邮箱寄送同一份类型），缺回执时投影会抛
  「背包刷新缺少提交回执」。同时**提交后的快照必须安装回会话**：不安装时在线快照停在提交前，
  下一笔背包操作（含连续上架第二件）会在写事务里被 revision 复核拒绝。
  这两条是同一个入口的两半，缺任何一半都会让上架后的连接断掉。
- **队列顺序**：先应答 183、再发背包列刷新；反了会让客户端先收到物品变化而界面仍处于锁定态。
- **失败只能回白名单里的错误码**（见[协议页的错误码表](../协议/拍卖行.md#s2c-183-应答上架)）：
  客户端把未知码当成上架成功 ⇒ 界面假装成功而道具还在背包里，比「什么都不回」更糟。
  本仓库除「源道具定位失败」（静默码 `0x7e`，属过期操作）外一律回 `0xd2`，编码器再拒一次白名单外的码。
- **上架成功后该商品不出现在自己的搜索结果里**：搜索一直按「排除自己上架的」过滤，
  所以自己挂的东西搜不到、别人搜得到，这是本功能的验收点之一。

### 仍不确定的项

- `[1]` / `[2..3]` 的**语义**仍是推断（服务端靠交叉校验兜住，不依赖它扣道具）；
  日志里出现 `Fallback` 就说明推断与实际不符，据此可继续收敛。
- 失败码与客户端弹窗文本的**逐条对应**未实测，因此不做细分猜测。
- 上架成功时客户端是否另有成功弹窗未核实；服务端不额外补发提示包。
- 上架费用、结算的独立流转与竞价仍未接入（**下架、一口价购买已接入**，见上文 184 与 185 两节）；
  一口价购买的**佣金归属与保证金归属**是待实机判定的费用项，见 185 节的费用表。
- ★ **「竞拍入口」结案：本版客户端没有这个入口**（D95 转储离线反汇编定案）。「竞拍」文案 id `0xEA99`
  在**全地址空间零代码引用**（同组竞价文案 `0xEAA3`/`0xEAA4`/`0xEAAA`/`0xB557`/`0xB558`/`0xB553` 也全零引用，
  而同块其它串都有引用）⇒ 该构建裁掉了竞价 UI，不是「入口被隐藏」；186 回调 `0x023524E0` 只读
  `rec[44..47]`（itemId）与 `rec[49..52]`（value，丢行过滤器），两个填充函数（`0x26FF7D0`/`0x371A6C0`）
  **不读记录的任何偏移** ⇒ 服务端**无法**用任何记录字段或应答 `mode` 让入口出现。
  因此逐字段探针（`--auction-probe bid=` 的七个字段）**已退出默认轮换**（只按名字显式可达），
  `bidmode=` 只保留「窗口 6/7 分流」这一个已验证用途。**竞价 / 一口价的分支只能由服务端在
  CMD `0x00B9` 的字段上决定**；`[13..16] = -1` 已证实的只有「价格列不显示『售价』行」。
  细节与依据见[拍卖行协议](../协议/拍卖行.md)的「竞拍入口已结案」一节。
  **185 已按两个实机样本定案的布局接入**（30 字节，见上文 185 节）；**334 仍只注册为请求抓取桩**
  （不回包、不改状态），它的布局只有参考实现且自标偏移未定，接入前必须先用实机请求体锁定。
- ★ **「剩余时间」列保持不写是当前唯一正确的选择**：该列**不读 168B 记录**，而是读全局单例
  `G = [0x62EE560]` 的 64 位属性 `G + 0x7C8 + 0x1D*0x10 + 8`（语义 = 剩余秒数，除以 86400 / 3600
  得天数 / 小时；「天 / 小时 / 无限制」在道具提示侧由道具 flag `0xF6/F7/F8` 选），所以记录里保持 0。
  要真正生效必须先补一次「显示该列时采样」来定位这个属性的写入点，见[拍卖行协议](../协议/拍卖行.md)的
  「剩余时间列」一节。

## 分类过滤

分类 id 的映射在 [AuctionCategoryFilter](../../Server/DfoServer/Game/Auction/AuctionModels.cs)，
翻译成过滤条件在 [AuctionCategoryResolver](../../Server/DfoServer/Game/Auction/AuctionModels.cs)。

### id 空间与采集

客户端分类 id 是**扁平十进制**的 `父节点id + 序号`：父节点是 `…N00`，直接子节点从 `…N01` 起递增。
实证：`12001` 是首饰父节点 `12000` 的第 1 个子节点，而 D95 抓包确认 `12001` = 项链
（187 请求体 `[5..6]` 就是 `0x2EE1`），父节点的序号 `00` 不被任何子节点占用。

**整棵分类树已点遍采集**：本机运行实例的 `auction_search_category` 日志去重后得到
**140 个不同 id = 9 个顶层 + 131 个子叶**，全部固化在 `AuctionCategoryFilter.CollectedIds`，并由自测逐个锁定。
采集命令（读运行中实例的日志，注意该文件被服务端占用，必须用共享读打开）：

```powershell
$log = "Server/DfoServer/bin/Debug/net10.0/Logs/server.jsonl"
$fs = [IO.File]::Open($log,'Open','Read','ReadWrite'); $sr = [IO.StreamReader]::new($fs)
$lines = while(-not $sr.EndOfStream){ $sr.ReadLine() }; $sr.Close()
($lines | Where-Object { $_ -match '"Kind":"auction_search_category"' } |
    ForEach-Object { ($_ | ConvertFrom-Json).Detail.CategoryId } | Sort-Object -Unique).Count
```

> ⚠ 不要用 `[ordered]@{}$seen[$id]` 收集 id：`OrderedDictionary` 的 int 索引会走「位置」重载并抛
> `ArgumentOutOfRangeException`，用 `Sort-Object -Unique` 或 `HashSet[int]`。

### 武器/防具子叶的对账依据与边界

- **族 ↔ 职业/材质**：8 个武器族对应界面给出的 8 个武器节点名，5 个材质族对应 5 个防具节点名，
  两处都按 **id 升序 = 界面顺序** 一一对应。
  **顺序依据是本机界面顺序（用户给出），没有逐节点抓包**；族表的成员集合另有本机 PVF 实测支撑：
  每个武器族恰好对应 5 个物品组（族 101 = ssword/katana/club/lswd/beamswd，族 102 = knuckle/…），
  组名集合互不重叠，因此「哪一个族属于哪一个职业」在数据上是确定的。
- **武器类型（短剑/太刀…）取不到，不编**：物品模板没有 `[item group name]` 字段，而模板 id 的
  族内分段与组名的排序位置不一致（实测：族 101 的 5 个组各自占用一段 id，段号与组名排序无关）。
  因此同一族的 6 个子节点**维度相同**（族 + 职业 + 部位 12），点「短剑」会列出该职业的全部武器。
  这一点是刻意的：宁可粗（不漏东西），也不猜一个可能把别的职业武器放进来的序号映射。
- **防具两个维度都要**：材质（族号，来自模板 id）+ 部位（模板字段）。只按材质会让「点布甲」列出
  布甲的下装/鞋/腰带/头肩，只按部位会把别的材质混进来。
- **职业位来自模板自带的 `[usable job]`**（`ItemTemplate.Jobs`，与 `ItemCatalog.JobNames` 同序），
  不是另建一套职业编号；族表里的职业标签与 `JobNames` 逐项对应，自测断言两处清单同序。
- **★ 材质 114（板甲）与武器族 114（魔枪士）共用同一段号码**：族掩码读的是模板 id 的族号，
  无法只靠 id 区分，因此**武器族优先命中**，板甲子叶只靠部位维度收窄（不猜一个可能放进其它大类的材质掩码）。
  板甲武器族与板甲材质的冲突属于已知未确认项，见[拍卖行协议](../协议/拍卖行.md#仍未确认的项)。

### 仍未映射的子叶（已登记原因，点了只按所属顶层过滤）

也走同一条兜底：按所属顶层维度过滤，并在日志里写明原因。

**这些子叶的最终收敛方法**（留给实机核对，一次点击即可定案）：拿一件**已知类型**的道具，
点该大类下的第 1 个子节点，看它出现在哪个叶子里 —— 叶子↔类型的顺序一旦定下来，
把该子叶的 id 与对应维度加进 `AuctionCategoryFilter.Leaves` 即可，映射表与自测的计数断言会同步提示要改哪里。

### 三种维度的落地方式

不允许改表结构，因此三类维度的落地方式不同：

- **物品大类**（`13001`–`13006`、`33001`–`33004` 等）下推到 SQL，条件是 `auction_listings.item_kind IN (…)`。
- **装备部位**（武器/防具/首饰/称号/特殊装备/宠物装备）**在内存里**过滤。表里没有部位列，
  而首饰（项链/戒指/手镯）与宠物装备（红/蓝/绿）的 `item_kind` 与父节点完全相同，只有部位能区分。
  把部位展开成模板 id 再 `IN (…)` 已实测否决：武器一类约 23000 个模板 id，
  SQLite 每次查询约 12 秒，另有约 11 秒的一次性目录遍历。内存过滤只对**本次匹配到的挂牌**逐个查部位
  （按模板 id 缓存一次），实测 400 行在售挂牌冷启动 68 ms、热查询 3 ms。
- **武器族 / 防具材质族与职业位**也**在内存里**过滤，但**不查目录**：
  族号直接从模板 id 的数字段读出（`id / 1_000_000`），职业位取 `ItemTemplate.Jobs`。
  因此族判定与目录完整性无关，坏模板也不会把整行判成别的族。
  族掩码与部位掩码**都要命中**（`InCategory` 逐维判定）：「族 + 部位 12」既能挡住别的职业的武器，
  也能挡住落在武器族 id 段里的武器时装（部位 10）。
- **父节点与子节点共用一份口径**：有子叶的大类，其维度由子叶**合并**得出，只把子叶没覆盖到的维度用兜底补齐
  （首饰补只有父节点能显示的耳环 25，宠物补本体部位 26）。两边各写一份会出现「父节点收了子节点过滤不掉的物品」。
- **计数与本页必须来自同一份过滤结果**：客户端按每页 10 条算总页数并直接显示「搜索出 N 个」，
  用过滤前的条数会让页数虚高。因此内存过滤在分页**之前**完成（`LoadMatches` 取全量 → 过滤 → 分页+计数）。
- 分类 id 与 itemId 同时给出时取交集；分类过滤与「排除自己」可叠加。

| `12000` / `14000` / `32000` / `33000` | 首饰 / 宠物 / 特殊装备 / 副职业 | 该大类的 `item_kind` | 该大类的部位 | **0**（确无该类挂牌） |
| `31000` / `34000` | 设计图 / 其它 | 不过滤 | 不过滤 | **13** |

「排除自己」是**另一条独立的门**，不与分类过滤互相顶替：同一批数据下「全部」12 条、防具 5 条、武器仍是 4 条
（自己那条只在「排除自己」下消失）。

同组还逐层锁住「哪一层剩下多少行」，因此「某个分类被滤空」会直接落到具体一层：

1. **仓储**：`CountListings()` = 14（含已取消）；无分类条件的分页搜索回 13 条匹配、本页 10 条。
2. **SQL**：`item_kind IN (1)` 回 10 行、`IN (2,3,4,10)` 回 3 行 —— 大类下推不会把武器/防具整体滤掉，
   且 `Kinds` 为空的解析（设计图 `31000`、其它 `34000`、未映射 id）**不下推任何条件**。
3. **读用例**：上表的期望条数（内存维度只做武器/防具/首饰之间的区分）。
4. **应答编码**：帧头「匹配总数 / 本批条数」与记录数自洽，且每条记录的道具块都过客户端
   「`itemId` 合法 ⇒ 块 `+6` > 0」的静默丢行门闸（见[拍卖行协议](../协议/拍卖行.md)的道具块一节）。

「0 条」的两种情形因此可分辨：**确无数据**（族 104 的神枪手武器、首饰、副职业）在 SQL 侧仍取回行，
0 来自内存里的族/部位判定；**真被滤空**才会在 SQL 侧就已经是 0。

### 未识别 id 为什么不过滤

参考实现对未映射 id 回空列表，那是它对自己那份**已定案**的分类表做法；本仓库对**没采集过**的 id
保持不过滤——客户端界面可能已经变化，猜错的过滤会让列表整体变空，且与客户端「总数为 0 时不刷新页数」
的现象混在一起（看起来像搜索无反应），无法分辨是过滤错了还是本来就没有数据。
每次都把 id、解析状态、下推维度与**取舍说明**记进 `auction_search_category` 日志，便于逐次核对。

### 首版遗留的粗过滤

- `13003`/`13004`/`13006`（投掷/抽取/其它）与 `13001` 同按 `ItemKind.Consumable`：本仓库 Catalog
  对这几类 `[stackable type]` 都归入 Consumable，取不到更细的维度，不编。
- `33001`–`33004` 同按 `ItemKind.Profession`：参考表用 `[expert type]` 区分炼金/控偶/附魔，
  该字段没有进 `ItemTemplate`。
- `14000` 无法区分宠物蛋与宠物本体（同为 `Creature`，区分字段 `[output index]` 没有进模板）。


## 数据

[数据库](../开发/数据库.md) 的 v37 步骤建立了 `auction_listings`（跨账号可见的挂牌表，不建立指向 `characters`
的外键：机器人卖家为 NULL 且没有角色行），列名与约束以该步的建表语句为准。`item_entry` 保存物品条目的字节快照，
本模块只按固定偏移从中取道具块需要的 itemId / value / attr / 耐久 / 封印，不解释其余字段。

- 卖家名随挂牌保存（机器人卖家也在表里），但**应答不包含卖家名，且该项已关闭**：D95 转储离线分析定案
  —— 本版客户端**不渲染**这个字段（全转储 UTF-16LE 穷举「卖家」只有 3 处且都是道具描述/NPC 文案，
  没有任何 UI 标签；186 回调也没有读取记录 `[21..33]`，全转储 `mov ecx,0x7B; rep movsb` = 0 处）。
  搜索列表没有「卖家」列，记录里那段 13B 串区保持 0 是正确的；表里的 `seller_name` 列保留（数据模型不变），
  但服务端不必（也无法）把它送进应答。依据见[拍卖行协议](../协议/拍卖行.md)的搜索记录一节。

- 仓储只做 SQL（整批插入、按条件分页查询、计数、过期过滤）与单行插入入口；`IAuctionListingStore`
  的**实现方是 `CharacterRepository`**（与邮箱同一形态）：上架要与背包扣减共用同一个写事务，
  写背包的唯一实现入口在角色仓储，因此不让两个仓储互相构造。
  计数与本页查询在同一个读事务内完成，避免两批挂牌在两次查询之间到期，导致「匹配总数」与「本批条数」互相对不上。
- 搜索不接收账号 owner：它是跨账号只读查询，不读取也不修改任何角色资产。
  搜索按卖家**排除自己**；「我的拍卖品」（188/190）走同一份存储合同的 `LoadSellerListings`
  按卖家**取自己**的行，同样是只读查询、不分页。
- 上架提交接收 owner 与规划时的角色快照：写事务内重新核对角色 revision 与完整背包快照
  （复用背包模块的 `CommitInventoryInTransaction`），陈旧计划既不扣背包也不写挂牌。
  取消提交同样接收 owner 与快照，且在同事务内复核挂牌仍是「当前角色的、`state=0`」的那一行。
- `item_entry` 是**双向使用**的：上架经 `AuctionPackets.ItemEntrySnapshot` 保存核心，
  前123B保持原条目；带史诗交换来源时追加12B：`EPXO` 标识（4B）、来源版本（int32）与来源盒模板编号（int32）。
  带实例分解限制时再追加8B：`DJR1` 标识（4B）与限制位（uint32，1表示禁止分解、3同时禁止毁装灵魂返还）。
  两个尾部按来源、限制顺序组合，仅供服务端持久化，不给表加列存核心 JSON。取消时用严格互逆的
  `AuctionPackets.ItemCoreFromEntry` 把同一份条目逐字段读回核心，再交给既有发放入口还回背包。
  两个方向都在装配处注入，`Game/Auction` 因此不引用 Network；条目排列的唯一定义仍在
  [ItemListProtocolWriter](../../Server/DfoServer/Network/Builders/Inventory/ItemListProtocolWriter.cs)。
  **物品种类不在条目里**（挂牌表单独一列），由调用方传入并先与模板交叉校验。
  接受123/131/135/143B；旧123B不反推来源或限制。来源仅接受普通装备、版本1和正数来源编号，限制仅接受装备和位值1或3；未知长度、标识或元数据拒绝，不能发放残缺核心。
  搜索、详情及其他客户端道具块仍按原123B核心解释，诊断条目也只取前123B，服务端尾部不进入wire。
  回退旧二进制前须核对其支持的挂牌长度及完整资产兼容与备份恢复方案，
  不得截断尾部或静默丢失来源与限制。来源语义与旧JSON兼容见[完整实例](背包与装备.md#分层与唯一状态)。
- **开发种子**：`--auction-seed <条数>`（默认 0 = 不种子，上限 10000）。启动时在建库/迁移之后、开始监听之前，
  若表内一条挂牌都没有则写入。候选池共 **12 件**，覆盖多个大类：四件低阶武器（训练用刀 101010912、
  训练用东方棍 102040571、训练用魔杖 106020596、长矛 106000064）、**五件低阶防具**（粗布衬衫 10001、
  牛皮背心 10400、牛皮短裤 12400、牛皮腰带 16400、牛皮拖鞋 18400）、**两件常见材料**（无色小晶块 3037、
  金色小晶块 3262）与粗布腰带随机礼盒（10014751）。**不使用 3033–3037 这类账号钱包物品**。
  取值固定便于实机核对：第 n 行（从 0 起）起拍价 `12000 + 1000×n`；每第三行一口价为 `-1`（纯竞拍），
  其余为起拍价两倍；到期时间为启动时间 + 24 小时；卖家名在「拍卖机器人甲 / 乙 / 丙」之间轮换且
  `seller_character_id` 为 NULL。本机 PVF 缺失的候选物品会被跳过并记入 `auction_seed` 日志的
  `UnresolvedItemIds`；候选物品全部缺失时启动失败（显式报错，不用默认物品伪造挂牌）。
- 尚未接入：上架费用、结算的独立流转与竞价（**下架与一口价购买已接入**；334 仍只注册为抓包桩）。

## 开发诊断：均价应答结构探针

记录布局与应答通道已定案，因此搜索候选轮换**默认关闭**：关闭时 186/187 走真实挂牌数据，
只有 182 均价查询与「我的拍卖品」（188/189/190）会按候选轮换（这两处的结构还在收敛），
另有已停用的搜索记录**逐字段探针**（原用于判断竞拍按钮由哪个字段决定，**该问题已定案关闭**，
候选只按名字显式可达、不进任何默认轮换）：

```text
--auction-probe "avg=flag58,flag33,flag25,ref58;avgonly=1"
--auction-probe "mylist=a21-151,a21-159,mirror-168,head-only"
--auction-probe "bidmode=0,1"
--auction-probe "bid=allpure,flag8,market17,flag42,tail34,tail38,remain156"   # 已停用：仅存史/对照
--auction-probe off
```

- **五组候选各有独立下标**：搜索布局一组、均价一组、「我的拍卖品」按页签各一组、搜索记录字段一组、
  搜索应答 `mode` 一组。均价候选在客户端每拖一次物品时前进一个，「我的拍卖品」候选在该页签每请求一次时前进一个，
  搜索记录字段与 `mode` 候选在每次搜索时各前进一个；**都不会改变搜索返回什么**
  （`avgonly=1` 把这条规则写死：搜索整条路径忽略探针）。
- ★ **`bidmode=0,1`：同一个搜索请求交替用 `mode=0` / `mode=1` 应答，记录内容完全相同**（只用 0/1：
  客户端按应答 mode 分流到 `GetWindow(6)` / `GetWindow(7)` 两套填充，其它取值没有对应分支可判）。
  它验证的是**「应答 mode 决定窗口 6/7 分流」**（**已实机闭环**），**不影响竞拍入口**
  —— 本版客户端没有那个控件，详见[拍卖行协议](../协议/拍卖行.md)的「竞拍入口已结案」一节。
  未给该键时 `mode` 一律回显请求首字节（既有行为不变）。
  日志 `auction_search` / `auction_search_result` 记 `Mode`（请求里的字节）、`ReplyMode`（**本次实际写入的**）、
  `ModeProbe`（探针取值，`-1` = 回显）。
- ★ **只配 `avg=` / `mylist=` / `bid=` / `bidmode=` 不会替换真实搜索结果**（`AuctionProbeSettings.SearchOverride`）：
  为了看某个记录字段或某个窗口而开探针时，搜索仍然读真实挂牌 —— 否则真实行会被合成行换掉，反而看不到要观察的按钮。
  只有显式给出 `rows` / `presets` / `total` / `reply` / `kind` / `pad` / `items` / `count` / `price` / `buyout`
  才切到合成探针行。
- 「我的拍卖品」候选名与结构假设见 [AuctionMyListReply](../../Server/DfoServer/Game/Auction/AuctionMyListReply.cs)：
  `a21-151`（188/190 默认）、`a21-159`（189 默认）、`a21-151-noremain`（对照「剩余时间字段写坏整行」）、
  `mirror-168` / `mirror-168-word`（对照「与 186 搜索共用一套记录」）、
  `head-only`（哨兵：只回 `flag+mode+count=0`，用于分辨「面板打不开」与「记录读不出」）。
  未给 `mylist=` 时每个页签各用参考实现的默认候选。
- 搜索记录字段候选见 [AuctionSearchRecordProbe](../../Server/DfoServer/Game/Auction/AuctionSearchRecordProbe.cs)：
  `contract`（对照，逐字节等于合同编码）、`allpure`（只改 `[13..16] = -1`）、
  `flag8` / `market17` / `flag42` / `tail34` / `tail38` / `remain156`（各只改一个字段）。
  ★ **这组候选已停用**（D95 反汇编定案）：本版客户端没有竞拍入口，七个字段与入口无关
  （判据不是「位置未解」而是**不存在**），因此**默认轮换序只剩 `contract`**（一个字段都不改），
  七个候选只按名字显式可达 —— 保留的是排查现场与「每个候选只改一个字段、差异字节正好落在该字段宽度内」
  的编码回归（自测断言），其中 `market17` 还兼作「平均市价非 0 时客户端是否跳过『高于市价 2 倍』提示」的诊断。
  **不要再**用它们找竞拍入口（`allpure` 把每行一口价都写成 `-1`、与库内真实挂牌不符，本来就只能在
  显式点名时用一个来回合）。
- 缺省候选是 `flag58`（**flag + 57B 参考结构**：CMD 应答体自带 1 字节 flag，见上文）；
  候选名与各自的**结构假设**见 [AuctionAveragePriceReply](../../Server/DfoServer/Game/Auction/AuctionAveragePriceReply.cs)
  与[协议页的候选表](../协议/拍卖行.md#结构候选当前轮换集)。
  `flag33` / `flag25` 只用于分辨「是 flag 位置问题还是长度问题」，`ref58` 是「多余字节在尾部」的对照。
- **安全底线**：均价数据体 < 8 字节的候选会读崩客户端，因此候选表里不存在这种项，
  `avg=` 里点不到它们，编码器与发送处还会各拒一次；「我的拍卖品」的安全底线是
  「体长不短于结构与空列表头部所需 + flag 在体首」，同样由候选表与编码自检各挡一道。
- 每次 182 请求都会写 `auction_average_price_result`（候选名、形状、数据体长度、发几条、是否发 795）
  与逐条 `auction_average_price_reply`（mode、长度、**真正下发的十六进制**），
  客户端随后的 `C2S 217 OVERFLOW_INFO`（body `01 B6 00`）因此可以与具体候选一一对应；
  每次「我的拍卖品」请求写一条 `auction_my_list`（页签、mode、是否有回落、卖家、count、候选名、
  记录尺寸/道具块偏移/计数宽度、体长与实发头部十六进制）。
- 价格与挂牌数据本身仍来自真实数据，候选只改结构与发送顺序、不改业务取值。
- 参数与键的完整列表见 [AuctionProbe](../../Server/DfoServer/Development/Auction/AuctionProbe.cs)；
  搜索候选（`rows` / `presets` / `reply` / `kind` / `total` / `pad`）只在 `avgonly=0` 时生效，
  并会用真实物品模板构造真实条目字节覆盖真实挂牌数据，仅供继续排查未确认的量使用。

## 与其它模块的边界

- 物品条目的字节排列只由[物品协议](../协议/物品.md)的 `ItemListProtocolWriter` 产生；
  拍卖行道具块按固定偏移取字段后**逐字段**写进 83B 块，绝不截断或整体移位普通条目
  （条目以 `slot:u16` 开头、块以物品种类开头，且块内 attr/value 顺序相反；错一位客户端会静默丢弃整行）。
  上架保存的挂牌快照同样走这个入口（`AuctionPackets.ItemEntrySnapshot`）。
- `Game/Auction` 不引用 Network 与 Persistence 实现：挂牌读写走领域存储合同 `IAuctionListingStore`（实现归 Persistence），
  条目字节的编码入口由 [ServerRuntime](../../Server/DfoServer/Infrastructure/ServerRuntime.cs) 在装配处传入。
- 上架**只用一个外层事务**：扣物品、写挂牌、写背包审计共用同一个写事务
  （见 [并发、事务与响应延迟](../规范/并发事务与响应延迟.md)）。分两次提交会出现「背包扣了、挂牌没写上」的
  半成品，而上架是会改背包资产的操作，半成品只能靠人工补偿，因此不允许。
  取消同样只用一个外层事务（道具还回背包 + 挂牌置为已下架 + 审计），方向相反、口径一致。
- **在线角色快照与提交回执归 Session**：上架/取消提交后由
  [GameSession.RegisterListing / CancelListing](../../Server/DfoServer/Game/Session/GameSession.Auction.cs)
  安装提交后的快照并产出 `InventoryCommitReceipt`（与常规背包写用例、邮箱寄送同一份类型），
  Handler 只把会话给出的刷新请求交给投影。业务层（`Game/Auction`）不持有会话状态，
  投影也不接受未经提交的回执 —— 这条分工让「扣了物品但客户端不知道」在结构上无法发生；
  取消则连「提交后的刷新成为失败点」也不可能（回执由会话在安装快照时给出）。
- 上架时的可交易判定与[邮箱](邮件.md)共用同一套物品字段口径（`AttachType` / `TradeRestriction` / `SealFlag` /
  `Attr` 高 3 位交易次数 / 租赁与期限），不新建第二套；差别只在「账号绑定在拍卖行必然跨账号，因此直接拒绝」。
  取消时的「道具还回背包」复用发放服务的 `TryGrantCore`（含背包满判定），不新建第二套放置规则。
- **一口价购买（185）是目前唯一的跨账号写路径**：只取**买方**一把租约，卖方不取锁、其角色行不被改写，
  所得只进**托管邮件**（`auction:gold:{listingId}`，卖方领取时才落进钱包）；买方道具同样走托管邮件
  （`auction:item:{listingId}`）而不是直接入包 —— 理由是硬性的：185 回调会本地乐观扣一次金币，
  购买时直接入包就必须补发含金币槽的背包差量，会被客户端叠加成「再扣一次」。
  挂牌条件更新、买方扣款与两封托管行在**同一个外层事务**里提交；
  托管行复用邮件模块既有的 `DeliverMailInTransaction`（同一份 SQL 与幂等键规则），不另写第二份。
  锁序、失败恢复与费用口径见[并发、事务与响应延迟](../规范/并发事务与响应延迟.md#跨账号转移拍卖行一口价购买)。
  **CMD 334 仍是请求抓取桩**（布局未定），接入前必须先用实机请求体锁定。
  取消上架（184）不涉及跨账号转移（道具回到原主背包），已按其同事务口径接入。
