# 背包与装备

当前实现满扩展 Main 背包、快捷栏、普通穿戴、时装与宠物容器、勋章与守护珠容器及镶嵌、移动/拆分/合并/交换、整理、普通丢弃、排序锁、装备安全锁、选角到期清理、CHR 初始装备、角色/账号钱包、金币上限扩容、个人和账号仓库、普通 NPC 商店购买/材料兑换/出售/限购、商城点券购买、单件/全部/快速金币修理、普通武器锻造与固定/增量锻造券、普通 NPC 与便携式装备分解、时装合成、账号史诗碎片图鉴与配方制作、S5A9 租赁点充值与装备租赁，以及普通奖池和普通物品选择型礼包的单次与批量开箱。普通`[waste]`类消耗品接入指定槽单件消费与完整使用收尾，恢复和临时效果由客户端处理；服务端权威HP/MP、秘商、其他特殊容器、装备属性重算及战斗效果仍需独立接入。

## S5A9 租赁

- C2S1002 `CHARGE_RENTPOINT` 只接受固定 21B 请求，`offset 13` 为类型、`offset 17` 为充值数量。幸运星余额保存于账号钱包的 `rental_points`，只通过 S2C988 `EQUIPMENT_RENTAL_LIST` 投影，不创建 Main/消耗品实体。
- C2S1001 `RENT_EQUIPMENT_ITEM` 只接受固定 21B 请求，`offset 13` 为 PVF 装备 ID、`offset 17` 为职业/等级组。租赁领取以客户端请求的等级组查匹配 PVF 商品与费用，不再按角色等级重算档位，也不使用装备穿戴等级拦截领取；职业、商品分组、账号余额、Main 装备页空槽和 24 小时过期时间仍在同一个 InventoryPlan 中校验并提交。租赁实例标记 `IsRental`，普通 C2S19 穿戴仍校验原 PVF 等级，锁、到期清理和重启恢复沿用原规则。
- 可租商品由客户端结合 `etc/chnrentsystem/rentsysteminfo.etc` 与装备 PVF 配置提供，服务端不下发可租商品目录。S2C988 只发送余额、已租且有效的模板 ID 及剩余秒数，同模板保留最晚截止。Main 全量与差量物品行的租赁装备期限在 `+0x38` 同样投影为剩余秒数，各包使用单一发送时间快照；数据库仍保存 Unix 绝对时间，新租赁为 24 小时。到期实例在选角准备阶段原子清理，不进入租赁面板或任何背包页。988 的数值依据及客户端消费者验证边界见[租赁协议](../协议/租赁.md)。
- 失败请求发送对应失败收尾包，发送成功发生在事务提交之后；同一账号共享余额由账号钱包 revision 串行校验。实机仍需核对租赁面板、不同部位装备穿脱和到期后重登画面。

本页是业务规则、在线状态与持久化的唯一说明；字段表及原码依据见[物品协议](../协议/物品.md)。新增钱包/detail/邮件/交易等玩法时，另读[物品扩展](../规范/物品扩展.md)相关条目，不因普通背包改动加载全部后续业务。

## 普通恢复药

[CMD44使用服务](../../Server/DfoServer/Game/Inventory/Services/InventoryConsumableUseService.cs)按`[stackable type]`的`[waste]`、`[throw]`和`[set]`大类处理普通客户端效果道具，不按目录、物品ID、子型数值、item group或固定恢复四元组建立白名单。HP/MP恢复、持续属性、异常状态解除、随机效果及投掷/放置物件由客户端消费本地PVF；服务端不验证其效果数值、目标、持续时间或物件脚本，也不据此生成另一套血蓝或物件状态。1113入门MP药剂、食物、状态药、飞盘及藤蔓种子沿同一分类入口；投掷和放置类要求已加载且角色存活的正式副本实例，城镇、加载及结算不能伪造战斗使用。契约、礼包、宠物、经验/升级券等大类及明确使用action请求或booster产物的道具保留专用业务，不能靠普通成功ACK代替服务端资产处理。

Runtime从共享stackable名册和物品目录装配[使用目录](../../Server/DfoServer/GameWorld/Items/RecoveryConsumableCatalog.cs)，已知资源首次使用在账号锁外解析，按资源ID缓存并共享并发加载；未知ID不建立负缓存。缓存归目录实例，随本次PVF生命周期结束，不扫描全量STK或持有另一份归档。

请求指定Main药剂页或真实快捷栏源槽，单次消费1件，验证原模板、持久UID、完整Core、数量、原最低等级、安全锁及提交时期限；排序锁不被扩大为禁止使用。已Ready城镇、正式战斗或结算可处理；加载、选图、未决死亡/拾取/结算/任务场景及活动门禁拒绝。锁外规划后，在原owner内复验角色快照、revision、选角epoch、实际phase和副本房间身份，复用CommitInventory的库存及审计事务。未知提交结果关闭原连接、不自动重做SQL或补发ACK，重连只加载实际数量，不承诺撤销客户端已开始的本地效果。

提交成功才发完整ACK44，由客户端消费1件、耗尽清槽及结束pending等待。普通使用不先发或再发源NOTI14，防止重复扣减或先清原对象；同事务更新的实际寻物条件仍发布。发布守卫绑定原owner、Selected引用、epoch、phase和房间身份，过房、换角、接管或库存变化后旧回执失效。字节、包序和opaque依据见[物品协议](../协议/物品.md#普通恢复药-cmd44)。

本服将PVF的cool time按毫秒解释，cooltime group决定共享组；省略cool time按0处理，省略组时按物品独立计时。记录使用单调时钟且只在实际提交后推进，换角、End和重连清理，不增加持久schema；记录键仅来自资源名册及其组声明。原生标签到时钟单位完整链尚未闭合，此处属于本服约定，不把某个样品的10秒或组0/1强加给其他道具。opaque生成范围0–32767，含0且后续可复用；不能作为永久操作身份。成功冷却窗口内相同完整请求关闭原连接且不重发成功或失败ACK，源已耗尽或同槽换新UID也不解除歧义；窗口后重新校验真实源。同组不同请求冷却拒绝仍回复完整中立123收尾，不永久保存token集合。

服务端没有当前HP/MP owner，本入口不另建平行血蓝状态或伪造恢复包。客户端匹配PVF的效果先后、全满血蓝时失败撤销、冷却结束后第二次使用、同房间拾取及UDP/同屏仍需隔离Windows验收。`consumable-use` TCP及原声明/规则/Session文件库回归验证数量和使用收尾，不等于完成权威回血或完整药效。

普通练习、修炼场和职业体验统一由入场计划的`HasFreeCombatConsumption`免扣上述普通效果道具，包含`[throw]`投掷物和`[set]`放置物。即时效果由客户端发送端执行；服务端验证原源、资格和冷却后，采用原生结果位0、错误码0的ACK44结束pending，不再发送库存通知，最后1件也不发生客户端删槽及重建。该应答在客户端日志中可显示`Result: Error ErrCode: 0`，但服务端业务结果是已接受免扣，不等于资格拒绝或数据库失败。

独立标签`[sub type] 2`将效果延后到成功应答，不能套即时效果的0/0应答；它仍接收成功ACK44，再以完整NOTI13恢复真实Main、钱包和锁状态。完整载入抑制新图标标记，不使用仍可触发图标effect的1681，也不发送只有源格的伪完整列表。缺省子类型按0解释，不把`[stackable type]`后面的整数当成该标签。两种免耗路径均保留原冷却、UID及元数据，不写revision或消费审计；不依据禁止翻牌或免疲劳等单个资源标记泛放其他副本。普通模式成功使用实际扣1件，退出免耗玩法后不保留豁免。原生0/0应答、应答后效果分支及13抑制图标已有匹配原码依据，最终药效、投掷/放置和召唤助手显示仍须客户端验收。

## 技能材料扣除

CMD18的Main/type2/flag0按本次请求足额扣除材料，城镇与地下城均可处理；无色等虚拟晶体/灵魂按匹配物品ID和槽位扣账号钱包，不创建实体。材料不足、非正数、重复槽或错误映射整批拒绝并保持连接，普通type0丢弃的数量归一规则不变。所有材料、角色/账号revision及审计复用原有库存事务，后段失败整笔回滚；成功ACK18返回本次实际删除量，材料槽不再发送14差量，避免获得物品提示。不能将扣除后的余额放入删除量字段，否则客户端会再次扣减该余额。同批普通丢弃槽及其他操作的差量仍正常发送。账号其他角色重登读取同一余额。

普通练习、修炼场和职业体验统一免扣Main/type2技能材料及type3装备脚本材料，包括无色、有色晶块与实体材料。仍验证实际源及足额数量，成功ACK18回删除量0，不写库存、钱包、revision或消费审计。混合包中的type0/1真实丢弃仍按实际删除量提交并同步；商城等付费事务继续扣点券。对应玩法身份见[副本](副本.md#副本练习模式)，不把普通副本误归免耗。

这条CMD18请求只实现库存消费，不从它推导命中、伤害、冷却、施法资格或任务进度；CMD38仍记录使用通知。尾部客户端状态无明确事务编号，不按相同正文去重连续施法。

装备脚本的CMD18/Main/type3/flag0沿同一材料事务处理。六色晶体仍归账号钱包，实体材料仍按实际槽位与源值核对；数量必须正且足额，混合请求整体提交或回滚。普通场景成功ACK回本次消耗量与type3，前述免耗玩法回0；不再追加材料槽的14差量。请求不携带装备脚本ID，不能只按晶块模板断言来源是晶体契约，也不以契约选择或服务端另造的计时器收窄其他合法装备消费。

## 副本地面丢弃

CMD47 是副本及结算阶段的地面丢弃，与城镇 CMD18 的直接销毁分开。原生请求包含坐标、容器、槽和完整数量；坐标及尾byte不提供资产资格。复用库存规划，支持 Main 和普通穿戴槽中的可交易普通物品；已过期、租赁、安全锁、不可交易及缺独立detail的时装/宠物拒绝。严格按正且足额的请求数量扣除，不套 CMD18 的整堆归一策略。

Session 在原账号owner内冻结角色、Run/epoch、源完整实例和请求；模板查询及纯规划在锁外，返回后复验原快照。MAP、地面对象和拾取状态只在原Run内存保存，不新增表或升级schema。实际扣物、既有库存审计和已存在的对象key高水位同事务提交，成功后才发布 ACK47→NOTI40→必要源槽/穿戴刷新。未知提交结果保留原准备，其他库存变更、过房、领奖和回城不得覆盖它；恢复时复验原事务的库存审计、精确revision和完整资产，不重新分配key或扣物。正常请求不扫描历史审计，只有结果不明恢复才查询本操作标记。结果明确失败也只沿原准备重试。

物品归当前MAP和Run，过房保留未拾取对象，回访完成加载后按当前epoch拾取；来源epoch、完整Core及请求位置不改写。拾取复用库存原子提交和审计，失败保留原地面准备；已拾取对象不复活，退出和新挑战不继承，服务重启不恢复未拾取地面。部分丢弃保留剩余堆UID，拾取合并保留目标UID；源整件已移除时，空槽拾取分配新UID并保留全部核心、期限和属性，不按模板重抽。普通怪物掉落、钱包、翻牌和修炼场免耗规则保持不变，修炼场丢弃仍真正扣物。

无资源检查覆盖12B解析、8B/4B回执、136B通知、数量和保护边界；`dungeon-settlement` 定向检查实际 Handler/SQLite 的末段回滚、结果丢失恢复、跨房回访拾取及重选。实机动画、客户端被动对象缓存及地面显示与这些自动检查分别验收。

## 分层与唯一状态

```text
Network/Parsers/Inventory       body → 类型化请求
Network/Handlers/Inventory      调用用例、回复、提交后刷新
Game/Session                   当前 owner、generation、Ready及实际阶段
Game/Inventory/Models          ItemCore、位置、不可变快照与变更计划
Game/Inventory/Services        发放、移动、穿脱、删除、整理、锁与期限的规则和预检
Game/Currency                  角色/账号数量、货币获得/消费、携带上限和扩容规划
GameWorld/Items                匹配 PVF 模板、类型、部位与资格
Persistence                    角色 revision、实例/位置/审计同事务提交
Network/Builders/Inventory     实体条目、装备摘要、protobuf 回复
Network/Projection/Inventory   仅发布已提交事实与同场景装备变化
```

入口为 [InventoryService](../../Server/DfoServer/Game/Inventory/Services/InventoryService.cs)；在线真源是当前 `GameSession.Selected.Inventory` 的不可变快照。规划读取该快照，提交成功后由 Session 一次替换。拒绝、预检或提交失败不修改在线状态。Repository 查询仅用于装载、事务核对和恢复，不为每个业务重新创建第二份可修改背包。

[InventoryPlan](../../Server/DfoServer/Game/Inventory/Models/InventoryPlan.cs)固定规划前后快照，按需建立操作内槽位/UID 索引，一次计算并复用不可变的槽位、货币与碎片变化集合。槽位比较使用完整实例值，输出仍按容器、槽位排序；临时 UID=0 不进入实例索引。索引不挂到可派生的快照上，后续规划重新建立自己的索引。持久化和投影复用本次计划，避免重复逐槽全表扫描。

Session 提交并安装实际角色后，在 `InventoryResult.Receipt` 返回 `InventoryCommitReceipt`：包含真实 UID、revision、generation 与选角 epoch。投影读取该回执，禁止使用规划结果代替提交状态，也不在 ACK 后重新选取另一份当前背包。发送队列出队时再次核对原 owner、选角及 revision；换角、接管或更新版本后尚未发送的旧差量丢弃。已开始的网络写入与状态切换仍可能交叠，不能据此宣称取消了所有在途帧。失败不产生成功回执，发送失败也不重做已提交业务。

Models、Services、资源 Catalog、持久化与协议分别组织；领域不引用 Network、Persistence 实现或 Development，GameWorld 的资源读取依赖 PvfLib。SQLite 实现保留在当前项目的 Persistence，不因参考目录把 SQL 移进 Game。Runtime 显式装配，Handler 无玩家状态、SQL、PVF 扫描或手写物品字节，不通过一个 Handler 调另一个 Handler 拼接业务。按实际规模拆文件，不引入空接口、DI 容器或无职责的转发层。

`ItemCore` 是完整类型化实例属性；`InventorySlot` 是容器和槽位，`InventoryItem.Uid` 是持久实例身份。移动位置不重建核心、不改变 UID。空槽为 null，只为真实物品分配核心；禁止预建全部空核心、共享可变空对象、用零物品冒充空槽或为规划建立第二套在线状态。当前记录不可变，可直接共享读取；未来可变 detail 或外部传入核心必须提供独立副本。

不得引入旧资产门面、旧 InventoryModel/InvenItem/ItemExtraView/通用资产 DTO，也不得以 `byte[]`、不透明 extra_json 或旧序列化包体承载物品业务。当前 `item_core` 保存可验证的类型化 ItemCore JSON，不是 wire blob；未知字段保留明确的 Extension 名称，查明后再命名。业务只能修改语义字段，完整 wire 排列统一交给 Writer。

## owner、生命周期与并发

1. 选角通过当前账号 lease 装载角色及背包，并由 [InventoryExpiryService](../../Server/DfoServer/Game/Inventory/Services/InventoryExpiryService.cs) 清理所有已到期实例，包括快捷栏、穿戴及带锁物品。清理与审计提交成功后才发布 Selected 和入城投影；永久与未到期物品保持原样。普通背包移动/整理/丢弃及锁操作要求选中角色且Ready，允许地下城和结算阶段；不涉及副本奖励或死亡事实。涉及个人/账号仓库及NPC服务时仍校验Town等使用场景。提交回执记录实际阶段，出队时阶段变化使旧投影失效。
2. 每次变更在原 lease 内核对 generation、角色及 expected revision。generation 表示账号在线所有权，revision 表示持久角色版本，两者不能互相替代。旧连接不能写新会话、广播结果或释放新 owner。
3. 当前使用 AccountOwners gate 内的同步 SQLite 事务。锁内不 await、不发包、不等待客户端、不获取另一个玩家的发送队列锁；不得用 Task.Run 绕过 owner。
4. 同一连接顺序执行请求。异步通知和排队消息重新核对 owner、角色及场景 epoch；后台奖励、宠物时钟、到期清理等也必须绑定原 owner/角色，切角后不能按账号名投递给新角色。
5. 当前每次物品业务立即提交，无 dirty 缓冲，位置/GM 保存必须保留已装载背包；返回选角、断线及重启重新装载已提交状态，不补发创建奖励。

## 创建、发放与空间预检

[InventoryRewardGrantService](../../Server/DfoServer/Game/Inventory/Services/InventoryRewardGrantService.cs) 是新物品发放入口。模板、类别、部位、堆叠上限、职业、等级与技能条件来自匹配 PVF；reason、初始品级、耐久、封装、期限等由明确的创建策略决定，不在各 Handler 自行拼核心。

`TryGrantCore`为已经冻结的普通装备及现有堆叠类别规划入包，显式接收匹配模板和史诗碎片目录。它不重新创建物品或计算期限，保留完整`ItemCore`及锁字段；新实例使用临时UID0，合并保持目标UID及排序锁。放置与`TryGrantBatch`共用同一操作内算法，沿用首兼容堆完整容纳、类别空槽、堆叠上限和整笔拒绝规则。已到期、模板不匹配、无效核心、虚拟钱包/史诗碎片或缺少独立detail的特殊实例均不能借此成为普通实体。

地面拾取（普通单件、集合掉落及丢弃回拾）先按快捷栏、所属分页的顺序寻找兼容堆；专用容器的可快捷栏STK也沿用此顺序。首个兼容堆必须完整容纳本条数量，满堆或容量不足仍拒绝，不能以空槽回退绕过上限或拆分本条资产。没有兼容堆时，消耗品分栏优先选择 Main 快捷栏3–8的首个空槽，全部占满才使用消耗品页；普通装备和其他允许进入快捷栏的STK先找所属分页空格，该分页满后才回退快捷栏。所有候选按槽号升序查找，所属页与合法快捷栏都满时整笔拒绝，不占其他分类空页。

快捷栏资格复用 `ItemSlotBoundService.Allows`，不能只按EQU/STK文件后缀放行。宠物、宠物装备、宠物消耗品、时装及徽章等不因满页进入快捷栏；守护珠仍先使用其专用页，满页才允许回退Main快捷槽。集合及特殊对象回执沿已有完整Core分类和实际槽号恢复目标列表，专用容器合法时优先解释，保证提交、通知和结果丢失恢复一致，不改回执结构。此策略仅由拾取入口显式启用；任务授予、翻牌、商城、邮件和拍卖返还等默认发放规则不变，成功投影使用本次实际提交的目标槽和UID。

选择顺序对照 `df_game_r9.1` 的 `CInventory::tryInsertItemIntoInventory`（08501ECA）及实际入库入口（08502D86）：消耗品分支先在08503178尝试快捷栏、再在08503224尝试所属分页；其他分类先在085032D4尝试所属分页、再在08503370尝试快捷栏。已有堆超限与没有空格是不同失败分支，不能混为满页回退。旧服普通分页基址与本版ARAD不同，槽号和类别限制仍以本版边界服务为准。

该纯规划入口不接收存量UID，不确认掉落来源、任务资格或重复拾取；完整拾取与任务业务仍须由原实例owner在同一事务提交资产及receipt，再发布实际角色。`InventoryCoreGrantTests`覆盖全部核心字段保留、零品级装备、属性不兼容、锁、首堆容量、满页、期限及匹配资源；`dungeon-pickup-slots` TCP组验证实际丢弃与回拾请求、满页拒绝后重试、快捷槽通知、完整资产落库及重连回放，不能替代客户端画面验收。

- 普通建角使用 CHR `[create equipment list]` 的五件物品，按部位穿戴；满模板耐久、品级 seed 为 999999998，其余新增属性为零，无期限。仅正常创建执行，离线准备和重开已有角色不赠送。
- 装备模板由 PvfLib 的 [EquipmentFile.ReadScript](../../Tools/PvfLib/Models/EquipmentFile.cs) 解析 `[import script]`，引用路径以 `equipment/` 为根；当前脚本的显式字段优先，未声明字段继承引用模板，物品编号仍为当前装备。匹配客户端 原生入口 `0412E010` 先载入引用、再重读当前脚本，因此覆盖与标签位置无关，`[value] 0` 和显式空字段不能当作缺省值。[PvfDocument](../../Tools/PvfLib/Scripting/PvfDocument.cs) 一次建立字段索引，ItemCatalog 再投影并缓存继承后的部位、职业、等级、耐久、价格、期限及限制，同一物品的并发首次请求共用解析，礼包发放与其他背包业务不另造简化模板；循环、缺失或畸形引用拒绝装载，不缓存残缺结果。
- 普通装备与堆叠物品创建读取 `[usable period]` 与 `[expiration date]`：正数使用天数优先按本批创建时刻计算，否则使用绝对期限；日期按 UTC+8，Unix 秒与 yyyyMMdd 也可解析。无配置才为永久。同一批次使用同一时刻，合并仍需期限等完整属性一致；已经到期的奖励整批拒绝。已有实例不重新计算期限。
- PVF绝对日期以64位Unix秒保存原值，合法的2038年以后日期不再中断模板装载；格式错误、非正日历时间、负数使用天数及超出64位的数字仍拒绝。新实例创建时，绝对日期与相对天数计算结果统一映射至匹配客户端的有符号32位上限 `2147483647`（UTC+8的2038-01-19 11:14:07），不溢出为负数或改为永久。资源原声明不被改写，已有核心/detail、存档格式及wire宽度不变；该兼容映射不表示客户端可表达2099年的真实截止，消费者依据见[期限协议](../协议/物品.md)。
- 批量发放先在不可变计划中完整预检，检查所有模板、数量、完整属性兼容、堆叠上限和可用格子，再一次提交。不能先放入第一件、后面失败却留下部分奖励。
- 新实例在 Repository 的同一事务统一分配 UID；预检和 create-only 不访问序列、不产生持久实例。已有完整物品插入必须保留 UID 转移策略、属性、期限、绑定、装备锁及 detail，不能只用 itemId 再造一件。
- 只合并同模板且全部资产属性兼容的堆叠，保留目标 UID；排序锁不影响兼容性，合并或补入奖励保留目标排序锁。拆分只为新增分堆分配一个 UID，并复制完整属性。普通装备不能堆叠；品级 seed=0 仍是有效装备，不能按空堆处理。
- 自动发放按目标容器槽号查找首个兼容堆叠，Main 包含快捷栏；该堆必须完整容纳本条奖励，否则整批拒绝，不溢出到后续堆叠或另起一格。没有兼容堆叠时才按所属页面分配空格，单条堆叠奖励本身也不能超过上限。购买、开箱、分解、兑换等统一沿用此入口，失败不扣费用或输入物品；例如 `[stack limit] 1` 的可堆叠礼盒不能通过重复发放生成第二个兼容堆叠。普通装备的上限1不表示只能持有一件。
- 堆叠上限以 PVF 的正数 `[stack limit]` 为准；未配置或非正数沿用数量类型上限 `int.MaxValue`，不自行增加1000等限制。stackable 中的 `[creature]`/`[feed]` 进入宠物消耗品页，与 equipment 的 `[creature]` 宠物实例区分；`[flag gem]` 为守护珠，进入勋章容器的守护珠页。
- 空间检查按类别、已开放槽范围和锁定位置计算，不能按物品总数或背包重量判断格子。重量与携带金币上限是各自独立约束。

批量发放在本次操作内按容器与物品编号建立有序候选，仍逐项调用完整属性堆叠规则；分配空槽使用各页面的递增游标。候选与游标不跨操作保留，不改变首个兼容堆叠、奖励行顺序及整批拒绝规则。

[InventoryMaterialConsumptionService](../../Server/DfoServer/Game/Inventory/Services/InventoryMaterialConsumptionService.cs) 先合计同编号费用，再一次扫描 Main（含快捷栏）建立所需物品的槽位候选，跳过锁定及到期实例。物理材料在操作内工作数组中按槽扣除，复用删除服务的单实例数量规则，成功后一次生成物品快照；钱包、碎片和物理材料仍组成同一计划，任一费用不足都不提交部分扣除。

## 移动、穿脱、删除与整理

移动统一由 [InventoryMoveService](../../Server/DfoServer/Game/Inventory/Services/InventoryMoveService.cs) 规划，删除由 [InventoryDeleteService](../../Server/DfoServer/Game/Inventory/Services/InventoryDeleteService.cs) 规划；调用方不能直接修改槽位集合或从数据库删物品。

- 检查源/目标容器、槽位、完整实例、请求校验字段、数量、堆叠上限、期限及锁。C2S19 的两格回显模板 itemId，空格为0；Core.Value 的装备品级 seed/堆叠数量不能代替模板编号。普通装备数量归一为1；堆叠数量为非正数或超过现有量时归一为整堆，其余按指定数量。普通丢弃也沿用此数量约定，但批量发放仍要求正数。
- 同容器的同模板拖放须完整容纳本次归一后的数量，容量不足或资产属性不兼容时整笔拒绝，不截少移动数量，也不退化为交换。同容器仍允许向空格手动拆分，包括快捷栏。不同模板的整堆交换保留两侧完整实例，交换 ACK 的 moveCount 为1；拆分不允许借交换隐式改变请求数量。
- 可堆叠物品跨容器存取时，按目标槽号优先寻找能完整容纳本次移动的兼容堆叠；前面的满堆不阻止搜索后续堆叠。没有可合并堆叠时，允许使用请求空格；请求格已占用则寻找目标容器合法空格，全部无空间才拒绝。此规则适用于个人/账号仓库存取及两仓之间移动，不把自动发放的容量拒绝扩大为所有移动都禁止另起一格。ACK 使用实际源/目标槽位，提交后差量与之保持一致。
- 穿脱请求按 Main/Equipment 顺序发来，卸装可能第一格为空。先对两格原位置校验 itemId，再解析实际移动方向；ACK保留原顺序。不能因第一格为空直接拒绝，也不能先反转再校验而将重复穿戴误解为卸装。
- 穿戴检查 PVF 部位、可用职业、等级与所需技能，交换时同时检查反向物品。女鬼剑 job11、基础转职4（忽略觉醒高位）的普通武器可进入副武器槽24，仍保留模板资格校验。匹配 PVF 没有 `[required growtype]`，不假设该字段并增加通用转职限制。
- 有效账号霸王契约22按PVF `[overequip list]` 的装备类型名单及父 `[over equipinfo]` 对应组增量放宽穿戴等级资格；不借首组或最大增量补缺失类型。其他职业、技能、部位、槽位解锁和实例期限继续校验，宠物、勋章与守护珠不扩展这项规则。移动规划冻结同一UTC秒数，实际依赖加成的穿戴及反向交换保存原契约截止，库存提交前再次核对当前时间；准确到期秒即失去越级资格。原等级已合格的穿戴、普通移格和卸装不额外依赖契约，契约到期不会自动删除已有装备或阻止卸下。
- 女法师 job3、基础转职5的小魔女实际已学非零级技能368“黑魔法扫把”时，可满足普通扫把武器的技能91要求；限定武器槽12、继承后的 `sub type` 值4及原要求91，觉醒高位不改变该资格。依据匹配 `character/mage/mage.chr` 的小魔女赠技与扫把准入声明、`skill/mage/darkmagicbroom.skl` 的装备说明，不补赠魔道技能91或推广为通用技能替换。其他部位、职业、等级、所需技能及交换双方校验继续保留；资源与自动回归不代替Windows实际穿戴验收。
- 辅助装备22、魔法石23、耳环25分别要求角色装备槽标志1、2、16；任务解锁后同事务持久化，重登回放。标志只控制对应槽位，穿戴还须符合实际物品职业、等级和技能；旧角色不自动补开，已穿戴物品仍可卸下。
- 普通装备、宠物装备与勋章穿戴仅解除模板 `[sealing]` 对应的 SealFlag，保留原 TradeRestriction；不自行追加交易限制，也不在投影时解绑。时装封装和宠物类型字段不套用普通装备的解除封装规则。
- 同栏移动、整件交换和拆分保留资产属性。装备锁禁止丢弃及受保护的消耗/改造，不禁止普通整件位置移动或整理；进入账号仓库另有跨角色准入检查。排序锁固定整理位置，不禁止手动移动或补入同类堆叠。Main页面与快捷栏之间移动、快捷格互换，以及不涉及穿戴栏的跨容器转移会清除移动实例的排序锁；同一仓库内移动、页内移动和穿脱保留排序锁。锁定实例的部分拆分不能复制安全锁 ID。
- 普通丢弃接受 Main、Avatar、Pet、GuildMedal、Equipment 和个人仓库的普通删除类型，批量逐项预检、整笔提交；重复槽、空槽或实例 value 不符不写库。时装客户端 value 是倒计时，不用它匹配服务端详情 UID，删除以当前 owner、角色及槽位的已装载实例为准。账号仓库物品先取出，再按普通规则删除。穿戴栏删除同样提交后刷新穿戴差量与公共外观。使用、技能材料、现金栏等删除类型需独立恢复业务，不借普通丢弃推进任务或成就。
- 整理先清除当前页面全部到期实例（含排序锁、安全锁），再固定未到期的排序锁位置并重排其他实例，保留 UID 和全部属性。普通页面默认排序不读取 PVF，到期排序只读实例；时装默认稀有度排序读取模板；稀有度/等级/部位/类型排序才查询模板。

Main容器内的CMD19移动（背包页内、快捷格3–8格间及两者往返）不重触发获得图标效果：整堆移动/交换由ACK19移动客户端已有对象；拆分/合并在ACK后以完整NOTI13同步绝对数量，保留全部实例字段、钱包、扩展值与锁。耗尽的物理源格先用NOTI14空条目清除，避免客户端保留快捷格。

Main与普通穿戴槽12–25之间的穿脱、替换保留图标获得effect，但不播放获得音效或显示获得装备通知。ACK19后的Main更新复用NOTI1681：凡有装备返回Main，先静默清除ACK已放入的客户端对象，再完整写回；脱到空格、快捷栏和同模板交换也采用此包序，不能只在服务端旧槽模板不同时清槽。纯穿上后的Main空槽仍只发空条目。不跳过实例属性、本人及同屏外观、锁状态或持久化，也不改用完整列表去抑制图标effect。仓库存取、时装/宠物等特殊容器移动及真实发奖仍沿用普通NOTI14，整理与丢弃不套用上述策略；不新增私有包或修改客户端。字节依据见[物品协议](../协议/物品.md#移动与穿脱-cmd19)。

## 时装与宠物容器

[SpecialItemDetails](../../Server/DfoServer/Game/Inventory/Models/SpecialItemDetails.cs) 定义不可变 `AvatarDetail` / `CreatureDetail`；它们随 `InventoryItem` 进入同一规划、所有权检查和事务，没有独立的可修改在线缓存。类别按 PVF 的 equipment/stackable type 判断：Creature=5、CreatureEquipment=6、CreatureConsumable=7、Avatar=8。普通装备、时装、宠物和宠物装备均为单件，宠物消耗品遵循完整核心堆叠规则。

- 统一发放为每件时装/宠物创建详情，预检时 UID 为0；提交分配实例 UID，并将其作为详情键及 Core.Value。宠物 wire 使用 i32 UID，超过范围时整笔回滚。详情的名称、等级、经验、饱食、模式扩展、染色和五个独立孔位完整持久化；移动、交换、整理、穿脱不重建详情。
- 时装默认技能选项为0；`[emblem socket default]` 与 `[avatar emblem socket num]` 决定默认孔位，开放空孔的徽章编号为-1。宠物默认名称为空、等级1、经验0、饱食100、模式0；后续成长系统通过完整详情快照接入，不由容器模拟成长或战斗效果。

## 宠物幻化

开通资格按角色保存在既有 `EquipmentSlotFlags` 的 bit5（32），不增加账号级开通或平行存档。资源同时声明 `[action type] [open creature skin slot]`、使用地点 `[village]` 和 `use action packet=0` 才能成为开栏券。商城购买只获得券；城镇可通过开栏确认CMD865，或券右键确认CMD515/action224使用。两入口共用Main源槽、真实资源模板、实例、锁、期限及角色资格校验，在同一库存事务内消费一张并设置开通位，保留其他装备栏标志。515成功ACK由客户端扣一张，随后发送权威Player恢复开栏位；服务端不再对同一源槽发送扣券通知。缺券引导商城不扣费；已开通、重复、非法源、禁止地点和事务失败不消耗券。

幻化栏为Equipment33，仅已开通角色可放入部位26、subtype0、完整详情的成宠；蛋与奖励胶囊不能充当外观。装卸和双向交换沿CMD19移动同一UID，保留完整Core、详情、锁和期限，不创建副本或修改Equipment26。角色职业、等级及技能不额外成为成宠外观资格；规划冻结开通位、revision及所依赖的实例期限。

真实宠物始终由Equipment26投影，幻化模板走独立Actor头字段；只有真实宠物与幻化实例都有效且角色已开通时才显示幻化，否则发送0清外观而保留33资产。匹配客户端的联机消费者为33屏蔽人物属性应用，专用外观实体与真实宠物的component分离；技能、冷却和真实宠物属性仍取真实对象。资源定义的宠物能力不能被当成幻化奖励叠加。本人及同屏沿既有Actor投影，真实26或幻化33变化时，城镇、选图、副本和结算均先同步详情及必要差量，再发布保持对应场景状态的Actor→Player。重登恢复同一开通位与资产，不依赖上次临时界面状态。

定向入口 `--selftest-tcp creature-skin,formal-dungeon` 覆盖购买、865按钮与515右键使用、回滚、重复、角色隔离、重启、真宠/幻化分别装卸及副本连续过房；515共享分派还需回归 `quest-extras`。纯规则覆盖全部基础职业。自动协议与持久化回归不代替匹配客户端的商城定位、右键确认、外观、技能及伤害验收。字段合同见[宠物幻化协议](../协议/物品.md#宠物幻化栏)。

## 光环幻化

## 时装合成

CMD99 `COMPOUND_AVATAR` 仅在已Ready城镇会话处理。服务端按`etc/compoundavatar.etc`为角色当前0-based职业选择1-based配置，严格读取普通/高级`grade`、八部位两组万分比概率、三档材料和每部位的稀有/普通目标加权候选；`neck/belt`分别对应EQU部位`breast/waist`。双源必须是Avatar容器内两个不同槽的完整独立实例，客户端回显模板须一致；两件均未到期、未安全锁、同部位且品级只能是该职业配置的普通或高级。材料按真实Main槽和模板核对并扣一份，请求末尾的客户端分类byte不授予材料资格。所选目标须位于该部位非稀有候选、职业和模板部位匹配，能力编号须存在于目标及实际抽中的稀有时装资源。

基础稀有概率为该部位`rare rate`：普通+普通不加成，混合加`upper rare rate / 2`，高级+高级加完整`upper rare rate`；三档材料再分别加0/200/400，最终限制在0–10000。每次合法规划先固定一次万分比结果，命中后再按稀有池正权重固定第二个模板；客户端所选普通目标始终作为第一件产出，稀有时装只作为第二件。冲突、换角、接管或数据库失败不重抽。源时装和材料先在同一不可变工作快照中释放，再按当前`AvatarExpansion`升序放置一至两件新实例，因此满栏仍可复用两个源槽；产出以模板创建新Core、默认孔位和空染色，不继承输入UID、期限、徽章或颜色。

材料、双源删除、全部产出详情、UID、revision及`avatar_compound`审计在一个库存事务提交；源或新产出的最早期限与原角色revision参与提交前复验。成功ACK99自身先按三条扣除记录移除输入，再创建一至两个完整时装对象，故这些变化槽全部视为已由ACK消费，不再发送普通NOTI14；重连仍由NOTI13的165B完整条目恢复。失败统一使用客户端已确认安全的错误22，细分原因及部位、材料、概率分支和已提交revision只进入有界日志。字段与消费者证据见[时装合成协议](../协议/物品.md#时装合成-cmd99)；定向入口`--selftest-tcp avatar-compound`覆盖分派、回滚、重放和重连，结果窗口、动画及提示文案仍需匹配客户端实机验收。

## 时装漂染

CMD498以两个槽位选择Main中的染色剂（含快捷栏）和Avatar背包中的时装，仅允许已Ready的城镇会话。使用`AvatarDyeCatalog`共享当前PVF的`[dye type]`、`[dye info]`、`etc/avatarcolorvariation.etc`及目标EQU继承后的`[enable dye]`；当前支持type1的单个固定颜色/权重对，不按名称或固定物品编号发色。颜色0为洗色，其余必须在颜色表中存在；未核对的类型、多行声明或附加资格保持拒绝。

## 德利拉结算窗口

普通城镇出售、金币修理及普通装备分解仍沿既有规则和统一资产事务。副本结束后的德利拉出售请求使用 `NpcContext=1000`、`WindowState=1000`；[结算准入](../../Server/DfoServer/Game/Session/GameSession.Settlement.cs)只在正式清图事实和通关结算已提交、角色Ready且没有待处理拾取、死亡、结算或任务转场时开放出售、修理和分解。加载、战斗、未提交通关及其他NPC出售窗口不能绕过城镇门禁；购买、仓库和其他城镇服务仍按各自资格处理。

修理请求没有NPC身份字段，分解的context完整语义尚未确定；这两个入口依当前正式结算资格准入，不伪造NPC字段或用context授予玩家分解机资格。单件、全部和快速修理，以及普通NPC、便携工具分解均保留各自原有容器、期限、锁、费用、随机产物及容量规则。修理和分解在原角色不可变快照上锁外规划，再在原lease内复验角色引用、选角epoch、阶段及原副本实例；冲突拒绝原计划，不自动重抽或覆盖后来的资产。

费用、输入、耐久、全部产物、revision和审计同事务提交，提交后以当前阶段回执发布ACK及库存差量。成功和失败回复核对原会话，回城、重选、接管及快照失效后的旧结果不能发布到新状态。穿戴修理在结算阶段只刷新当前Player；牌面奖励已独立冻结，出售、修理和分解不会更改或重抽本次免费牌。

[结算Session回归](../../Server/DfoServer/SelfTests/DungeonSettlementSessionTests.cs)覆盖阶段门禁、单件/全部/快速修理、零变化、完整核心及租赁期限、NPC/便携分解、SQL回滚、规划冲突和旧回执失效。[正式副本TCP](../../Server/DfoServer/SelfTests/Tcp/FormalDungeonTcpTests.Delilah.cs)复用真实通关流程，核对修理和分解ACK、已提交差量及结算后的翻牌和回城；定向入口为 `--selftest-tcp "repair,disjoint,formal-dungeon,dungeon-settlement"`。德利拉界面的实际操作、提示和动画仍需匹配客户端验收。

## 锁操作

[InventoryLockService](../../Server/DfoServer/Game/Inventory/Services/InventoryLockService.cs) 规划 Main、Avatar、Pet、GuildMedal、Equipment、个人仓库的真实实例及账号仓库排序锁，走统一 Session 提交，不另建可修改的锁缓存或位置副本。账号仓库不支持角色装备安全锁。

- 排序锁设置/解除按本版两个请求分别处理，重复设置保持原状态；锁只约束整理位置，手动移动与堆叠规则仍按上文执行。
- 装备安全锁用于普通装备、时装、宠物、宠物装备和勋章实例，角色内分配未占用的 1–255 ID；重复加锁拒绝。非零类型的宠物及交易后删除类型的称号不能加锁。锁 ID 跟随 UID 与完整核心保存，位置从当前槽位取得，避免移动后保留旧坐标。
- 解锁立即清除 ID，ACK 剩余秒数为 0，随后通知客户端解除状态。取消解锁只确认仍带锁的物品；已经解锁的物品不能通过取消请求重新锁住。当前没有延迟解锁状态或倒计时表。
- 未 Ready、未知容器、空槽、到期目标及不支持的实例拒绝。失败不写库、不发送成功；重复确认或重复排序锁不增加 revision 与审计。
- 登录在完整物品投影后恢复排序锁和装备锁；移动、整理、穿脱的差量后按新位置恢复锁状态。快捷栏转换清除排序锁时单独发解除排序锁响应，装备安全锁保留。

## 持久化、审计与提交结果

物品与账号、角色共用 `Data/game.db`，初始化和版本管理见[数据库](../开发/数据库.md)。物品存储将实例 `character_inventory_items` 与位置 `character_inventory_slots` 分开，外键与唯一约束保证一个实例只有一个合法归属。两表都保存账号；角色物品保存 character_id，账号仓库的 character_id 为 NULL。生成列 owner_character_id 将 NULL 映射为0，组合外键核对实例和位置的真实 owner，避免 NULL 外键绕过归属检查。账号仓库转移更新同一实例的 owner，不复制物品，也不另分配 UID。`inventory_avatar_details` / `inventory_creature_details` 以实例 UID 为一对一主键并级联删除，保存可校验的类型化 JSON；读取快照验证种类、UID 和详情匹配。容器位置约束与详情表不生成额外赠品；逐条 DDL 与版本号在同一事务内提交。特殊实例的审计摘要同时覆盖核心与详情。

角色 cargo_capacity、account_cargo 及仓库审计表随完整基线建立。个人仓库默认为8格，账号仓库默认未开通。普通背包默认扩展为24，领域仍可校验0/8/16/24。`inventory_audit_log` 与变更同事务保存账号、操作角色、generation、动作、位置、旧/新 UID、模板、类别、value、数量及核心摘要；装备数量为1，不能把品级 seed 当数量。

新建单库、约束、重开、错误库拒绝与增量升级失败回滚由[数据库回归](../../Server/DfoServer/SelfTests/DatabaseSchemaTests.cs)验证。定向入口 `--selftest-tcp inventory-persistence` 执行数据库及物品提交边界用例，不加载完整领域回归；各功能 TCP 验证资产业务与断线回放，公共背包 TCP 保留真实进程重启恢复。

标准提交由 [CharacterRepository.Inventory](../../Server/DfoServer/Persistence/CharacterRepository.Inventory.cs) 完成：

1. 在 owner 内确认计划 Before 等于在线快照；移动计划同时冻结角色id/revision、职业、转职、等级及独立技能数组。提交时expected必须匹配该原始前提，不能将旧计划重新绑定到刷新后的角色。拒绝或零变化不增加revision、不写审计。
2. 开启SQLite写事务，读取当前角色与完整库存，核对物品、容器和移动资格。GM进度编辑不增加revision，因此等级、职业、转职和技能变化仍会使旧移动计划失效；调用方须重新读取并重新规划。用 `id + account + expected revision` 条件更新角色，必须恰好一行。
3. 先清理变化槽绑定，再对原 UID 执行 UPDATE 或删除，只给新核心 INSERT 分配 UID，最后建立新绑定。交换不使用 REPLACE，避免删除旧实例和 detail。
4. 用实际事务前状态写审计，不用客户端参数、缓存 DTO 或发送包反推旧值。返回事务内实读角色与 UID 分配后的库存，保留未参与本操作的最新任务、剧情与学习状态。
5. 同一次提交覆盖物品归属/位置、角色及账号货币、金币上限、背包/仓库容量、仓库金币、商店额度、账号史诗碎片和相关审计；成功提交后 Session 才替换 Selected，Handler 才发送成功 ACK。

审计是诊断摘要，不是物品真源，也不保存协议 blob 或玩家凭据。删除审计保留原模板及 UID。`currency_audit_log` 保存货币类别、真实 owner 范围、变更前后数量、角色、账号、generation 和业务原因；扩容扣费与携带/拍卖上限同事务。数量资产不创建虚构实体或物品审计。

库存前提比较复用不可变快照与计划槽位索引，不为比较反复排序；数组顺序不同不表示资产不同，仍须逐项核对完整实例和全部余额、容量、限购及版本。每次提交复用实际写库的核心与详情 JSON 计算审计摘要，纯位置变更可复用同一实例的摘要；新详情实例使用分配 UID 后的最终核心。复用只在本次写事务内有效，不改变既有摘要的 JSON 属性顺序、空值及编码。

## 钱包与金币上限

[CurrencyWallet](../../Server/DfoServer/Game/Currency/CurrencyWallet.cs) 区分角色金币、复活币、胜点，以及账号共享的六色晶体、六种灵魂、点券、代币券和欢乐代币券。账号余额保存在游戏库的 `account_wallets` / `account_currency_balances`，使用账号身份和独立 revision；不写入认证表 `accounts`，也不按角色复制；这些表均属于同一 `game.db`。在线账号余额仍只存在于 Selected.Inventory 的不可变快照中，返回选角后查询和换角重新装载。

余额存储不限制合法的物品业务渠道。六色晶块支持从钱包虚拟槽寄出及从邮件领取，扣减、托管与到账仍遵循原账号事务；托管不是角色物品栏中的实体，具体合同见[邮件](邮件.md#寄送)。

- [CurrencyService](../../Server/DfoServer/Game/Currency/CurrencyService.cs) 规划获得、扣减和扩容。数量非负，零操作不改余额；扣费必须足额，不部分扣款。获得使用 long 中间计算，普通货币饱和到 int.MaxValue，金币按有效携带上限饱和；已有超上限金币保持原量；角色金币按 u32 保存、读取与投影，统一钱包运算使用 long，旧库中超过 int.MaxValue 的金币也可无损扣费。
- 统一批量奖励先分流金币、复活币奖励 ID 1/42、胜点、晶体、灵魂及两种账号券，其余才查询普通物品模板。钱和物品共用一个 InventoryPlan 和提交事务，任一物品放不下则整批不生效。钱包不占背包格，不分配 ItemCore/UID；零余额不表示丢弃实体。
- 每次资产提交在事务内核对角色 revision、完整旧背包、账号余额和账号 revision。外部数量改动即使未递增 revision 也不能被覆盖。只在账号余额真正变化时递增账号 revision；提交失败保留旧在线快照。
- 基础携带上限由匹配 PVF `etc/goldlimitbylevel.etc` 的 `[gold limit from level]` 决定；Lv1 为10万，Lv60–95为4亿。网络选角保存已达到的基础上限，降级不缩减已存上限。
- Lv60起可依次扩容至5/6/7/8亿，每级扣500万金币，携带与拍卖上限同时更新；基础拍卖上限4亿。请求必须是当前下一阶段，防止重复帧再次扣费。资格或余额不足时同步权威阶段，不伪造未核实的失败错误码。
- 新角色只初始化自己的数量资产，并装载账号已有余额。[正式副本复活](副本.md#角色死亡与复活币)使用现有角色钱包和库存事务扣币；每日免费复活币领取、商城消费及其他货币产出由对应玩法接入。

## NPC 商店买卖与限购

[InventoryShopService](../../Server/DfoServer/Game/Inventory/Services/InventoryShopService.cs) 规划普通 NPC 的购买、材料兑换和出售；[NpcShopCatalog](../../Server/DfoServer/GameWorld/Items/NpcShopCatalog.cs) 从 `itemshop/itemshop.lst` 与各 `.shp` 校验 NPC、shopId 和商品。出售页、职业分页及 `one a day item` 的物品编号均纳入目录；缺失的基础文件按资源实际的 `(r)`、`(f)` 前缀解析。分页本身不增加职业或穿戴等级购买限制。协议字节与消费者见[商店交互](../协议/物品交互参考.md#商店购买与限购查询)。

- 普通装备购买允许客户端数量字段为0，按一件计价、发放及累计限购；其他商品请求数量须为1至100万，负数及超限请求均不扣费、不发奖。正数装备请求仍固定购买一件。普通金币价格取 `[price]`，未声明才回退 `[value]`；材料兑换取 `[need material]` 并使用非负的 `[price]+[add price]`，未声明 price 时金币费用为0，不能把出售 value 当作兑换金币。乘法使用 long，溢出和余额不足整笔拒绝。
- `[need material]` 的全部物品/数量对参与扣费，与购买数量相乘后合并同编号材料。商店和图鉴制作共用 [InventoryMaterialConsumptionService](../../Server/DfoServer/Game/Inventory/Services/InventoryMaterialConsumptionService.cs)：Main（含快捷栏）跨堆扣除，跳过到期及装备安全锁；装备材料每件计1，不把品级当数量；晶体、灵魂等虚拟材料扣真实钱包，碎片扣账号图鉴，不从仓库暗扣。先规划全部扣费，再按释放后的空间完整发放，任一材料不足或数量溢出都整笔失败。奖励可补入兼容的快捷栏堆叠，保留 UID、属性和排序锁。付费获得的数量不能用钱包饱和截断充当成功。
- 出售 Main（含快捷栏）、Pet、GuildMedal、个人仓库与穿戴栏的合法物品；账号仓库物品需先取出，时装实例（含已穿戴时装）拒绝出售。材料、普通消耗品、礼包、装备与宠物等实体沿同一规则校验，不因职业或单个物品编号另设放行表；出售礼包只删除本体，不展开奖励。安全锁及到期实例拒绝，排序锁不限制出售。装备卖一件；实体堆叠非正数或超过现有量时卖整堆。普通装备按本版客户端以单精度计算 `value × equipment/pricetable.tbl [rate] 第一项 × 0.001 × min(当前耐久,最大耐久) / 最大耐久`，截断后再用整数计算 `×90/100`；无最大耐久时不做耐久折算，零售价不抬高为1金币。满耐久的初始腰带和拖鞋均为25金币。堆叠仍为 value/5，缺失 value 才取 price/5。金币超过有效携带上限时整笔拒绝。删除走统一入口，穿戴变化随后刷新本人和同场景外观。
- 实体与钱包共同遵守 `etc/chn_undeletable_item.etc` 的 `[undeletable item]` 禁售名册；正售价不能替代资格检查，零售价也不单独构成禁售。名册由 NpcShopCatalog 在装配时读取并去重；明确空块合法，缺失、未闭合、重复块或无效编号使装配失败，不静默允许全部出售。此名册只用于已确认的 NPC 售卖资格，不扩展成丢弃、邮件或拍卖规则。
- Main 虚拟槽的黑、白、红、蓝、无色、金色小晶块按真实账号钱包出售，沿用对应模板的堆叠售价，不创建库存实体。请求数量必须为正数且不超过余额；不沿用实体堆叠的整堆数量约定。扣晶块、加金币及审计在原库存事务中一起提交，金币超上限整笔拒绝；成功回执携带实际售出数量与最终金币，并同步钱包虚拟槽。灵魂、点券及其他钱包种类不通过此入口出售；场景资格仍归 Session 原有城镇与结算门禁。
- `[daily purchase limit]` 按 account 或 character/charac 区分 owner；只有同时存在 `[reset daily purchase item]` 才在 UTC+8 06:00 切换计数日，否则为不自动重置的限购。商品名或说明含“每日”不能替代标记。当前支持模板定义的限购；活动场景资格、秘商动态库存、每日轮换商品及限量商店专用 opcode 仍归各自玩法。
- `shop_purchase_counts` 按账号、角色范围（character_id=0 表示账号）、NPC、物品和重置类型保存计数与计数日。它属于 Selected.Inventory 的不可变快照；新角色保留账号已有额度，换角/重登/重启重读。所有费用、物品、钱包、限购和审计共用现有事务，提交前核对角色 revision 与完整旧限购状态。数据库失败不发布新快照或成功 ACK。
- CMD715 返回该 NPC 当前有效的购买计数，合法空结果也发送完整结构。购买和出售没有已确认的永久请求 ID；每个有效请求按当前资产处理，不能把出售 check 字段当作防重票据。发送失败不自动重跑已提交买卖。

普通 NPC 的已支持奖励为已实现容器的物品和已有 Main 虚拟钱包；兑换回执支持多条材料余量，成功后同步全部变化槽和数量资产。匹配资源中的苍穹武器按600个苍穹碎片加15个精炼的时空石兑换，镇魂钟每个消耗10个生锈的铁片及10个白色小晶块；费用只来自PVF，不额外要求职业、穿戴等级或固定数量的空格。独立点券券/图鉴碎片取得展示、秘商、租赁及活动商店的专用条件不由普通入口伪造成功。匹配普通商店目录没有图鉴碎片商品。

[多材料回归](../../Server/DfoServer/SelfTests/Inventory/MaterialExchangeTests.cs)覆盖跨堆、快捷栏、实物与钱包混合费用、重复材料合计、倍率溢出、锁/期限、装备材料、完整输出和SQL回滚；[多材料TCP](../../Server/DfoServer/SelfTests/Tcp/MaterialExchangeTcpTests.cs)检查多行回执、提交后差量、首堆锁定后的可用材料、重复请求及重连恢复。多材料兑换界面仍待匹配客户端验收。定向入口 `--selftest-tcp material-exchange`。

商城点券购买（64）使用资源商品号查出价格、数量及附赠，与账号点券和整批物品沿原库存事务提交。失败返回3字节通用失败，不细分原因；字节合同见[商城购买响应](../协议/物品.md#商城购买响应)。

`[avatar dye]`是独立的九列商城商品分类，数量取第三列、点券价取第六列，目标为普通染色剂STK，不套用六列`[avatar]`的期限/属性选择。它与时装散件可以同车购买，仍按整车总费用和完整奖励原子提交；非时装行中的属性/类型255是客户端未选择标记，不作为时装选项，也不传入染色剂实例。使用见[时装漂染](#时装漂染)。

### 锻造券与系统接入

[RefinementTicketDefinition](../../Server/DfoServer/GameWorld/Items/RefinementTicketDefinition.cs) 从 `[equipment separate reinforcement ticket]` 读取等级、百分比成功率、`fixed/additional` 和可选使用前等级上限（省略或负数表示无独立上限）。百分比乘100成为万分权重；未知模式、附加字段及无效参数保留为未支持定义，物品仍可显示、存放，不能消费。`[reinforcement usable item list]` 非空时只允许明确列出的装备；这是 PVF 限定，不按道具名称、角色职业或稀有度自行推导名单。

- 固定券成功时直接覆盖为声明等级，包括覆盖更高或相同等级；不额外套普通锻造上限。增量券成功时增加声明等级，使用前等级既不能超过券声明的非负上限，也不能使结果超过锻造表上限。超限整笔拒绝，不截断结果或偷偷换成固定券。
- 每次接受的尝试只消耗所选槽一张券，不另扣金币或普通材料；失败保留原等级。券类不要求满耐久，成功也不修复耐久；装备安全锁和双方实例期限仍检查。目标完整核心与UID沿用原对象；固定券同等级成功仍消耗一张，协议不提供永久重放幂等。
- [IRefinementEffects](../../Server/DfoServer/Network/Projection/Inventory/IRefinementEffects.cs) 是可选的提交后接口：接收本次已提交 Character、完整目标实例、来源编号、结果及刷新标记。只有已穿戴装备的锻造等级变化才标记 `NeedsAttributeRefresh`；`Announce` 在结果等级至少5时对普通尝试置位，对券类仅成功时置位。接口在ACK及库存差量之后调用，入口和后续发送遵守 generation；失败不撤销已提交资产、不重试锻造。
- 当前 Runtime 未注入该接口实现，独立攻击属性重算和全服锻造广播留待所属系统接入。接口用于可重建的派生状态及展示通知，不是持久化事件队列；额外费用、一次性奖励或资格必须纳入原事务，不能放到回调里补写。

[锻造回归](../../Server/DfoServer/SelfTests/Inventory/RefinementTests.cs)覆盖成本与概率边界、快捷栏/穿戴、拒绝不抽取、失败保级、完整核心/UID、旧revision/generation和材料耗尽后的重放；[锻造券回归](../../Server/DfoServer/SelfTests/Inventory/RefinementTicketTests.cs)覆盖固定覆盖、增量边界、PVF装备名单、损坏装备、期限及接口的提交/异常边界。[锻造TCP](../../Server/DfoServer/SelfTests/Tcp/RefinementTcpTests.cs)与[锻造券TCP](../../Server/DfoServer/SelfTests/Tcp/RefinementTicketTcpTests.cs)覆盖13B结果、提交后差量、晚期数据库异常回滚及断线重连。可定向运行 `--selftest-tcp "refinement,refinement-tickets"`，共用该轮资源；界面操作和锻造动画仍待匹配客户端验收。

## 宝珠附魔

## 强化与增幅券

## 普通装备分解

[InventoryDisjointService](../../Server/DfoServer/Game/Inventory/Services/InventoryDisjointService.cs) 规划输入删除、工具消耗和统一 grant；[DisjointCatalog](../../Server/DfoServer/GameWorld/Items/DisjointCatalog.cs) 读取匹配 `etc/disjoint.etc`，领域计算器产生一次确定的随机结果。请求与增量返回见[分解交互](../协议/物品交互参考.md#普通装备分解)。

- CMD26 接收 Main 装备，包括快捷栏；排序锁和封装本身不禁止分解。装备安全锁、到期、未净化红字、`[trade delete]` 和 PVF `disjoint` 禁止标记阻止销毁。穿戴及仓库中的装备须先取到 Main。
- 工具槽为-1使用普通 NPC 规则；其他值必须指向实际未到期的便携式分解机，每次成功消耗一张。`[portable disjoint]` 0–4 分别对应30/50/70/85/95级装备上限；此限制不应用到 NPC 分解。工具可在快捷栏，剩余数量、UID、期限和锁原样保留。
- 无色数量为 `max(1, floor(基础出售价值 × 稀有度倍率 / cubeBase))`。基础出售价值来自模板 value/price 与出售倍率，不叠加 NPC 售出时的耐久和90%折价。普通附加材料按完整候选均匀选取，GreatChance选择等级数量分母，小数部分随机进位，至少1个。
- 灵魂按七档稀有度的 `[additional result expand]` 读取概率、等级分母与追加数量；空异界行只消费一个0，不能错移后面的传说配置。`[exclude additional result expand]` 禁止对应模板产出灵魂。史诗物品10158124入账号数值14、Main365；传说物品10099775入数值13、Main364，持久余额编号与客户端槽位保持对应。
- 源装备、便携工具、全部材料、账号钱包及审计同事务。空间预检先释放本次输入，按真实堆叠容量规划；纯钱包产物不需要材料空格，不固定要求三个空格。余额溢出或任一产物放不下整笔拒绝，不能截断奖励。提交成功后 ACK 给各目标槽的本次增量，再推最终差量；失败不发布结果，发送失败不重新随机或发奖。
- 玩家分解机、时装分解、活动/独立产物及史诗碎片结算尚未接入。PVF的特殊输入、活动输入和碎片图鉴关联装备保留原物品并返回拒绝，避免销毁后漏发专属产物；普通结果不能替代这些结算。

[分解自测](../../Server/DfoServer/SelfTests/Inventory/DisjointTests.cs)覆盖PVF变长行、七档灵魂、随机边界、快捷栏、工具等级、堆叠与钱包容量、锁、重复请求、revision/generation和真实SQL回滚；[分解TCP](../../Server/DfoServer/SelfTests/Tcp/DisjointTcpTests.cs)覆盖字段宽度、ACK增量/差量顺序、工具耗尽、提交回放及失败后重连。分解界面与便携工具打开界面尚待匹配客户端验收。

## 账号史诗碎片图鉴与制作

- [EpicPieceCraftService](../../Server/DfoServer/Game/Inventory/Services/EpicPieceCraftService.cs) 按装备编号查配方，足额消耗图鉴碎片、账号晶体/灵魂或 Main 实物材料。实物可在快捷栏，跨堆消耗且跳过安全锁和到期实例；排序锁不阻止消耗。相同材料声明合计，不从个人/账号仓库暗扣。
- 先规划全部扣料，再按释放后的容量调用统一发放，创建一件完整装备核心；不增加职业、等级、排序锁或额外预留空格限制。背包放不下时保留全部材料，尚未启用[邮件](邮件.md)溢出投递。每个满足配方的请求都消耗一次配方，已耗尽后的重复请求失败；发送失败不重复发奖。

- 入城发送 mode=0 全量图鉴，包括空图鉴；成功变更发送 mode=1，条目始终是提交后的总数量，包含消耗至0的条目。制作成功先 ACK，再发送成品和材料差量、图鉴差量。合同见[史诗图鉴协议](../协议/物品.md#史诗碎片图鉴与制作)。
- 匹配配方中的耳环可制作、入包并沿用普通物品存取；其穿戴槽尚未核实，模板以0表示未映射，不占用其他装备的穿戴位。史诗碎片掉落、特殊分解产出、碎片交换/转移及邮件溢出尚未接入；图鉴能力不会自动改变这些产出规则。

## 礼包开箱

[BoosterCatalog](../../Server/DfoServer/GameWorld/Items/BoosterCatalog.cs) 按物品模板缓存 `[booster]`、`[cera booster]`、`[booster random]` 的普通 `[booster info]` 奖池、`[booster selection]` 的选择定义，以及 `[usable cera package]` 的固定 `[package data]` 清单。[InventoryBoosterService](../../Server/DfoServer/Game/Inventory/Services/InventoryBoosterService.cs) 负责只读抽取或选项校验，统一规划消耗和发奖，通过已有背包事务提交，不新增另一套发放入口。

`[upgradable legacy] 1` 袖珍罐使用独立 CMD27：模式0每次消费一只，从完整 `[int data]` 的 `物品号、权重、数量` 三列中按权重抽取一行。保留重复编号的独立资源行，拒绝空池、零总权重、负数和不完整行；CMD160不能消费此类物品。沿既有资格、期限、容量和原子事务发奖，源消耗释放格位后才规划奖励，不凭客户端显示推定额外费用。应答展示首个普通背包奖励记录，魔王双倍装备各有独立UID并由NOTI14完整同步；货币、契约及特殊容器奖励仍拒绝，不扣源或只发一部分。匹配实例490705163的六项奖励按原表总权重10000抽取，每项数量1。

袖珍罐成功ACK中的堆叠数量为本次增量，后续NOTI14携带提交后的总数；奖励槽位和核心来自实际提交回执。协议见[袖珍罐开箱](../协议/物品交互参考.md#袖珍罐开箱)。`--selftest-tcp lottery`共用资源验证六项权重区间两端、满包、释放源格、非法模式、期限、已有堆叠、耗尽重放、晚期SQL回滚及重启恢复；与共享普通开箱相关的回归组为`booster`。界面窗口和实际领取仍需匹配客户端验收。

已有开箱入口与商城共用上述期限调试开关，预检奖励和实际grant使用开箱入口冻结的状态；开启时内部道具统一2038截止，关闭恢复原绝对/相对期限。嵌套礼盒作为道具发放，同样覆盖实例期限，其后每次已支持的开箱继续按当次开关发奖。开关不放宽源物品期限、锁、选择资格、随机池或契约激活等原条件。

固定CERA礼包使用专用518，每次消费一件源并发放 `[package data]` 全部固定奖励；普通160开箱与518固定入口分别校验源定义。固定包只接受空时装选择列表；非空选择仅在源定义具有完整装扮分类时进入专属服务，未知选择不能忽略。成功518回执为 `01 + sourceSlot:u16`，匹配消费者按源槽减一或删格并关闭礼包窗口，证据见[礼包开箱](../协议/物品交互参考.md#礼包开箱)。

[装扮礼盒目录](../../Server/DfoServer/GameWorld/Items/AvatarPackageCatalog.cs)与[服务](../../Server/DfoServer/Game/Inventory/Services/InventoryAvatarPackageService.cs)接收CMD160完整分类、奖励清单及5B属性选项。数量、期限/孔位类型与合法能力来自PVF，所选能力保存在Core.Durability；不写死职业套装、期限或加成。源消费、完整时装原型及UID/detail与审计同事务，160满页拒绝，允许的518邮件溢出保留完整详情；最早期限包含源和全部奖励原型。存在装扮分类但规则未闭合的源不回落普通开箱，非法或缺项选项不消费。协议与真实91B请求边界见[时装礼包](../协议/时装礼包.md)，定向入口`--selftest-tcp avatar-package`，实际选择属性、期限、孔位与穿戴仍需客户端验收。

光环、武器装扮未声明可选能力时，CMD160可省略5B属性记录；有能力声明的部位仍须显式提交合法选择，重复、外来编号及伪造能力拒绝。零分类维度只开放坐标0。未声明`[avatar type select]`时使用奖励模板本身的期限和孔位，不虚构7天/30天类型；明确声明但为空、未闭合或越界的期限表仍拒绝。宠物自选段`[creature]`按物品/数量对读取，实际模板必须是宠物，通过统一grant创建完整详情、进入宠物容器并在提交后同步；满页拒绝且保留礼包。截图对应光环及宠物各两项选择、详情写入失败回滚、耗尽重放和重登恢复由`avatar-package`覆盖，共享普通自选由`booster-selection`覆盖；两类礼包的资源与规划边界可独立运行`gift-selection-resources`，新增网络用例可用`gift-selection-tcp`续跑而不重复既有九件装扮和邮件检查。截断源槽等可识别的畸形160请求沿既有失败ACK拒绝，资产不变且连接保持可用；日志保留源物品编号与拒绝原因。未知附加选择段继续保持未实现。这些自动检查不代替客户端显示及实际穿戴验收。

- 支持 `[etc]`、`[cera]`、`[equipment]`、`[stackable]`、`[booster]`、`[emblem]` 的“抽取次数 + 物品/权重/数量”结构，以及 `[grow type]` 的职业/转职随机奖池。`[grow type]` 行宽为职业标签、最低/最高等级、转职分支、抽数，其后同样是物品/权重/数量；开箱按 `JobTag`、`GrowType` 低 4 位和角色等级只抽匹配段，无匹配池回错误 19 并保留源，不抽其他职业或分支。同名重复块分别抽取，批量按每个源礼包执行相同抽数；小数权重按共同精度转成整数，保持原始比例。零权重不会命中，资源中的空占位池不造奖励，同模板抽取结果合计数量，溢出整批拒绝。`[hide booster info]` 只影响客户端预览。

## 个人与账号仓库

[InventoryCargoService](../../Server/DfoServer/Game/Inventory/Services/InventoryCargoService.cs) 规划仓库费用、容量和金币；物品流转继续使用同一 Move/Sort/Delete/Lock 服务。[CargoCatalog](../../Server/DfoServer/GameWorld/Items/CargoCatalog.cs) 从匹配 PVF 装载账号档位、开通等级、金币上限、材料和商城费用。仓库内实体仍保存在 Selected.Inventory.Items；AccountCargoState 只保存共享容量、金币和独立 revision，不建立第二份物品集合。

- 个人仓库列表2，槽位0起、初始8格；账号仓库列表12，未开通为0格。当前物理范围分别为0–263、0–239；只允许进入实际已开放格。两者支持装备、消耗品、材料、副职业物品，拒绝任务物品和徽章，宠物/时装使用各自容器。
- 个人仓库拒绝模板 `[trade delete]` 和 `[impossible contents]` 中的 `charac cargo`；允许锁定装备存取。账号仓库只接收 `[free]`、`[account]`、`[sealing]`，拒绝 `account cargo` 禁入标记、EquipmentLockId非0和TradeRestriction=1。解除封装本身不增加 TradeRestriction，也不额外禁止已解除封装的 `[sealing]` 装备。
- 跨仓库、Main、快捷栏和穿戴栏共用完整实例移动；交换校验两侧准入，拆分只给新分堆分配 UID，合并保留目标 UID。个人仓库整理 category=11，账号仓库整理整个已开放区；默认按类别/模板/原槽排序，不读无关PVF条件，不合并堆叠，排序锁固定位置。选角清理两个仓库的过期物品，整理清理当前仓库过期物品，锁不延长期限。
- 账号开通等级与费用来自 `etc/accountcargo.etc`：当前Lv60、10万金币开1格，再花200万升8格；以后按表推进至240格。16格及40格起的商品费用从 `etc/(r)cerashop.etc [item etc]` 的商品号解析并扣账号点券；24/32格各消耗250个虚空魔石。材料从Main包括快捷栏跨堆足额扣除，跳过到期和锁定实例。后续档位不能因为参考代码缺少费用而免费扩容。
- 账号仓库金币为独立账号余额；只接受正数存取，整笔检查来源余额、目标范围和溢出。存入遵守当前PVF档位金币上限，取出遵守角色有效携带上限；不饱和截断转移数量。存取、角色金币、账号仓库 revision 和审计同事务。
- CMD408 使用Main槽中的个人仓库升级工具；目标容量来自该模板说明的明确格数，上限264。必须高于当前容量，成功消费一件并保存容量；无工具、到期、锁定或目标不提升均不扣除。通用道具使用、增量升级券、账号工具使用和商城购买入口仍由对应后续玩法接入。
- 同账号不同角色重新装载相同账号仓库；新建角色不覆盖共享状态。每次提交检查完整旧实例、角色 revision、账号钱包和账号仓库 revision；物品/容量/金币变化时递增账号仓库版本。跨角色仓库转移与所有费用共用一个SQLite事务，失败不发布在线快照、不发成功。`cargo_audit_log` 记录操作角色、账号、generation及容量/金币前后值，物品核心和位置摘要仍归 inventory_audit_log。
- 305重复开通被拒绝；306空请求本身没有档位或唯一请求号，每个有效请求按当前下一档处理。金币存取同样不含唯一请求号，不能承诺跨连接重放幂等；提交后的发送失败不自动再执行业务。

提交异常或连接断开不能被统一解释为“未扣费”。有明确 rollback 的失败不发送成功；结果不明时重读或关闭恢复，禁止自动重跑扣费、抽奖、交易和奖励。C2S19/18 没有已证明的永久请求 ID：移动通过两格模板编号/空格回显拒绝明显过期请求，丢弃按本身的value字段校验，generation/revision约束会话与保存。同模板的已占用双槽不能仅靠itemId辨别相同请求是否重放；不能宣称所有交换/合并请求具备 exactly-once，也不能把帧未知字段或每次新生成的 ID 当作幂等票据。未来需要一次性资格的业务必须保存真实 receipt/唯一约束。

## 投影、通知与公共外观

`ItemListProtocolWriter` 是实体条目的唯一编码入口，具体读宽见[物品协议](../协议/物品.md)，不沿用其他版本的核心长度。角色货币、晶体与灵魂由 CurrencyPackets 做数量投影，不能分配 ItemCore/UID。数据库核心与网络排列分别演化。

- 移动/整理/丢弃的已提交变更先 ACK。Main内CMD19的整堆移动与交换只发ACK，拆分/合并按上文策略清空耗尽源格并完整载入；其他移动及丢弃沿用 UPDATE_ITEM_LIST 差量，整理使用下述无播报投影。CMD19 穿脱、覆盖交换的普通装备、装扮和勋章穿戴槽由 ACK 更新，不重复发送列表3的通用差量；跨容器涉及的Main及Avatar/GuildMedal实际变化仍发差量。宠物部位26与宠物装备27–29保留专属装备槽和Pet容器差量，宠物详情在差量和Player之前同步。锁恢复始终使用全部已提交槽位，Main完整载入后恢复全部Main锁，不因省略差量遗漏穿戴槽。锁操作使用自身 ACK 与锁通知，不重复发送获得提示或装备外观。拒绝、零变化不写审计。

属性块、重量、战斗装备效果和成长是独立领域；当前 CHR 初始属性不等于已完成装备属性重算。接入这些效果时使用提交后的装备重新计算，不让 Builder 直接加减角色属性。时装/宠物 core 中的 value 若表示 detail UID，wire 的有效期必须由 detail 计算并按本版合同投影，不能直接发送 UID 充当剩余时间。

### 匹配客户端验收

新角色入城、五件初始装备显示、卸下至背包及重新穿戴、装备放入快捷栏和移出已获 Windows 客户端确认；现场物品UID与完整核心保持不变。卸装与拖入快捷栏使用Main空格在前的请求，模板编号校验及原序ACK已覆盖实收包。自动化通过不代表其他交互已验收；继续检查 Main 各页面、其他类别快捷栏操作、占用格交换、整理、拆合、普通丢弃、返回选角、断线重登与服务重启。核对请求、回复与画面；由用户操作客户端。

创建奖励只在正常建角事务中发放，重开库、重登或换角不再次赠送。非零强化/附魔/增幅、时装/宠物 detail、满扩展及锁操作的界面显示、装备属性效果需分别做对应实机用例，不由初始装备显示或服务端回归推定。

钱包的数量、归属、整批回滚、上限和重启恢复由[货币回归](../../Server/DfoServer/SelfTests/Inventory/CurrencyTests.cs)覆盖；[货币 TCP](../../Server/DfoServer/SelfTests/Tcp/CurrencyTcpTests.cs)覆盖登录、选角前查询、扩容扣费、重复请求与换角共享。新增钱包界面和扩容交互尚未获客户端验收。普通背包默认满扩展，未接付费购买背包扩展。当前同步提交不使用 dirty 缓冲或后台保存。验证命令见[贡献指南](../../CONTRIBUTING.md#验证)，不在本页记录每轮测试数量或运行日志。
