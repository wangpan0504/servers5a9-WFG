# 物品扩展规范

本页保存新增资产玩法必须继承的业务约束，不是开发计划或完成清单。仅在接入对应功能时读取相应条目；背包、装备与钱包的当前实现以[背包与装备](../模块/背包与装备.md)为准。

## 跨功能资产约束

多人交易等业务扩展锁模型时，先约定固定角色 ID 锁序和取消边界，等待后再验租约。单角色实现不预建空交易框架。

后续掉落、结算、任务、活动、礼包、抽奖、GM 发物、邮件领取和商店获取都使用统一 grant 流程。批量邮件、随机结果和永久奖励 receipt 应在提交前确定，发送失败不重新随机或再次发放。

未来 Avatar/Creature detail、锁表、钱包、容器状态、称号、成就、收集箱和奖励资格必须参与所属业务的同一外层事务。`SaveDirtyInTransaction` 等底层保存入口接收现成连接/事务，不自行 Commit，不提前清 dirty，不重复保存同一变化槽。

未来引入定时脏保存时，统一生命周期服务负责注册、定时保存、主动保存、切角及离线释放；外层事务成功后只清除同一 dirty 版本。失败保持或恢复精确快照，不能提前清 dirty，也不能用全库重载覆盖其他尚未提交变化。

后续钱包券、虚拟晶体/灵魂、史诗碎片等先分流到其真实 owner 与数量模型，不伪装为普通实体。只允许明确支持且有效的物品创建，不能把未知类型默认为任意容器。

邮件溢出仅适用于业务明确允许的普通奖励。容量不足、无效模板、未知 detail、数量错误是不同失败原因，不能统一“发邮件成功”。永久邮件附件保留完整核心；资格登记、扣材料、附件及邮箱状态与奖励来源共用外层事务。

后续好友、公会和公共资料交付必须显式发布最新已提交外观，按现有可靠队列/合并策略投递，不能等待观察者网络或在发送锁内查库。查看角色资料按请求重建最新完整资料，不保存持续查看订阅；未实现的查看 subtype 不造成功包。

## 各业务的约束

| 业务 | 实现时必须遵守 |
|---|---|
| NPC 商店/秘商/租赁 | 校验真实店铺、物品索引、等级/条件、价格、货币 owner、库存与期限；扣费与完整实例、租赁 detail/数量一次提交。不能把玩家挑战 opcode10/11 当商店 |
| 商城/技能页/名称装饰 | 使用确认的商品与账号钱包；页扩展、装饰期限及实例共事务，完整保留特有堆叠规则，不借 Main 实体余额 |
| 使用消耗品/经验券/升级券 | 标准删除入口；扣数量、冷却/持续效果账本、角色进度、等级奖励资格及任务标记同事务。计入会话尚未保存的经验；成功后回填当前角色，再按本版包序投影 |
| 礼包/抽奖/随机盒 | 完整解析匹配奖励池，先计划全部产出、容量、永久邮件及资格，再提交。不得在 ACK 后补资格或重新随机 |
| 掉落/任务/活动奖励 | 掉落归属、任务完成、数量扣减、奖励和永久 receipt 原子提交；重复结算不重复赠送 |
| 强化/增幅/锻造/附魔/镶嵌/修理 | 检查装备锁、期限、材料/金币、模板资格和目标完整快照；结果、扣费、耐久、绑定和 detail 同事务，失败规则由明确业务政策及本版 PVF 决定 |
| 分解/合成/赛丽亚合成 | 输入扣除与完整产物同事务，容量预检考虑将释放的格子；保留原始奖池与过滤规则，替换模板使用提交后清空再更新 |
| 时装/宠物获取 | grant/create 创建独立 detail UID 和核心；染色、孔位、透明时装、名字、等级、饱食度、经验及期限完整保存。不能只有 core 或重复创建 detail |
| 时装/宠物到期与存取 | 核心、detail、容器和锁同事务；解引用、取消时钟、切角与 owner 释放有明确边界 |
| 个人/账号仓库 | owner 按角色/账号区分，完整核心独立插入或转移；实例与槽位同事务，仓库初始化与实际存取协议分开 |
| 虚拟钱包/晶体/灵魂/复活币 | 数量模型与真实 owner，溢出和携带上限检查；零数量合法，不创建实体。账号券先分流钱包，不能变成邮件附件 |
| 史诗碎片图鉴 | 按匹配 `etc/epicpieceinfo.etc [piece list]` 的顺序保存账号 count[]；不用 ItemCore，不凭 itemId 推定位置 |
| 称号簿 | 完整核心独立副本，取放与实体容器共事务；不共享可变对象，不恢复旧资产 DTO |
| 成就/称号奖励 | 材料扣除、进度与完成称号同事务；普通丢弃不能推进材料事件，已完成事件保持幂等 |
| 收集箱 | 装载时冻结角色/账号共享范围，选用索引按角色持久化；保存模板槽，不重复拥有完整物品。放入/取出与背包同事务 |
| 收集箱范围切换 | 开放连接前按已提交开关状态一次迁移；返还原角色/账号接收角色、邮件拆分、源表清空和生效状态同事务，失败阻止启动，重启不重发 |
| 装备锁/排序锁 | 锁模型、锁列表和实例 ID 统一；操作逐项检查，不在投影或迁移中自动解锁 |
| 守护者盾牌窗口 | 虚拟 deck/图鉴与真实穿戴分开；任务盾与等级盾从匹配资源和已提交进度判断，5个deck位置只保存itemId，真实主盾核心仍在支持装备栏。不得把虚拟窗口写进普通物品表；本版wire空间另行确认 |
| 公会勋章/守护珠 | 恢复本版类型和栏位后统一完整核心、槽位预检及提交；读取完整PVF奖池和品质，启动预热检查失效LST与候选，失败恢复本次精确变化，不重发已入库产物，模板替换按清槽规则 |
| 玩家直接交易 | 当前租约、不同账号、可交易状态、完整报价快照及数量/余额；固定锁序下最终重验，双方实例、钱包、次数与 receipt 同一事务，不能逐角色分别 Commit |

交易邀请先交付双方必要角色资料再邀请，发送和协商失败取消原绑定；取消不能覆盖新交易或已提交资产。一方收包慢不得阻塞另一方收尾或无关玩家。最终只投递一次已提交差量；失败、取消不发送获得提示。现有单角色主路径不预设交易栏、晶体别名或跨区域资格，这些均须按 匹配客户端 恢复后落地。

改造玩法接入时同时核对下列既定业务政策与匹配 PVF，禁止因为移植遗漏而恢复旧错误：

- NPC购买 ACK 的购入数量是本次增量，材料附加段是扣除后绝对剩余量，不能写成奖励累计量、限购次数或将增量清零来制造提示。获得提示由本版原生消费者决定，不能改成服务器广播、先刷库存再ACK或写临时库存掩盖数量错误；材料与奖励同ID、耗尽槽复用、首次/连续/批量购买分别验证。

- 幸运强化/增幅券按 `[lucky enchant deed]` 首参数 0/1 分流强化/增幅，每次一张、无金币；目标 +0 至 +14，保留部位、封装、稀有度资格，失败规则不误用普通破坏/保护券，ACK 使用实际结果模式。
- 增幅低等级保护：从当前 +1 至 +9 尝试失败保持等级；从当前 +10 尝试 +11 起使用正常高等级失败规则。该政策只适用于增幅，不能影响强化。
- 徽章合成先按完整原始 booster 权重抽取，普通结果不职业过滤；只有首次为 rarity6 白金结果时，在同一池按权重重抽基础职业白金。职业来自 `[enchant] [skill levelup]`；swordman/demonic swordman、mage/at mage 分别同基础职业，不按名称猜职业。
- 赛丽亚装备合成使用部位、材料及排除表；传说装备的 creation rate=0 低等级候选按明确政策处理，不能把这个例外应用到所有稀有度。

这些规则尚未接入本版相关玩法；开发时将确定的政策、字段依据、效果与失败测试一起交付，不能靠文档表格宣称完成。

持久化优化也不能改变业务提交语义。引入延迟保存前必须证明独立修改版本、不可变源/目标/detail快照、同步事务与后台批次顺序、失败不重跑业务、确定已提交批次不重复审计、账号换角与跨角色锁序。背压在确认新操作前生效；正常切角/退出/重连/停服先排空已接收版本再释放owner。旧批次不能覆盖新值，不能一边持角色锁等待批次、一边让完成路径等待同一把锁。必须同时检查在线状态、独立数据库与重启恢复，不能只测dirty或ACK；仓库试点不代表交易/邮件/奖励也可延迟。当前同步提交不启用这些优化。

## 接入检查与验证

新增业务依次确认本版 Parser、模板/实例与 owner，做只读规划、原子提交、成功/失败 ACK、差量及外观，再接 Runtime 注册。迁移保持已有角色、任务、技能和位置，不删库、不重排已发布迁移、不在登录恢复中赠送。

禁止以下模式：Handler SQL/拼核心字节；grant 后另写任务或扣费；先发成功再保存；REPLACE 破坏 UID/detail；部分批量成功；外层事务被底层 Commit；锁内网络等待；异常自动重试奖励；预检分配 UID；全背包重载丢失未提交状态；把客户端 pending 当幂等；把测试通过当实机通过。

必须覆盖成功、拒绝、零变化、重复/过期请求、旧 generation、revision 冲突、真实数据库回滚、完整属性/UID 保留、重登/重启与存量迁移。真实 TCP 检查帧、CRC、sequence、ACK 后差量、清空后替换、失败后继续操作及同屏刷新。[物品自测](../../Server/DfoServer/SelfTests/Inventory/InventorySelfTests.cs)和[TCP 物品用例](../../Server/DfoServer/SelfTests/Tcp/InventoryTcpTests.cs)使用 C#，独立库/进程/端口。

自动化验证按[贡献指南](../../CONTRIBUTING.md#验证)执行，客户端另验收实际交互。强化、随机属性、装备属性效果及特殊容器需要对应玩法与本版消费者证据，不能由初始五件零扩展装备推定。
