# 并发、事务与响应延迟

本页约束所有模块的请求处理、占用锁、持久化、批量计算、定时任务与消息交付。按本次修改选择对应场景；分层、现有锁和生命周期见[服务端架构](服务端架构.md)，资产业务见[物品扩展](物品扩展.md)，当前功能与wire以[模块索引](../README.md)为准。正文描述应遵守的行为及原因，不是开发记录；尚未接入的商城、战斗、组队等场景在接入时执行这些要求，不能据此宣称功能或优化已完成。

## 锁与道具占用

- 明确每把锁保护的状态、粒度、顺序和释放者。`AccountOwners` 使用短注册表锁与每账号锁；`Lease.Execute` 会阻塞本账号后续工作和接管。普通跨账号嵌套锁以及在 Execute 中获取新 owner 被拒绝；副职业双在线结算只经 `Lease.ExecuteTogether` 按账号名 Ordinal 升序锁定预定双方，禁止单锁升级、引入第三方或不同目录混用；成员锁/发送锁不得反向取得账号锁。不同账号仍竞争 SQLite writer、成员索引和共享资源，不能把账号锁独立等同于无等待。新增锁或改变顺序须连同接管、存储、发送和清理证明一致性。
- 临时道具占用属于特定会话generation、角色/选角epoch及实例UID；需要数量或报价时同时冻结其版本与完整快照。槽号可复用，不能单靠槽号判定仍是原道具。最终提交前重验所有权、数量、完整属性和持久化revision，任何等待结束后再次核对。
- 临时占用在成功、拒绝、取消、异常、换角、断线及接管时由原owner释放，使用 `finally` 或同等明确的生命周期收尾。旧回调只释放自己的占用，不能按账号名找到新会话并清掉新占用。临时占用与持久安全锁/排序锁是不同状态，清理临时操作不得解除玩家设置的锁；单角色业务没有需求时不预建占用框架。
- 多角色业务预先确定唯一参与者、固定锁序及取消边界，不在持锁后动态扩充参与者或乱序获取另一角色锁。费用、资产和资格需原子变化时使用同一外层事务，逐角色提交不等于原子提交。
- 组队副本使用`Lease.ExecuteGroup`预定1–4个不同账号及角色，按账号名Ordinal升序获取同一注册表的owner，获取后全员复验generation。只允许同一固定组及其成员的单账号操作重入，禁止从单锁/双锁升级、换组或引入组外owner。统一顺序为队伍命令门禁→参与连接命令门禁→固定组账号锁→副本实例gate；释放逆序，清理和接管不能持实例锁反向等待账号锁。
- 锁内仅保留必要校验、状态变更及当前同步提交。PVF解析、目录扫描、批量随机规划和大集合构造放在启动阶段或锁外；不在锁内等待网络、外部脚本、另一后台任务或可反向等待本锁的队列。不能用 `Task.Run` 包住整个持锁回调来声称消除阻塞。
- 锁外规划使用不可变输入，不修改在线对象或发放资产；重新进入原lease后验证原角色、epoch、资产及业务资格。GM修改、换角和接管可能发生在规划期间。冲突时拒绝或按明确业务合同恢复，不自动重抽、再次扣费或让旧计划覆盖新状态。

## 事务与数据库等待

一次业务只有一个事务owner。扣款、实例/detail、钱包、任务/成长进度、限购、奖励资格和receipt属于该业务时共同提交，提交成功后才更新在线快照并回复成功。失败恢复本次精确变更；不以全背包重载覆盖其他未提交状态，不提前清dirty，不以“稍后保存”兑现成功。

已有连接/事务必须沿调用链传递；内层保存或资源解释只能参与原事务，不另开连接写入、不再次申请写入准入、不内部Commit或Rollback。SQLite允许同一文件一个writer：外层已持有writer时，内层独立事务会等待自身直到超时，还会堵住其他账号。仅仅读取职业、携带上限或钱包时也需审计默认 `BeginTransaction` 是否申请写锁；使用纯SELECT或明确的只读快照，不能在读取里隐式建行、补默认值或保存。

引入写入准入前检查完整调用链中的连接、事务、独立保存、任务参与者和角色锁，定义统一锁序、容量、等待截止时间、取消及失败反馈。已有外层事务不得二次准入。准入超时只约束该段等待，SQLite外部writer、业务计算、发送仍需单独度量，不能当作请求总超时。禁止靠加大busy timeout掩盖自锁，或重跑整个随机/扣费回调处理竞争。

零变化与只读操作仍检查租约及业务资格，但不申请无用writer、不复制整个背包、不标dirty、不重写相同耐久或保存别人的dirty。业务“接受”与“实际变化”分开，合法零变化按协议响应，不能为了省事务改变成功语义。已有独立保存入口也纳入竞争审计；只优化某个公共提交器不能证明其他路径互不阻塞。

通用后台落库不是默认优化方向。确需引入时先定义不可变版本、合并规则、队列字节/数量上限、背压、故障恢复、提交结果不明的处理及停服排空；旧批次不得覆盖新值，不重试已提交奖励。换角/接管交接先完成被确认的修改再释放owner；禁止持角色锁等待完成路径也需要同一把锁的批次。不能借后台队列提前确认原本要求同步持久化的业务。

**瞬时忙锁的重试与丢弃边界。** `SQLITE_BUSY`(5) 与 `SQLITE_LOCKED`(6) 表示写锁正被其他连接占用，既不是连接故障，也不是业务拒绝。分发层对这两类错误最多重试 4 次（25/50/100/200ms，带抖动），重试单位是**当前包的命令分派**，提交后的自动刷新另起一段重试，不重放已完成的命令：忙锁表示本次写事务尚未提交，成功应答在提交之后才发送，因此重试期间客户端不会先收到成功。重试耗尽后只写一条 `db_busy`（连接、阶段、opcode、尝试次数、原始消息）并**丢弃这一包**，会话继续读下一帧；其它 `SqliteException`（约束、损坏、语法）不重试、不吞掉，仍按原语义结束连接。连接级忙等与命令超时都是 30 秒，只用于等待写锁，不能用来掩盖自锁，也不能代替上面“一个业务一个事务”的提交边界；重试只作长忙等之后的有界兜底，不放宽幂等、revision 或资产原子性要求。

**写入准入（进程内单写者闸门）。** 上面的重试只处理"已经撞上写锁"之后的事；撞锁本身要消掉。进程把写竞争前移到一处闸门：所有写事务在 BEGIN 前获取一个 `SemaphoreSlim(1,1)`，提交或回滚后释放，因此同一进程内不再有第二个连接去抢写锁。实现与字段见[数据库](../开发/数据库.md#写入串行化与慢-sql-诊断)。

- **只串行化写。** 只读事务走 `BeginRead`（deferred、不取闸门），WAL 下读者之间与读写之间都不互相阻塞；把只读事务也纳入闸门会连带拖慢名册、背包等纯查询路径。
- **闸门不改变提交边界。** 事务owner、revision复核、回滚与应答时机与闸门无关；已有外层事务必须沿调用链传递，闸门内不得再开第二个写事务（同线程重入按深度放行，内层真写仍会由 SQLite 报忙锁）。单语句自动提交的写同样取闸门。
- **等待不设上限，但必须可归因。** 排队时长不受 `busy_timeout` 约束，因此长持有必须能从日志看出来：任何一次 `gate_wait`、`write_transaction` 或 `begin_transaction` 超过 **1000ms** 就产生一条 `db_slow`（Stage/Action/ElapsedMs/SqlHead/Connection），控制台按 WARN 输出。阈值与[延迟目标](#延迟目标和测量)中的"单次 ≥1s 停顿必须定位"一致，不能靠提高阈值掩盖。
- **外部 writer 仍是另一类来源。** GM 工具、另一个服务实例占库时，进程内闸门无效，仍由忙等与 `db_busy` 重试处理；这类停顿在 `db_slow` 的 `begin_transaction` 阶段（以及 `db_busy`）里可见，不能据此推断成本进程内的竞争。

## 跨账号转移：拍卖行一口价购买

拍卖行**一口价购买**是通过托管邮件同时影响两个账号资产的玩法（买方金币出、卖方金币入、挂牌道具易主），
而本仓库的租约模型一次只允许一个账号：`AccountOwners.Lease.Execute` 内不允许再取新 owner，
跨账号嵌套锁被直接拒绝。因此这里固定三件事 —— **只取买方一把租约、卖方交付走托管邮件、
金钱与状态的移动在同一个事务** —— 再给出锁序、失败恢复与幂等口径。
功能与字节合同以[拍卖行模块](../模块/拍卖行.md)与[拍卖行协议](../协议/拍卖行.md)为准；本节写规则与边界。

### 参与方与租约

| 参与方 | 是谁 | 在本事务里怎么处理 |
|---|---|---|
| 买方 | 发起请求的连接角色（连接已持有其账号租约） | **唯一取锁的角色**：扣款、写审计、提交后安装在线快照都由它自己的 lease 完成 |
| 卖方 | 挂牌的 `seller_character_id`（可能不在线、甚至没有角色行） | **不取租约**：只能由本事务写入**托管邮件行**（跨账号收件行，与邮件寄送/系统邮件同一形态），**不直接改卖方角色行** |
| 挂牌行 | `auction_listings` 的公共行（不归属任何账号） | 由事务内的条件 UPDATE 保护，不参与锁序 |

- **为什么不能直接给卖方角色行加钱**：卖方会话可能在线并持有旧快照，改它的行会让对方下一笔写入在 revision 复核处被拒；
  而购买事务里拿不到（也不允许拿）卖方租约去安装新快照。卖方所得因此**先托管**，卖方在自己的会话里领取时才落进钱包。
  这条对**同账号的另一个角色**同样成立：当前选中的角色只有一个，另一个角色行不能绕过它被直接改写。
- **挂牌行没有指向 `characters` 的外键**（机器人卖家的 `seller_character_id` 为 NULL）：事务内找不到卖方角色行是**合法数据**，不是错误。

### 锁序

一次购买**只按下列顺序取用资源**，全程只持有买方一把账号租约：

```text
挂牌行（事务内条件更新） → 买方角色（同一事务：写金币、背包与审计） → 托管邮件行（同一事务，无租约）
```

- 需要多把角色锁时**一律按账号名 Ordinal 升序**；本业务当前不需要（卖方不取锁）。将来若改成「在线卖方直接入账」，
  必须按此序与买方锁**同时申请**，不能先取买方再取卖方，也不能在持锁期间等待卖方会话。
- **既有路径核对**（所有会同时涉及两个角色的路径）：

| 路径 | 取的租约 | 与购买的关系 |
|---|---|---|
| 登录会话（`LoginHandler`） | 本账号一把；`TryAcquire` 在 `Execute` 内直接抛错 ⇒ 跨账号嵌套结构上不可能 | 购买复用同一把，不新增锁 |
| 邮件寄送（`SendMail`） | 发件人一把；收件人的邮件行与托管实例行在同一事务内写入，**不取收件人租约** | 与卖方托管同形，购买沿用这一形态 |
| 系统邮件投递（`DeliverMail`） | 不取任何租约（自己拥有事务），按幂等键投递 | 托管行沿用同一行形状与幂等键语义 |
| 拍卖上架 / 取消（183 / 184） | 单角色一把（背包与挂牌行同一事务） | 单账号、单向，与购买不构成环 |
| 开发 GM、离线准备、启动工具 | 单账号一把，且拒绝接管在线账号 | 与游戏内路径互斥，不参与业务锁序 |
| 城镇同屏 / 广播 | 只读投影 + 每连接发送队列，**不取对方账号锁** | 不进入写入锁序 |

⇒ 现有生产路径里**没有任何一处同时持有两个账号租约**，因此「买方（唯一新锁）+ 无锁的托管行」不会与既有路径形成环。
若将来出现第二条跨账号写入路径，必须先与本节对齐顺序，不能各自定义。
- 规划（模板解析、道具条目快照解码为物品核心、卖方收件人查询）全部在**锁外**完成；持锁期间只做状态复核与原子提交，
  不等待卖方会话、不等待网络、不在发送锁内查库。

### 事务边界

```text
同一个外层事务（由买方租约下的用例拥有，已有连接/事务沿调用链传递、只参与不提交）：
  ① 事务内重读挂牌行：**内容**（一口价、数量、物品模板、卖家）与未过期复核，条目快照可解码；
  ② 挂牌行置为已成交：UPDATE … SET state=1, settled_at_unix=<now> WHERE listing_id=? AND state=0，影响行数必须为 1；
  ③ 买方扣款：成交价从买方钱包扣除，复用背包提交器（revision 复核与审计同一路径，不写裸 SQL 改金币列）；
  ④ 托管行：买方道具邮件（item）与卖方所得邮件（gold）各自的幂等键唯一；机器人卖家或卖方角色行已不存在时跳过金币托管；
  ⑤ 审计：买方扣款进 currency_audit_log（金币是 characters.gold 这一列；背包槽没有变化，inventory_audit_log
     因此不产生新行）；托管邮件自带 mailbox_audit_log。
提交成功后才：安装买方快照 → 回复成功 → 买方邮件到达提醒（走邮件模块既有入口）。**不发任何背包/金币刷新**（见下）。
```

- ② 在 ③ 之前不是随意的：挂牌行是**先于买方角色**取的资源（见上节锁序「挂牌行 → 买方角色 → 托管邮件行」），
  而且「这一行已经被买走」能在**任何一笔写之前**判出来 —— 重复点击与并发第二笔直接整体拒绝，不会先扣一次钱再回滚。
- 扣款与挂牌状态**必须同一个事务**：分两次提交会出现「钱扣了、挂牌还是别人的」或「挂牌成交了、钱没扣」，
  而这是跨账号资产，任何半成品都只能人工补偿。
- ★ 道具**不在购买事务里进买方背包**，而是进托管邮件（买方领取时才入包），两个原因缺一不可：
  ① 参考实现（另一客户端版本）的交付方式就是「成交后由系统邮件投递」，邮件模块已有成熟的领取路径与提交回执，
     购买阶段因此不会因背包满失败；
  ② 若购买时直接入包，就必须补发背包差量，而客户端 185 回调会**本地乐观扣一次金币**，
     再补发 `0x000D`/`0x000E` 会被叠加成「再扣一次」（参考实现实测：余额不足时界面显示「余额清空」）。
  容量判定落在**领取邮件**时（邮件模块既有规则：背包满则拒绝领取、邮件保留）。
- 锁外：模板/道具资源解析、条目快照解码、托管收件人查询、构帧与全部网络发送、邮件到达提醒。
- 托管邮件**不受邮箱容量限制**：邮箱的 `StorageLimit` 只约束「永久保存」的数量，投递与领取都不看它，
  因此买方或卖方邮箱再满也不会让成交失败、也不会让托管丢失（投递失败只剩「收件人角色行已被删除」一种，见失败矩阵）。

### 失败与恢复矩阵

失败码**只能取 183 那张白名单**（客户端把未知码 fall-through 成成功）。

| 情形 | 持久结果 | 应答 |
|---|---|---|
| 写库失败（任一 SQL 或提交失败） | 整体回滚：双方资产、挂牌状态、审计、托管行全部回到请求前 | **不发成功**；按既有约定由协议层处理异常，不编一个可能被当成成功的码 |
| 提交成功、成功应答发送失败 | 已成交（以提交为准），资产不会重复转移 | 不重跑业务；客户端重试同一挂牌会命中「已不在售」 |
| 连接中断 / 请求未提交 | 未成交，零变化 | 无应答（连接已断） |
| 重复点击 / 重放同一挂牌 | 条件更新影响 0 行 ⇒ 整体拒绝 | 静默码 `0x7e`（只刷新窗口、不弹框） |
| 挂牌在读取后被他人买走 | 同上（条件更新 0 行 ⇒ 回滚，不产生「钱扣了没货」） | `0x7e` |
| 挂牌不存在 / 非在售 / 已过期 | 零变化 | `0x7e` |
| 请求金额与库里的单价、总额都不符 | 零变化：成交价一律取库里的 `buyout_price × item_count`，不采信请求里的数字 | `0x7e`，并记下请求金额、库里单价与总额供离线核对 |
| `[26..29]` 的物品模板 id 与库内挂牌不符 / 请求体不足 30 字节 | 零变化（拿不到模板 id 就无法交叉校验） | `0xd2` |
| 一口价为 `-1`（纯竞拍）或请求走到竞价分支 | 零变化：**竞价不实现**，不得按一口价成交 | `0x7e` |
| 买自己的挂牌 | 零变化 | `0x69`（参考实现里该码就是「不能买自己的挂牌」；**D95 未实测**，接入时按此发并看界面） |
| 买方金币不足 | 零变化 | `0xd2`（余额不足必须让玩家看到） |
| 买方背包满 | **不是购买失败**：购买阶段不检查买方背包容量（道具进托管邮件），容量判定发生在**领取**时 | 成交照常；领取时按邮件模块既有规则拒绝（背包满则拒绝领取、邮件保留） |
| 挂牌数据不可用（模板解析失败 / 条目快照读不回 / 金额溢出） | 零变化，挂牌保持 `state=0` | `0xd2` |
| 提交时买方 revision / 背包快照已变化（换角、接管、GM 修改） | 零变化 | `0xd2`（陈旧计划不自动重试、不重新扣费） |
| 卖方是机器人（`seller_character_id IS NULL`）或卖方角色行已不存在 | **成交照常**：道具与买方扣款按正常路径完成，卖方所得不入账（无收件人） | 成功（不是失败） |
| 提交后买方邮件到达提醒发送失败 | 已成交，托管行已在库里 | 不影响成功语义，不重跑业务 |
| 卖方领取托管邮件时背包满 / 金币达携带上限 | 邮件保留（**托管 ≠ 入账**），卖方清出空间后再领 | 走邮件模块既有码，与购买应答无关 |

- **码的分档口径**（三档，不允许出现第四档）：**操作前提已经没了**（已不在售、被别人买走、请求金额不符、不是你的可买对象、走到竞价分支）
  用静默 `0x7e`（只刷新窗口、不弹框，与 184 的「已不在」同款）；**必须让玩家处理或知情**的失败（金币不足、数据不可用、陈旧计划、请求不完整）用 `0xd2`；
  `0x69` **只用于「买自己的挂牌」**（参考实现里该码就是这条语义，D95 未实测其文本）。
  绝不使用白名单以外的码 —— 那会被客户端当成成交。
- ★ **金额校验是保守口径，不是猜**：`[1..4]` 只要等于库里的**单价**或**总额**之一就接受（命中哪一个写进
  `auction_buy` 日志的 `AmountBasis`），成交**一律按库里的总额结算**；两个都不等才拒绝。
  两个实机样本的数量都是 1（单价 = 总额），因此**必须再点一件数量 &gt; 1 的挂牌**才能判定客户端发的是哪一个口径；
  第三个样本到达后，`UnitPriceOnly` / `TotalPriceOnly` 会直接出现在日志里，此时才考虑收紧成单一口径。
- 「卖方角色行不存在」**不能**当成失败：挂牌行没有外键，机器人挂牌是常规数据（开发种子即机器人卖家），
  判成失败会让一整批挂牌根本买不了。金币也不会落到别的角色身上：不入账即**系统回收**，
  由日志（卖方 id 为 NULL / 收件人缺失）与「是否生成托管行」本身作为可核对证据。
  ⚠ 托管行所在的邮件表**有指向 `characters(id,account)` 的外键**，所以「卖方角色行是否仍存在」必须在**事务内**按
  `seller_character_id` 重查一遍：查不到就**不插**托管行（否则外键会让整笔成交回滚），而不是先插再等约束报错。
- **不给机器人建角色行**：那会侵入角色系统（占用角色槽位、出现在选角名册、被其它模块当成真实角色），
  而挂牌表本来就不要求角色存在；参考实现同样只为「插入机器人挂牌」这一条路径关闭外键检查。

### 幂等性

- 唯一幂等判据是**挂牌行状态**：`UPDATE … WHERE listing_id=? AND state=0` 的**影响行数必须为 1**；为 0 就抛异常让整个事务回滚。
  这样重复点击、重放、以及「提交成功但应答丢失后的重试」都不会第二次扣款或第二次发货。
- 不引入客户端请求 id 或去重表：客户端没有可用的幂等键，而「同一挂牌只能成交一次」本身就是业务不变量；
  也不能把客户端 pending 状态当作幂等判据。
- 托管邮件行另有唯一幂等键（按挂牌 id 命名）作为第二道防线：它与挂牌状态在同一事务提交，正常路径不可能重复；
  真出现重复投递时由唯一约束直接拒绝，而不是投两份。
- 判据必须在**写事务内**用条件更新表达，不做「先查后改」：查与改之间的窗口正是并发购买出问题的地方。

### 费用与上限（**逐项标注证据等级**）

| 项 | 实机界面显示 | 参考实现（另一客户端版本） | 本方案取值 |
|---|---|---|---|
| 保证金 10,000 金币 | **是**（用户实机截图） | 金币寄售上架基础手续费 `GoldListingFlatFee = 10_000`（每笔固定） | **购买时不收**（用户口径确认）；保证金在**挂牌阶段**从卖方扣 —— 本仓库 183 目前不收费，接入时按上架前后余额差额定案扣点与退还口径 |
| 手续费 5% | **是**（用户实机截图） | 成交税 `SaleTaxRate = 0.05`，从卖家所得中抽 | **卖方侧**成交税：卖方实收 = `floor(成交价 × 0.95)`；买方只付成交价 —— **已确认（用户口径）**。持「拍卖行优惠券」时 5% → **3%**（金币寄售 5% → **1%**）；本实现**未实现优惠券**，仍按无券 5% 结算 |
| 拍卖额上限 400,000,000 | **是**（用户实机截图） | `MaxPrice = 400_000_000`（与金币额度上限对齐） | 取 `characters.auction_gold_limit`（默认 4 亿），**挂牌时**校验；购买时不再按买方的上限拒绝（否则会用买方配置拒绝别人的合法挂牌） |

- 成交价 = 库里的 `buyout_price × item_count`（服务端权威，用 `long` 计算）；结果 `> int.MaxValue` 视为数据异常拒绝 ——
  客户端搜索记录里该字段已被夹到 `int.MaxValue`，不能拿一个客户端根本显示不出的数成交。
- **不写死常数、不加列、不加迁移**：费率与上限都从既有政策/既有列取；确需新列时先评审。
- **仍待确认项的确认方法**：
  ① 保证金归属：实机点一次上架并比对 `characters.gold`（183 已接入但今天不收费）——上架前后余额不变即说明那 10,000 不是上架时从该角色扣的；
     再对一笔成交比对买卖双方余额，可分辨它是「成交时从卖方所得扣」还是「仅界面展示」。
  ② 手续费归属已按用户口径定为**卖方侧 5%**（购买时不收保证金）。如需实机复核：让另一个账号买走自己小号的一件挂牌，
     比对买方扣款（应恰等于成交价）与卖方到账（= 成交价 × 95%）。
     优惠券（拍卖行 5% → 3%、金币寄售 5% → 1%）尚未实现，接入时只改 `SaleTaxPercent` 一处并补券的持有判定。
  ③ 上限：`characters.auction_gold_limit` 是现成列，界面 4 亿与其默认值一致，数值本身无需再确认。
- 结算**没有独立的定时任务**：托管邮件与挂牌状态在同一事务提交，因此不需要「先提交、后补发邮件」的两阶段补偿，
  也不会出现「挂牌成交了但邮件没发」的半完成态。

### 客户端契约

请求体布局的置信度分两档，**只有 185 有本客户端证据**：

- ★ **CMD 185 的请求体已由两个实机样本差分定案**（30 字节：前导 0 + 一口价 i32 + 挂牌 id i32 + 到期回传 i32 +
  13 字节保留 0 + 物品模板 id i32），偏移表与样本见[拍卖行协议](../协议/拍卖行.md#c2s-185-auction_bidding一口价购买)。
  服务端按此**严格解析**（不足 30 字节即拒绝），不再使用参考实现那套 26 字节读数。
  ⚠ 仍未定的只有两点：`[1..4]` 是单价还是总额（两个样本数量都是 1 ⇒ 需要数量 &gt; 1 的挂牌）、
  以及 `[9..12]` 是否该从「只记日志」升级成硬门闸（先不发明会误拒的规则）。
- **CMD 334 的请求体仍只有参考实现**（前导字节与挂牌 id 偏移自标未定），因此它保持「只抓请求体」的桩：
  不回任何应答、不改任何状态。实机点出它的请求体后再按同一套流程接入。

应答契约：

- 应答一律走 **CMD 路径**，且**体首字节必须是 flag**（帧头不补这一字节）。
- 成功（参考实现 §4.10 / §4.11，**均未在 D95 验证**）：185 回 `flag + mode`（`mode=0` 刷新浏览窗口、
  `1` 刷新金币寄售窗口，与 183/184 同款；本仓库只发 `mode=0`），334 回**单字节** `flag`。
  失败：`flag=0 + errcode`，码只能取 183 的白名单
  （`0xd2` / `0x69` / `0x72` / `0x7e` / `0xce` / `0x7b` / `0x89`）；未知码会被当成**成功**，界面就会假装成交而资产没动。
- ★ **成交后不补发金币刷新包**：185 回调自身会本地乐观扣一次金币，再补发 `0x000D`/`0x000E` 会被叠加成「再扣一次」
  （参考实现实测：余额不足时显示「余额清空」）；服务端只同步内存金币值，供重新选角等后续刷新读到正确值。
- 购买不涉及「源槽被业务窗口持有」的残留锁（那是上架 183 的问题），因此**不需要**整列背包刷新；
  买方道具与卖方金币都通过邮件模块的**领取路径**入包/入钱包，那条路径已有自己的提交回执与差量发布。
  成交后唯一的客户端可见动作是给买方本人发一条**新邮件到达提醒**（邮件模块既有入口）。

## 到期结算：拍卖行「到期未售」（道具退回 + 退保证金）

时间驱动、**离线可完成**的一次结算：卖家可能已经下线，挂牌却在到期。本仓库没有定时任务，因此它挂在
**卖家查看自己挂牌的读路径**上（CMD 188/190，与邮箱 `ExpireMailbox` 在打开邮箱时清理同一形态）。

**锁序与事务边界**

- 锁序只有一条：`挂牌行（事务内条件更新） → 托管邮件行`。**不修改卖家角色行**（道具与退还的保证金都进
  托管邮件，卖家领取时才入包/入钱包），因此这条路径**没有 revision 依赖**、也不需要第二把租约 ——
  与[跨账号转移](#跨账号转移拍卖行一口价购买)相比少一个参与方。
- 结算在**持有本人租约**的情况下提交（与同账号其它提交串行），进锁后复核「计划所依据的角色仍是当前在线角色」；
  换角/接管后不再结算旧角色的挂牌。
- 一批挂牌的「状态流转 + 全部退回邮件」在**同一个外层事务**里提交：任一步失败整批回滚，
  下次访问重试。这样不会出现「挂牌已过期但道具没退」的半成品。

**幂等与一致性和它们的判据**

- 唯一幂等判据是**状态条件更新** `UPDATE auction_listings SET state=3 WHERE listing_id=? AND seller_character_id=? AND state=0`
  的**影响行数必须为 1**；为 0（已被下架/成交/并发结算）就**跳过这一行并记原因**，不抛异常 ——
  到期结算是批量清扫，一行被卖走不该让整批都结算不了。
- 退回邮件另有唯一幂等键 `auction:return:{listingId}`（`mailbox_messages.delivery_key` 的 UNIQUE），
  是「不会退两份」的第二道防线。
- 退还金额取自**行内实收金额**（`auction_listings.deposit_gold`，迁移 v37 逐行落库），不是当前政策常数：
  历史行（该列出现之前上架、没交过保证金）退 0，**绝不凭空造币**；取消上架不退（那条路径不产生退款）。

**为什么不在读路径里吞掉写失败**：结算是**写**操作，SQL/事务失败照旧向上抛（不编一个假成功）。
只有「这一行投不出去」这类领域级失败被记成 `auction_expire_failed` 并继续返回列表 ——
一次到期退回的失败不该把整个「我的拍卖品」面板打成「点了没反应」，下一次访问会重试。

## 场景约束与原因

| 场景 | 必须保持的行为与需要排除的阻塞 |
|---|---|
| 背包移动、穿脱、仓库存取、整理 | 统一完整实例、UID、锁和原子提交；空移动/零变化免无用写入。连续存取属于核心请求，不能因其他账号的低频功能持writer而排队数秒 |
| NPC商店、商城、礼包展开 | 商品与资源目录共享复用；扣款、全部奖励和资格在同一事务。礼包解析若需要角色信息，读取传入快照或复用现成事务，不能再开写事务查询职业；检查其他账号同时存取/刷图 |
| 开箱、抽奖、合成、批量奖励 | 复杂度和分配量不得直接随不受约束的请求数量增长。能按数学上等价的分布聚合时保留原权重、重复池、每行数量和随机语义；逐实例属性仅在实际容量可容纳后生成。不得截断数量、改成均值、过滤奖池或额外限制合法批量来制造性能改善 |
| 奖励容量预检、掉落候选 | 复用容器索引和有界枚举，不为每次击杀或发放建立覆盖全部可能空槽的巨大集合。稳定目录在监听前按需预热，只读复用；预热不能生成掉落、消费随机数或为每角色复制整份PVF |
| 连续击杀、整房死亡突发、掉落与拾取 | 以权威死亡结果及必要掉落通知收齐为响应边界，不能只计首个包或单次handler。覆盖多只怪同批到达、重复死亡、普通/金币拾取及真实任务掉落；保持掉落UID、归属、数量、去重与失败反馈 |
| 满级经验、荣誉/成长、升级与奖励 | 这些写入可能处于击杀响应之前，归入核心路径预算；不能以“等级不变”推断没有数据库工作。等级、满级奖励和任务组合分别核对，禁止让诊断日志为了统计而加载全部满级角色 |
| 技能材料扣除、耐久 | 同连接顺序处理时，扣材料卡住会推迟后面的死亡包；同时审计前置消耗和后续响应。耐久未变化仍验证当前装备和lease，但不写库/重载；实际消耗、耐久变化与失败语义保持原合同 |
| 任务接受、完成、进度、自动掉落 | 沿原事务owner保存，复验activation/版本和事件去重；保留局部回滚与receipt。空任务范围/无推进不启事务，非空范围不能免保存。合法进度版本变化按业务核对，不因同activation版本更新一概拒绝 |
| 每日挑战、列表查询、金币携带上限 | 纯查询不因“确保存在”取得writer；缺省值与建行分开。外部writer占用真实文件库时仍验证只读与无变化路径，不能只用内存库证明无锁竞争 |
| 组队进图、队员先到/迟到/重复选图 | 队长驱动准入、共享实例和扣票，成员保留自身run/结算状态。合法成员通知按当前冻结名单和场景识别，不重复扣票、建实例、消费连图授权或补发入场包；错误身份和过期授权仍拒绝 |
| 城镇同屏、公共队伍列表、好友/公会资料 | 慢接收者只能影响自己的投递，不让创建/离队/进退图等待所有socket。公共发现列表可合并到最新内容，队内必要通知、本人ACK和奖励结果不得套用丢弃策略；详见下一节 |
| 登录/选角的大包、换区及回城 | 保持必需包序、完整字段和ready边界；大包发送慢需区分排队、构帧、抓包和socket。不得减少必要字段、提前宣布ready或截断正在写出的帧以降低耗时 |
| 宠物饱食度/期限、定时保存、在线清理 | 时钟和周期任务有明确注册、停止、切角与owner边界，只处理实际到期或变化项；不逐tick全库扫描、无变化保存或每实例创建无界任务。旧epoch不得复活已移除的道具、角色或发布缓存 |
| 拍卖行一口价购买（跨账号资产与金币） | 只取买方一把租约，卖方所得走托管邮件；挂牌条件更新、买方扣款与两封托管行同一事务；道具不进买方背包（领取时才判定容量）；锁序、失败矩阵与幂等见上文「跨账号转移：拍卖行一口价购买」一节 |

这些规则约束实现方式，不能增加与当前业务和匹配资源不符的使用地点、物品类别、快捷栏、职业、品质或数量限制。

## 请求顺序与消息交付

每连接保持协议要求的请求顺序。等待前一请求提交和必要回复造成的后续排队属于本请求体验的一部分，不能并行乱序处理同角色指令来掩盖等待。事务锁释放后再网络await；发送工厂/guard只读当前内存投影和身份，不能在发送锁内SQL、等待角色锁、网络I/O或变更业务。

可合并的公共列表/外观刷新使用现有Runtime与每连接发送机制：重复意图只推进待更新版本，每接收者只保留有界最新状态，不每次创建任务或保存全部历史包。未就绪、换区、入队、换角、替换连接及关闭时核对可见性和epoch；业务owner完成转换及必要本人包后才能发布ready。不能只因状态字节相同就忽略实例/场景变化。

列表删除以**上次成功发送**的条目为基线；构造、入队、失败、取消不算送达。同ID的成员、队长或设置变化也需更新，不能仅按ID去重。切区需要保留足够旧基线清除残留，装载重置按模块协议处理。这里只指服务端写入完成，不代表客户端业务确认。发送中途场景变化不截断帧，超时只关闭对应连接；失败保留必要待更新意图，由后续变化/ready触发，不无限重试或新增轮询线程。

当前城镇同屏的可靠队列、移动合并及上限见[城镇同屏](../模块/城镇同屏.md)。其他发现列表接入时复用适用机制，不凭本规范预建平行广播框架。慢连接验证必须确实观测发送阻塞，单纯让客户端不读一次小包不足以证明socket被堵住。

## 延迟目标和测量

以下为验收目标，**不是当前版本已达到的性能或容量承诺**。核心包含连续仓库存取、死亡/掉落通知、拾取以及直接阻塞它们的内部保存/任务。低频预算只适用于不拖慢其他玩家核心操作的交互；特殊场景须在测量前定义预算，不能事后放宽掩盖异常。

| 正常预热负载 | 目标 |
|---|---|
| 1/3个独立活跃账号的核心请求 | P95 ≤ 50ms，P99 ≤ 100ms |
| 10/20个独立活跃账号的核心请求 | P95 ≤ 100ms，P99 ≤ 250ms；数据库竞争造成的单次 ≥1s 停顿必须定位 |
| 低频交互及正常公共列表更新 | 500ms内完成；不能持共享锁或writer拖慢其他账号 |
| 吞吐与公平性 | 有效请求无系统失败/超时，稳态完成率至少为计划速率99%，欠账不持续增长；总体与每账号分别检查，无角色饥饿 |

报告源码/产物标识、配置、PVF/schema、数据库初始状态、硬件与抓包模式。同条件比较，Release用于正式性能测量，Debug用于功能验证；冷启动/首次操作单列保留，不删掉慢样本。连续存取可用每角色2次/秒，另列5次/秒突发；独立账号并发与同账号顺序换角是不同用例，不把同账号多开作为前提。

使用单调时钟记录计划发送→完整必要响应、实际发送→完整必要响应两种口径及P50/P95/P99/最大值、≥100/250/1000ms次数。固定计划发送率，保留发送欠账、失败/超时与未完成样本；闭环等待响应后才发送会隐藏服务变慢造成的排队。报告样本数，少量短测不能当稳定P99或线上容量。

归因分开记录接收队列、handler/规划、锁等待与持有、写入准入、连接/BEGIN等待、SQL保存、COMMIT/恢复、发送队列、构帧/抓包和socket。SQLite等待常发生在BEGIN而非COMMIT；低频业务的持锁时间、同连接队列和跨账号writer竞争需一起看。仅有socket等待不能直接归因于带宽或用户网络。

慢日志应有阈值和有界限流，正常热路径不额外拼逐包字符串、同步刷盘、查库或枚举全角色。限流后的缺失日志不证明没有阻塞，suppressed不属于下一条打印的角色；已读批次queued时间不是完整请求队列或网络RTT。全量分位数使用测试计时或有界聚合，不能从抽样慢日志推算，不为采样保留无界请求列表。

## 验证与停止边界

- 首先使用独立真实文件库做聚焦复现：长规划期间另一账号仍可操作，事务内连接不自锁，零变化/纯读不申请writer，旧generation/epoch、GM更新、revision冲突及SQL中途失败不产生成功或半份资产。多角色锁顺序、双方回滚及去重按实际业务验证。
- 受控注入100ms、250ms、1s的writer等待、发送阻塞及取消，单列故障轮次，不套用正常时延门槛；验证等待有界、恢复后可继续、慢连接不拖健康接收者。两账号混合商城与满级击杀/材料扣除能暴露单业务成功测试遗漏的阻塞链。
- 核心回归覆盖真实TCP完整帧和必要通知，核对在线内存、独立读库、重连与重启；包含任务/无任务、普通/满级、单人/组队和整房突发中本次受影响的组合。不要以纯背包基准代替战斗，或用少量玩家不卡顿代替并发证据。
- 资源测试与构建串行；声明进程树内存、时间和进程数预算，运行前检查系统可用物理内存及提交余量，越界终止本轮并定位。复用只读PVF，控制fixture进程与stdout缓冲，检查退出后回收；不得并行重复加载整份资源、无上限加压或在资源不足后连续重试。测试详细要求见[贡献指南](../../CONTRIBUTING.md#验证)。
- 只有当前改动或未决证据需要时才做性能长测，默认预热2分钟、正式5分钟的一轮主要负载；其余人数/成对短测按问题选择，不机械重复全矩阵。停止输入后检查欠账排空和可解释的存活内存，短观察不能声称无长期泄漏。
- 在核心体验与低频预算已满足、正确性已证实时停止扩大优化；不为完成阶段表引入后台保存、额外缓存或全局调度框架。编译、自测、协议、性能测量和客户端实机分别报告，未执行的项目保留明确边界。


## 副职业双在线店铺交易

`OnlineSessionDirectory` 继续保存唯一会话索引，只扩展本连接门禁与投影回调，不复制在线角色状态。顾客命令已持自己的 CommandGate；只非阻塞尝试店主 CommandGate，忙则拒绝，不允许互相等待。成功保留直到双方资产投影完成，finally 释放原连接门禁。

资源规划在账号锁外。进入店铺时记住店铺实例及选角 epoch；重开或改价更换实例，使旧报价失效，消耗耐久不会重建价格实例。提交时在两个有序租约内复验原角色引用、就绪阶段、开店、报价、活动门禁、同一公共场景及频道。持锁时不等待网络，双方费用、材料、产出、熟练度与耐久在一个 SQLite writer 事务中完成，各自 revision 只增加一次。免费店主也因耐久变化推进一次 revision。

双方快照仅在提交成功后安装；顾客收到自己的产物/效果，店主收到费用与职业状态，发送泵复验各自 generation/epoch/角色回执。客人不能获得只适用于本人机器的零件。槽号协议没有独立操作 nonce，不宣称跨换槽后的相同字节具备永久幂等；提交版本与实际源 UID/完整快照保护规划期间的重放和并发，已消费源的重复请求不能二次收费。
