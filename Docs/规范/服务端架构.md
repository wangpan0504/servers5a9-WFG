# 服务端架构与公共状态

本页只维护跨模块规则。业务行为、存储字段和验收边界以[模块入口](../README.md)所列文档为准；工作流程与验证见[贡献指南](../../CONTRIBUTING.md)。目标为 C# / .NET 10、DfoServer 与 S5A9 匹配客户端。

## 分层和装配

| 层 | 职责与入口 |
|---|---|
| Application / Infrastructure | [ServerApplication](../../Server/DfoServer/Application/ServerApplication.cs)分派命令并加载资源；[ServerLifetime](../../Server/DfoServer/Infrastructure/ServerLifetime.cs)管理取消/退出；[ServerRuntime](../../Server/DfoServer/Infrastructure/ServerRuntime.cs)显式装配依赖，完成注册后封存命令表 |
| Network/Core、Protocol | [ServerHost](../../Server/DfoServer/Network/Core/ServerHost.cs)管理监听和连接；[GameFrame](../../Server/DfoServer/Network/Core/GameFrame.cs)编码帧；[GameCommandRegistry](../../Server/DfoServer/Network/Protocol/GameCommandRegistry.cs)分派模块；发送泵统一序号与写入 |
| Parser / Handler | Parser 严格验证长度/编码并输出类型化请求；Handler 组织业务调用及回复，不写 SQL、不持有玩家状态 |
| PvfLib | [独立类库](../../Tools/PvfLib/README.md)负责归档、字符串池、分块缓存、token、脚本字段查询及物品资源声明；不依赖服务端 |
| GameWorld | 按领域组织匹配 PVF 定义、共享值、目录、缓存与查询规则；资源读取依赖 PvfLib，不持有在线角色/副本实例 |
| Game | 领域模型、账号 owner、会话状态和业务规则；使用 GameWorld 与持久化接口，不引用 Network、Persistence 实现或 Development |
| Persistence | 实现 [ICharacterRepository](../../Server/DfoServer/Game/Characters/ICharacterRepository.cs)等存储边界，负责 SQL、迁移、版本校验和事务；不发送包或解析 GM 文本/PVF |
| Builder / Projection | Builder 从已提交数据构造包体，Projection 编排包序与可见性；不推进任务、发奖或写库 |
| Development / SelfTests | 开发工具与正式用例分离；服务端测试使用 C#，独立 TCP 入口不依赖 Python |

### 程序集与访问边界

服务端采用模块化单体：Game、GameWorld、Persistence、Network、Application、Infrastructure、Development 与 SelfTests 保留在同一个 `DfoServer` 程序集中，通过目录、命名空间、明确合同和构建期语义检查约束依赖。PvfLib、PvfLib.Tests 与 ArchitectureCheck 保持独立项目。日常开发和分层维护沿用这一结构，不将 Core、Persistence、Host 或 SelfTests 的物理程序集拆分作为交付要求。

- 同一程序集中的可访问性不代表允许跨层调用；依赖方向遵循本页职责表和下方自动检查，新增调用先核对合同与状态所有者。
- 类型与成员保持满足实际调用所需的最小访问范围，不为目录整理批量改为 `public`、添加友元程序集或引入只有转发职责的接口。业务通过明确的用例或领域存储合同调用持久化实现，依赖由应用入口显式装配。
- SelfTests 通过现有自测命令运行，允许测试调用被测层；应用入口仅负责测试命令校验与分派。玩法、资源目录、持久化和网络处理不得借用测试夹具、断言或测试辅助逻辑。正式服务与开发诊断的状态和注册规则继续分开。
- 分层变更保留原有 owner、锁序、事务与提交后发布边界；目录或接口调整不能另建在线状态、拆开原子提交或提前回复成功。构建分析器与行为回归共同验证这些边界，不以项目数量判断分层质量。

### 领域依赖与资源装配

Game 按业务建目录，命名空间与目录一致；角色模型/持久化接口归 Game/Characters，在线状态归 Game/Session。新增玩法在有实际实现时建立对应目录，不把业务持续堆入 GameSession，不预建空 Handler、接口或事件总线。

Application 显式加载和验证 Catalog，Runtime 通过构造参数注入所需依赖。缓存属于 Catalog 实例；Runtime 不是业务查找依赖的容器。Catalog 输出类型化字段，包体排列只在 Builder；保持现有固定值和未知字段的证据说明。不引入 DI 或无职责的转发层，遵循 `.editorconfig` 并展开控制流。

应用入口持有一份 `PvfArchive`，在服务生命周期和资源读取结束后释放；Catalog 共享借用该归档，不自行关闭它。库负责有界的底层块/文本缓存，GameWorld 负责领域目录和已解析定义，两者的所有权分开。

`ItemResources` 仅供应用入口、Runtime 和测试夹具装配物品相关目录。`ItemCatalog` 只负责物品模板索引与缓存，构造时显式接收装备/堆叠列表及装备出售比例；它不创建金币上限、仓库、商店、修理、锻造、分解、史诗碎片或礼包目录。各玩法服务和投影通过构造参数接收实际使用的目录，不接收装配集合，也不经角色目录查找物品依赖。

`CharacterCatalog.Load` 接收共享的 `ItemCatalog` 以解析初始装备，加载后只保存角色定义，不持有或公开物品目录。物品目录和礼包目录共享同一份堆叠列表。任务资源目录归 `GameWorld/Quests`。Game 调用类型化的资源查询（如 `DungeonMaze.ConnectsQuest`），不直接解释 PVF token。

### 自动依赖检查

[LayerDependencyAnalyzer](../../Tools/ArchitectureCheck/LayerDependencyAnalyzer.cs)作为构建分析器接入服务端及 PvfLib，违反依赖方向时报 `S5A9001` 并使构建失败。检查按语义符号解析，覆盖限定名、别名和静态引用，同时按目录和命名空间判断所属层；没有存量违规白名单。

- Game 不引用 Network、Persistence 实现、Development、应用装配、PvfLib 或 SQLite。
- GameWorld 不引用 Game、网络、持久化、开发诊断或应用装配；Persistence 不引用网络、诊断、应用入口或 PvfLib。
- Handler、Parser、Builder、Projection 不引用具体持久化、开发诊断、PvfLib 或 SQLite。Parser/Builder 还禁止引用 Session、账号 owner、仓储/认证合同、Handler/Projection 和文件读写类型。
- PvfLib 不引用服务端。纯值和只读业务结果可供 Builder 使用；开发诊断在 Development 中通过独立模块接入。
- Persistence 不实现或引用认证用例入口；Handler 不直接调用凭据存储合同，Parser/Builder 不调用认证服务或凭据存储。认证规则与 SQL 的当前边界见[认证与会话](../模块/认证与会话.md)。

分析器保护静态依赖边界，不能证明任意业务方法无副作用，也不代替事务、并发和发布回归。规则的合成正反例及统一运行入口见[贡献指南](../../CONTRIBUTING.md#验证)。

## 注册与连接生命周期

`IGameCommandModule.Register(GameCommandRegistry)` 注册本模块支持的 opcode。分派返回以下结果：

| 结果 | 协议层行为 |
|---|---|
| `Handled` | 已完成当前请求，读取下一帧；可能是按合同静默拒绝，不等于必有成功 ACK |
| `Unhandled` | 记录原生名称和长度，保持连接，不构造通用成功 |
| `CloseConnection` | Handler 已发送必要响应，协议结束循环并清理连接 |

结构错误、非法会话状态及存储异常继续抛异常并关闭当前连接。未知 opcode、END 和尚未实现的子型不注册占位成功处理；枚举完整并不表示玩法完整。注册表在 Handler 前后核对 owner，单个连接始终顺序执行请求。

退出时先校验模式、结束角色状态和清场，再等待 ACK3 发完，最后返回 `CloseConnection`。协议清理依次移除准确的在线会话、城镇成员，停止发送泵，释放原 owner。索引以“账号 + 会话引用”原子移除，旧连接不能删除新连接。启动失败或某个监听退出时取消同一实例的其他监听，等待所有连接清理后结束。

`ServerLifetime` 创建并释放共享 `ServerLog`，`ServerRuntime` 将该实例传给需要记录日志的模块；`ServerHost` 持有可选的 `PacketCapture`，全部连接清理结束后释放。二者共用 `Infrastructure/BufferedLogFile` 的单写入器与固定缓冲，明确关闭时刷新尾部；刷新、故障与实时读取规则见[环境与配置](../开发/环境与配置.md#包体抓包)。

`GameConnectionContext` 提供连接身份、取消令牌、owner、当前 Session、Sender 及名册请求状态；不复制 `Selected`、`Ready`，也不携带全部 Repository 或 Runtime。可选的 [IGameConnectionActivity](../../Server/DfoServer/Network/Protocol/IGameConnectionActivity.cs)只暴露城镇操作门禁和清理合同，由 Runtime 按连接装配；具体活动状态由所属模块持有，返回选角/退出及连接关闭时清理本连接活动。GM 从同一个 `OnlineSessionDirectory` 找到 Session，因此在线调整和网络处理共享角色状态。

正式副本选择与开发诊断由 Runtime 互斥注册，共用独立的选图界面入口；诊断状态和候选构包归 `Development/Dungeons`，`Game` 与普通 Handler 不引用它们。默认连接不分配诊断状态。具体模式和未实现边界见[副本模块](../模块/副本.md)，不得将诊断运行对象当作正式实例或战斗事实来源。

未知命令及错误参数由应用入口返回 2，不启动监听或创建角色库。需后台执行的工作由 Runtime 显式建立启动、取消及等待边界；不得按账号名借用后来建立的新会话发布旧结果。

## 所有权与并发

### 账号 generation

`AccountOwners.TryAcquire(account, disconnect, policy, ...)` 在锁内安装新 lease 并递增 generation。`Reject` 在已有 owner 时返回 `DuplicateAccountOwner`，不调用旧连接的断开回调；内部离线 GM 占用使用此策略。`ReplaceExisting` 在锁外断开旧连接。`Acquire(account, disconnect)` 只保留离线工具和测试的兼容入口，固定使用 `ReplaceExisting`。原生登录验证凭据后使用 `TryAcquire`，登录策略固定 `ReplaceExisting`，不提供配置参数。`Lease.Execute` 通过引用比较确认自己仍是该账号的 current owner，过期 lease 抛 `InvalidOperationException`。`Dispose` 也只移除仍归自己拥有的条目，旧连接不能释放新 owner。

generation保护当前进程中的账号会话；它不保存在数据库，不代替角色revision，也不是跨进程租约。任何无变化请求仍须检查lease，不能用“位置没变”绕过owner校验。当前每连接发送泵在每帧构造前、异步写入后检查目标lease，成员帧另检查源身份及接收视图epoch；检查和写入不是原子区间。接管与已开始发送之间仍可能交叠，不能宣称目前完全排除了旧帧在途。

### 角色 revision 与会话状态

`CharacterRequests.Select` 校验body宽度，`GameSession.Select(ushort slot)` 只允许未选角会话和属于该账号的slot。Session装载目标角色，调用 `Game/Characters/CharacterSelection` 完成出生归一化、到期清理和金币上限准备，再安装实际Selected及完成任务集合、递增epoch并保持Ready=false。准备保持原lease锁，具体提交顺序与失败恢复见[NPC与出生](../模块/NPC与出生.md)。CharacterHandler 等待 TownProjection 发完入城完成124后才调用 MarkReady 并加入场景。选择失败或发送中断后由连接生命周期关闭；下一连接重新加载数据库，不重放已提交资产写入。

`Save` 以 `id + account + expected revision` 更新位置、方向和返回地区，影响行数必须为1，revision在同次提交中加1。事务提交后返回新的Character，Session再替换Selected。旧revision、SQL错误及过期generation不得被重试包装成成功；需要重读恢复时先明确重读后的业务资格与重复请求语义。

35/631每次有效位置变化同步提交，重复位置不写库；36/1426按切图业务提交。移动只更新位置/返回字段，保留job、grow、level、任务、CG、技能。未来新增资产字段应逐业务定义修改集合，不能用整行默认值覆盖未参与的资产。

### 现有锁与吞吐限制

所有模块修改锁、请求处理、保存或投递时，遵循[并发、事务与响应延迟](并发事务与响应延迟.md)。该页维护行为与验收约束，不表示其中尚未接入的业务已实现。

- `AccountOwners` 的注册表锁只管理账号锁条目、等待获取者及 generation；不在注册表锁内等待账号锁。`Lease.Execute` 持该账号锁，允许 Session → Repository 对同账号重入；不同账号可独立执行。接管和释放也取得原账号锁，因此不会在同步提交中途撤销租约。没有当前 owner 和等待获取者时回收条目，旧租约不会使已回收的条目重新生效。
- 每个game连接按收包 → 同步业务 → await发送依次处理。不同连接任务并发；Accept阶段按active.Count限制连接，当前不是经过多玩家压测的容量保证。
- 城镇成员使用独立成员锁，锁序为账号锁 → 成员锁 → 发送队列锁；精确离场只需成员锁。成员可见性读取租约的单向失效标记，不反向取得源账号锁。注册表不调用业务、成员或发送代码，SQLite 不回调账号锁。每连接发送泵串行构帧、分配 sequence 及写入；取消回调异步执行并在发送器释放时等待，详见[城镇同屏](../模块/城镇同屏.md)。
- Repository每次操作独立连接，`Pooling=false`，`busy_timeout=5000`，foreign_keys开启，数据库使用WAL。当前没有后台保存、dirty合并、异步数据库提交或跨角色交易。
- 服务进程与离线导入/准备入口共用 `DataDirectory/server.lock` 的独占文件句柄。不能另开进程或脚本绕过该锁写同一个运行库。
- 当前lease锁内只执行同步状态/数据库工作，网络await在锁外。新增代码不得持SQLite事务跨网络await，或在lease锁内等待网络/外部脚本。
- 批量开箱使用 `GameSession.PlanAndCommitInventory`：锁内取得原角色快照与选角epoch，锁外只读规划，重新取得原lease后核对Ready、epoch和快照身份，再同步提交。规划不得修改在线状态或写库；冲突拒绝原计划，不自动重跑随机业务。其他现有 `MutateInventory` 调用仍在账号锁内规划，会阻塞本账号后续请求和接管。
- 建角、技能初始化与学习也采用锁外资源规划、锁内复查与提交。建角规则归 `Game/Characters/CharacterCreation`，学习规则归 `Game/Skills/SkillLearning`；Session 保留选角 epoch、阶段和当前角色快照的唯一所有权。具体失败与发布合同见[角色](../模块/角色.md)和[技能学习](../模块/技能学习.md)。
- 移动、旅行和出房规则归 `Game/Town/TownTravel`，规则只返回位置计划；Session 在原 lease 内校验阶段、提交并安装角色。切图投影使用本次 `TownTravelReceipt`，清场与新场景成员加入也受原回执约束，具体失效与在途边界见[城镇](../模块/城镇.md#状态与拒绝语义)。当前旅行与选角准备仍同步运行在所属账号锁内。

`Lease.Execute` 内禁止获取新的 owner，跨账号嵌套 Execute/Dispose 会立即拒绝，避免反向锁序。当前没有跨账号原子用例，新增交易等功能须单独定义参与者、固定锁序和同一数据库事务。账号锁拆分不改变 SQLite 单 writer 限制、同账号请求顺序或在途帧边界；不能据此承诺所有请求互不阻塞或已经完成多玩家容量验证。

## 事务与迁移

1. Parser 保留完整字段；资源解析和重计算可在不可变快照上锁外规划，提交前在当前 lease 内重新验证身份、状态、原快照和本次业务资格。
2. Repository 在一个事务中提交本业务的全部费用、资产、进度和一次性资格；以 revision/唯一约束拒绝过期或重复写入。
3. Commit 成功后返回实际新状态，Session 再替换在线快照，Handler 才回复成功并投影。
4. 发送失败不回滚已提交事实，也不自动重跑扣费、奖励或随机结果；重连从已提交数据恢复。

持久化只修改本业务字段，保留其他模块状态。未知结果不能包装成成功或直接重试。跨角色业务必须明确定义事务及固定锁序，不能把两个独立 Commit 当作原子操作。

账号与游戏 Repository 共用 `Data/game.db` 和 [SqliteGameDatabase](../../Server/DfoServer/Persistence/SqliteGameDatabase.cs) 连接设置。初始化、完整 SQL、基线标识及连续版本迁移统一由[数据库入口](../开发/数据库.md)管理；业务字段属于对应模块。新增迁移保持已发布版本的数据，验证建库、升级、失败回滚、重开库和较新版本拒绝；不重排已发布迁移、不回退 user_version，不以删库解决兼容。共享 schema 变更协调版本号。

## 协议和资源边界

本版 category/opcode、宽度、编码、状态与失败收尾须由匹配证据确认。信令枚举存在不代表实现；未知值保持未知，不复制其他版本数字、不返回通用成功、不省略必读字段。网络基础合同见[帧与频道](../协议/帧与频道.md)。

业务配置从匹配 PVF 加载。必需资源缺失明确失败，可选缺项按业务说明处理，不伪造默认资源或把未知实例条件视为已满足。角色行为不可因迁移遗漏而收窄；确有版本差异时记录依据。业务测试及实机验收边界由所属模块维护。
