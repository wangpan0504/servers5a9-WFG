# 属性声明与消费

本页区分匹配资源声明、已确认消费者和仍缺少的数学合同。业务状态归属见[角色属性](../模块/角色属性.md)。

## CHR 分块

`character/character.lst` 中 job0 指向 `character/swordman/swordman.chr`。初始块声明 HP180、MP140、physical attack/defense各7.5、magical attack/defense各4.5、dark20、light−20。`[growtype 1]`声明 HP45、MP25、physical attack/defense各4.8、magical attack/defense各4.2、inventory300、MP regen2.5和hit recovery1.5。4.8的原始float32位模式为4099999A；文本导出的小数位不能替代原始数值。

匹配解析器 `040B94F0` 的 `[initial value]` 分支 `040B98D0..040B992A` 选择模板+124的89B区域；`[growtype 1]` 分支 `040B992F..040B99AB` 选择+17D并将局部选择索引置0。后续 growtype 分支顺序设置1、2等索引；awakening属于其所在growtype，不能与初始块或其他转职合并。这个 parser 索引证据尚不能独立证明业务 GrowType 的实际选择、等级乘数或累计取整顺序。

HP读取 `040BA001..040BA03B`、physical attack读取 `040BA0C0..040BA0FA` 都先读float32，再乘10并调用 `01606490` 写入89B对应字段。`01606490` 对非负值加0.5、负值减0.5后执行 `cvttss2si`；常量 `050E654C=10`、`0509D564=0`、`05099CC4=0.5`已与匹配只读节核对。不能用这一转换函数直接证明 `initial+(level−1)*grow`或成长累计取整顺序。

`CharacterAttributeDefinition`保留资源分块和标量，不在原始声明中补0，`CharacterCatalog`只提供声明和职业目录查询。Game层的 `CharacterStatComputer.ComputeLevelBaseStats` 沿下述已证规则评估基础分量；真实缺声明使用 `040AF0A0` 的DTO初始化零，不能把未支持资源类型或重复/损坏声明当作零。计算结果仍为类型化 `CharacterStats`，89B编码由Network层的 `CharacterStatsPackets`完成。

正常模式等级评估 `02B53920`：复制静态模板+124的89B初始结构，`02B53A83..02B53AA6`选择+17D的growtype1结构、以 `min(L,18)-1`作为系数；`02B53A65..02B53A81`在L>18时选择 `+17D+growIndex*59h`，系数L−18。`02B53AAF..02B53C3D`对已经转换的整数逐字段乘加，不在每级重新处理float32。业务GrowType低4位为firstGrow，映射到`[growtype firstGrow+1]`。所有16职业均按此正常基础公式评估；growIndex0两段使用同一声明，合并为 `initialFixed+(L−1)*growthFixed`。觉醒高4位按职业目录校验，原始awakening块独立保留；该正常CHR基础循环不选择awakening数组，也没有旧版50/75级分段，不能仅因资源有不同觉醒声明就追加永久分量。运行时Data内联于模板+8，所取编码+1C对应Data+14等级；Actor等级读取 `02676FC7..0267702B`写同一Data+14编码字段。

该评估第三段还加运行时+4D8的89B修正，并存在后续模式/技能等分支。+4D8通过 `04026F5D..04026F66→040AF130→040AF0A0`初始化为零，之后可从其他来源复制。服务器基础目录不把这些合法修正视为始终零或塞入CHR成长；基础计算结果不表示最终能力。评估结尾 `02B55363..02B55371`调用Player同一虚表+BC4安装89B，证明客户端自己也生成基础/修正DTO，不能仅凭服务端InitialStats恒定推断客户端没有成长。
## 89B 与本地能力

`02676250`消费长度/raw并调用Player虚表+BC4及+BCC；属性安装 `02B6B3A0`对HP和四个short存在门禁。`028FA240`读取模式管理对象+1010并调用 `03EF9640`，仅值59或60返回true。模式名称和正常3145实际分支仍需对应证据，不能把该门禁对象误认为Player。

正常等级owner另有明确来源：`02BAF507..02BAF5F1`从Actor Data+14写能力buffer0第一个整数；`02AD2FB0`在普通流程取最终buffer3同分量。因此普通+41C是等级owner，不能因特殊门禁下wire HP覆盖同位置就改称普通HP getter。HP业务getter `02AC5750→03DF2D20`读取编码qword的另一分量。

offset24..59为18个signed short，`02B6B869..02B6B880`按每项/10安装能力分量；它们不是9个DWORD，也不能任意填STR/INT或装备总额。后续客户端明确枚举真实装备槽，并调用item虚表+200（已核实例为 `029AD8E0`）应用装备效果。最终能力getter使用派生buffer，因此89B DTO、装备分量、面板及战斗结果不能混为同一个值。

派生责任已确认：`02AFAC40`阶段1将buffer1复制到buffer2，阶段2复制到最终buffer3，再于 `02AFB048..02AFB055`调用Player+31A8的buff manager `02DBF4A0`。该manager调用真实buff对象虚表+0C，普通精通对象为 `02EE0DD0`，511的HP/MP等效果在此阶段本地应用；174另在 `02B7C9AC/02B7CAA0/02B7CB7F`取得index3修改攻击倍率分量。服务端将这些值加入89B会重复计入派生结果。

NOTI402 `CHARACTER_STATUS`不是属性更新：注册 `02398771`指向 `0237ECB0→028FD9C0`；消费者读取当前final buffer3并构造111B快照，`028FE4B7..028FE4DD`以C2S460回传。它不能替代等级基础刷新，后续实机取证可将这一快照与对应面板/战斗getter关联。

16职业及合法转职/觉醒编码的正常等级基础计算与升级刷新已接入。装备、强化、附魔、增幅、精通及被动的全部最终属性规则仍需闭合。基础成长及资源读取回归不证明面板或实际战斗属性正确；集中客户端验收需核对同一角色、等级、实际穿戴、完整Core、技能树及提交revision，并覆盖重选、重登和实际服务重启。
