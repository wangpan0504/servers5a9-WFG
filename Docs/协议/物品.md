## DNF礼遇特权

NOTI1643由`00978F60`消费固定62槽，每槽`slot:i32,status:i32`共8B；空槽为`-1,2`，其余状态为0有效、1过期、2未购买。NOTI1644由`00978B30`消费严格21B：`status:i32,expiresAt:u32,dailyClaimed:u8,loginDays:i32,milestoneBits:u32,rewardSeason:i32`。有效状态的expiresAt为绝对Unix秒，其他状态发送0；不是剩余秒。名册和本人状态在选角本人Player后恢复，购买或领奖提交后沿同一投影刷新。

CMD1640领取正文严格21B。匹配发送器前13B未初始化，不能用作角色、季或资格；只读取末尾`mode:u32,value:u32`，mode0为每日领取，mode1为资源声明的累计天数。成功提交后刷新库存及礼遇状态，再回`01 + result:i32=0`共5B；背包空间失败为`00 + error:u16=0 + result:i32=3`共7B，私有3才驱动背包空间提示。`028F82A0`公共派发先消费success及失败error（仅18/20豁免），`028F2970`随后调用`00978C80`固定读取4B；这4B不能当作完整ACK，其余拒绝恢复权威状态，不猜错误码或返回成功。

CMD1641（0x669）是礼遇传送，不能当作换季入口。正文严格19B，发送器`0284FFE8`前13B未初始化，不参与身份或资格；末尾为`town:u8,area:u8,x:u16,y:u16`，朝向沿用实际角色。公共派发消费成功字节和失败时的`error:u16`后，ACK消费者`00978D00`再固定消费但不使用5B；本服以零占位，成功共6B=`01 + 5B`，失败共8B=`00 + error:u16 + 5B`。地区拒绝用已证error2，其他拒绝用非零error1，不能发送error0误触发成功冷却。成功由客户端按资源`[teleport cooltime]`启动相对冷却，后5B不是服务端截止时间，不另造冷却NOTI。资格、频道和位置事务见[礼遇传送](../模块/城镇.md#7-礼遇传送)。NOTI1641属于另一功能，不能混同；`0097AD20/0097ABB0`的29B状态也不是礼遇21B。

## 成就任务完成券 CMD515/action99、183

`[achievement quest clear]`的19B请求沿CMD515公共布局，reserved及两个参数均为0。匹配客户端`028C0AE0`成功读取slot:u16、list:u8、action:u32；99由`028BE970`默认分支消费一张源，专用尾部回调表没有99。成功使用`01 + slot:u16 + list:u8 + action:u32=99`共8B，不追加完成任务或奖励数组；失败保留公共7B布局，不把资格或无目标拒绝回成成功。

本服成就券的普通任务范围是`[grade] [achievement]`与`[reward type] [title]`的交集，另外独立发放称号簿`general`全组，不能套普通77范围。原子提交完成后先ACK515，再以NOTI14发布普通背包中的实际称号实例；称号簿使用NOTI359进度及五类NOTI358完整列表，不把专用容器塞进NOTI14，不逐项重放称号获得弹窗。general章节邮件另发邮箱提醒，随后沿574、21、356同步活动、候选和完成列表。源仍仅由消费ACK扣一张；两类范围均无待完成项时不扣券，已提交回执恢复原UID及操作身份。业务限制见[任务模块](../模块/任务.md#任务掉落与职业奖励)。

181、182、183在`028C5980`使用前回调表均指向`028BABE0→028BA200`，独立producer仍写515及公共19B正文；两个参数和reserved为0，指定等级来自STK而非网络参数。ACK保留实际动作号，成功公共8B、失败7B，不伪装升级券418、普通任务34或追加等级尾段。181仅发布主线完成表，182/183有称号变化时再按359/358及普通背包14分流。

101在`028C5980`注册`028BDD40`，确认回调`028BFFF0→0200A1A0`先发1430及源STK模板键，准备成功后mode0经`02350C60→028BA3F0`发送实际action101的515；171注册`028BB420`，直接调用`028BA200`。最终515均为公共19B、零reserved和两个零参数，成功8B及失败7B保留实际动作号；101有称号时沿359/358与普通背包14分流，171只同步完成状态。

## 单主线任务完成券 CMD34/action110

110的使用前回调`028B8240`仅打开1215号`UI/Chn_QuestClearCoupon/QuestClearCouponWindow.xui`。确认发送器`02123900`依次调用u16写入器，正文固定10B：`opcode:u16=34,questId:u16,rewardSelector:u16=FFFF,multiplier:u16=1,sourceMainSlot:u16`。末尾槽位由`029CBD60`按源物品模板在Main中查找；不能当作普通领奖的FFFF保留字，也不能伪装成515/action110。本版反编译将selector显示为255，但对应指令实际为`push 0FFFFh`，按真实写入值处理。

## 库存重同步 CMD870

匹配客户端的`028FAA50`发送一字节正文，1000ms本地限频；已核直接调用点`02373C66`与进图`CNRDStage::setMap`中的`02D265C1`均传`FF`。该字节保留原值，不解释为容量或客户端权威库存；其他值也恢复完整五容器，不猜测尚未核证的请求位语义。

服务端只读当前已安装快照，依次发送宠物详情105、Main/Avatar/Pet/Equipment/AccountCommon五个NOTI13、克隆来源1449及原物品锁，最后回复`01`。`0233CC00`成功分支不再读取业务正文，其日志为“装备同步成功”；内部manager的key19不是网络连接编号。失败分支另读公共error:u16和穿戴/背包/装扮/宠物四位mask，当前畸形请求及未就绪请求不伪造该失败语义或成功回包。

穿戴列表3沿`023BDDF0`共同头`list:u8,count:u16`，不带Main/Avatar扩展；`023BE32E → 029DED30`清旧容器，随后按实际行数载入123B核心，时装仍附原RAW30/RAW4。空列表必须发`03 00 00`以清幽灵装备。快照及每次实际发送均复验owner代次、选角epoch、角色引用、阶段与正式实例；不重载数据库、不写revision或资产。包序与自动回归不等于客户端进图及装备表现已验收。

## 助手能力探测

配套助手在选角就绪后主动发送CMD870的保留ASCII扩展：`95_HELPER_CAPS/1 <nonce> <characterId>`，恰一个空格；nonce为32位非全零小写hex，角色号为无前导零的正ushort。正文最多90B，版本、长度及字段均严格核对。普通一字节CMD870保持原库存恢复语义；此前仅支持一字节的服务端会静默消费该扩展，不进入聊天、不修改库存。

仅探测角色与当前就绪角色相同时，回复NOTI1709 AAS_TIPS，标题`95_HELPER_CAPS/1`，type0，正文为`1|nonce|characterId|selectionEpoch|hell,cargo`。不在选角流程向所有客户端主动发送。客户端配套前置消费者须先吞掉匹配机器标题，并核nonce、角色及会话；未取得当前能力回执时不得经普通聊天向旧服探测助手业务。该扩展为本服自定义合同，不是原版库存同步功能。

新版助手可发送`95_HELPER_CAPS/2 <nonce> <characterId>`探测直入包能力；服务端仅对版本2回`95_HELPER_CAPS/2`，正文为`1|nonce|characterId|selectionEpoch|hell,cargo,direct-bag/1`。版本1合同保持不变，旧客户端不会误收到新增能力。

取得版本2能力后，助手可在角色生命周期内发送`#95-helper/1 <nonce> <characterId> pickup 1`开启副本掉落直入包，发送`pickup 0`关闭。服务端回`95_HELPER_PICKUP/1`，正文为`1|nonce|characterId|selectionEpoch|ok/rejected|0/1`。开关及协商资格按账号owner代次、选角epoch和角色绑定，换角或重连后默认关闭；未完成当前角色的版本2探测时拒绝开启。未取得成功回执时物品仍会正常落地供玩家手动拾取。

直入包沿原死亡掉落随机结果和完整Core执行，一次死亡与成长共用一个库存事务。可容纳的普通实体物品、史诗碎片、账号材料、金币及钱包货币直接提交，成功后发送真实库存/图鉴/账号材料差量；金币、复活币、胜点、晶块及灵魂使用原虚拟槽差量，代币券使用原CERA通知。背包、金币携带或余额上限不足时整件保留地面，不截断数量、不伪造NOTI39或拾取ACK。玩家丢弃及被动特殊来源沿原路径处理。该能力不改变组队归属，每名队员仍使用自己的冻结掉落账本。

助手仓库请求及回执见[助手机器命名空间](聊天.md#助手机器命名空间)，资格与失效边界见[助手随身仓库](../模块/背包与装备.md#助手随身仓库)。

## 助手物品处理资格

CMD17保留命名空间接受 `#95-helper/1 <nonce> <characterId> safe 2`，用于请求支持精确源授权的服务端；旧 `safe 1` 继续兼容，相同身份、频道和长度校验见[助手机器命名空间](聊天.md#助手机器命名空间)。只接受当前就绪城镇角色。只识别旧参数1的服务端不会回复参数2，客户端不能据能力探测或普通库存同步成功推断本扩展已支持。

`safe 3` 请求职业史诗元数据，响应标题为 `95_HELPER_SAFE/2`；正文头仍为 `1|nonce|characterId|selectionEpoch|pageIndex|pageCount|entries`，每项严格为 `slot:fingerprint:operations:wearableEpic`，末段只允许0或1，每页仍最多12项。`safe 1` 和 `safe 2` 始终返回原 `95_HELPER_SAFE/1` 三段条目。版本2仅追加元数据，不改变指纹、操作值或服务端精确授权。职业、性别及分支判据见[助手城镇物品处理资格](../模块/背包与装备.md#助手城镇物品处理资格)。

成功查询先发送同一快照的Main完整NOTI13、账号仓库完整NOTI13及各自既有锁，再以NOTI1709标题 `95_HELPER_SAFE/1` 返回分页正文 `1|nonce|characterId|selectionEpoch|pageIndex|pageCount|entries`。页号从0开始，每页最多12项，空候选仍发一页；条目以逗号分隔，每项为 `slot:fingerprint:operations`。指纹为完整123B普通物品条目（含槽位）的FNV-1a 64位小写16位hex，零值改为1；操作位1为材料归账号库，2为装备分解或出售。此指纹不携带服务端UID，不是新物品身份，也不能替代服务端保存的真实UID和完整实例。

精确授权有效期5分钟，绑定当前owner代次、角色、选角epoch及阶段代次；目录解析后安装与每次提交前均复验。对应候选槽位的原CMD19、出售及CMD26逐件核对实际UID、完整属性与当前保护规则，成功提交变化才消费；同槽替换、属性变化、已消费或过期均拒绝。普通手动同类请求落入已登记槽位也受此限制，直到重新查询或阶段切换；其他槽位保持原规则。CMD26字节、context与普通NPC产物不变，未取得精确资格的未净化气息仍按普通规则拒绝。

客户端必须收到本次nonce和角色匹配的全部资格页才能执行本批处理；整包刷新只能用于重核本批既有槽位和完整条目，不把同内容记录当作相同服务端实例。授权到期即结束本批，不能自动重新查询并把城镇新取得的物品加入旧批次。资格不跨换角、阶段或账号接管恢复。业务保护与手动操作边界见[助手城镇物品处理资格](../模块/背包与装备.md#助手城镇物品处理资格)。

新客户端先请求 `safe 3`，旧服务端不答复时可使用新nonce有界回退 `safe 2`，按当前owner缓存协议版本；明确畸形的版本2回复不得降级绕过。不同版本、旧nonce与晚到分页不能混为一批。版本1没有职业信息：开启保护时仅回城自动分解保守跳过所有史诗，出售、手动快捷键及其他品级继续按原资格处理。

## 账号材料通知

NOTI563 为账号材料独立容器：`mode:u8,count:u8,{itemId:u32,balance:u32}×count`。mode0清原容器，mode1逐项更新，余额0删除已有项。全量为空仍发送 `00 00`，超过255项先mode0再mode1分片；普通物品Main列表不承担该余额。选角时在会员1760/1761之后、Mileage427之前初始化，提交后在原库存回执守卫下发送实际差量。

NOTI1460/1461 分别更新账号/角色攻坚材料额度：`count:u16,{itemId:u32,valueA:u32,valueB:u32}×count`。匹配客户端 `0161D3B0/0161D4B0` 按三u32读取，`01618B90/01618C20` 以模板ID查找二元组，`014CCD60` 按原序格式化为 `%4d / %4d 个`。当前发送当周已获得/上限；二元组宽度与显示顺序已证，原生标签的业务含义仍待实机核对。CMD563和CMD1460/1461属于其他功能，不与同号NOTI混用。

### 充值票据与网页窗口

`CMD65 GEN_CERATICKET` 的请求正文为空，由既有货币模块处理，最低资格为WorldReady且已选角色，不在加载期签发。服务端签发只属于本账号当前Session的短期票据，回复不修改金币、点券、会员或游戏阶段；网页模态不冒充新的副本或user状态。畸形正文及不满足资格的请求保持未处理，不猜测失败错误码。

成功回复为 `kind=1/opcode=65`，正文 `01:u8 + ticketLength:u32 + ticketBytes[ticketLength] + ticketNumber:u32`，整数均为小端。票据使用非空ASCII字符串且字节长度小于64，不在声明长度内追加NUL。一个32字节票据的成功正文共41字节，不能以单字节 `01` 替代。公共命令分派器先消费成功标志，回调才读取字符串和末尾票据号。

当前票据为 `原生账号.随机Base64URL后缀`，后缀由16字节安全随机数编码为22字符；最长53字节。票据号为1–65535的随机值，仍按4字节发送。账号前缀仅用于定位既有在线Session，完整票据及号必须在原owner内验证；票据还绑定generation、选角epoch及角色ID。每Session只保留一张，有效期10分钟，到期等号拒绝；重新签发、换角、退出和接管使旧票据失效。验证和实际充值在同一个owner内完成，不另建在线账号副本、全局票据队列或数据库表。

客户端导航适配保持普通与黑钻两个路径，以`?ticket=<票据>&ticketKey=<无符号十进制号>`传递。内置HTTP复用原GM用例验票并回读账号，再启用模拟加值；票据请求不能附带另一套account/mode参数。无效、缺项或失效票据不得退回默认账号。充值监听默认HTTP23104，与管理网页开关独立，此能力不作为真实支付凭据。

- ACK65在 `0237C1CB` 注册到 `0234B520`；`0234B56F` 经 `03BE26C0 → 03BE25F0` 读取长度前缀的多字节串并转为UTF-16，容量为64。`0234B57B` 经 `03C85290` 再读取4字节票据号。

带模板期限的堆叠物品不能用 `expireTime=0` 强制永久：`027F85B1` 将条目offset56读入内部核心 `+70`，`028B3E71..028B3ECF` 再传给实例 setter `029B73D0`。setter 对 `-1` 在模板期限为正时回退到模板值，对0及正数保留实例值；期限消费者 `029B7090` 仍按模板资格启用期限分支，并用实例截止减客户端当前秒数，非正结果归零。本服对有限实例统一采用 `2145823200`（2037-12-31 06:00:00，UTC+8）作为安全下发上限，超出则钳位而非报错；商城/礼包的期限忽略开关也不改为0。相对期限先按最终截止钳位，再计算剩余秒，不能仅把持续秒数钳到同一个整数。原永久物品仍为0，旧存档仅在投影时截断，不回写原核心或详情，见[背包模块](../模块/背包与装备.md)。2099 Unix 秒超出当前有符号32位期限合同；匹配原码局部回放验证直接写入会得到0剩余秒，不把该结果称为完整UI或实机验收。

每周删除复用同一offset56绝对期限，不新增包字段。匹配ARAD 6.3.7.24的`04150DE8`登记`[weekly delete item]`为token`0x4744`；`04151B6C`减去该基值并经`04153EE8/04153EAC`两级表落到`04150DD6→04151B8A`，模板`+FEA`写启用1，`+FEC`保存且限制整数0..6。`03817EA1`消费该星期：0转7、再加`0xB6CB`取dstr，46796..46802依次为周一..周日，dstr300000144模板为“每%s凌晨6点删除。”；所以值0明确显示周日六点，不能解释成禁用。实际期限仍由`028B3ECF→029B73D0`从核心安装，`029B755A`写实例`+530`；每周标志使`029B70EF→029B71E4`进入期限分支，`029B725E`读取`+530`减当前秒数，非正归零。服务端沿既有UTC+8政策冻结真实截止；显示文本本身不证明团本通关次数、购票盒或账号额度也在此时重置。以上为原文件静态消费者与匹配dstr证据，不是客户端执行/实机验收。

PVF模板日期本身也须在客户端的32位时间范围内。`[expiration date] 2040-12-31 06:00:00`在匹配ARAD的实际资源对象中解析为`-1`，不能用服务端把实例期限夹到2038年来证明客户端可用。尤其宠物的`02948770`优先返回EQU模板`+456`中任何非零绝对日期，包含这个无效的`-1`；`0294B160`再与客户端当前秒数比较并判为到期，即使物品条目已提供正的剩余秒数也不能覆盖。修正这类PVF日期时须同时核对进化产物，客户端须重新加载资源；不通过取消使用门禁、改UID或补成功ACK绕过。

强化、附魔升级、锻造使用三个不同字段。NOTI13 的 `023BE97C..023BE989` 调用 `027F7AC0` 将123B原始条目转为内部核心：`027F82D5` 读取offset10并调用 `027EDF50`，其中 `027EE0C9` 用 `0x1F` 提取强化存入内部 `+8`，高3位另存；ACK80 `02373D90` 的成功分支在 `023744EA..0237459D` 更新同一 `+8`。offset18在 `027F834C` 存入内部 `+20`，是独立的附魔卡升级字段。offset87在 `027F860F` 以有符号byte读取并存入内部 `+78`；ACK438 `02847B60` 在 `02847F2E..02847FB6` 将锻造结果写入同一 `+78`。因此发放装备时固定强化范围为0..31、非负锻造范围为0..127，随机强化哨兵255仅留在资源定义中，不能直接写入实例。地址绑定本页匹配客户端构建，现有字段序列与条目长度不变。

## 时装与宠物列表

`InventoryPackets.SpecialFull/Creatures` 与 `ItemListProtocolWriter` 使用下列合同。RAW 均包含自身的 `length:u32`；清槽 itemId=-1 的处理发生在资源扩展读取之后。

## 武器幻化与皮肤仓库

匹配客户端 `013EB970` 发送 `CMD1599 MAKE_SKIN`，正文8B：`skinType:u8 + recipe:i32 + list:u8 + slot:u16`。武器类别为4，配方、产物和材料取 `skin/weaponskincontainer.etc`。`013EEE90`为制作窗口1490注册 `013ED0C0`；成功回调 `013ECE20`只更新制作表现，不再读取附加产物，也不在本地扣源，因此成功正文为 `01`，失败为 `00 + error:u16`。服务端在提交后先发实际源、材料和产物差量，再发成功ACK。

原生制作回调已确认的特殊错误：93/212为有限期限或不可分解（dstr100007182），106为神奇模具当前角色佩戴资格（100007149），116为外观已入库（100007186），204为不可交易外观仓库容量（100007187），20为已拥有同种不可交易外观（100007188）。3等状态拒绝显示100007138。未闭合的缺料、产物容量原因使用已确认的状态拒绝，并在服务端记录原因，不照搬其他opcode的错误码含义。

外观券是普通123B堆叠记录，但offset14的 `EnchantCardId:i32` 承载原武器编号：`027F7AC0`将该值放入扩展核心的加密字段+24，`028B3E30 → 020C6300`写入运行时物品+692，并更新来源名称及图标。`028B4D00`按 `[add skin storage] 40000`识别武器外观券。此处不发送装备品级代替数量，不把来源填入透明装扮的来源表；其他物品的真实附魔字段不变。

右键使用是`CMD515/action199`，不是CMD44。`040D4F60`将`[add skin storage]`映射为199，`028BA3F0`发送19B：`slot:u16 + list:u8 + reserved:u32=0 + action:u32=199 + arg1:u32=0 + arg2:u32=0`。`028C0AE0`成功读`slot:u16 + list:u8 + action:u32`后自行扣一张；`028C73BD`注册199到`028C0930`，回调只按模板声明打开入库结果，不额外读取网络正文。因此成功ACK为`01 + slot:u16 + list:u8 + 199:u32`；失败为`00 + error:u16 + slot:u16 + list:u8 + 199:u8`。提交后先ACK，再同步目录及最近加入，不能额外发送源数量或获得差量造成重复消费。

## 丢弃 CMD18 与整理 CMD20 的 protobuf

`0041CA50` 只对18/20返回true；公共ACK分派 `028F85F6..028F8761` 因此跳过它们失败时的公共u16错误码。不能把其他CMD的 `00+error:u16` 套到这两种响应。

## 装扮预设 CMD1593 CMD1594 CMD1595

装扮预设使用0x0639–0x063F区间的五个包。三笔C2S都没有专用成功/失败ACK：成功只回放已提交状态——改名、新建、选择（含装扮不变、仅当前槽变化）、交换与扩容回0x063D整表，其他提交带来的预设内容变化回0x063F单条记录；解析或业务失败只写`avatar_preset_*`日志、一个包都不回，客户端表现为点击无反应，不能为此补一帧通用成功。

C2S名称是`slot:u8 + byteLength:u32 + name:CP936`，`byteLength`是名字字节数（小端u32）且必须与剩余正文完全一致；客户端写入侧为`FUN_0095ee80 → FUN_03bdf8e0 → FUN_03c783b0/FUN_03bdf850`，不带结尾NUL。实测正文`00 03 00 00 00 31 31 31`（“111”）与`00 0B 00 00 00 D0 C2 D7 B0 B0 E7 D4 A4 C9 E8 33`（“新装扮预设3”，11个CP936字节）。`byteLength=0`是合法的“恢复默认名”，客户端显示自己的默认标签（字符串0xB743），不是畸形请求；非空名才拒绝控制字符、非法CP936序列（含不完整双字节）和首尾空白，名称最长127个字符（CP936不超过254字节）。S2C名称写成`nameLength:u32 + CP936字节`，不带结尾NUL；客户端读取侧`FUN_03be26c0 → FUN_03be25f0`先读u32字节数并原样复制字节，显示侧按CP936解码（写成UTF-16LE字节会被当作GBK显示成乱码，例如“装扮”的UTF-16LE字节显示成“nb”）；长度0或≥0x100时按空名回退且不消费名字字节，名字长度前缀缺失或与名字字节数不符会让后续部位整条错位，必须逐记录精确写出。三个槽位字段都必须小于提交时的容量，选择与交换不接受尾随字节。1593在空槽上按当前穿戴创建快照（按部位升序保存实例UID、模板、`clearAvatarId`、染色与五孔），已有槽只改名称并保留原部位。改名与新建都回0x063D整表：客户端0x063F只覆盖缓存、不重绘行文字，只有整表会重绘六行名字；整表按`0..capacity-1`补齐占位，客户端缓存里每个槽都存在，不会走到未知槽的崩溃分支。整表回放同时把客户端当前行与名称框恢复到已应用槽（见1594说明）。

1597的首字节`activeSlot`是已应用槽位，`count`决定客户端绘制的预设格子数：服务端按`0..capacity-1`逐槽发记录，已保存槽发真实名称与部位，未使用槽发`slot + nameLength:u32=0 + partCount:u8=0`的空名零部位占位。占位只在构建回包时按落库状态合成，不写入`avatar_preset_state`，因此不会覆盖已保存的预设；客户端把空名替换成自己的默认标签。空槽仍可用1593按当前穿戴创建；1594在没有记录的空槽上按空预设成功处理（卸下全部当前穿戴），与客户端“首次选择新橱窗解除所有装扮”的语义一致；1595在源槽没有记录时仍拒绝。

1594由服务端按保存的实例UID重新穿脱，客户端正文只有槽位。任一部件的UID已不存在、模板编号变化或不再是时装时整笔拒绝，不穿一半；随后按UID先穿入目标部位，沿公共移动规则原子互换已占用部位，空部位穿入释放背包格，最后卸下多余装扮。满包但最终空间足够时仍允许成功；最终空间不足或任一步资格不符则整笔不提交。成功后先发库存差量（先装扮列表、后装备列表，装备变化再补本人Actor→Player），随后总是回0x063D整表：客户端的应用按钮`FUN_02852420`只发0x063A。整表解析器`FUN_008407B0`将首字段`activeSlot`写入模型已应用槽与浏览槽，并投递`0x18=activeSlot`；`FUN_028563F0`据此刷新名称、高亮和应用按钮。`FUN_0083E870`比较浏览与已应用槽：相同则显示当前穿戴，不同才经`FUN_02854D10`生成预设纸娃娃（部位缺失写-1沿用当前穿戴）。即使两套使用完全相同的实例、仅当前槽变化，也必须回整表。首字段不能写容量，否则越界时`FUN_0083E940`回槽0；旧“容量字段、固定跳1号”的解释不适用。选择会按这次实际穿戴重新采样该槽部位，凡提交后预设内容与提交前不同的槽仍按0x063F补发（选择重采样、C2S19穿戴/卸下/同模板实例互换、穿戴中时装的CMD498漂染走同一条判定，按槽逐条发，内容相同的槽不发），该包只覆盖缓存、不重绘。选择成功后角色行记录当前橱窗`ActiveSlot`；此后C2S19的穿戴/卸下（含同模板实例互换）与CMD498漂染都在同一库存事务把最新部位回写该槽，不需要额外的保存/应用包；1595交换时当前橱窗随内容换到新槽号。选角时若槽0不存在，服务端按当前穿戴补建1号橱窗后再发1597。

1595只改预设表：目标槽为空时把源记录移到空洞，两槽都有内容时交换完整记录，同名槽是无变化成功；时装实例不移动。它只回0x063D整表。

就绪包序固定为`MarkReady`之后先发0x063D、再发每周地下城720/721；共享`Select`读取器和自定义读取器都先消费1597。该帧恢复已应用槽与预设缓存、不打开窗口，缺少时窗口为空且点击不发包。扩展券走CMD515 action216：成功先回ACK515由客户端自行扣一张，再发0x063D整表；失败ACK515带错误码19且不扣券，错误码0会让客户端静默、容量已满时完全没有提示；源槽按已确认槽处理，不重复发NOTI14。重连由角色行的`avatar_preset_state` JSON恢复整表。业务规则见[装扮预设](../模块/背包与装备.md#装扮预设)。

## 原生史诗交换 CMD1569

休亚的炼金术实验室确认窗口发送 CMD1569 `EXCHANGE_EPIC_ITEM`（0x621），正文固定12B：`sourceSlot:i32 + sourceItemId:i32 + targetItemId:i32`。实机抓包证明首字段是来源实例的主背包槽位：三种来源分别送 18/19/9，与库内 100250656/100130610/101000783 的 Main 槽位逐一对应，来源编号则排在第二字段。发送入口 `013E0920` 连续写三个u32；构块 `013E27D0` 按 `[main+0x398, 来源编号, 目标编号]` 排列，两个编号都经物品包装对象的 `vtable+0x28()` 取出，无效物品为 -1，因此 `-1` 只是来源无效时的取值而不是常量。服务端优先按槽位定位来源实例，槽位为负或该槽位不是同编号合格实例时退回主背包最小槽位；不携带UID或期望次数。

回执同opcode 0x621，正文为 `success:u8 + code:u16`。确认窗口构造 `013E2000` 末尾 `013E2198..013E219D` 把 `013E09F0` 注册到0x621，静态交叉引用只有这一处；该函数签名是 `(ctx, char success, u16 code)`。失败码7/0x16/0x17/0x5F/0xD6映射到客户端本地化文案，其余走通用错误提示。服务端成功时只发1B成功标志，失败再补u16，与图鉴、仓库等可选错误码回执同形；当前使用4（请求或资格）、10（金币）、17（容量），未逐条核对客户端文案。

客户端交换实例位在123B条目offset119（内部核心 `+0xC1`）：`027EDE30` 取bit0作为交换资格，`027EDE20` 取 `(byte>>1)&0x1F` 作为已交换次数。物品信息面板 `015908C0` 与描述构建 `03849B50` 只在资格位为1且次数小于4时显示交换入口，次数达到4改用另一种颜色提示；这是客户端4次上限的直接来源。服务端按该位判来源资格（bit0=1、bits1..5<4）并读取次数计价，实例位语义见[背包与装备](../模块/背包与装备.md#原生史诗交换)。0x624 `REWARD_EPIC_EXCHANGE` 属于窗体0x157/0x158/0x15a的另一模块与另一段代码，不是本功能回执，保持未注册。

## 装备传承 CMD1688

### UDP140副本商人替换

匹配ARAD `0162AD00` 通过原生发送器vt+8以 `140,2` 初始化消息，经vt+48写两个i32，再经vt+36写四个u8，调用 `036B1560(1,0)` 提交。已核对的内层业务正文为12B：`npcId:i32 + nameColor:i32 + color0:u8 + color1:u8 + color2:u8 + color3:u8`。名字颜色由 `01624BD0` 按好感百分比和颜色表计算，四通道值由 `016239B0` 读取。无候选时NPC编号为0；不能把-1或空正文当成相同回退。这里的12B不包含原生消息头或当前服务端Native关联外层，不可直接作为TCP NOTI140发送。

客户端原生分发表 `036CC70C + 140*4 → 036C9655` 以vt+0x60读取两个i32，以vt+0x54读取四个u8；`01622940` 查找或取得默认1000商人对象。非零NPC经 `02A57010` 替换定义，`01624E30` 应用四通道颜色，`02A44230` 更新名字颜色；0分支恢复默认对象，末端同步已有商店窗口。普通结算商人创建 `039F57C0` 在默认商人和单人/队长相关分支调用该发送流程；完整触发资格仍须结合实际结算帧验证，不能把其它模式的同名窗口当成普通副本消费者。

内层消息头为 `kind:u8 + opcode:u16 + crc:u32`，随后是上述12B正文，特定房间消息还带前置的X/Y两个字节。CRC使用普通游戏CRC多项式 `0x4DB89129` 但只计算明文正文；匹配构建的UDP密钥初始化值由3084777加UDP枚举末值202得到，经 `0369FC00` 的三轮LCG生成 `0x52FEC36E`。发送对每字节异或低字节0x6E后右旋3位，接收反向；不使用登录IP或Native关联值代替该密钥。

## 怪物卡片升级 CMD603

卡片加工器升级使用category=1/opcode603 `UPGRADE_CARD`，与NOTI603副本限时、CMD1122卡片复合区分。匹配客户端两个发送入口 `00946840`、`01441C50` 写 `目标container:u8 + 目标slot:u16 + 材料数:u8 + (材料container:u8 + 材料slot:u16)×N`，container均为0（Main），请求不携带编号或数量；每个槽对应一张，正文严格为 `4+3*N` B，N为1–4。正常加工器四个输入栏包含目标，最多三张材料。跨容器、越界和尾字节均拒绝。原生选择栏`009456A0`调用`029DF1F0`每次从源堆移入一张，同时记录原Main槽；因此重复材料槽及目标同源材料都是合法张数，服务端按源槽累计校验库存，目标另留一张。

窗口回调 `00948160`、`014442E0` 在公共成功字节后只读取 `result:u8 + itemId:i32 + level:u8`，成功正文严格7B（含首字节1），result非零展示升级成功，0展示概率失败，level为该次实际等级。业务拒绝沿公共 `0:u8 + error:u16`，当前22为通用失败。该ACK不扣卡也不写背包槽，服务端提交成功后先发ACK，再发NOTI14真实差量。

NOTI14的123B条目由 `027F7AC0` 转换：wire条目+0x12对应core+0x20，即 `EnchantUpgrade`；物品初始化 `028B3E30` 经 `028B40C3→029B7ED0` 写入等级，ACK结果对象也使用该字段。`009420B7` 预览下一等级，`009422F9` 用附魔表项数减一检查上限；`00940AD0→03FB7C00` 按目标稀有度和材料数减一读取 `upgrade infos` 百分率，`009408F0` 校验材料同稀有度。客户端 `009464A0` 在发送后清空加工器选择栏，不代表库存消耗成功。单张扣除、失败扣材和堆叠分离属于服务端库存规则，不能仅凭ACK字节声称已由客户端证明。业务及验证入口见[怪物卡片升级](../模块/背包与装备.md#怪物卡片升级)。

同模板既有堆叠对象不会重新初始化卡片等级：`023BF55D..023BF5A5`查槽并仅在模板变化时删除旧对象；`023BF65D..023BF67F`更新数量，`023BF784..023BF789`随后跳过完整初始化。因此升级后仅发送含新等级的普通差量会留下旧卡片属性。同模板堆叠卡片的 `EnchantUpgrade` 变化时，先发NOTI14的该槽空条目（itemId=-1），再发实际提交的完整差量；`023BF5CC..023BF5E4`删除旧槽，回填沿新对象初始化写入等级。两次通知均受原库存提交回执的owner、选角、阶段及revision门禁保护；纯数量变化不额外重建。
