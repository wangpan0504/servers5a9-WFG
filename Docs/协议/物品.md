# 物品协议

本页维护 匹配客户端 实体条目、Actor/Player 装备、CMD18/19/20、物品锁、钱包、仓库与史诗图鉴的 wire 与消费者证据。业务、持久化及验收边界见[背包与装备](../模块/背包与装备.md)；商店/修理/分解等交互合同见[物品交互参考](物品交互参考.md)。

## 条目读取边界

普通标量分别按 u8、u16、u32 读取。RAW 字段为 `length:u32 + bytes[length]`，读取时同步推进游标并扣减剩余长度；长度为 0/4/8/30 时分别消费 4/8/12/34B。

NOTI13/14 的普通实体条目均复制 123 字节。服务端自测和 TCP 回归不代替客户端显示与装备属性效果验收。

普通创建列表只有领域槽位标签与模板ID，没有数量、背包索引或实例属性；这些CHR也未声明普通初始消耗品或金币。`[inventory limit]` 不能用作背包格子数量。`[pvp private create equipment list]` 属于另一套声明，不用于普通创建；离线Lv95准备也不由本表推导装备。

领域槽位标签不能代替Actor/Player的wire数值槽位；装备脚本 `[equipment type]` 后的数字同样不能直接作为该索引。模板耐久、rarity、grade与attach type不证明实例当前耐久、随机品级、强化、绑定、唯一ID或客户端编码的默认状态。当前明确的服务端创建策略为已穿戴、满模板耐久、品级 seed=999999998、无强化/附魔/期限；其他扩展字段为零。模板不存在、部位或职业/等级/技能资格不符则拒绝创建，不写部分物品。

这些资源足以确定普通创建的模板选择，创建角色与初始物品须同事务提交。存量角色是否补发、补发哪些实例属于独立迁移策略，不能由CHR推导；若接入补发，须有持久化标记或唯一约束，避免重启、重登或重复迁移再次赠送，并保留既有generation/revision、任务与技能。专用Lv95角色单独处理，不能在普通创建初始化或迁移中无条件套用本表。

## 容器与普通条目

当前容器编号为 Main=0、PersonalCargo=2、Equipment=3、AccountCargo=12。槽位编号、可用范围及类别规则由[背包业务文档](../模块/背包与装备.md#移动穿脱删除与整理)统一维护。

`NOTI13 Main = list:u8 + expansionSlots:u16 + count:u16 + entry[123]*count`，expansionSlots 直接发送扩展格数0/8/16/24；列出存在的实体和全部15个货币虚拟槽，按 slot 升序。`NOTI14 = list:u8 + count:u16 + entry[123]*count`，没有扩展字段。清空实体条目为目标 slot、itemId=-1，其余零。数量虚拟槽使用自己的 itemId、value=余额，零余额仍保留该 itemId，不分配实体 UID。仓库全量的专属头见下节，差量继续使用 NOTI14。

Main读取链为 `023BDF17` 读u16、`023BDF38` 右移3位，得到0–3档；经 `02873370` 的事件10、`02873FAB → 039835B0` 保存扩展次数。`039837F0` 按该次数累加扩展负重配置。24格须编码为 `18 00`，不能编码为 `00 03`：后者表示768格，客户端解为96档并读取配置外的数据。有界原码回放覆盖0/8/16/24及错误768输入，止于右移后的 `023BDF3B`；静态链路及崩溃栈确认越界原因，不将此前缀作为整个UI验收。

| 信令 | body及处理 |
|---|---|
| C2S63 CERA | 空body，选角前后均查询本账号余额 |
| NOTI53 CERA | `flag=1:u8 + cera:i32 + tokenCera:i32 + happyTokenCera:i32`，共13B |
| C2S980 UPGRADE_CARRY_GOLD | 固定14B，offset13为请求下一阶段，其余13B保留为不透明上下文，不作为服务器余额或费用 |

### 实体字段

实体字段由[ItemListProtocolWriter](../../Server/DfoServer/Network/Builders/Inventory/ItemListProtocolWriter.cs)唯一排列：[ItemCore](../../Server/DfoServer/Game/Inventory/Models/ItemCore.cs)保存类型化属性，不保存网络 blob。offset 均相对123B条目：

| offset | 字段与宽度 |
|---|---|
| 0 / 2 / 6 | slot:u16 / itemId:i32 / value:i32；装备 value 为品级 seed，堆叠物为数量 |
| 10 / 11 / 13 | attr:u8 / durability:u16 / sealFlag:u8 |
| 14 / 18 / 19 / 20 / 22 | enchantCardId:i32 / enchantUpgrade:u8 / amplifyType:u8 / amplifyValue:u16 / marker16:i32 |
| 26 / 27 / 31 / 35 | Extension26:u8；Extension27/31/35 各 u32 |
| 39 | Chronicle count:u8，最多2；40/44为两个ID；48/49为两个job，50/51为两个grow，52/53为两个equipmentType，54/55为两个number |
| 56 / 60 / 61 / 65 / 69 | expireTime:i32 / emblemCount:u8 / emblem1:i32 / emblem2:i32 / rune:u16 |
| 71 | Random count:u8，最多3；72–74为三个type，75–77为三个value1，78–80为三个value2 |
| 81–86 | RandomState/ChangedIndex/ChangeState 各u8，RandomChange为3个u8 |
| 87 / 88 / 89 / 90 | GenuineUpgrade/EmancipateLevel/TradeRestriction各u8，Extension90:u16 |
| 92–96 | Extension92/93、RemainUseCount、SortLockFlag、EquipmentLockId，各u8 |
| 97 / 101 / 109 / 110 | Extension97:u32 / GuardianGemKeys:u64 / Extension109:u8 / Extension110:u32 |
| 114 / 118 / 119 / 120 / 121 | Extension114.Value:u32、Flag:u8；Extension119/120各u8；Extension121:u16 |

未确认业务含义的字段保留 Extension 名称，不能因宽度已确认而自行启用效果。ctor `005E5CE0` 初始化123B结构，扩展 ctor `03DAAB70` 的5B顺序是 DWORD 后 byte；不是按持久 record 参数排列。时装、宠物等还可能在基础条目后读取额外资源/detail，当前不能只靠123B开启它们。

强化、附魔升级、锻造使用三个不同字段。NOTI13 的 `023BE97C..023BE989` 调用 `027F7AC0` 将123B原始条目转为内部核心：`027F82D5` 读取offset10并调用 `027EDF50`，其中 `027EE0C9` 用 `0x1F` 提取强化存入内部 `+8`，高3位另存；ACK80 `02373D90` 的成功分支在 `023744EA..0237459D` 更新同一 `+8`。offset18在 `027F834C` 存入内部 `+20`，是独立的附魔卡升级字段。offset87在 `027F860F` 以有符号byte读取并存入内部 `+78`；ACK438 `02847B60` 在 `02847F2E..02847FB6` 将锻造结果写入同一 `+78`。因此发放装备时固定强化范围为0..31、非负锻造范围为0..127，随机强化哨兵255仅留在资源定义中，不能直接写入实例。地址绑定本页匹配客户端构建，现有字段序列与条目长度不变。

品级seed由 `03FA9940` 及跳表 `03FA9994` 映射百分比：999999993→20%、999999995→80%、999999996→40%、999999998→100%、999999999→60%；当前普通创建默认999999998。该映射只证明实例seed的含义，选择礼包 `[booster equipment grade]` 数值到seed的规则仍未确认，不直接套用品级序号或稀有度。

## 时装与宠物列表

`InventoryPackets.SpecialFull/Creatures` 与 `ItemListProtocolWriter` 使用下列合同。RAW 均包含自身的 `length:u32`；清槽 itemId=-1 的处理发生在资源扩展读取之后。

| 通知 | body |
|---|---|
| NOTI13 Avatar | `1:u8 + expansion:u16 + count:u16 + avatarEntry[count]`；当前 expansion=105，加基础105格后为210格 |
| NOTI13 Pet | `7:u8 + count:u16 + entry123[count]` |
| NOTI14 Avatar | `1:u8 + count:u16 + avatarEntry[count]`，包括清槽条目 |
| NOTI14 Equipment | `3:u8 + count:u16`，实际时装使用 avatarEntry，其余及清空槽使用 entry123 |
| NOTI105 Creature | `count:u8`，随后每项 `uid:i32 + satiety:u8 + mode:u8 + experience:i32 + [mode1Field0:u8 + mode1Field1:u8，仅mode=1] + level:u8 + nameLength:u32 + name:CP936 + tailFlag:u8` |

AvatarEntry = `entry123 + RAW30 + RAW4`，合计165B。RAW30为五组 `socketType:u16 + emblemId:i32`；RAW4为两项染色 `color1:u16 + color2:u16`。永久时装的 entry.value 为0，有期限时为详情剩余秒数，不能发送持久化详情 UID。宠物的 entry.value 则为详情 UID，entry offset22 的 Marker16 为剩余秒数；宠物装备、消耗品仍使用各自普通核心值。宠物名称上限30个 CP936 字节。NOTI105 默认条目16B，加通知count共17B，模式1额外2B。

消费者依据：NOTI13 在 `023BDFEA` 读取时装扩展值，`02870DD0 → 02852980` 更新容量，`028529D2` 增加基础0x69格；列表选择 `029089D0` 将1/7分别映射到时装/宠物容器。条目后 `023BE747/023BE775` 与 NOTI14 `023BED95/023BEDC3` 调用 `028F2A30/028F2A80`：list=1 无条件消费两块，list=3 根据资源类型 `02938540` 判断时装（resource+500≤0B）。`03FA9AE0` 对五个孔位初始化，`028F2E40` 仅拷贝核心已有徽章，不追加读包。

宠物通知注册为 `023CCC3D → 0239F760`、type=0x69。count 在 `0239F794` 读取；每项 `0239F7AA/B4/BE/C7` 读取4/1/1/4B，mode=1在 `0239F7D9/E3` 读两字节；`0239F7F0/7FE/808` 依次读等级、Dstr及尾字节。宠物资源类型为0x1A（26），`027EE270` 将 entry 的 Marker16 投影到宠物内部字段；不能套用其他版本的25。

Player 时装在普通26B前段之后插入 RAW30/RAW4，因此零其他扩展时每件133B；宠物在该处插入剩余秒数:i32，因此每件95B，宠物装备仍为91B。读取落点为 `023C3CB1/3CD9` 与 `023C3E37`。前段 unknown5 对时装投影 ClearAvatarId（非零）或 SealFlag；slot9且 ClearAvatarId 为时装资源时，在附魔字段之前还会消费 RAW30（`023C3C35` 后的资源分支）。Actor/名册的4B资源块投影时装染色，ClearAvatarId 放入原 unknownC；slot9的同类分支在附魔字段前消费 RAW30。普通条目合同不变。

登录在本人 Player 之前发送宠物详情，Avatar/Pet 全量在仓库之后、锁恢复之前发送。提交后宠物变化先同步详情，再发容器差量和必要的 Player；时装/Pet 仍使用 CMD19 和现有丢弃/整理入口。原码的字段消费、C#独立读包断言及 TCP 持久化检查不代表宠物成长、染色操作或客户端界面已验收。

## 勋章列表与守护珠镶嵌

匹配 S5A9 的 `029089D0` 在 `02908A2B..02908A36` 将列表38路由到勋章容器；NOTI13 的 `023BE283/023BE285` 用98格和列表38初始化容器。它沿用共同 count:u16 和123B普通条目，不带 Main/Avatar 扩展值或个人仓库尾部。业务分区为勋章0–48、守护珠49–97，category 分别为12/13，移动、删除、整理和锁仍走原公共命令。勋章穿戴部位为32：`02971AE3` 比较资源 equipment type=0x20 后应用守护珠字段，不能使用其他版本的部位31。

| 信令 | body |
|---|---|
| NOTI13 勋章全量 | `38:u8 + count:u16 + entry[123]*count`，空列表也是3B |
| NOTI14 勋章/穿戴差量 | 公共 `list:u8 + count:u16 + entry[123]*count`，清槽 itemId=-1 |
| CMD831 USE_GEM | `medalItemId:i32 + materialSlot:u16 + gemItemId:i32 + socket:u8`，共11B |
| ACK831 成功 | `1:u8` |
| ACK831 失败 | `0:u8 + error:u16` |

发送端 `0127164E..01271699` 先写831，再通过 `03BDF780/03BDF750/03BDF780/03BDF720` 写入上述四字段；覆盖确认路径 `01271732..01271781` 使用同一布局。ACK 注册 `0237C0CE → 0234B1C0`，成功分支不再读取包体，只更新界面；失败在 `0234B274` 按u16比较0x12并取字符串0xADDC，其他失败走通用分支。无效目标/孔位用4，材料缺失或其他孔同属性用0x12。

普通条目offset101的8B及 Player 对应RAW8保存四个小端 key。`02971B07..02971B57` 循环4次读取u16，0为空，其余经 `movsx` 扩展后加89999；因此有效新 key 范围为1..32767。该字段随完整核心持久化，覆盖镶嵌不改其他扩展。提交后先发成功 ACK，再发穿戴与材料列表的绝对值差量，最后刷新本人/同屏穿戴。以上是匹配发送、消费静态依据及 C# TCP 合同，未执行完整客户端 UI 或该入口的原机器码回放。

## 名册与 Actor 装备摘要

`USERINFO subtype0` 和名册 subtype2 共用消费者 `02675DE0`。先 count:u8，每条普通装备25B：`slot:u8 + itemId:i32 + RAW[4] + packed:u8 + unknownA:u8 + unknownB:u8 + unknownC:i32 + unknownD:i32 + unknownE:u8`。RAW[4] 包含4B长度前缀及4B数据。

必经 helper 为 `02675E84 → 028F2A80(mode=2F) → 03BE25C0`，直接 reader 位于 `02675E5C/65/9D/AE/B9/F1E/F4C/F57`。packed 拆成 `>>1` 和 `&1`；slot12有武器分支。slot9且unknownC非零会按资源条件读取额外RAW30，当前普通部位不进入。

[EquipmentProtocolWriter.Appearance](../../Server/DfoServer/Network/Builders/Inventory/EquipmentProtocolWriter.cs) 输出普通模板、部位与零资源扩展；当前属性映射使用 Attr、增幅标志、GenuineUpgrade、EmancipateLevel、Marker16、EnchantCardId/Upgrade。初始装备这些属性全部为零；强化与锻造的实例字段见上文，实际非零显示、同屏特效及装备属性效果仍需对应实机验收，不把穿脱用例扩展为强化效果验收。

名册每角色原70+姓名字节数，再加25×穿戴数；Actor原243+姓名字节数，再加25×穿戴数。五件初始装备增加125B，不影响 name 的 CP936 长度合同。

## Player 普通装备

`USERINFO subtype1` 由 `023C3A90` 消费。普通条目先26B：`slot:u8 + itemId:i32 + value:i32 + attr:u8 + durability:u16 + unknown3:u8 + unknown4:u8 + unknown5:i32 + enchantCardId:i32 + enchantUpgrade:u8 + amplifyType:u8 + amplifyValue:u16`。两个资源属性当前为零，unknown5 当前投影 SealFlag；非零含义待对应封装/特殊装备流程确认。

资源 helper `028F2A30/028F2A80(mode=3)` 只对特定时装资源插入RAW30/RAW4，资源对象+500<=0B；资源enum1A还额外读u32。这些条件枚举与本版普通装备区分，不能用另一个版本的宠物编号替代。普通装备后续为：

1. Chronicle count:u8，每项 `id:i32 + job/grow/equipmentType/number:u8`，8B。
2. expireTime:i32；emblemCount:u8，每个 emblem:i32。
3. Rune:u16，由 `023C3F7C → 024B2D60` 的嵌套读包消费。
4. Random count:u8，由 `023C3F88 → 022913F0` 消费；数量零仍占1B。每项为 `type/value1/value2:u8`，交错排列。数量非零后读 `state:u8 + changedIndex:u8`；changedIndex不是FF时再读 `changeState:u8 + changedType/value1/value2:u8`。与123B结构的固定数组不同，不能省略这段或无条件补六个状态字节。
5. 上表87–96的10B尾部。
6. 五个RAW块，顺序4/8/4/5/4B，第二个与第三个之间另有一个u8。对应 `023C4064/4078/4095/40A1/40AD`；RAW数据与Core的97/101、110、114、119–122对应。

普通初始条目91B，非空 Chronicle/Emblem 每项分别加8/4B；Random非空增加3×数量，再加2或6B条件状态。整组装备后仍需 `scalar:u32 + extraCount:u8 + i32[extraCount]`，不能把这5B并入最后一件或省略。Player总长=`167 + 6×技能数 + Σ装备条目长度`；初始五件为`622 + 6×技能数`。所有字段见统一 Writer；原始读取、扩展对象宽度及 RAW 原码对拍不代表未知属性效果已完成。

必须追踪嵌套helper的读包副作用。省略Rune和Random数量会使每件少3B，普通零属性下第二个RAW长度被错读为2048，继续读取即可能在第三个RAW的memcpy越界；整体长度断言或单独RAW函数对拍不能发现这个缺口。当前C#回归按上述嵌套消费顺序检查五件初始装备及非空随机属性，不只检查Writer计算的总长。

## 移动与穿脱 CMD19

普通发送出口 `021586E9..0215883A`、`029D3826..029D3967`、`029CB13A..029CB269`、`029DA3E3..029DA71C` 使用 category1/opcode19，完整body28B：

| offset | 字段 |
|---|---|
| 0 / 1 / 3 / 7 | sourceList:u8 / sourceSlot:u16 / sourceItemId:i32 / count:i32 |
| 11 / 12 / 14 / 18 | targetList:u8 / targetSlot:u16 / targetItemId:i32 / targetCount:i32=0 |
| 22 / 26 / 27 | actor:i32（普通路径-1或本地索引0）/ flag0:u8=0 / flag1:u8=0 |

count=0整件/整堆，穿脱数量1，拆分为指定数量。服务端数量兼容规则为：普通装备一律1，堆叠的非正数或超出现有数量归一为整堆。同模板合并不截少本次数量；整件/不同模板整堆交换成功的moveCount为1。数量归一及锁策略属于业务规则，不能反过来当作客户端已实发这些边界值的证据。两侧 itemId 均为该槽的模板编号，空格为0，不是 Core.Value 的品级 seed/堆叠数量，也不是实例 UID 或请求 ID。发送端 `029DA48B..029DA4D6` 和 `029DA5C5..029DA613` 从物品资源 `+0x14` 取编号；堆叠路径同样读取资源编号，数量另行编码。

source/target 表示请求中的第一/第二格，不能直接当作物品移动方向。卸装时客户端仍将 Main 放在前、Equipment 放在后：第一格为空时，服务端从第二格取出物品放入第一格。必须先按原顺序核对两格 itemId，再解析移动方向；否则重复的穿戴请求可能被误解为卸装。两格均有物品时按兼容属性合并或整件交换，双向检查容器范围与穿戴资格；保留完整核心及 UID。

实收卸装请求：Main9为空，Equipment16为模板12400，数量1；该装备 Core.Value 为999999998，不能用于请求校验。

```text
C2S19: 00 09 00 00 00 00 00 01 00 00 00 03 10 00 70 30 00 00 00 00 00 00 FF FF FF FF 00 00
S2C19成功: 01 00 09 00 01 00 00 00 03 10 00
```

装备从背包拖入快捷栏也会把空格放前面。实收Main21的模板18400拖至Main3时，count=0表示整件；不能因快捷栏曾只允许消耗品而拒绝。该请求及成功格式已纳入C# TCP回归，并验证重选/服务重启后的完整列表仍保留快捷栏位置：

```text
C2S19: 00 03 00 00 00 00 00 00 00 00 00 00 15 00 E0 47 00 00 00 00 00 00 FF FF FF FF 00 00
S2C19成功: 01 00 03 00 01 00 00 00 00 15 00
```

ACK注册 `0237BF54 → 02372610`。成功11B=`01 + sourceList:u8 + sourceSlot:u16 + movedCount:i32 + targetList:u8 + targetSlot:u16`；失败5B=`00 + error:u16 + sourceList:u8 + targetList:u8`，列表追加消费见`02373888`。普通移动及穿脱保留原请求顺序；Main→Equipment 消费分支 `02372E81 → 029D0880` 用两格处理穿脱，不能把卸装ACK改成反向列表顺序。可堆叠物品跨容器自动选格则回复实际移动方向和最终槽位，不能仍回显未使用的请求空格。`02372683..023726B5` 读取成功字段；任一列表为2/12时经 `02372A91 → 023734D1` 进入仓库存取分支，按ACK列表/槽位调用 `029089D0` / `02908AC0` 定位容器和物品，`02373517..0237353A` 将源槽、数量与目标槽交给转移调用。该证据确认字段用途，不代替客户端界面验收。提交后才回成功，再发14差量，穿脱另刷新本人Actor/Player及同场景Actor。

当前普通物品校验拒绝使用 error23=`17 00`，`02373AB2 → 0x89BD` 显示“无法移动该物品”。error1在 `02373AC3` 的普通城镇分支取 `0xADB4`，显示“当前地区无法进行移动”，仅保留给会话/场景拒绝；error4取`0x5598`为“金库空间不足， 无法放入物品。”，不能当通用背包错误。文本来自匹配 dstr.dat，不将其他协议的同号错误码套入此响应。

## 丢弃 CMD18 与整理 CMD20 的 protobuf

`0041CA50` 只对18/20返回true；公共ACK分派 `028F85F6..028F8761` 因此跳过它们失败时的公共u16错误码。不能把其他CMD的 `00+error:u16` 套到这两种响应。

C2S普通丢弃与整理使用 `length:u32 + protobuf[length]`，发送链 `03BDFC70 → 03BDFA20 → 03BDF7E0`。技能材料扣除的CMD18另在消息后写 `clientState:u8`，不计入length；该状态字节原样保留，尚不作为消费资格或去重依据。S2C使用 `success:u8 + length:u32 + protobuf[length]`。字段均为protobuf tag number，不是固定偏移：

| 消息 | 本版字段 | native依据 |
|---|---|---|
| Sort请求 | 1=opcode20可选；2=list；3=page/itemKind；4=condition | ctor004142E0、serializer00414370、parser00416270、sender029D4B50 |
| Sort返回 | 1=list；2=error | ctor00414260、serializer0041D880、parser00416000、callback0234AC00 |
| Delete请求 | 1=opcode18可选；2=list；3=repeated子项；4=flag | ctor004148C0、sender02148CC5..02148EB8 |
| Delete子项 | 1=deletionType；2=slot；3=sourceValue；4=count | serializer0041DF70、parser00415C40 |
| Delete返回 | 1=list；2=repeated结果；3=error | ctor00414580、callback02364DD0 |
| Delete结果子项 | 1=slot；2=remainingCount；3=type | ctor004141E0、成功结果使用02365089 |

Delete子项3与Move的模板编号字段不同：`02148D61..02148DE5` 从物品虚方法`+28`返回对象的`+18`取实例value，经内部helper写入子项`+1C`；保留品级/数量校验。普通丢弃按[业务规范](../模块/背包与装备.md)归一数量，ACK回传提交后的剩余量，不回显请求数量。对排序条件不适用或未知的情况回退该页默认排序。

字段宽度由生成的 serializer/parser、setter 和真实发送调用恢复，不依赖其他版本的flat body。普通删除接受 Main/Equipment、type0/flag0；ACK消费者`023650B9..023650BF`按list=3进入`023652B9`穿戴处理分支，服务端删除穿戴物后追加Equipment差量及Actor/Player/同屏刷新，不加“只能先卸到背包再丢弃”的业务限制。技能材料消费支持Main/type2/flag0：实体校验sourceValue，虚拟晶体/灵魂校验真实槽位与物品ID；数量必须正且足额，ACK子项返回实际剩余余额和type2，由ACK消费者更新数量，材料槽不追加14差量，避免触发获得物品提示；同批普通丢弃槽继续原有差量。其他消费类型尚未接入，回业务失败。整理接受 Main，page 对应当前六类。CMD18严格区分无尾部与单字节尾部，整理不接受该尾部；其余结构长度不符、截断varint、重复scalar、非法嵌套或未知字段拒绝并关闭，业务拒绝发送对应完整protobuf失败结果并保持连接。

当前客户端无色消耗实收 `10 00 00 00 10 00 1A 0A 08 02 10 E6 02 18 DD 17 20 05 20 00 01`：声明protobuf为16B，子项为type2/slot358/sourceValue3037/count5，外层flag0，最后01是独立客户端状态。不能把整个17B余段当protobuf，也不能把无色钱包当实体格。

Sort成功：01 04 00 00 00 08 00 10 00

## 排序锁与装备安全锁

以下均属于本页 S5A9 匹配输入。C2S category=1 的五个请求统一为 3B：`list:u8 + slot:u16`。发送端 `036F3A42..036F3A92` 选择装备锁三个 opcode，`036F3A9C..036F3B17` 选择两个排序锁 opcode，均通过 `03BDF720/03BDF750` 依次写列表/槽位。排序锁设置与解除是独立操作，不把重复设置解释成开关翻转。

S2C ACK category=1：公共分派先读 `flag:u8`，flag=0 再读 `error:u16`；以下均不属于 18/20 的 protobuf 例外。

| opcode | 操作与消费者 | 成功 body | 失败 body |
|---|---|---|---|
| 267 / 010B | 加装备锁，`0234E450` | `01 + list:u8 + slot:u16` | `00 + error:u16` |
| 268 / 010C | 解装备锁，`0235B620` | `01 + list:u8 + slot:u16 + remaining:i32` | `00 + error:u16 + remaining:i32` |
| 269 / 010D | 取消解锁，`0234E540` | `01 + list:u8 + slot:u16` | `00 + error:u16` |
| 713 / 02C9 | 设置排序锁，`0233DB60` | `01 + list:u8 + slot:u16` | `00 + error:u16 + reserved:u8` |
| 714 / 02CA | 解除排序锁，`0233DBC0` | `01 + list:u8 + slot:u16` | `00 + error:u16 + reserved:u8` |

排序锁成功分支直接将实例 `+0x2FA` 写为 1/0；失败在 `0233DBAE/0233DC0B` 还消费一个字节，当前填 0。装备锁和取消解锁成功写状态 1；解锁成功先写状态 2 并读取 remaining。当前立即解锁策略使用 remaining=0，紧跟 NOTI252 清除状态，不能只发解锁 ACK。业务拒绝码为 17（交易后删除称号）、19（无效目标/状态）、21（空槽）、22（无空闲锁 ID）；不能复用移动 ACK 的错误语义。

S2C category=0：

| opcode | 消费者 | body |
|---|---|---|
| 251 / 00FB `ITEM_LOCK_LIST` | `0239CA80` | `count:u16 + {list:u8 + slot:u16 + state:u8 + [remaining:i32，仅 state=2]}` |
| 252 / 00FC `ITEM_UNLOCK` | `0239CB30` | `list:u8 + slot:u16` |

各消费者用 `02908AC0(list,slot)` 定位实例：Main=0、普通穿戴=3，不能把穿戴映射到时装列表 1。锁通知通过状态 1/0 操作实例，wire 不发送内部 EquipmentLockId。全量物品与穿戴初始化后恢复锁通知；位置变化后用已提交的新槽位恢复。
