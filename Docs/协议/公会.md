# 公会协议

本文件只记录**已经由实机抓包或客户端逆向确证**的字节合同。未闭合字段保持待确认，不写成结论。

## 1. 创建公会窗口的两次查重

客户端在创建公会窗口里点「重复确认」（名称）或地址查重时发送，服务端必须应答，否则按钮不解锁。

| 方向 | opcode | 名称 | 正文 |
|---|---|---|---|
| C2S | 0x009C | `CHECK_GUILD_NAME_DOUBLE` | `u32 字节长度 + CP936 文本` |
| C2S | 0x009D | `CHECK_GUILD_ADDREASS_DOUBLE` | 同上（地址文本） |

实测样本（`Logs/packet_log.txt:72912`，2026-10-13T20:02:37）：

```
07 00 00 00 42 55 47 B9 AB BB E1   ->  长度 7，CP936「BUG公会」
```

应答走 **CMD 通道（kind=1）且与请求同号** 的 opcode，正文两段式：首字节为标志，标志为 0 时其后跟一个 u16LE 错误码。

| 情况 | 名称（0x9C）正文 | 地址（0x9D）正文 |
|---|---|---|
| 可用 | `01` | `01` |
| 已被占用 | `00 6B 00` | `00 6F 00` |
| 长度违规 | `00 6A 00` | `00 6E 00` |
| 含非法字符 | `00 6C 00` | `00 70 00` |

客户端表现（由客户端逆向确认）：可用时弹「可以使用的公会名。」并置创建按钮前置标志；`0x6B` 对应「此公会名称已被其他公会使用。」；`0x6A` 对应长度上限提示（中文 7 字符或英文 14 字符）；其余码落到默认提示。地址码 0x6E/0x6F/0x70 与名称码一一对应。

判据：`guilds.name` / `guilds.address` 的**唯一索引**。服务端不另建内存去重表。

本版客户端镜像里 `0x9D` **没有发包点**（创建窗口没有域名输入框），因此服务端建会时用**公会名**兜底作地址，见[公会模块](../模块/公会.md#2-建会认证链路)。

## 2. 创建窗口「介绍」校验（CMD 0x2E3）

| 方向 | opcode | 名称 | 正文 |
|---|---|---|---|
| C2S | 0x02E3 | `CHECK_GUILD_CREATE_PROMOTE_MSG` | `u32 字节长度 + CP936 文本`（实测 `04 00 00 00 32 32 32 32` = 「2222」） |
| S2C | 0x02E3 | 同上（CMD 通道、同号） | `01` = 可用；`00 6C 00` = 介绍含非法字符 |

客户端处理器（`0x0234EB40`）只在 **flag≠0** 时继续：**自动发出认证邀请 `0x2E5`**；flag=0 且错误码 0x6C 时弹「公会介绍包含非法字符。」，其它码静默。服务端因此只回这两种结果，且空串合法（窗口计数器从 0/80 起）。

## 3. 建会认证链路（0x2E5 / 0x2AD / 0x2E6 / 0x2AE / 0x2E7 / 0x2AF）

| 方向 | opcode | 名称 | 正文 |
|---|---|---|---|
| C2S | 0x02E5 | `REQUEST_GUILD_CREATE_PERMIT` | `u8 大区序号 + u32 名称字节长度 + CP936 角色名` |
| S2C（CMD 同号） | 0x02E5 | 同上 | `01` = 已受理；`00 + u16LE 失败码` = 拒绝，码表见下 |
| S2C | 0x02AD | `REQUEST_GUILD_CREATE_PERMIT`（NOTI） | `DSTR 公会名 + u8 大区 + DSTR 创建者角色名 + DSTR 介绍`；在线立即投递，离线等入城补投 |
| C2S | 0x02E6 | `REPLY_GUILD_CREATE_PERMIT` | **恰好 1 字节**：`01` 接受、`00` 拒绝（窗口关闭或 60 秒超时自动发 0） |
| S2C（CMD 同号） | 0x02E6 | 同上 | `01` = 认可成功；`00 + u16LE 失败码` = 失败，码表见下 |
| S2C | 0x02AE | `REPLY_GUILD_CREATE_PERMIT`（NOTI） | **1 字节结果**：`01` 对方已认可、`00` 拒绝/建会失败、`08` 对方处于拒绝状态、`2D` 对方在挑战地下城 |
| C2S | 0x02E7 | `CANCEL_GUILD_CREATE` | 空包体（关闭创建窗口时发送；**客户端无处理器，服务端不回包**。**关窗 ≠ 取消**，见下） |
| S2C | 0x02AF | `CANCEL_GUILD_CREATE`（NOTI） | 空包体（被邀请方关窗并自动回 `0x2E6 [00]`）；**当前没有发送路径**，保留给将来的正式取消协议 |

实测样本（`packet_log.txt`，2026-10-13T22:36:25）：

```
RECV 0x2E5 body = 02 | 05 00 00 00 61 64 6D 69 6E     大区 2 +「admin」
```

首字节是**大区（服务器）序号**，不是角色 id / 槽位 / 行号。取串函数 `0x290B6D0(v) = GetString(v + 0x11814)`，创建窗口的下拉条目数据就是它（值域 1..0xF9）。

链路时序（客户端行为逐条由逆向确认）：

1. 创建者在建会窗口点「认证邀请」→ `CMD 0x2E5`；客户端**在发包时本地**把按钮改成「等待认证」（`[esi+0x358]=2`），不看服务端应答。服务端因此只按「目标角色存在、与创建者不同账号、尚未入会」受理，**不要求目标在线**：受理即回 `01`。
2. 服务端按角色名解析目标，将完整邀请发到**被邀请方连接**，客户端打开窗口0xE8。`023CF470`先读公会名，再读大区、创建者角色名和介绍；`0387A070`将名称送入创建者说明与公会名称控件。大区按请求值原样回送，不是频道号。在线邀请与入城补投使用同一冻结文本和Builder，补投仍位于最后一条NOTI124之后。
3. 被邀请方点接受 → `CMD 0x2E6 [01]`；点拒绝、关窗或停留 60 秒超时 → `CMD 0x2E6 [00]`。
4. 扣费、公会及两名成员提交成功后，认可方收到ACK742=`01`，随后收到58入会、Actor和70基础资料；其当前角色快照同步所属公会。在线创建者先收到金币差额，再收到686=`01`、71建会、58入会、Actor和70资料。创建者离线时仍使用拒绝接管的离线租约提交，但只向认可方发布；创建者下次选角从成员表读取真实公会并初始化，不重播建会消息。
5. 创建者关闭创建窗口 → `CMD 0x2E7`（空体）。**关窗不是取消**：服务端只清创建窗口草稿（公会名/地址/介绍），**不回收**登记表里的待认证申请，也不推 `NOTI 0x2AF`。顺序模式下这正是建会的常规操作顺序——创建者邀请完关掉客户端，被邀请方上线入城仍会收到 `NOTI 0x2AD`，接受即扣费建会；申请在 600 秒内一直有效（见「申请有效期」）。关窗后同一角色要再发起邀请，必须重新做一次名称查重（`0x9C`）：草稿已经被清掉，直接发 `0x2E5` 会因无可用名称回 34。

`NOTI 0x2AF`（被邀请方关窗并自动回 `0x2E6 [00]`）的字节合同与客户端处理器都已确证，但**当前没有任何发送路径**：`0x2E7` 不再触发它，取消能力只保留在两处——申请自然过期（600 秒）与将来的正式取消协议（服务端 `CancelByInitiator` 与 `0x2AF` 投递路径都在，前者当前只有 `0x2E5` 当场投递失败的回滚会用到）。

| 5 | 该角色与创建者属于同一账号。 | 目标的 `characters.account` 与创建者相同 |
| 23 | 无法加入该公会。 | 目标已在 `guild_members` |
| 34 | 无法创建公会。 | 创建者已在公会、没有可用的名称草稿、创建者不在城镇 |
| 39 | 该用户已加入公会或正处于等待加入公会的状态 | 未使用 |
| 40 | 对方角色需到上午6点疲劳值初始化后才能接受。 | 未使用 |
| 45 | 该玩家已经认可了其它公会的创建，无法发送认可申请。 | 未使用 |
| 104 | 需要上午6点疲劳值初始化后才能进行。 | 未使用 |

成功（flag≠0）分支客户端什么都不做；表外的码静默并把认证邀请按钮复位。

`0x2E6` 应答（客户端文案表 `0x234EDA4`，只处理 3..0x68）：

| code | 客户端文案 | 服务端何时回 |
|---:|---|---|
| 3 | 无法找到指定玩家 | 创建者账号仍在线但不是发起角色（换角/未入城/在副本），或租约被在线连接持有 |
| 23 | 无对应文案 | 未使用，不能沿用邀请错误表 |
| 34 | （无文案） | 被邀请方拒绝、创建者在线时提交失败 |
| 39 | 您已加入公会或正处于等待加入公会的状态 | 被邀请方在申请等待期间已入会 |
| 45 | 已经认可公会创建，无法认可其它公会的创建。 | 未使用 |
| 103 | 公会邀请的等待时间已达到上限 | 申请不存在/已过期；或**创建者离线**时离线提交失败（金币不足、名称被占用等，具体原因只进服务端日志） |

其它码静默。服务端当前只使用 3 / 39 / 34 / 103：`0234ED30`的case0x27读取dstr21720，已入会答复使用39，与邀请错误表的23分开。拒绝与在线路径的建会失败用表外的 **34** 保持静默（拒绝后再弹「已经完成认可创建公会。」是错的）；离线路径的失败没有更贴切的文案，用 **103**（这份邀请已经无法完成）如实回被邀请方。

### 申请有效期

客户端在被邀请方窗口停留 **60 秒**（`cmp eax,0xEA60`）后自动发 `0x2E6 [00]`，服务端的申请有效期取 **600 秒**：
申请兼容创建者与被邀请方先后上线，必须能等到被邀请方下一次入城；同时在线仍按原连接直接投递。
有效期只由申请自己的登记时刻决定：**关窗（`0x2E7`）不会结束它**（草稿随窗口关闭丢弃，申请继续有效，见链路时序第 5 条），
到期由答复或入城补投查询顺手清理。窗口出现后客户端自己的超时拒绝（最长 60 秒）仍在有效期内，因此仍能匹配到申请。被邀请方若在有效期最后 60 秒内才入城，弹窗出现后可能因申请到期而收到 103，重新发起邀请即可。

## 4. 入会与基础资料

| 方向 | opcode | 名称 | 客户端读取 | 行为 |
|---|---|---|---|---|

| S2C | 0x003A | `GUILD_ENTER` | `u32 公会ID + u32 保留引用 + DSTR 公会名 + DSTR 角色名` | 设置本人公会ID、显示入会消息、关闭创建窗口并请求成员列表 |
| S2C | 0x0046 | `GUILD_INFO` | 下表 | 初始化实际所属公会的基础资料与客户端目录 |

`03BE26C0 → 03BE25F0`是带缺省值的包内字符串读取器：先读u32字节长度，再读CP936数据，最后转换为宽字符。dstr666、672、676、677分别是读取失败时的兜底，不是固定文案；漏发字符串会破坏后续字段位置，不能把截短正文当作合法格式。

`023D3A10`和`023D34A0`把第一个u32经保护值写入助手存到本人Actor模板`+800`，该值是公会ID，不能误送角色ID。58的第二个u32在本处理器中未消费，本服保留实际角色ID作引用，完整业务含义待确认。认可方也必须收到58及所属公会投影，不能仅写成员表或向创建者发送消息。

## 5. 客户端不需要应答的请求

以下请求在客户端的两张运行期处理器注册表（CMD 表由 `0x28F8C30` 建、NOTI 表由 `0x28F8FE0` 建）里**都没有处理器**，服务端即使回包也会被丢弃，因此保持静默是正确行为：

`CMD 0x004A`、`0x009E OPEN_GUILD_CREATE_WINDOW`、`0x02E7 CANCEL_GUILD_CREATE`。

公会窗口打开时会连发 `0x05AD`（6字节搜索条件）→ `0x05AE`（空）→ `0x016D`（空）。搜索与本人账号公会查询按本版实际消费合同实现，不能仅凭静态注册表未命中便认定无需响应。`0x2E7` 不回包，但服务端必须处理：**只清创建窗口草稿，不取消申请、不推 `0x2AF`**。
