## 魔界大战专用开始

## 退图虚弱确认

匹配ARAD的dstr `38254`（`956E`）为放弃副本后的虚弱警告。客户端在发送退图请求之前独立决定是否打开该确认窗，不等待ACK42，也不直接读取服务端的`DisableGiveupPenalty`。将本人Stamina百分比投影为100或在服务端跳过保存惩罚，不会自动关闭这一提示。

| 输入 | 原生消费者及含义 |

## ACK15成功与失败

Class1/op15在 `02349E73` 注册到 `02348ED0`。公共ACK分派先读取成功u8；失败另读错误u16。handler在 `02348EFD` 检查传入成功标志；非零跳到 `0234948E` epilogue，不追加包体读取，也不写入口对象 `+78`。因此成功ACK的handler部分不要求额外字段，但成功flag不能替代后续NOTI27选图通知，也不能把入口状态从 5 改成 8。

失败分支因错误码不同可能继续读取额外字段；已确认样本 `00 01 00` 沿错误1清TownScene等待状态。当前有效选图请求若资源没有合法安全返回点，使用这一已确认的错误1正文拒绝并保留原连接和选择状态；C2S15长度或会话状态不符仍抛出结构/状态错误并关闭连接。当前成功字节只表示选图入口应答，不表示副本准入或实例创建；不得将所有失败码套成同一3B。

### 当前选图应答与排队C2S16的边界

指定路径的原码顺序是 `01E0D51F → 03BE0FF0` 提交C2S15，紧接着在同一调用内准备 `-1、0、0、039EC320返回值、0FA1` 五个参数，于 `01E0D550` 调用 `03BB9A90`。对应区间为 `01E0D4F2..01E0D555`（99B）。caller没有等待应答，但callee仍可能因资格拒绝而不发送16；它证明合法前置成立时16可能在ACK15到达前排队，不证明每次15后必有16。

当前服务端行为：

- 已就绪且已选角的4B C2S15建立MapSelect及本次返回上下文，退出城镇同屏；先回ACK `01`，再发本人NOTI3 `state=1`；正文u32为0时追加本节NOTI27（空名单基础42B，深渊任务名单每项另占2B），非0不重发列表。重复请求保留原返回点，活动已占用场景时不重新开选图。匹配客户端左入口已观察到正文0，开始冒险已观察到正文3。上述应答不改变位置、revision或任务，也不创建副本实例；取消路径见[选择界面返回城镇](#选择界面返回城镇)。
- C2S15长度错误、未就绪或未选角属于结构/状态错误，关闭连接；当前并不返回失败样本 `00 01 00`。
- 默认配置下C2S16由DungeonHandler接入任务显式路线准入，实际持久角色owner/任务及资源资格成立时预留身份，再发送NOTI28/29；入场不以职业、转职或双树初始化作门禁。准入拒绝见下文完整静默ACK16合同，未知宽度仍unhandled。具体行为见副本模块，通知不等于实机验收。
- 隔离TCP验证上述包序、无虚假ACK16及后续连接行为；实际进图还需要NOTI28/29、加载完成和实例生命周期的独立验证。

入口路径 `01E0D400` 读取 `[[062EF53C]+FF9C]+754`：等于1时发送C2S15正文0；等于0时使用同对象 `+758`，随后调用 `03BB9A90`。因此仅看到正文0且没有C2S16，不能反推 `+754==1`：另一分支也可能因资格不满足而未发16。`01E0D555` 把入口对象 `+78` 写成5；状态分派 `01E0E86C/01E0E974` 的5、6分支不自行推进状态。`01FCBFF0` 在虚表 `+AC` 调用中写入状态参数，状态7路径 `01E0E720` 可请求状态8；这些原生状态不能由成功ACK替代。

`03BB9B3E → 01826E60` 只在 `028FBEC0` 返回2或3时才可能返回1，但返回非1后仍继续后续检查；“场景不是2/3”本身不足以解释不发送C2S16。副本成功/失败包序应以实际运行对象、分支与请求记录核对，不通过无关opcode或强改状态绕过资格。

### ACK16读取与恢复边界

ACK16为category=1、opcode16。成功正文为 `01`；它只确认请求应答，地图与怪物初始化仍由后续通知完成。

失败正文的已确认前缀为 `success:u8=0 + error:u16 + memberSlot:u8`。成员槽为0–7的队伍成员索引，用于部分提示中的成员名，单人使用0。

当前普通单人准入拒绝使用完整正文 **`00 09 00 00`**。错误9静默处理，并进入客户端既有的失败状态恢复；服务端保留选图与原返回上下文，让玩家继续选择或返回城镇。其他错误分支的间接读取和完整正文尚有待确认部分，不能统一套用四字节包体。完整客户端恢复效果仍待实机验收。

正文offset42的u32来自`02A78951..02A78964`所取对象虚表`+41C`返回值，`029083BB..029083C7`读取第三实参并写入；虚表`+44`的flags虽作为第二实参传入，helper不读取该参数，不能对offset42使用`0x21`的flags资格判断。已核对的虚表`+41C`为`02A75BE0`，只返回`this+15A8`，不写传入的局部上下文；`02A86ADA..02A86B41`将其初值设为1，其他路径可复制所属对象的返回值。Parser以`Unknown42`保留完整u32，其完整业务意义保持待确认，不作为唯一物件实例key。39与迷宫终末的场景准入仍要求完整形状、正文摘要、当前MAP中的唯一模板行、资源任务死亡声明或原Run冻结的单物件迷宫终末条件及原接取身份；同模板多实例不能据offset42反猜身份。猎杀通道33的逐次计数见任务模块，不把该字段当作那些份数的身份。

原生`[clear condition]`的0662分派经`0409C45F→04080310`解释；`04080436`比较`[destroy object]`，`04080472`写条件type0。物件终末`02A7EC61`核对type0，`02A7ECE9`比较目标与物件`+1754`，`02A7ED71`检查剩余条件，`02A7EDF7`减一次，经物件资格后`02A7EE10→02A787A0`发送同一完整39。这条来源不要求OBJ另声明quest type；另一路`[destroy passive object]`的type3条件不能混同。服务器不凭任意33或46构造物件清图事实，业务见[物件终末](../模块/单人副本实例.md#战斗事件与结算)。

剧情演员另有74B零参与者终末格式：reporter可以是实际角色号，不能要求FFFF。3151安全区实收角色12、object key626及改写标志22；奖励事实使用当前已发布且存活的演员、房间、摘要和实例事件账本。未知、其他房间、旧Run或已结算普通敌人目标仅审计并忽略，不回38，不创建奖励或通关事实。合法安全区终末事件可通关，无须补造原Boss死亡。88B普通怪物路径保持自身布局；截断包和摘要不匹配不能形成有效事件。

## 过房与怪物死亡的字段

C2S45 的已确认普通路径为 **100B**，前两 byte 是目标格 x/y；其后两个 u32、u8、u16、八个 u16、八个 u32、u16，`01DE2560` 再追加六个 u16、u32、三个 u16、u64、u32、u16，最后 u8。偏移85..92的u64不能漏计成92B请求。Parser保留未解释字段，不把这些统计值当伤害或通关资格。

普通怪物和APC的C2S39统计正文为`74 + 14 × count`字节，参与者数量为1–254；单参与者是88B，两参与者是102B。前缀为对象key:u32和上层报送上下文:u16，贡献列表与尾部布局见下文。其他发送点保留各自格式，不按此统计形状统一解析。

匹配 S5A9 客户端的定向运行代码已补齐 `02B52FE6`、`02C5AA0B` 两条生产者。公共前缀依次为 `key:u32、reporter:u16、Unknown6:u64、Unknown14:u32、Unknown18:u64、Unknown26:u32`。`02B52FE6..02B5305E`、`02C5AA0B..02C5AA70` 的原码已分别核对；后者当前直接调用包体 writer，不再依赖早期记录缺失的映像外入口。

偏移30为参与者数量u8；每行是`kind:u16、objectKey:u16、CumulativeHpDecrease:u64、PositiveHpDecreaseCount:u16`，14B。循环写宽分别在`02B533D0..02B53493`和`02C5AE02..02C5AEC3`核对；原生数量上限为254。Parser按完整长度保留贡献者原序和所有u64高位，尾部从`31 + 14 × count`开始，共43B。报送上下文独立于贡献列表；列表首项不表示最后击杀者，列表也可以只有APC贡献。

普通发送者在`02B52FD4`将Reporter初始化为`FFFF`；上层上下文为空时直接保留该值，非空时才调用`02B64480`读取上下文`+6DC8`。该分支在贡献数量和行循环之前，因此`FFFF`也可出现于包含本人或多个来源的报告。来源kind由对象虚表`+44`取得，`0211`已有实收且对应实际发布的普通monster；APC发送者另可在`02C5AD79`由虚表`+48`分支写`F111`，其值不等同于友方阵营。S5A9保留Reporter及全部kind/key来源值用于审计，不以来源类别、key、阵营、房间或本人参与设置死亡门槛。

真正当前HP setter `02AFC260`在`02AFC30A..32B`计算旧值减新输入的正64位差，调用monster虚表`+A28 → 02C4A1B0 → 02B159A0`，按归属来源累加目标实例`+3AF8`的HP降低量和`+3B30`的正降低次数。`02AFE270/02AFE160`读取它们形成参与者数据。统计发生在夹取之前，允许overkill；累计量不能命名为死亡时当前HP，也不能要求恰等于初始HP。

同一普通sender的27B统计尾由`029083A0`写入，count1形状中偏移55为`RewriteFlag:u8`、56为`SpawnLevel:u32`、60为`SpawnHpSnapshot:u64`。快照来自创建链`02A0B354..36F`调用同目标对象当前HP getter，并保存到`this+1140/+1144`；它是创建HP快照，未恢复服务端独立最大HP公式。68..81的七个u16及82/83尾byte继续按原字节保留。

`RewriteFlag`区分客户端写入前缀统计的方式。它不是服务端改写包体的开关，也不单独赋予Boss身份。服务端保留标志原值，不以其取值限制当前敌对活对象的死亡。已恢复的客户端统计字段含义如下：

| 字段 | `RewriteFlag=0`：未改写报告 | `RewriteFlag=1`：Boss改写报告 |
|---|---|---|
| `Unknown18:u64` | 该怪物全部来源的累计HP降低量加`random % 200` | 改写中间量`V`加`random % 200` |
| `Unknown26:u32` | 该怪物全部来源的正HP降低事件次数 | `max(1, floor(V / 300))`，属于派生次数 |
| `CumulativeHpDecrease:u64` | 本贡献者来源累计HP降低量 | 本贡献者来源累计HP降低量 |
| `PositiveHpDecreaseCount:u16` | 本贡献者来源正HP降低次数 | 本贡献者来源正HP降低次数 |
| `SpawnHpSnapshot:u64` | 客户端创建时的当前HP快照 | 客户端创建时的当前HP快照 |

服务端核对完整正文检查值、包体形状、wire宽度及真实会话owner、选角、正式实例和阶段，不以生成等级、创建HP、累计量、次数或改写标志决定是否死亡。当前房间已登记敌人沿一次奖励事务确认死亡，目标事件缓存保证来源或统计变化后的SQL重试仍使用原冻结计划。当前路线友方/非阻挡对象退场及其重复报告回复空掉落NOTI38，只更新Run内显示集合；未知、其他房间、旧Run、已结算普通敌人和清场目标仅审计并忽略，不回38，不创建经验、掉落、任务或清图事实。来源或目标身份不作为额外拒绝门槛，缺少实际目标不造奖励。一个参与者行只包含对应来源的分项，不表示目标所有HP降低事件都归属于本人。

客户端Boss改写链构造中间量`V = 最大HP + random % 10000`，再写入`Unknown18 = V + random % 200`及`Unknown26 = max(1, floor(V / 300))`。这些原码含义用于解释报告，服务端不检查公式相容性，也不比较总量、本人量与创建HP之间的大小关系。稳定死亡事件与经验/掉落去重由正式Run及事务账本保障，经验使用服务端生成计划等级。

末4B是通用发送前处理为opcode39追加的正文检查值，与技能包共用[MD5折叠公式](客户端通知.md#普通单人技能使用记录)，输入为此前全部正文；88B样本的检查值仍在84..87。历史88B及实收102B样本用于布局和检查值对拍，不能替代客户端验收。Parser只报告`BodyChecksum/ChecksumMatches`，不因不匹配改变诊断长度接受行为。结构解析和诊断通知不签发`ConfirmedDungeonMonsterDeath`，不提交成长或资产奖励；Unknown6/14保持未知。

匹配原码 `02395310` 的 NOTI38 零掉落普通路径读取 `key:u16, dropCount:u16=0, optionalFlag:u8=0, mode:u8=0, grade:u8=FF, extraFlag:u8=0, deathFlag:u8=0`，共9B。key=256示例为 `00 01 00 00 00 00 FF 00 00`；grade=FF跳过grade更新分支，不附ACK39、掉落或经验通知。早期原生记录含不完整的映像外前置调用，不能把其局部u16直接当作完整包证据。

上述`extraFlag`在mode0/3分支是Boss目标更新标志：`02395C8E`读取，值1时`02395CAC/02395CBA`继续读`bossX:u8,bossY:u8`，分别写迷宫实例`+DE8/+DF0`的加密整数包装，随后`02395F96`才读原末尾死亡标志。零掉落、key256、下一目标2/3的独立正文为`00 01 00 00 00 00 FF 01 02 03 00`，共11B；非零掉落仍完整消费全部131B条目后再读此尾部。`df_game_r::_MakeNotiPacketDieMonster`（0830B8CC）按原dummy演员标志写此分支，不新发NOTI28。目标必须来自原Run冻结路线，死亡提交后才发布；普通死亡及清场移除保留原9B尾部。

旧端`CMap::set_map`（0834E18A）在MAP类型2且源演员角色3时改为角色1并保留dummy死亡标志，但该发送行为不能套到本版。ARAD的`02A01E91`将线上角色存到记录`+14`；`02A15E46`先要求该值为3，`02A15E65..02A15E74`才根据MAP的`+A0=2`置dummy参数，随后`02A0B270`设置Boss身份，类型3分支再通过`02C404C0`写入actor的dummy标志`+56C0`。因此当前START_MAP的22B行在offset13保留Boss类型3，不借行末清房排除位传递dummy，也不增加演员字段；下发1既变成精英，也会跳过原生dummy Boss初始化。生成类型、服务端终末资格及奖励品级分别处理，业务见[假Boss迷宫](../模块/单人副本实例.md#假boss迷宫)。MAP级dummy与普通MAP内`[boss]+[dummy]`修饰不混用；实际迷宫标记推进依赖上述NOTI38，而不是把所有Boss候选同时标成Boss房。

同一匹配客户端的非零普通掉落循环 `023958C0..02395BC6` 为每条读取 `objectKey:u32 + itemEntry[123] + ContextValue:u16 + VisibilityFilter:u16`，固定部分共131B；所有条目结束后再读上述5B死亡尾部。`023958E0` 调 `03C85290`，`023958F3..023958FC` 明确以 `0x7B` 调 `03C85300`，`02395AA6/02395AB2` 再读两个u16。物品布局复用[物品协议](物品.md#实体字段)的定长核心；`028F2E40`不追加读包，`028F2A30/028F2A80(mode=3)`的时装或宠物附加分支另见该协议，不能用123B开启特殊物品。

这两个u16不是掉落坐标。上述读取将它们放入108B创建记录的`+16/+18`，经 `02396664` 的actor virtual `+AC0` 进入 `02B0FA50`；普通monster vtable `055EE884+AC0` 指向同一函数。`02B0FA96..02B0FB3C`检查第二项：0直接通过；非零必须等于 `0643A52C` 的加密全局值，否则跳到 `02B10027` 返回，尚未执行物品资源创建或场景注册。`VisibilityFilter`仅描述已确认的过滤用途，全局值的完整业务身份仍未知。第一项在特定模式12的 `02B0FF57..63` 被使用，其完整语义未恢复；普通路径显式发送两项0，不推导特殊上下文。

通过过滤后，`02B0FD4A`以模板与完整属性调用 `02E615B0`，`02B0FEF0..02B0FF12`以条目总数、散落方向/速度及死亡actor建立地面对象，随后 `02B0FF21..40` 将原u32地面key注册为kind `0121`。构造链 `02A42DA0 → 02A40880` 在 `02A40980/02A4098A` 从传入actor取得位置，再处理边界与散落；不能把服务端预留的怪物出生X/Y塞入这两个上下文字段，也不能用C2S43的坐标提供资产资格。

以上新增地址为VA，绑定同一匹配的 x86 客户端及映像基址 `00400000`，RVA为VA减该基址。匹配运行映像的定向原码与加密getter有界回放确认：普通0通过过滤，而208、276、218在观测全局值1时均提前返回。该回放只证明创建过滤分支；后续资源显示、地面拾取和Windows界面仍须实机验收，不由发送日志、账本或回放代替。

`DungeonPackets.MonsterDeath`编码已经由调用方确定的普通掉落对象、完整物品属性、显式record slot及两个创建上下文，长度为 `9 + 131 * count`，不抽奖、创建资产或确认死亡。它拒绝重复地面对象key、非法物品核心、缺失特殊物品附加数据及超过帧上限的集合；不会截掉超量条目。零条目保持既有9B合同。正式Handler为普通消耗品明确传入上下文0/0，冻结来源中的X/Y仍只用于存储核对。字段编码、可控随机的生产Handler与真实TCP回归分别见 `DungeonDropPacketsTests`、`FormalDungeonPublicationTests`、`FormalDungeonTcpTests`。

## 普通拾取codec与生产边界

[DungeonPickupRequests](../../Server/DfoServer/Network/Parsers/DungeonPickupRequests.cs)提供匹配普通生产者 `029CABC0` 的精确20B解析：`groundKey:u32 + fixedZero:u8 + context:u8 + playerX/Y:u16 + token0:u16 + groundX/Y:u16 + token1/2:u16`。固定字段必须为0，其余未知字段保留完整原值；位置和token不提供资产资格。`038521C0`另有18B变体，不截成普通请求。普通opcode43在通用检查分派不追加MD5尾，因此24B也拒绝。

[DungeonPickupPackets](../../Server/DfoServer/Network/Builders/DungeonPickupPackets.cs)的普通NOTI39为19B：`groundKey:u32 + firstPicker:u16 + flags8:8B + recipient:u16 + destinationSlot:u16 + tail:u8`，绑定消费者 `023C8E00`。它使用既有地面物品对象入包或作堆叠增量；数量不是本通知的新字段。调用方必须明确提供完整8字节flags及tail，Builder不补默认值、不推断未知语义；资源0/1199特殊分支不在此codec内。ACK43成功仅公共字节1，失败公共0加u16错误；单独成功ACK不代表物品入包，也不额外发空NOTI42。

图鉴碎片使用相同19B通知但`destinationSlot=FFFF`，不借用真实Main空格或清除已有装备。`029CAA95..029CAACA`在查槽前检查容量，`029CFF1A..029CFF1D`在写入vector前检查目标上界，FFFF不能安装成Main物品；材料沿`023C`消费者的数量类型分支收尾。随后1152以片种ID同步已提交的绝对余额，不发送虚假Main14行；地面消失、获得表现和提示仍须匹配客户端验收。

当前正式普通拾取由Session地面owner、冻结掉落及库存事务提供资格，详见[单人副本实例](../模块/单人副本实例.md)；未知特殊资源分支与Windows成功/拒绝显示仍待验收，不得以codec通过代替拾取完成。[DungeonPickupProtocolTests](../../Server/DfoServer/SelfTests/DungeonPickupProtocolTests.cs)接无资源Core入口，用固定合成字节和独立读器核对完整消费、长度拒绝、无符号上界及缓冲冻结。

资源ID0的金币NOTI39不走上述19B普通物品尾部。匹配 `023C936D..023C9396` 对ID0/1199分支到 `023C97CE`，共同头仍是 `groundKey:u32 + firstPicker:u16`。`023C97F6..023C9A78`按成员0..7逐项读取 `participates:u8 + amount:u32`，不参与的成员也须有四字节金额；本人参与时额外读取 `extraCount:u8`，非零再读`bonus:u32[extraCount] + guildFund:u32`。单人选择成员0参与、本人extraCount1且bonus/guildFund均0，其余七成员标记0/金额0，完整长度55B。[SinglePlayerGoldNotification](../../Server/DfoServer/Network/Builders/DungeonPickupPackets.cs)只编码显式正增量，不伪造奖金或基金，无普通recipient/slot/tail，也不借A21的117B通知；本版 `029C9A20` 从本人库存对象vector首项取得金币对象，`023C9855..023C9863`以本次u32更新。

金币扩展段不仅决定附加文字。`023C999F..023C99D5`在获得参数中保留当前地面对象并调用`0292A3E0`，其金币路径经`0292ABCB..0292ABF3 → 029B6190 → 029B5FC0`建立拾取数值表现。`029B6193/029B619F`要求玩家和地面对象均非零；extraCount0的47B简化路径在`023C99F7 → 0292B3E0`将该对象上下文置零，因此只能同步余额/文字而不能代替完整拾取表现。`df_game_r`的`CParty::get_item`即使附加金币和基金为0也发送扩展段，只用于业务对照，不提供本版opcode、成员数量或读宽。本服不新增自动加余额入口，经过既有CMD43资格核验的自动拾取请求也使用此通知；生产金币资格、事务、客户端音效和头顶数字仍须分别验证。

死亡、相邻房间、缓存和失败行为由[副本模块](../模块/副本.md)维护；客户端裸报告必须经过原实例权威与事务核验，不能直接作为清图、经验或任务资格。
