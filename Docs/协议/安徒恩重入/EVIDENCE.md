# 安徒恩 668 客户端恢复通知证据

## 结论和适用范围

开启 `AntonRejoinEnabled` 后，668 恢复原团、原普通分队与原 Run，再使用**本服场景重放策略**恢复新客户端。成功 `01` 只确认原成员能力已安装；实际场景通过既有名册、27、28、MAI、29消费者重建，真实客户端37之后才发送本人30。此顺序由本服明确选择，**不是已取得原厂成功668抓包**。

静态地址均为 VA，适用 PE32/x86、ImageBase `0x00400000`、V31.0.24.0 的 `ARAD.exe`。其他构建不得直接套用。下列出处均为本机只读材料；原始内容不入 Git。

## 本服恢复合同

- 原 owner 失效、同账号同角色同频道、候选 key、原团/原分队/原 Run 能力及幸存者进度全部匹配后才安装。保持既有 owner → 分队 → 目录/Battle 锁序；位置 SQL 提交在目录/Battle 锁外，失败不消费候选。不开新团、不新建 Run、不重新666或16、不重扣票。
- 新客户端收到原团名册、普通分队成员/端点/主机，再由27进入选图模块、28安装原DGN、MAI绑定218观测场景、29建立原房间。28/29取新Session当前回执、原seed、当前存活怪与已消费对象投影；不引用旧角色资产，不重发入场ConsumedSlots。
- 新Session保留原业务Phase，原Run保持原阶段。Session自有呈现令牌绑定generation、选角epoch与Run identity；未确认期间拒绝战斗、走图、复活和奖励写入。29实际Written才授予37确认资格，入队不是Written。42与超时正式退场继续可用；原场景失效后排队中的旧27/28/29受原能力守卫淘汰。
- 原Run已在Dungeon/Settlement时，37仅消费新客户端的呈现令牌，不执行普通CompleteLoading，不增加Run epoch、不重计任务初始化/疲劳、不向幸存者重发30。原业务仍Loading时，37复用原全员屏障和正式加载提交；已在Dungeon的幸存者无需重新37。
- 重复668、错误key或进度过期返回原失败19，不重复安装或扣款。呈现中再次断线仍保存同一原业务阶段与能力；发送失败不回滚已提交成员，也不能直接标记客户端已加载。

## 正式场景消费者的匹配原码依据

正常进图链的消费者已单独还原，和ACK668函数分开核对：

| 通知 | 消费者 | 已证作用 |
|---|---|---|
| NOTI27 | `023D8AC0` | 直接调用 `029075C0(2)` 切换module2，建立选图场景前提 |
| NOTI28 | `0238A3F0` | 独立构建DGN，经 `022ECE60` 查询、`03B99780` 安装，不依赖ACK668 |
| NOTI29 | `0238E3F0` | 按mode1/2创建MAP，使用已安装的DGN/房间信息 |
| ACK668成功 | `0234447C → 0055D870` | Anton频道 `0x17` 直接返回，不能替代DGN/MAP装载 |

因此本服采用27→28→MAI→29；MAI沿本服已有中性场景协议，在218绑定原生对象观测身份。它不修改原生29，不伪造Native生成、37或30。正式包体合同见[副本协议](../副本.md)。

## 已证的入口和 ACK

1. **S2C NOTI835，kind=0，opcode=835（0x0343），7B。** 顺序为 `key:u32`、尾 `u8`、尾 `u16`。注册点 `023CDA19` 将 `023AB820` 绑定到 `0x343`。消费者 `023AB851 call 03C85290` 读首 u32；`023AB859 push 1`、`023AB860 call 03C851B0` 读尾 u8；`023AB86C call 03C85220` 读尾 u16。
   出处：KB-20261025T173606-7fa0419ec7 的 `antun-20261025-2346/b-668-notification-registration.txt`；KB-20261026T035322-82d38db868 的 `antun-parallel-20261026-1139/COMBAT/disconnect835-23ab820.txt`。二者路径均相对于本机 `codex-runs` 证据根；完整路径由KB条目记录。
2. **C2S CMD668，kind=1，opcode=668（0x029C），唯一正文 `key:u32`，4B。** 已存在本地团记录时 `023AB87A call 01DC72F0`、`023AB881 jne 023ABAB1` 直接收尾；无记录且 key 高两字节匹配本地服务器/频道字段时，`023AB9FA push 0x29C`、`023AB9FF call 03BDEDD0` 起包；`023ABA06 call 03BDF610` 写 opcode；`023ABA0B mov ecx,[ebp-0x18]`、`023ABA0E push ecx`、`023ABA16 call 03BDF780` 写原 key；`023ABA1B call 03BE0FF0` 发送，`023ABA31 ret`。不是重走 666/16 的证据。
   出处：同 KB 的 `b-668-actual-sender.txt`，及上述 `disconnect835-23ab820.txt`。
3. **S2C ACK668，kind=1，成功是公共成功字节，后续没有业务正文读取。** `02344439 cmp byte ptr [ebp+0xC],0`、`0234443D je 02344486` 判断成功；成功走 `0234447C call 0055D870`、`02344481 jmp 02344625` 收尾。失败在 `023444A3 mov ax,[ebp+0x10]` 取公共错误 u16，`023444DE cmp ax,0x13` 匹配错误19，`023444E4 push 0x7D3C` 选字符串32060。服务端现用失败体 `00 13 00`；成功体 `01` 的可消费性不能证明恢复完成。
   出处：`antun-20261025-2346/b-ack668.txt`，KB-20261027T150809-274089169c 的 `anton-raid-grok-20261027/rejoin-static.md`。该报告对同一 EXE 的发送/注册/ACK 字节作过交叉核对。

这些证据只建立 **835 → 满足条件时客户端自动发668 → ACK668 分支** 的因果关系，不建立其他通知相对 ACK 的顺序。

835 尾部在同频道自动 668 分支中读后未使用。异高位提示分支 `023ABA4C..023ABA74` 把尾 u8/u16 和 key 高两字节放入回调；`023AC590` 交给 `01DDC140`，未携带 key 低16位。`01DC6360/01DC63B4` 将 u8 索引0..5映射为频道类型 `17/20/2D/32/3E/3F`（十六进制），索引6直接返回；这不能解释为恢复时限或允许异频道重入。出处：同 KB 的 `rejoin2-disasm3.txt`、`rejoin2-disasm4.txt`。

## 团本状态与原厂证据边界

585/586/583/587及成员表复用原Battle当前视图和既有正式投影，感染身份、能量、阶段、参与者与剩余时间都来自现存聚合，不新增默认值。它们参与本服恢复，不表示原厂668必需的集合或相对ACK顺序已经证实。奖励牌面仍须原阶段真实资格与提交，668本身不创建600/601胜利或领取事实。

现有原厂抓包没有同构建成功668会话。835尾部语义、原厂成功恢复的通知集合及顺序仍未知；本服场景重放不能改名为原厂成功包序。旧测试仅主动37、而668后没有27/28/29的结果不能证明新客户端已加载。现在TCP要求先观察完整恢复场景，再模拟客户端37；自然加载、画面、多人host迁移和实机断线恢复仍须实际客户端QA。

- `anton-raid-rejoin`：配置关闭、候战室恢复、重复/错误key、原团原普通分队、原位置和资产不重复提交。
- `anton-raid-rejoin-recover`：原业务Loading断线后，668重放27/28/29，确认前无30；真实37才完成原加载，不要求已加载幸存者重发37。

- 正式进图组复用同轮资源验证真实发送泵：29入队未Written时37拒绝；成功Written后纯呈现37不增加Run epoch；场景排队后真实42或owner接管使旧27/28/29和Written完成失效。死亡、复活、牌背、影片及奖励入口不能越过呈现屏障。
