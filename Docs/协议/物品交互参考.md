# 物品交互协议参考

本页记录普通 NPC 商店买卖、限购查询、装备修理、锻造、分解、随机和普通选择型礼包开箱及尚未接入的玩家挑战交互。业务现状见[背包与装备](../模块/背包与装备.md)，条目读取规则见[物品协议](物品.md#条目读取边界)。仅在修改相关交互或核对错误文本时读取。

## 袖珍罐开箱

构建边界：ARAD.exe SHA256=`3941E531FDC62C11B38149A767ACBED09F056443C5C6BE21C129E6B95AEBA329`。当前运行代码的`01295BD1..01295BFA`及`01445C3C..01445C69`发送CMD27；`0237C020..0237C025`注册ACK27到`02375CB0`。不能套用CMD160的礼包回包。

| 方向 | 小端正文 | 宽度与消费者 |
| --- | --- | --- |
| C2S CMD27 | `mode:u16 + sourceSlot:i16` | 4B；两个已核对出口均写mode=0；实收`00007500`对应源槽117 |
| S2C ACK27成功 | `success:u8=1 + sourceSlot:u16 + rewardRecord:123B + fallbackQuantity:u32` | 130B；`02375CFC`读源槽，`02375DB9`读普通条目，`02375F1C`读末尾u32 |
| S2C ACK27失败 | `success:u8=0 + error:u16` | 3B；公共分派消费错误码，`02376976`分支显示失败 |

普通条目沿[条目读取边界](物品.md#条目读取边界)，包括真实奖励槽位、物品号及完整核心。客户端先扣源一只；`02375F56`对既有奖励堆叠相加，因此堆叠记录的数量必须是本次增量，不能填合并后的总数。`023766AF..023766D2`仅在条目的物品号和数量均为0时使用`fallbackQuantity`，当前实体奖励写0。服务端提交成功后先ACK，再投影NOTI14权威总数；事务失败不返回成功。资源规则及待确认边界归[背包与装备](../模块/背包与装备.md)。

该合同由匹配构建的当前运行代码与CMD27实收正文交叉核对。修改前请求到达后记录 `handler_not_registered`；新入口完成提交后回完整ACK与权威差量。原始抓包和运行资产不入仓库，资源及UI验收边界分别记录。

### 符文与护石随机箱

`[stackable type]` 为 `` `[legacy]` 0 ``、根级恰两段 `[action type]` 且正文为 `` `[rune random box]` 族 档 `` 的消耗品共用上表的请求与宽度：C2S 仍是4B `mode=0 + sourceSlot:i16`，源在主背包；成功130B、失败3B，普通拒绝为19、容器46无空位为4。奖励记录同样取实际提交槽位与完整核心；护石不可堆叠，123B记录的数量字段是实例品级seed（999999998），符文为本次增量1。

包序与前文 `[upgradable legacy]` 罐不同：成功 ACK 之后不再发 NOTI14 增量，而是先发主背包 NOTI13 全量、再发容器46 NOTI13 全量（`[0]=46`）。客户端确认后立即读取奖励容器，只发增量会保留其预置的奖励槽。抽取规则、候选池与提交边界见[护石](../模块/护石.md#随机箱)。

## 候选物品请求与 actor 交互

客户端 `03BDF610` 将 category 写为 1、opcode 写为 u16；`03BDF720/750/780` 分别追加 1/2/4B，`03BE0FF0` 提交发送。以下读宽只约束列出的出口，不代表同 opcode 的全部调用路径：

| C2S category/opcode | 发送出口 | 此出口 body | 分类与边界 |
|---|---|---|---|
| 1/10 | `03B36BAB..03B36BF9` | `targetActor:u16 + mode:u8（此处为04或0D） + u32=0 + u32=0`，11B | 玩家挑战交互；mode 及具体 UI 状态待确认，不作为商店买入合同 |
| 1/11 | `03B385DD..03B3861F` | `actor:u16 + mode:u8（此处为04或0D） + u32=0`，7B | 玩家挑战交互；此出口 EBX 保持0，末字段不能命名为物品数量或价格 |

10/11 的首 u16 属于 actor 查询键，依据如下：

- `02D90700` 是 cdecl 查询，使用 arg0 的低 u16，从全局对象 `062EF4F8` 的 `+4` 树查询并返回节点 `+0C` 对象；它不以传入 ECX 选择 owner。同一查询也用于 NOTI22 的 `023D27E0`，不能将其解释为物品槽位或模板 ID。
- `02D90E80` 解出 `0643A52C` 中的本地 ID，调用上述查询并缓存对象到 `+6C`；`0208E830` 仅返回所查对象的 `+40`。调用链 `03B37A80 → 03B37C6C → 03B369E0` 将目标 ID、传入名称与本地对象比较，避免对自己操作，再沿11B出口发送10。
- 11 的 `03B383E0` 先读取 u16/u8，再通过 `02D90700 → 0208E830` 使用目标对象名称；`03B38411` 将 EBX 清零，`03B38612` 将其作为末尾 u32 发送。不能仅凭4/0D或相邻 opcode 把该动作命名为买卖、穿脱、组队或玩家交易。

按10/11出口构造的宽度样本分别为 `00 00 0D 00 00 00 00 00 00 00 00` 与 `00 00 0D 00 00 00 00`。这些不是实收请求，不可作为买卖样本或直接注入当前连接。

本版 ACK 注册为 op10 的 `0237BE6F → 02363C00`、op11 的 `0237BE7F → 02354540`、op19 的 `0237BF54 → 02372610`。公共分派 `028F8600` 读取 `success:u8`；10/11失败时还在 `028F8655` 读取 `error:u16`。`0041CA50` 只对 opcode `0x12/0x14` 跳过公共错误码，10/11不属于该例外。

| S2C category/opcode | handler 在公共字段之后的读取 | 已确认布局与条件 |
|---|---|---|
| 1/10成功 | 无 | `success:u8=1`，共1B；`02363C31` 直接跳到 `02364B3C` 收尾 |
| 1/10失败 | u8（`02363C47`） | `success:u8=0 + error:u16 + unknown:u8`，共4B；追加字节参与错误显示分支，含义待确认 |
| 1/11成功 | u16、u8（`02354576/02354584`） | 公共成功标志后读 actor 查询键及未知字节；只有查询对象存在且该 byte 为1时才在 `023545C3` 另读 u8 |
| 1/11失败 | u8（`0235466A`） | 公共失败标志、错误码后另读未知 u8，不能省略 |

上述成功布局只证明消费者读宽，不表示业务已实现；不能给未实现请求统一回 `01`，失败也不能省略额外字节。10/11具体 UI 动作、mode 枚举、通知包序及状态推进仍须独立恢复；op19 已单独接入上文普通物品移动合同。

匹配客户端文字进一步确认上述链属于玩家挑战交互，关联街头争霸和公会擂台；它不是 NPC 商店买卖合同。以下是链内真实调用 `03DDC8F0` 的消息 ID 与匹配字典文本，不能用它们推导未恢复的按钮、状态或 mode 枚举：

| 消息 ID（hex） | 匹配文本 | 本链调用位置 |
|---|---|---|
| `4AF8` | 现在是无敌状态 | `03B36C31` |
| `4B0E` | 只能向Lv30及以上的玩家发起挑战 | `03B36C17` |
| `1999` | 无法进行街头争霸或公会擂台战。 | `03B37DB5` |
| `56DD` | 只有队长才能够发起街头争霸挑战 | `03B3813B` |

## 商店购买与限购查询

### C2S 购买

category=1、opcode=21（hex `0015`）。普通商店发送出口 `037C59D4..037C5AB0` 写四个 i32，body 固定16B：`itemId + count + shopId + npcId`。其中 shopId 来自全局 `0621860C`，npcId 来自 `062CECC4`；其他商品 UI 出口 `037C5882/037C5989` 也按相同宽度发送。服务端使用 PVF 商品目录校验三者关系，不把客户端字段当价格。

交易窗口（时空石商人等）同样发本 opcode，`shopId` 固定为 `-1`（`FFFFFFFF`），商品与价格由 `etc/tradingsystem.etc` 名册决定，回包形状与普通商店相同。

普通装备购买实收 `count=0`，仍表示购买一件；例如 `986C0000000000000200000001000000` 为 itemId=27800、count=0、shopId=2、npcId=1。服务端按装备模板归一成一件后计算费用和限购，不能将该字段直接判为超过购买限制。堆叠及其他商品的零数量仍拒绝。

### S2C 购买

ACK21 注册为 `0237BF74 → 0236B0A0`。失败为 `00 + error:u16`，3B；成功结构如下：

| 顺序 | 字段 | 消费者及含义 |
|---|---|---|
| 1 | `success:u8=1` | 公共分派读取 |
| 2 | `gold:i32 + winPoints:i32 + specialPoints:i32 + cera:i32` | `0236B132/13E/14A/156`；普通商店 specialPoints=0，其他数值为扣费后、获得前的余额 |
| 3 | 普通物品条目123B | `0236B16F` 指定 `7B` 长度，`0236B172 → 03C85300` 读取；布局复用[统一物品条目](物品.md) |
| 4 | `materialCount:u8` | `0236B2FC`；表示本次附带的材料更新条数，金币购买为0，可包含多条 |
| 5 | `(itemId:i32 + remaining:i32) × materialCount` | `0236B327/333`；材料扣费后的余量 |

包体长度为 `141 + 8 × materialCount`；单条149B，两条157B。`0236B34D..0236B357` 将循环索引与u8条数比较并回到 `0236B310`，逐条消费两个i32；这个字段不是有无材料的布尔标志。首余额经 `029C9A20` 取得 Main 虚拟槽0并调用 `+40` 设置；第二余额经 `029C9A40` 取得槽2；第四余额写点券对象。第三字段进入特殊商店 UI 状态，普通入口只发0，不据此实现未知点数玩法。

材料尾段在奖励前逐条应用：`0236B619` 后通过模板找到首个旧槽，余量非0调用 `+40` 设置，否则移除；`0236B6F9..0236B709` 控制更新循环。物理材料跨堆时，此处填写扣费后首个旧槽的余量，其余槽用提交后的差量同步；不能填所有堆叠的合计，也不能用发放奖励后的数量代替。若首个旧槽因安全锁或到期未参与消耗，则省略该模板的尾段条目，避免碰触未变化的物品；实际被扣的后续格由NOTI14同步。图鉴和非Main钱包由各自余额通知同步，不构造假实体材料条目。条数上限来自u8宽度，必须在提交之前验证。

奖励槽已存在相同模板时，`0236B74A` 调用 `+4C`，其实现 `020C1300` 在 `020C1362..136A` 将传入数量加到当前数量。同一数量又在 `0236BF62..0236BF8F` 传入购买计数更新；`01FD47C6` 累加当前商品已购数。因此 ACK 堆叠条目须填写本次完整购买量，跨堆时也不能只填写首格增量；填最终总数则会重复增加。业务回执保留完整核心，Builder 投影购买增量。服务端先提交完整交易，再发 ACK，最后用权威物品/钱包差量同步所有实际变化槽；跨堆分配不能靠限制成只能购买一堆实现。装备条目仍携带完整核心，虚拟钱包使用对应 Main 槽的数量条目。

匹配消息字典与购买失败分支对应：

| error | 消息 ID | 文本 |
|---|---|---|
| 4 | `02EA` | 物品栏空间不足 |
| 10 | `02EB` | 所持金额不足 |
| 17 | `8CA0` | 不存在该道具 |
| `85`（hex） | `ADB1` | 超过购买限制 |

### 限购查询与清除通知

C2S category=1、opcode=715（hex `02CB`），body 为 `npcId:i32`，4B；发送点 `01FD1603..01FD1625`。ACK 注册为 `0237CF60 → 02350220`，失败3B，成功为 `01` 后依次四组 `count:i32 + (itemId:i32 + purchased:i32) × count`。合法空结果也必须发送17B。

四次 count 读取在 `0235024F/28C/2CC/30C`。第1/3组经 `01FD4740` 写同一购买计数缓存，第2/4组经 `01FD4760` 写另一缓存，都是设值而非相加；不能省略后两组。普通商店将当前 NPC 有效的模板限购计数放在第1组，后三组为空；n条为17+8n字节。账号/角色与是否重置属于服务端持久规则，不臆测为这四组的分类。

NOTI672 的 `023E33D9 → 023D03B0` 只调用 `01FD1BB0` 清缓存及 `01FD1630` 刷新 UI，没有 body 读取。它不是限购列表；当前服务端不以该通知代替 CMD715，也不伪造未知库存。

## 商店出售

匹配 `dstr.dat` 的消息 `0456` 为“出售[%s]\\n总出售价为%d金币， 确定要出售吗？”，其原生调用点为 `037CE29F`。确认窗口 `037CE0C0` 经确认动作 `037CE530 → 037CE5FE` 调用 `037CDC90`；该发送函数的原生字符串明确为 `ItemSellConfirmWindow::sendSellItemPacket`，同时使用 `SELL_ITEM PACKET LOCK STATE` 标识发送状态。对应响应函数使用 `CMDFUNC_ENUM_CMDPACKET_SELL_ITEM` 标识。这是城镇出售链，不使用前述10/11玩家挑战合同；普通NPC与其他销售来源的准入分支仍须分别核对。

### 普通装备计价

确认窗口在 `037CE19A..037CE1A0` 调用物品虚方法 `+94` 取得单价，再在 `037CE23D..037CE243` 乘出售数量。装备计价函数 `02949DA0` 取模板 value、当前/最大耐久，`02949EB9..02949EBF` 向 `040C13A0` 传入末参数1。普通装备使用 `[rate]` 第一项；有耐久时 `040C1487..040C14B5` 依次用单精度计算 `value × rate × 0.001 × min(current,max) / max`，max=0 时由 `040C141C..040C1434` 计算 `rate × 0.001 × value`。`040C14BE` 先截断，再由 `040C14C5..040C14D9` 用整数计算 `×90/100`。不能省略90%系数，也不能先取整基础售价或给零结果补1金币。

匹配 S5A9 原码合成回放完整返回：value=144、rate=200、耐久20/20为25金币，10/20为12金币，0/20为0金币，超过最大耐久时按20/20处理；value=360、耐久16/33为30金币。该结果限定普通装备计价，特殊装备价格状态仍须按对应消费者接入。服务端按真实实例计算后提交，ACK与钱包差量均携带同一最终余额。

### C2S 请求

category=1、opcode=22（hex `0016`），`037CDE94..037CDF3A` 经 `03BDF610` 建帧、公共 writer 追加字段，最终由 `03BE0FF0` 提交。此出口 body 固定19B：

| offset | 宽度 | 原码数值来源与边界 |
|---|---|---|
| 0 | u8 | containerArgument 的低8位；来自发送函数参数 `[ebp+14h]`，已接入 Main=0、个人仓库=2、普通穿戴=3 |
| 1 | u16 | EDI 槽位索引的低16位；由容器内对象查找或角色装备对象查找得到，不能作为物品模板或实例ID |
| 3 | u32 | ESI 数量，来自 `[ebp+0Ch]`；此出口先以有符号比较拒绝非正数，并核对对象存在及数量足够 |
| 7 | u32 | npcContext，直接读取全局 `062CECC4`，与普通购买的NPC来源相同；其他销售来源的状态仍须分别确认 |
| 11 | u32 | windowState，窗口编号 `0110` 的对象 `+214`，由 `037341D0` 取得；窗口缺席时写 `FFFFFFFF` |
| 15 | u32 | check，按下述32位表达式产生 |

`037CDF1E..037CDF35` 的精确表达式为：

```text
check = u32(2 * (EDI + ESI + containerArgument) + confirmedBit)
```

这里使用原始32位寄存器和参数，不能先把 containerArgument 或 EDI 截成 wire 宽度再代算。confirmedBit 为 `022B2870` 返回对象 `+4C` 的 byte 是否等于1；确认动作在 `037CE5BA` 将其置1，发送路径在 `037CDF26` 将其清零。该值不是请求编号、帧CRC或可直接使用的业务幂等键。

windowState 已有清零、写1及写2的原码依据（`03739520`、`0373AEA9`、`0373B121`）；它不能命名为NPC ID，具体状态枚举仍待确认。普通出售由服务端根据真实物品及 PVF 计算价格，npcContext、windowState 和 check 均不参与计价，也不充当一次性授权票据。

以下完整指令片段来自匹配原生记录，可从真实边界复核；它们不构成实收请求样本：

```text
037CDE94: 6A 16 E8 35 0F 41 00 8B C8 E8 6E 17 41 00
           push 16h; call 03BDEDD0; mov ecx,eax; call 03BDF610
037CDF1E: 03 FE 03 7D 14 0F BE D3 C6 40 4C 00 8D 04 7A 50
           add edi,esi; add edi,[ebp+14h]; movsx edx,bl
           mov byte ptr [eax+4Ch],0; lea eax,[edx+edi*2]; push eax
```

### S2C 响应及刷新

ACK22注册为 `0237BF84 → 023552A0`，category=1、opcode=22。公共分派先读取成功标志，失败时读取 u16 错误码；22不属于跳过公共错误码的例外。

| 状态 | 完整 body | 真实追加读取 |
|---|---|---|
| 成功 | `01 + gold:i32 + container:u8 + slot:u16 + soldCount:i32`，12B | `02355317`、`02355325`、`02355331`、`0235533D` |
| 失败 | `00 + error:u16`，3B | handler不追加body读取 |

四个追加读取 call 的原字节分别为 `E8 74 FF 92 01`、`E8 86 FE 92 01`、`E8 EA FE 92 01`、`E8 4E FF 92 01`，依次进入 `03C85290/03C851B0/03C85220/03C85290`，对应4/1/2/4B。

成功路径将金币余额交给 `029C9A20` 返回的 Main 槽0对象，调用虚方法 `+40` 设置。S5A9 中对应对象的虚表为 `055D9384`，`+40=020C6400` 设置数量，`+48=020C1260` 读取数量；其对象位置只属于该快照，不硬编码到服务端。

出售数量少于现有数量时扣减，否则移除槽位；末字段是本次出售数量，使用 u32，不能填写剩余数量。

### 状态与接入边界

发送函数先通过 `028F3B30` 检查pending；已有pending时停止发送，提交后通过 `028F3A00(1)`置位。这是客户端发送状态，不提供服务端防重复事务依据，也不保证异常断线时的完整恢复行为。不得将check或每次到达请求的新服务端ID用作重复扣费、奖励的依据。

普通 NPC 入口已在有效 generation/revision 下同事务提交费用、物品、钱包、限购与审计，成功后才发布响应；失败不发布成功，发送失败不重跑已提交交易。买卖均无已确认的永久请求 ID，每个有效请求按当前状态独立处理，不能宣称跨连接重放幂等。特殊商店来源、windowState 完整枚举、时装/宠物 detail 和活动资格仍由各自业务接入。协议回归与原码依据不能代替匹配客户端的界面验收。

## 战斗耐久报告

C2S category=1、opcode=48（hex `0030`，`DECREASE_DURABILITY`），匹配客户端实收body为 `slot:u8`，例如 `0C` 指穿戴武器槽12，不是损失数量或槽位位图。仅接入这条1B报告，不接受未经确认的扩展尾字段。ARAD ACK注册在 `0237C107` 的47和 `0237C117` 的50之间没有48处理器，不构造ACK48。

C2S 普通入口固定6B：`slot:i16 + count:i32`，来源为 Main。发送 `02E52B28..02E52B56` 分别通过 `03BDF750/03BDF780` 写2/4B；`02E53FC4..02E53FF0` 和 `024B9758..024B978B` 的单次出口写相同布局、count=1。

同opcode的普通物品选择请求为 `slot:i16 + count:i32 + category:u8 + subcategory:u8 + itemId:i32×N + optionCountA:u8=0 + optionCountB:u8=0`，总长`10+4N`，没有额外的所选ID数量字段。`027BC1DC..027BC22B` 写6B前缀及两个分类字节；`027BC25A..027BC318` 按定义的选择数量是否为0，分别发送完整分类列表或所选ID向量。`027BC333..027BC405` 追加第一组选项计数及可选的5B记录，再写第二计数并flush；无附加选项的路径在`027BF564..027BF57E`直接写两个0后flush，`00AA6F6B..00AA6F94`也使用相同尾段。原生单次出口的count为1。

两个分类字节是PVF分组键，不是将所有分组按出现顺序展开的单个索引。客户端`027BD7BD..027BD835`用这两个字节查分组，`027BD844`区分全领与所选列表。ID清单只用于选择，奖励数量由服务端读取对应物品/数量对；具体数量政策见模块文档。普通入口接收6B格式和无附加选项的普通物品选择格式；具有完整装扮分类的真实源另走[时装礼包](时装礼包.md#cmd160装扮选择)的完整选项Parser和服务。其他不能匹配的扩展body走Unhandled；匹配外形后仍须领域核对来源、分类、ID及数量，含未实现detail或字段的分组不发奖。不能仅凭尾字节推定支持时装属性，或截断扩展body降级为普通开箱。

公共ACK分派先读成功u8；失败读error:u16，再进入handler的失败分支 `02370EA3 → 0234D430`，无额外包体读取。当前拒绝使用19，无足额交付空间/数值范围使用4；错误文本由本版公共道具错误入口决定。

成功body为 `18 + 8×count` B：

| offset | 字段 | 读取/消费依据 |
|---|---|---|
| 0 | `success:u8=1` | 公共分派 |
| 1 | `result:u8=0` | `0237087C → 03C851B0`；非零在`02370E93..02370EA7`追加错误提示 |
| 2 | `sourceItemId:i32` | `0237088E → 03C85290`；用于读取来源模板与展示方式 |
| 6 | `sourceSlot:i16` | `0237089A → 03C85220`；`02370C8A..02370C98`查询来源槽 |
| 8 | `reserved:u32=0` | `023708A6 → 03C85290`；局部`ebp-128`读后未用于此handler其他操作，不解释为余额 |
| 12 | `displayMode:i32=0` | `023708B8 → 03C85290`；`02370CA3..02370E93`仅对1/2追加专属UI，普通路径用0 |
| 16 | `count:u16` | `023708C4 → 03C85220` |
| 18 | `{itemId:i32, gainedCount:i32} × count` | `02370A67/02370A73`读两次4B，循环条件在`02370C6E..02370C84` |

来源模板参与结果窗创建及特定窗口分支，不能填零物品ID；清单数量是本次获得量，不是背包最终总量。该handler消费清单用于展示，不替服务端推进资产；成功后再发提交后的NOTI14，以及有变化时的NOTI53/1152。不同模板复用耗尽槽仍按公共投影先清槽后更新，不用虚假的获得消息替代原生清单。

单帧body上限65520B使此合同最多容纳8187项，领域在提交前检查；不能先扣礼包再因回包超长失败。未知body及特殊礼包没有通用成功占位。上述字段来自静态native消费与C#独立TCP验证；不据此宣称所有UI辅助函数均已原码回放或客户端实机验收。

## 每日保留礼盒次数

NOTI541 `SET_USABLE_COUNT_INFO`正文为三组连续列表：`A:u8 + {templateId:i32, used:u8}×A + B:u8 + {templateId:i32, value:u8}×B + C:u8 + {templateId:i32, value:u8}×C`，完整长度`3+5(A+B+C)`。匹配消费者`023C7CB0`将第一组写入模板/共享组计数map；`029BB690`计算`max(total usable count-used,0)`，因此第一组是已用次数，不是剩余次数。每模板次数上限和每包条数上限各为255，是独立约束；正文没有UID、槽或日期，不借ItemCore.RemainUseCount表达服务日。

当前仅接第一组每日保留能力，第二、三组固定为空，未赋予其未经确认的业务语义；未来接入这些组时必须替换固定空组策略。第一组显式投影当前角色的有效used，并对本连接历史key、Catalog支持模板及角色账本中的其他key发送0，超过255项分片全部发送。非空第一组逐项setter不保证清旧map；本实现不依赖`A=0`分支清缓存。跨选角保留连接历史key，空闲跨服务日同样显式归零。

保留源沿原CMD160成功`18+8R`合同，成功消费者没有自行扣源或更新次数；服务端提交后不发源删除差量，先发ACK160及奖励NOTI14，之后发541。没有给ACK尾部追加次数或猜测字段。失败沿既有错误19且资产与次数均不变。账本owner、UTC+8 06:00服务日及522生命周期限制见[礼包开箱](../模块/背包与装备.md#礼包开箱)，这些本服政策不由541证明。

## 固定商城礼包与账号契约

CMD518 `OPEN_CERAPACKAGE` 请求为 `slot:u16 + count:u8 + {itemId:i32, option:u8} × count`，完整长度为 `3+5×count`。匹配冻结原码发送入口 `025162DC`，槽、数量及记录读写点为 `025162F5`、`0251631A`、`02516377`、`02516388`。这里的 count 是选择记录数，不是开包次数；不含时装的固定 `[usable cera package]` 合法 count=0，一次消费源一件并按 PVF 固定清单发奖。含时装的固定包在选择集合等于 `[package data]` 全部时装编号时同样发放整包，option 写入 `Durability`。装扮源的非空选择由[时装礼包](时装礼包.md)核对完整PVF分类与属性，不忽略选项。固定包不借 CMD160 消费；普通随机盒也不能借 CMD518 使用。

失败采用公共 `00 + error:u16` 收尾，当前固定礼包拒绝为 `00 04 00`。成功为 `01 + sourceSlot:u16`：匹配原码 `04F914C2/04F914D3` 注册消费者 `02515F40`，成功分支 `02515F88` 读取源槽，按本格实际剩余数量删格或减一并关闭603窗口。之后投影已提交库存、钱包和必要邮件提示；消费者证据与服务端TCP包序不代替客户端获得清单和完整时装选择的实机验收。

NOTI1760 `PREMIUM_INFO_LIST` 为 `count:u8 + {type:u8, remainingSeconds:i64} × count`，type 范围为 0–131。匹配消费者 `028F9EE0` 读取 tick 差，`028F9F18` 按无符号除以1000转换为秒，`028F9F24/028F9F26` 扣除经过秒数；setter `028FC3AC` 保存基准 tick。服务端保存绝对到期秒数，仅在构包时计算非负剩余秒数，不把毫秒或 Unix 截止值直接写入剩余期限。

遗留契约实体复用 [CMD44 使用合同](物品.md#普通恢复药-cmd44) 的10B和15B请求，完整保留 opaque u32；仅接受目录明确支持的22、27、84、97。成功 ACK44 后发布同事务账号期限1760及实际变化的任务条件，不再次用14扣源。相同正文有足额源时可以连续使用，不设永久 opaque 去重或药剂冷却；耗尽后拒绝。期限通知本身不能证明所有契约的玩法效果已经实现。

## 魔法封印解封

`CMD401 / UNSEAL_RANDOM_OPTION` 的请求为4B：`Main槽号:i16 + inventoryManagerState:u16`。第二字段原样保留，不解释为金币、实例UID或固定零；负槽号及长度不符拒绝。状态ACK为1B，成功1、失败0，未确认错误码不追加通用错误字段。

成功包序为已提交的 `NOTI14 Main` 目标装备/金币差量，再发 `ACK401`；零费用时没有金币差量。123B装备条目的 offset71 为词条数量，72–74为三个type，75–77和78–80为两组端点，81为RandomState，82为RandomChangedIndex，83–86为变换候选；解封后81置0、82置255、83–86清零，普通封装字段保持原值。拒绝仅回失败ACK，不发物品差量。

请求与状态ACK沿用本机既有兼容实现的解封合同，编号由本仓库 [PacketTypes](../../Server/DfoServer/Network/Core/PacketTypes.cs)核对，完整条目沿用[物品协议](物品.md#实体字段)；[独立TCP用例](../../Server/DfoServer/SelfTests/Tcp/RandomOptionTcpTests.cs)验证帧、包序、城镇/副本与回滚恢复。401解封操作已获用户实机确认；原生消费者完整复核及全部失败窗口分支仍未覆盖，不把兼容实现或TCP通过当作这些分支的客户端证据。费用、资格与持久化见[业务模块](../模块/背包与装备.md#魔法封印解封)。

## 品质调整箱

本版 CMD81 请求 10B，小端 `target:i16, itemId:i32, material:i16, state:u16`；成功 ACK81 为 9B：`1:u8, material:i16, remaining:i32, type=2:u16`。CMD455 请求 6B，小端 `target:i16, material:i16, state:u16`，成功 ACK455 为单字节 1。末尾 state 是窗口状态，不作为词条索引。失败保持公共 `0:u8,error:u16`；成功先推 NOTI14 的目标及材料两格，再 ACK。基础品级、词条及箱子规则见背包与装备模块。
