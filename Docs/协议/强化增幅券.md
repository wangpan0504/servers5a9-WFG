# 强化与增幅券（S5A9 CMD80）

CMD80接入已核对参数的 `equipment reinforcement ticket` / `equipment amplify reinforcement ticket` 固定覆盖与增量券、`enchant random`随机强化券、幸运强化/增幅券、普通NPC强化与增幅、便携强化/增幅器及各自毁装保护，以及以公会硬币为材料的勋章强化。新增幅模式，以及额外使用资格未闭合的资源仍拒绝，不消耗资产。商店兑换价格不作为券的使用成本。业务行为及验证边界见[背包与装备](../模块/背包与装备.md#强化与增幅券)。

## 请求与消费者

C2S category=1 / opcode=80。完整宽度为 `20 + textLength`，严格保留以下字段：

```text
mode:u8 (0强化及幸运强化/1增幅/2随机强化/5幸运增幅)
targetList:u8, targetSlot:u16, targetItemId:i32
materialSlot:i16, protectionSlot:i16
textLength:i32, targetText:bytes[textLength]
auxiliarySlot0:i16, auxiliarySlot1:i16
```

文字最大256B，保留原字节但不写日志，不用于鉴权、费用或身份校验。当前路径仅接受三个附加槽均为 -1；自动毁装保护通过回执末端的独立槽同步，不把未知附加券槽当作普通保护券。
实际用户请求28B的目标为 Main21 / 模板27308，券源 Main86，文字长8，末尾两槽为 -1；文档不保存原文字。

当前x86消费者与producer来自同一 `DungeonHelper/Evidence/code.bin`，加载基址 `0x401000`：

- producer `029DE124/029DE12D` 写80头，`029DE13D/14D/15D/17B/18B/1D3` 依次写前六项。
- `029DE235 -> 03BDF8E0` 写DSTR，`029DE245/029DE255` 继续写两个u16，`029DE25A -> 03BE0FF0` 发送。
- 注册 `0237C325 -> 02373D90`。成功消费者 `02373E60..02373EFA` 读模式及固定前缀。
- `02374194..0237419A` 用绝对余量回填券；耗尽分支清源。
- `023744EA..023745B3` 将结果新等级装回装备快照；本命令未读取新的异次元Type/Value。
- `02374932/0237493E` 必读末端i16槽与i32余量，`023749A4/023749B2` 再读两个u8状态。

## 回包与发布

S2C category=1 / opcode=80。接受的事务（包括券概率失败）成功结构为27B：

```text
1:u8, mode:u8,
materialSlot:i16, materialRemaining:i32,
protectionSlot:i16=-1, protectionState:u8=0,
oldLevel:u8, result:u8 (0成功/1券失败保级), newLevel:u8,
targetList:u8, targetSlot:i16,
optionalSlot:i16=-1,
terminalSlot:i16=-1, terminalRemaining:i32=0,
tailState0:u8=0, tailState1:u8=0
```

该27B适用于没有销毁产物的成功、保级和降级结果。普通/便携增幅的mode为1，幸运增幅请求5回执也归一为mode1，但offset10的路径标志为4；不能把请求5原样复制到结果模式。offset12分别为0成功、1失败保级、2降级或保护后归零、3销毁。幸运路径4允许原生降级消费者，不借用普通增幅的低级保护政策。

销毁结果在offset17的optionalSlot之后追加`refundCount:u8 + {slot:u16,itemId:i32,increment:i32}×count`，然后继续原来的末端槽、余量及双状态。因此完整宽度为`28+10×count`，不能仍发27B。`02374730..0237474F`读取补偿行，已有对象在`0237479F..023747A5`调用虚表+0x4C加数量，空槽分支创建本次数量：这里是本次增量，不是已有余额或最终堆叠总数。后续公共差量再同步已提交完整核心及余额。

自动保护只有在本次会毁装的失败中消费一张；回执为结果2和实际保留等级，末端`terminalSlot/terminalRemaining`携带被扣保护的槽及绝对余量。成功或低等级保级不消费自动保护，末端槽为-1。源槽、目标的原位变化由ACK承担，普通/便携/幸运不再用NOTI14重建结果窗持有的对象；穿戴刷新、金币及真实补偿继续走公共投影。
正常拒绝沿公共 `0:u8 + error:u16`。普通NPC增幅（mode1、非便携或券源）的目标与源实体基础资格通过后，当前+31返回13；`02374ADD`将13映射到DSTR1654“该物品无法继续强化”。该拒绝不读取下一档概率或费用、不抽随机、不产生库存计划；其它资格、便携、幸运、强化及资源上限拒绝保持23。固定覆盖券仍由独立券合同处理，不因目标+31而套用NPC上限拒绝。错误23在`02374AC9`映射到DSTR1653“该道具无法进行强化和赋予异次元气息。”；原生界面仍需分别验收。
SQL异常沿现有会话错误传播，不能转成成功或自动重新随机。ACK后共享背包Projection发布已提交完整核心差量；穿戴目标沿Actor/Player刷新。
即使ACK已回填源余量与等级，差量使用绝对数量和完整核心，不另做第二次消费；目标无变化的覆盖券仅发布真实源差量。

## 资源、资格与事务

券声明为 `level percent fixed|additional rawFourthParameter`。模型保留第四整数为 `RawLevelLimit`；不将字段名字本身当作语义证据。
等级1..31、概率0..100、额外字段和未知模式不能夹紧成成功；第四参数须在 -1..127 内，与匹配客户端的有符号单字节存储一致。当前增量分支在第四参数非负时要求源等级严格小于该值，并遵守Attr五位最大值。
匹配客户端强化目标选择036eb253..036eb260以 current >= limit 拒绝；增幅目标选择采用同类判断。提示消费者另有 current+delta 比较，实际结果是否夹紧尚未闭合，不能据此将第四参数直接改成结果等级上限。
固定券第四参数是否也限制源等级尚未闭合；本阶段只支持真实样本的 -1，非 -1 固定券保持Pending，不能忽略该限制后覆盖装备。
支持显式目标物品清单和 `check usable itemlevel` 两项范围。Town门禁接收village及village加seria room；仅seria room的声明保持Pending，避免扩大到所有Town。
目标按有效装备脚本的 `impossible contents` 与真实部位限制，排除称号/宠物/时装，不靠名称推断资格。

源必须是Main中的真实可堆叠实例；目标仅Main/Equipment，保留身份、位置、锁、期限及完整快照。
强化只允许无异次元属性目标；增幅只允许已识别的Type1..4且非零基础Value，未净化高位状态拒绝。
每次扣指定格一券，无普通金币费用；券概率失败保留目标，与普通增幅当前+10冲+11的破坏政策分开。

目标只改变 `Attr & 0x1F` 对应的等级，保留高三位及AmplifyType/AmplifyValue。异次元基础值不在每次升级后加上PVF等级收益。
完整核心与本版PVF交给客户端派生属性；CHR基础Player属性不重复添加装备强化/增幅收益。
源数量、目标修改、审计和角色revision复用同一个InventoryPlan外层事务；有限源/目标期限由提交前置条件重验。

## 祝福与随机强化

`0373BF97..0373BFA1`把模式2、源和目标交给同一`029DDAF0`发送器，正文仍为上述`20+textLength`；不能以模式0使用随机券。成功回执仍为27B，`mode=2`、offset10的路径为1、offset12结果为0、offset13为本次绝对等级。`02374326..02374332`把结果模式2归一为强化显示，`023743A9..02374471`的路径1按随机等级检查，随后`023744F0..023745B3`原位写回目标。路径1目前支持+1至+13，超出本版消费者边界的资源保持拒绝。抽得比原装备更低的等级也是一次成功覆盖，不能发普通失败降级码2；该码在`02374357..02374363`只接受路径0/4。

## 普通与幸运增幅

便携强化的`[portable upgrade]`与`[new portable upgrade]`沿mode0/path0进入同一库存事务，但只读取`etc/upgrade.etc`的`normal`表；不使用增幅表或幸运强化表。每次扣一件源、免金币与无色小晶块，前两整数约束当前强化等级，第三整数为相对成功权重加成。当前normal表+0至+9失败保级，当前+10/+11失败降三级，+12起失败销毁；按行中普通政策8/10/11及完整目标资格执行。目标最大等级仍受实例Attr低五位约束，不因源声明50或86放开到不可保存的等级。

`[protect equipment]`只保护强化，`[new protect equipment] N`在强化毁装失败时保留至多N级；增幅保护只保护增幅。成功、普通失败保级及降级不消费保护券，真正毁装失败才从背包扣一张同类合法保护；保留原UID与完整核心，ACK末端槽报告实际保护余量。没有同类保护时原子规划完整分解及强化表补偿，强化表补偿仅叠加一次，不重复加增幅补偿。普通NPC强化按`etc/upgrade.etc`的`normal`表扣账号无色小晶块（虚拟槽358 / item 3037）及三段金币：`[cost]×[type]`、`[cost weights by rarity]`、`[cost weight by upgrade level]`各加0.5再截断；当前等级倍率段0..18且每行两列相等，超出沿用末档。客户端把材料槽写成358，服务端从钱包扣而不是实体格；保护券仍自动扫描，不能当作MaterialSlot。便携强化继续免金币与无色。

普通增幅按`etc/amplifyupgrade.etc [table] [table type] amplify`选择数据，不混入同文件的`new amplify`表。当前每行24项：索引8为十万分制失败权重，10/11为普通失败政策及参数，14/15为材料ID和数量；前后属性倍率不能当作金币系数或下一等级。表按当前等级索引，当前+0至+3的失败权重为0。`[cost]`按装备grade读取，依次乘`[type]`部位权重和`[cost weights by rarity]`，两步各加0.5再截断；普通增幅表没有强化用的等级费用倍率。耳环使用部位权重第12项，不直接用穿戴槽25减12得到索引。

df_game_r的`08900436`提供费用及当前等级索引，`08546342`校验材料、余额、满耐久、已识别状态和目标资格，`0854755A`执行概率抽取；其旧包号和旧表布局不复制。`08548D3C`的便携逻辑检查源声明的升级等级区间，材料改为源自身一件且金币归零。当前`[portable amplify]`同时保留`[check usable itemlevel]`及实际使用地点。

本版ARAD的`040D4F60`将`[new portable amplify]`映射为动作132，旧`[portable amplify]`为96；新动作不是新的CMD80模式，也不切换到`new amplify`概率表。源STK增加第三个整数成功加成，服务端按[相对成功权重规则](../模块/背包与装备.md#强化与增幅券)计算，继续发送mode1/path0的27B原位更新回包，不追加私有概率或动作字段。旧版df_game_r没有该新动作，不据其双整数长度拒绝本版三整数声明；10007839当前PVF的`0 14 30000`及“普通增幅器的130%”说明与此规则对应。

本服普通/便携从当前+1至+9失败保级；高等级沿普通失败政策，不能直接移植参考项目对+7至+9统一降一级的逻辑。销毁补偿复用普通分解目录，并分别叠加增幅表、强化表的`[disjoint]`奖励：按修正grade门槛、当前等级与`upgrade const for bonus item count`之差的平方、稀有度权重计算，保留原float32倍率后截断。df_game_r的`08546938/08546BBA`分别提供补偿及原子毁装业务参考。

幸运增幅使用`etc/chn_lucky_enchant_deed.etc`中值1的块及`enchant type amplify`，各行为`currentLevel,downWeight,sameWeight,upWeight`，总权重100，当前覆盖0至14。不使用旧端`eventupgradejar.etc`的活动fortune概率，也不额外扣金币、矛盾或保护券。STK的`enchant random`继续约束稀有度、部位和封装；`er_slot=0`不限部位，1武器、2防具、3首饰，`er_seal=1`要求封装，0/2不加封装门禁。

幸运强化10007406声明`lucky enchant deed 0`，沿`0373AC00..0373AC88`发送mode0；服务端按源动作分流，不将其无`er_enchant`的资格块当作损坏随机券。读取同文件值0的`strengthening`块，+14行为`14 85 0 15`，独立于增幅的`14 82 0 18`。ACK模式0、路径4，结果0升一级、1保级或2降一级；每次一券且无金币、毁装或保护消费。目标无异次元属性且满耐久，保留完整实例及所有资格。尚无本版producer证据的mode4继续拒绝。

`--selftest-tcp amplification-upgrade`补充当前资源、真实NPC增幅+1、真实NPC强化+1（槽358无色）、穿戴便携增幅、mode5幸运增幅、金币与源耗尽、SQL审计失败回滚和重连验证。确定性规划用例覆盖保级、幸运降级、毁装补偿、保护券、NPC强化钱包费用及满包预检；不将其称为高等级客户端界面验收。

## 勋章强化

勋章沿用同一C2S category=1 / opcode=80，请求宽度`20 + textLength`，字段顺序不变：`mode`固定0（强化），目标为列表38的勋章槽（0–48），`materialSlot`指向Main中的公会硬币，`targetItemId`必须等于目标勋章的物品ID，`protectionSlot`与两个附加槽均为 -1。服务端按`ItemKind.GuildMedal`与物品ID定位目标，不把列表38或某个具体槽位写死为唯一入口：勋章页、Main快捷栏3–8与穿戴槽32都是合法位置；请求本身仍带列表与槽位，回执原位更新同一实例。

概率、失败政策与材料数量来自`etc/upgrade.etc [table type] flag_upgrade_table`：行索引是当前强化等级，首行16项、其余24项，行尾8项依次为失败权重（十万分制）、政策对与材料ID/数量。成功条件为`roll >= 失败权重`（roll取`[0,100000)`，等于下界仍成功）。当前PVF的权重为0/15000/28000/…/95000，政策为`+1..+7`保级、`+8..+10`降3级、`+11`起销毁。失败降级与销毁沿用增幅的`Outcome`语义，成功只更新Attr低五位，高三位与其余核心字段保持不变。

费用只有公会硬币：`floor(行材料数量 × [cost weights by guild flag rarity][目标稀有度])`，当前权重为1/2.20/5.50/10.50/20.00/15/18.40，稀有度0..6；客户端实测稀有度6的勋章为18/36/55，稀有度3为10，与公式一致。不收金币，没有券定义，结尾`text`、保护槽与附加槽不改变费用或概率。材料数量不足、满级、错误模式、物品ID不符、过期、锁定或非硬币材料都在随机抽取之前拒绝。

回包仍是27B成功格式：`1, mode=0, materialSlot, 硬币绝对余量:i32, -1:i16, path=0, 旧等级, 结果码, 新等级, 38, 勋章槽:u16, -1:i16, terminalSlot=-1, terminalRemaining=0, 0, 0`；销毁时结果码为3、新等级0，槽位清空由该原位更新表达，不追加列表差量。拒绝使用`CargoPackets.Ack`的`[0, 23, 0]`，不消耗材料。
