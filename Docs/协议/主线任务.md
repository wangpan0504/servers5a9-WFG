# 主线任务协议与证据边界

本页维护 S5A9 新角色主线任务协议。创建与选角见[角色](../模块/角色.md)和[角色协议](角色与入城.md)。

## ACK4任务槽的状态scalar：零值不是初始进行中

ACK4的30槽读器 `02341AF3..02341B35` 固定读取每槽 `quest:u16 + scalar:u32`，空quest=FFFF时跳过，非空调用 `0203C450(quest,scalar,0)`。该u32已有状态消费者，不能继续命名为“未知保留值”或固定置0。

`0203C832..0203C83D` 以任务指针和scalar调用 `02E6A7C0` 构造12B active条目；条目+0为任务指针，+4为scalar holder，+8为holder辅助存储。`0200C8D0(task,kind=0)` 按taskId查该条目并在 `0200C968..0200C9EB` 读取并返回scalar，不重新判断地图通关。不存在任务返回FFFFFFFF，不能用0表示不存在。

多个本版UI路径直接测试该返回值为0：`0105E7ED..0105E7F7`、`01459D12..01459D1F`、`027CB865..027CB86C`、`03753962..0375396C`。其完成布尔值由 `test eax,eax; sete` 得到。新角色仅有active3145、未进副本及无completed记录时，ACK4投影scalar=0仍能让客户端显示条件已完成并发C2S34；数据库没有完成位不能防止该本地显示。当前创建保存 scalar=1；完整任务条件与领奖的验证边界见[任务模块](../模块/任务.md)。

`0417EEA0` 将scalar拆为3个9bit计数；`0417EEF0` 根据索引0/1/2取各计数：

```text
counter[0] = scalar & 0x1FF
counter[1] = (scalar >> 9) & 0x1FF
counter[2] = (scalar >> 18) & 0x1FF
```

`02031CD0..02031D16` 的任务文本路径将任务资源数量减去counter来显示达成量，这是剩余计数的证据。未解释通用scalar的bits27..31，不忽略这些位后伪造其他任务状态。三计数布局不能独自证明任何任务初值；3145的单Boolean合同由下述实际资源、真实type分派和clear-map条件分支单独闭合。不能推广成所有任务初值为1。

QST标签文字及真实分派如下。登记尾部jne检查静态初始化flag，**不能将登记尾当作当前标签consumer**；必须先读取真实switch表得到case入口，再跟该入口的分支。文字解密helper `03C75330` 的独立模型与真实原码对4个标签一致，不执行字符串缓存/锁/分配等未知调用。

| 标签 | 静态文字/登记ID | 真实分派与对象写入 |
|---|---|---|
| `[clear map]` | `059F7D68` / `0x5F1` | `04197751` 减0x5EB，`byte[0419D0A0+6]=2`，`dword[0419CFA0+8]=04196A34`；case入口 `04196A34..04196A3B → 04197C3F` 写Quest+350=**3**，随后跳到 `0419C673`，不写入口 `+758` 或任务 `+724` |
| `[quest clear]` | `059CB7A8` / `0x6C7` | 同switch，index220、selector55、target=`0419783F`；`04197846 → 04197F3C` 写Quest+350=`0x2C`。另一路+350=0x46与此不同，不混同 |
| `[sub type]` | `0553D664` / `0x773` | outer switch `041980B6` 减0x718，经byte表 `0419D218` / DWORD表 `0419D1C8` 到 `04192370`，再到 `04198561`；`04198569` 读取整数，`0419856E` 原值写Quest+374 |
| `[int data]` | `0553ACD8` / `0x78E` | outer switch index0x76、selector10，到 `04192436 → 04198661`；读取整数列表写vector+378，begin+37C/end+380 |

3145原PVF token是 `[sub type] -1`，`[int data] 76126`，只有该一个int data值，无附加数量/怪物ID。资源值在匹配PVF中直接核对，不能把sub type省略成默认0。

清图事件在 `02C9F654..02C9F663` 无条件调用 `0203BA80`，五个参数是 `2、+1198 处的 dword、0、3、1`。`0203BB5B` 看到第四个参数为 3 就把 EBX 清零，事件类型 2 从 `0203C394` 进入 `0203BEE8`，再以 `(指向任务指针的槽, 该 dword, 0)` 调用 `0201C410`。第三个参数是 0，`0201C44E` 对 `2` 的跳转不会发生。`0201CAA3` 的 `0290BEF0` 返回 0 才落到 `0201CAAF`：任务 `+350==3`，`[ebp+0C]` 等于 `+37C` 首项，并且 `+374` 非 0，然后 `0200EB60` 以 value 0 发 C2S 33。3145 的 `+374` 是 -1，`+37C` 首项是 76126。`0290BEF0` 经 `02330FF0 → 03E6BB60` 取选图对象；对象为空时 `0290BF1A` 返回 0。对象存在时 `03B9C820` 读取 `+47C` 的内部值，只有结果恰好为 1 才返回 1 并跳过比较。`+1198` 仍未证明是 `map.lst` 索引，因此这条发送还没有 76126 的实机样本。`this` 仍是缺失的 `062EF57C`。

同一事件在 `01617900` 为真时才调用 `020209F0`。它要求传入指针里的值是 2，并把这个 2 当作 `0201C410` 的第三个参数，所以从 `0201C44E` 跳到 `0201CD32`，不执行 `0201CAAF`。这条在 `0200C270` 命中后只返回 1。`0201C410` 的后续在 `0201CEE9` 调用 `020094C0`。该函数从 `0643A49C` 或 `0643A498` 取对象，调用虚表 `+70C`，再把返回值交给 `03DCAAD0` 做数值比较，在 `0200950B` 返回。直接调用里没有 `0200EB60`。调用方 `02020A5D` 随后返回，没有调用 `0200EB60`。因此第二次调用本身不发送 C2S 33。紧邻的 `02020A90` 会调用 `0200EB60`，但它先要求任务 `+350==0x14`，不是 3145 的清图类型 3。任务模块里其余先比较 `+350` 再发 C2S 33 的类型包括 1、`0xA`、`0xB`、`0xC`、`0x14`、`0x16`–`0x1B`、`0x26`–`0x28`、`0x2B`、`0x43`，没有 3。`020209F0` 返回后，只有在另一对象 `+98==1` 时执行 `02D205F0`，也就是把 `+920` 加 1。随后的分支表 `02C9F7EC` 里，命中项只把 `+928` 加 1 或读取本地字段。默认项创建或复用 `062B6ED4` 后调用 `00A070D0`，该函数在 `00A0729D` 返回，没有提交 C2S 33。

`0200EB60` 的kind0收尾 `0200EE11..0200EE29` 将第二参数 `value` 用 `setne` 规范化为Boolean，再调用 `02280690(taskId,FF,bool)`。后者发送C2S `(1,33)`：`echo:u16=33 + quest:u16 + value:u8 + reserved:u8=0`，6B；FF不写selector额外字节，只有selector10/20/40才有额外u8。清图达成的实际caller传value=0，归一后仍0。ACK33成功先看公共success字节；非0时 `02353133/0235313F` 只再读 quest:u16 和 scalar:u32。scalar为0的路径在 `0235322D` 返回前没有再调用 `03C851B0/03C85220/03C85290`。`02353109` 和 `0235317D` 仍使用缺页全局 `062EF57C` 调 `0200A2F0/020268A0`，所以这6字节只是直接读宽，不是可以单方面发出的完成包。服务端只在 C2S 33 恰好为这 6 字节且 echo 为 33 时记下 quest、value 和 tail，不回 ACK33，也不改条件。selector 为 10/20/40 的 7 字节形式仍不识别。

因此3145是单Boolean未达成/达成状态：**未达成为1，清图达成为0**。新接取3145的ACK4单槽应为 `49 0C 01 00 00 00`，初始scalar=`1`必须与接取同事务持久化，重登投影同值。这个值来自3145实际单清图Boolean合同，不能以任意非零代替，也不能套用于3146聚合或猎杀计数。服务端后续把scalar置0仍须有绑定本次接取身份的76126真实通关事实；UI显示完成不等于已领奖/清槽/完成位。

ACK31注册点 `0237C097..0237C0A2 → 0236DDE0`。成功正文在 `0236DE6A/0236DE76` 同样先读取quest:u16、scalar:u32，经过奖励数组后 `0236DFFB` 调同一 `0203C450(quest,scalar,0)`。这表明ACK4恢复与ACK31接取共用服务端提供的状态，客户端不会以清图资源自动替换错误初值。ACK31的完整成功奖励/失败合同仍未闭合，不为修任务UI额外发送它。

## C2S34：已收到的完成请求

方向/category/opcode 为 C2S `(1,34)`。已保存的本版样本及字段：

```text
22 00 49 0C FF FF 01 00 FF FF
u16 echo=34, u16 quest=3145, u16 reward=FFFF, u16 multiplier=1, u16 reserved=FFFF
```

发送入口为 `02123900`，具体写入 `02123BE7..02123C53`。`03BDF750` 在 `03BDF762` 将写长增加 2，`03BDF769` 传给 `03D640F0` 的长度是 2；这里的五次写入真实宽度为 u16，共 10B。它先写 echo34，再写 `[ebx]` 的低 16 位、常量 FFFF、常量 1、EDI 的低 16 位。样本 reserved=FFFF 是实际请求事实，EDI 的一般合法域尚未闭合。

`02123E80` 的事件入口只在第二参数=`0D` 且第一参数=`C9` 时调用 `02123900`；第一参数=`CA` 则调对象 vtable `+7C`。这是该 UI 回调的分支证据，尚不能命名为 NPC 对话结束事件。`02123BD6..02123BE5` 还以 `029CBD60` 返回值作为发送门槛，该返回语义未恢复。不能直接从按钮回调推断 NPC1247 已出现或交付场景合法。

FFFF 不允许跳过固定奖励。客户端倍率、保留值和自选槽的合法域需要对应消费者及资源约束，服务端不能直接将 multiplier 当作奖励金额倍数。

## ACK34 注册与公共失败包

方向/category/opcode 为 S2C `(1,34)`，注册指令原形：

```text
0237CE52 push 0
0237CE54 push 02376BF0
0237CE59 push 22
0237CE5B mov ecx, esi
0237CE5D call 028F8C30
```

`028F8C30` 保存 `(callback, userdata)` 二元记录；`028F8E35..028F8E3D` 分别把参数 callback 写 `[eax]`、userdata 写 `[eax+4]`。公共 ACK 路径如下：

1. `028F85F6..028F8600` 以 `03C851B0` 读取 **u8 success**。
2. success=0 时，`028F8644` 调 `0041CA50(opcode)`。该函数只对 opcode18/20 返回 true；34 返回 false，于 `028F8655` 再读 **u16 error**。success 非零时跳过 error，内部 error 初始化为0。
3. `028F8756..028F8761` 将 error、success 和 frame 传给 `028F2970`。
4. `028F29ED..028F29FC` 从注册记录取 userdata 和 callback，按 cdecl 参数 `(opcode, success, error, userdata)` 调 callback。34 的 userdata=0。
5. `02376C1E..02376C26` 检查 success，零值跳到 `023783A5`，非零值进入正文。

所以公共失败前缀精确为 `success:u8=0 + error:u16`，3B；不能用 ACK15 的错误含义解释 ACK34，也不能把所有错误码统一映射为“条件不足”。

| ACK34 error | `023783A5..0237850B` 的直接行为 | 额外直接流读取 |
|---|---|---|
| 4 | stringId=`0317`，经 `03DDC8F0` 取文案，再 `036DB2F0` | 无 |
| 19、22 | 跳过文案进入公共收尾 | 无 |
| 126 | stringId=`11175`，格式化及创建通知 UI | 无 |
| 210 | stringId=`11205`，UI code=`0483` | 无 |
| 105 | 格式化 stringId=`112EB`，读取当前连接对象作文本参数 | 无 |
| 209 | stringId=`54C4`，通用 UI code=`03EE` | 无 |
| 1 | stringId=`B4E2`，通用 UI code=`03EE` | 无 |
| 8 | stringId=`ADB3`，通用 UI code=`03EE` | 无 |
| 其他 | 不显示上表文案，进入公共收尾 | 无 |

这些文案 ID 的具体文本、业务适用范围尚未核实。失败后 `0237850C..0237852F` 取得连接对象、可能调用 `03B98290`，再调用 `016F8020`。`02378537` 接着读取全局 `062EF57C`，本记录缺这一页，所以 `0237852F..023786C3` 的任务/UI 收尾没有跑完。仅能确认 failure callback 本体没有直接调用流读取 helper，不能据此宣称全部 callee 不读取或连接已经可操作。错误 ACK Builder 暂不接入。

## ACK34 成功正文的直接读宽

以下是 **callback 的直接读取**，字段业务名称保持中立。它不含公共 success 字节，也未证明全部 callees 的网络流消费；因此不是可编码的完整成功合同。

| 顺序 | 字段/宽度 | 调用点与条件 |
|---|---|---|
| 1 | quest:u16 | `02376C3B → 03C85220`，用于查找任务对象 |
| 2 | conditionTag:u8 | `02377080 → 03C851B0` |
| 3 | conditionValue:u32 | `0237708C → 03C85290` |
| 4 | conditionCount:u8 | 仅 conditionTag=0 或25；`023770C4` |
| 5 | conditionCount 组 `kind:u8 + id:u16 + value:u32` | `023770FC/02377108/02377114`；每组7B |
| 6 | resultMode:u8 | `023772AA`，读取后切换后续分支 |

conditionTag=8 在 `023770AA` 调 `016F8020`，其余非0/25 tag 跳过第4/5项。kind=0/36 的条件项从物品管理器查对象，value 进入 vtable `+50`；kind=3 从当前 player vtable `+850` 按 id 查对象；kind=7不执行该组业务。这些分支只能证明读宽及消费对象，尚不能把 conditionValue 命名为经验或金币。

### resultMode=0 的奖励项布局

该分支在 `0237751E` 读 rewardCount:u8，每项的直接读取为：

| 字段 | 宽度 | read call VA | 后续消费 |
|---|---:|---|---|
| wireSlot | u16 | `02377576` | 传物品持有域的 `029CA9D0` / `029CFDD0` |
| itemId | u32 | `02377582` | 经 `020BF1D0 → 029089D0` 按资源物品类型查持有域，不是实体 UID |
| amountOrValue | u32 | `0237758E` | 已有对象 vtable `+4C`，或作为 `027F2430` 参数 |
| amplifyType | u8 | `0237759C` | 特定新装备核心 `+38`，对应普通123B条目offset19的AmplifyType |
| amplifyValue | u16 | `023775A8` | 同型核心 `+40`，对应普通123B条目offset20的AmplifyValue |
| expireTime | u32 | `023775BA` | 写临时核心 `+70`；与普通物品条目的 `ExpireTime` 同源，部分子类再交 `029B73D0` |
| sortLockFlag | u8 | `023775CF` | 写临时核心 `+A9`，对应123B条目偏移95 |
| remainUseCount | u8 | `023775E4` | 写临时核心 `+A8`，对应123B条目偏移94 |

每项19B；项数循环 `02377AC2..02377AD8`。读取全部19B后才查询持有域，即查不到对象也不能缩短这19B。3145 的 `10165055` 和 3146 的 `10164759` 在 `stackable/stackable.lst`；3145 的武器 `101010438`、防具 `10403/12403/14403/16403/18403`，以及 3146 的 `20002/24002/22002` 在 `equipment/equipment.lst`。奖励须由完整资产创建和提交结果提供增幅、期限、锁及剩余次数，不以默认零代替未知属性；领奖资格、成功头字段来源与完整提交仍未闭合，当前不发这些奖励，也不能改放消耗品列表。

奖励创建、字段对应和持有域写入的实际链如下：

- `023775F0 → 020BF1D0(itemId)` 返回持有域类型，再经 `023775F6 → 029089D0(type)` 取得对应 owner。`02377612 → 029CA9D0(owner,wireSlot)` 查已有对象；命中后先以对象虚表 `+5C(itemId)` 检查模板一致，再调用虚表 `+4C(amountOrValue)`。候选虚表 `055D8F64` 的 `+4C` 指向 `020C1300`；它读取对象 `+2F0` 的当前值，在 `020C1365` 加上传入参数，再调用虚表 `+40` 写回，因此该类型的已有堆叠分支需要本次增量，不能发送最终累计数量。其余类型仍须按各自虚方法核对。
- 未命中时，`02377657 → 027F2430` 初始化临时核心，基址为 `ebp-D8`，传入的 `amountOrValue` 写核心 `+0`。`0237770E → 02E615B0(itemId,core,1,0)` 按资源目录分派 `02696860` 或 `028B4D00` 创建对象，之后调用 `02E61540`、`020C0190`、`020C0CA0` 初始化。`027F2430` 和 `02E615B0` 是 callback 先后调用，不存在已证明的前者调用后者的边。
- `0237765F..023776E6` 将 `expireTime` 通过地址对齐的数值写入 helper 保存到 `ebp-68`，即临时核心 `+70`。普通 NOTI13 的 `023BE989 → 027F7AC0` 将123B条目转为相同核心；`027F85B1` 读取条目 `+38h`（偏移56的 `ExpireTime`）写核心 `+70`。运行物品初始化 `020C0570..020C05D0` 再读取该核心字段，写物品 `+39C`。因此这个 ACK34 u32 与期限字段对应，不能从其他版本的附魔卡偏移取值。
- `02377700` 将第一个尾 byte 写入 `ebp-2F`，即核心 `+A9`；`0237770B` 将第二个写入 `ebp-30`，即核心 `+A8`。同一123B转换的 `027F8765` 读取条目偏移94的 `RemainUseCount` 写核心 `+A8`，`027F876F` 读取偏移95的 `SortLockFlag` 写核心 `+A9`。ACK34 的尾部顺序是排序锁、剩余使用次数，与条目字段顺序相反；不能解释成附魔升级和增幅类型。
- `amplifyType/amplifyValue` 只在特定新对象分支参与写入：对象虚表 `+0` 返回2，经类型检查后由虚表 `+170` 取得另一核心；非零byte写该核心 `+38`，word写 `+40`，再由虚表 `+16C` 安装。候选虚表 `055D8F64` 的对应槽指向 `029380C0`（返回对象 `+F38`）及 `029B3E40`。普通123B转换 `027F8263`取得raw基址，`027F8424/027F8490`分别把raw offset19/20写入同型核心+38/+40，装备安装 `029B4167/029B4226`也比较这两个位置；由同版本完整转换链绑定为ItemCore.AmplifyType/AmplifyValue，不是按相同宽度猜字段，也不是Attr或Durability。
- `02377763 → 029CFDD0(owner,wireSlot,object,1,1)` 将新对象交给持有域。`029CFF6A` 以槽号索引 owner `+58` 的指针数组写入对象，再经对象虚表 `+34` 关联 owner 并更新附属状态。这证明了本分支的槽位写入边，尚不证明所有虚方法及 UI 收尾完成。

以上新增边来自同匹配映像的历史 Full Memory 转储离线反汇编：基址 `00400000`、映像大小 `0770F000`、时间戳 `5E19A8AA`、校验和 `03585062`，与本页匹配 ARAD 身份一致。事故部分转储的这些页不可读，不能用它声称已恢复本次领奖场景。历史初启对象不代表实际3145领奖对象；间接虚调用、所有 callee 的流读取、成功后的完整包序及实机效果仍须独立核验。离线 CDB 中最近导出的符号偏移不作为函数名称。

直接读取的 body 长度公式（包含公共 success）为：

```text
conditionTag∉{0,25}: 10 + 19 * rewardCount
conditionTag∈{0,25}: 11 + 7 * conditionCount + 19 * rewardCount
```

该公式仅适用于 resultMode=0 的直接读取路径；不能作为整个链的 total footprint。3145 固定奖励非空，rewardCount=0 会跳过真实奖励消费，不构成业务完成。已确认的创建与持有域边不替代全部 callee 流读取、奖励对象虚方法、完整任务收尾及实际领奖验收。
